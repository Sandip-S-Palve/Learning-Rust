Trees and heaps

Learning objectives

  • Use tree vocabulary precisely (root, child, leaf, height) and explain why a tree's height sets its cost
  • Explain binary search trees, why they can degrade to a list, and how balancing prevents it
  • Explain B-trees, and why Rust's BTreeMap and your database's indexes use them instead of binary trees
  • Explain binary heaps and priority queues: the array layout, sift-up and sift-down
  • Choose between HashMap, BTreeMap, a sorted Vec and BinaryHeap from measured trade-offs

Why this matters

💡 Why this matters

Two of your product's hardest problems are tree problems. The workflow engine must always know which timer fires next among millions. That's a priority queue, which in this chapter's lab picks the next 1,000 timers out of a million 18,000× faster than scanning a list. And every durable query the engine runs ("workflows due before 10:05", "events for W1 in order") is served by a B-tree index in PostgreSQL, the same structure as Rust's BTreeMap.

As a consultant you'll also be asked "should this be a Dictionary or a SortedDictionary?" every few weeks. After this chapter you can answer with numbers.

Intuition first: an org chart and a hospital triage desk

🧭 Analogy
  • A tree is an org chart: one person at the top, each person managing a few others. To reach anyone you walk down from the top, and the number of management levels decides how long that takes. A flat, wide chart is fast to navigate; a chain where everyone has exactly one report is slow.
  • A heap is a hospital triage desk. It doesn't keep patients in full order. It only guarantees that the most urgent one is always first in line. That's much less work than full sorting, and it's all a "who's next?" question needs.

Core explanation

Basic

Tree vocabulary

A tree is a set of nodes connected parent-to-child, with no loops. The top node is the root, nodes with no children are leaves, and a node's descendants form its subtree. A binary tree allows at most two children per node: left and right. The height is the number of nodes on the longest root-to-leaf path. Almost every tree operation walks one path, so tree operations cost O(height). The whole art of trees is keeping the height small.

Binary search trees

A binary search tree (BST) adds one rule: for every node, all keys in its left subtree are smaller and all keys in its right subtree are larger. Searching is the phone-book halving from chapter F2, done by walking: compare with the node, go left or right, repeat. If the tree is balanced, its height is about \(\log_2 n\), so search, insert and delete are O(log n), and an in-order walk yields the keys sorted.

But the shape depends on insertion order. Insert keys already in sorted order and every new key goes to the right of the last: the tree degenerates into a linked list of height n.

Balancing

A self-balancing tree restructures itself on every insert and delete so that its height stays O(log n) whatever the insertion order. The classic binary designs are AVL trees (1962) and red-black trees. Both use small local rearrangements called rotations. .NET's SortedSet<T> is documented as "a self-balancing tree", and SortedDictionary<TKey,TValue> as "a binary search tree with O(log n) retrieval".

Rust's standard library takes a different route: it has no binary search tree at all. Its sorted map is a B-tree.

B-trees: wide, shallow, cache-friendly

A B-tree (Bayer and McCreight, 1972) is a search tree whose nodes each hold many sorted keys in a small array, and so have many children. Its rules keep every leaf at the same depth, so it's always balanced. When a node overflows, it splits in two and passes its middle key up to its parent, so the tree grows at the root, never at one side. Step through it with a small node size (at most 3 keys):

Rust's documentation explains the choice directly: a perfectly balanced BST does the theoretical minimum number of comparisons, but "every element is stored in its own individually heap-allocated node. This means that every single insertion triggers a heap-allocation, and every comparison is a potential cache-miss due to the indirection." A B-tree instead "makes each node contain B-1 to 2B-1 elements in a contiguous array", which cuts allocations by a factor of B and improves cache efficiency. That's chapter F1's lesson, applied to trees. In the current standard-library source, B = 6, so each node holds 5 to 11 keys, searched with a simple linear scan.

🟣 Coming from C#/.NET

The closest equivalent of BTreeMap is SortedDictionary<K,V>: same O(log n) behaviour and sorted iteration, but a binary tree inside, one node per entry. And the B-tree is the structure you already rely on every day: SQL Server and PostgreSQL indexes are B-trees. PostgreSQL's docs: "By default, the CREATE INDEX command creates B-tree indexes", and they support < <= = >= > range queries and sorted retrieval. A database just uses bigger nodes (a whole disk page each) for the same reason Rust uses 11-key nodes: fetching one more neighbour is nearly free once you've fetched the block.

Binary heaps and priority queues

A priority queue is an ADT with two main operations: insert an item with a priority, and remove the item with the highest (or lowest) priority. The standard data structure for it is the binary heap: a binary tree that is

  • complete, filled level by level, left to right, so it fits perfectly in an array with no pointers at all: node i's children sit at 2i+1 and 2i+2, and its parent at (i−1)/2.
  • heap-ordered: every parent is ≥ its children (a max-heap), so the largest item is always at index 0. Siblings are in no particular order. That's the "triage desk" economy: it's much less ordering than a sorted list.

Push appends at the end and sifts up (swap with the parent while bigger). Pop takes the root, moves the last item to the top and sifts down (swap with the larger child while smaller). Each walks one path, so it's O(log n):

Rust's BinaryHeap is "a priority queue implemented with a binary heap. This will be a max-heap." Its docs give peek O(1), pop O(log n), and push O(1) expected on randomly ordered input (degrading to O(log n) amortised for ascending input). Wrap items in std::cmp::Reverse to make it a min-heap, which is what timers need.

🟣 Coming from C#/.NET

.NET's PriorityQueue<TElement,TPriority> is documented as "an array-backed, quaternary min-heap" (four children per node instead of two), so it's a min-heap by default, where Rust's is a max-heap. Both share one caveat, from Microsoft's docs: the type "does not guarantee first-in-first-out semantics for elements of equal priority". If ties must come out in arrival order (two timers due at the same millisecond), add a sequence number to the priority, for example (due_time, seq).

Tries (in brief)

A trie (prefix tree) stores strings by their characters: each edge adds one character, so all keys sharing a prefix share a path. Tries power autocomplete and URL routing, and lookup cost depends on the key's length rather than on how many keys are stored. You often don't need a dedicated trie in Rust: a sorted BTreeSet<String> plus a range query answers "all keys starting with ord" in O(log n + k), as Exercise 2 shows.

Deep dive: why B·log n comparisons can beat log₂ n

Rust's docs are candid that the B-tree does more comparisons: "searching for a random element is expected to take B * log(n) comparisons, which is generally worse than a BST. In practice, however, performance is excellent." How can more work be faster?

Count memory fetches instead of comparisons. In a binary tree of a million nodes, a lookup visits about 20 nodes, each a separate heap allocation somewhere in memory: up to 20 cache misses at about 100 ns each from RAM (chapter F1's ladder). A B-tree with up to 11 keys per node has fan-out up to 12, so a million keys need only about \(\log_{12} 10^6 \approx 6\) levels. Within a node, the keys are contiguous, so scanning them is a few cache lines that the CPU prefetches. Six likely misses plus some cheap in-cache comparisons beat twenty misses.

Databases push the same idea further: a disk or SSD read fetches a whole page (kilobytes), so database B-tree nodes hold hundreds of keys, and a table of a billion rows is typically only 3–5 levels deep. The general principle, which you'll reuse when designing the workflow engine's storage, is: minimise the number of slow fetches, not the number of fast operations.

The 6-level and 3–5-level figures are back-of-envelope estimates from fan-out, to show the shape of the argument. Real depths depend on fill factor and key size.

Step 1 — watch a BST degenerate

A minimal BST stored in an arena (chapter F3): nodes live in a Vec, and children are Option<usize> indices, where None means "no child". Option is Rust's "maybe a value" type (chapter 2.5); match handles both cases.

use std::hint::black_box;
use std::time::Instant;

/// A plain (unbalanced) binary search tree stored in an arena (chapter F3):
/// children are indices into `nodes`, `None` meaning "no child".
struct Node {
    key: u64,
    left: Option<usize>,
    right: Option<usize>,
}

struct Bst {
    nodes: Vec<Node>,
}

impl Bst {
    fn new() -> Bst {
        Bst { nodes: Vec::new() }
    }

    /// Walk down from the root: smaller keys go left, larger go right.
    fn insert(&mut self, key: u64) {
        let new_index = self.nodes.len();
        self.nodes.push(Node { key, left: None, right: None });
        if new_index == 0 {
            return; // first node is the root
        }
        let mut at = 0;
        loop {
            let go_left = key < self.nodes[at].key;
            let child = if go_left { self.nodes[at].left } else { self.nodes[at].right };
            match child {
                Some(next) => at = next,
                None => {
                    if go_left { self.nodes[at].left = Some(new_index); } else { self.nodes[at].right = Some(new_index); }
                    return;
                }
            }
        }
    }

    fn contains(&self, key: u64) -> bool {
        let mut cur = if self.nodes.is_empty() { None } else { Some(0) };
        while let Some(i) = cur {
            let n = &self.nodes[i];
            if key == n.key { return true; }
            cur = if key < n.key { n.left } else { n.right };
        }
        false
    }

    /// Height = number of nodes on the longest root-to-leaf path.
    fn height(&self, at: Option<usize>) -> usize {
        match at {
            None => 0,
            Some(i) => 1 + self.height(self.nodes[i].left).max(self.height(self.nodes[i].right)),
        }
    }
}

fn next_rand(s: &mut u64) -> u64 { *s ^= *s << 13; *s ^= *s >> 7; *s ^= *s << 17; *s }

fn main() {
    let n: u64 = 20_000;
    let sorted: Vec<u64> = (0..n).collect();
    let mut shuffled = sorted.clone();
    let mut seed = 7;
    for i in (1..shuffled.len()).rev() {
        let j = (next_rand(&mut seed) % (i as u64 + 1)) as usize;
        shuffled.swap(i, j);
    }
    for (label, keys) in [("random order", &shuffled), ("sorted order", &sorted)] {
        let mut t = Bst::new();
        for &k in keys.iter() { t.insert(k); }
        let start = Instant::now();
        let mut found = 0;
        for k in 0..n { if t.contains(black_box(k)) { found += 1; } }
        let ms = start.elapsed().as_secs_f64() * 1e3;
        println!("{label}: height {:>6}  (log2 n = {:.1})  look up all {n}: {:>8.2} ms  found {found}",
                 t.height(Some(0)), (n as f64).log2(), ms);
    }
}
random order: height     39  (log2 n = 14.3)  look up all 20000:     2.49 ms  found 20000
sorted order: height  20000  (log2 n = 14.3)  look up all 20000:   765.44 ms  found 20000

A random-order BST's height (39) is within a small factor of \(\log_2 n\) (14.3), which is typical. Sorted order produces the worst case. Note also that height is recursive: on the 20,000-deep tree it recurses 20,000 levels. That fits in the 8 MB main-thread stack here, but it's exactly the deep-recursion risk from chapter F1. A balanced tree avoids it by design.

Step 2 — map lookups head to head

use std::collections::{BTreeMap, HashMap};
use std::hint::black_box;
use std::time::Instant;

fn next_rand(s: &mut u64) -> u64 { *s ^= *s << 13; *s ^= *s >> 7; *s ^= *s << 17; *s }

fn main() {
    const N: usize = 1_000_000;
    let mut seed = 99;
    let keys: Vec<u64> = (0..N).map(|_| next_rand(&mut seed)).collect();
    let mut probes = keys.clone();
    for i in (1..N).rev() { let j = (next_rand(&mut seed) % (i as u64 + 1)) as usize; probes.swap(i, j); }

    let hash: HashMap<u64, u64> = keys.iter().map(|&k| (k, k)).collect();
    let btree: BTreeMap<u64, u64> = keys.iter().map(|&k| (k, k)).collect();
    let mut sorted: Vec<u64> = keys.clone();
    sorted.sort_unstable();

    let t = Instant::now();
    let mut hits = 0;
    for p in &probes { if hash.contains_key(black_box(p)) { hits += 1; } }
    let t_hash = t.elapsed();
    let t = Instant::now();
    for p in &probes { if btree.contains_key(black_box(p)) { hits += 1; } }
    let t_btree = t.elapsed();
    let t = Instant::now();
    for p in &probes { if sorted.binary_search(black_box(p)).is_ok() { hits += 1; } }
    let t_vec = t.elapsed();
    assert_eq!(hits, 3 * N);
    println!("1,000,000 random lookups among 1,000,000 u64 keys:");
    println!("  HashMap:                  {:>6.1} ms", t_hash.as_secs_f64() * 1e3);
    println!("  BTreeMap:                 {:>6.1} ms", t_btree.as_secs_f64() * 1e3);
    println!("  sorted Vec + binary_search: {:>4.1} ms", t_vec.as_secs_f64() * 1e3);
}

  HashMap:                    23.9 ms
  BTreeMap:                  114.7 ms
  sorted Vec + binary_search: 26.5 ms

Step 3 — what only an ordered map can do

use std::collections::BTreeMap;

fn main() {
    // Audit events keyed by timestamp (seconds). A BTreeMap keeps them ordered.
    let mut events: BTreeMap<u64, &str> = BTreeMap::new();
    events.insert(1_700_000_120, "rule R7 fired");
    events.insert(1_700_000_005, "workflow W1 started");
    events.insert(1_700_000_300, "workflow W1 completed");
    events.insert(1_700_000_060, "timer T3 due");
    events.insert(1_700_000_240, "rule R2 fired");

    // "What happened between t=60 and t=240 (exclusive)?" -- O(log n) to find the start.
    for (t, what) in events.range(1_700_000_060..1_700_000_240) {
        println!("{t}: {what}");
    }
    // First and last are O(log n) too:
    println!("earliest: {:?}", events.first_key_value());
    println!("latest:   {:?}", events.last_key_value());
}
1700000060: timer T3 due
1700000120: rule R7 fired
earliest: Some((1700000005, "workflow W1 started"))
latest:   Some((1700000300, "workflow W1 completed"))

a..b is a half-open range: it includes a and excludes b, so the event at 240 is not printed. Unlike a HashMap, the output is identical on every run.

Step 4 — the timer wheel problem

use std::cmp::Reverse;
use std::collections::BinaryHeap;
use std::hint::black_box;
use std::time::Instant;

fn next_rand(s: &mut u64) -> u64 { *s ^= *s << 13; *s ^= *s >> 7; *s ^= *s << 17; *s }

fn main() {
    const N: usize = 1_000_000; // pending timers: (due time, timer id)
    const FIRE: usize = 1_000;  // how many of the earliest timers we fire
    let mut seed = 5;
    let timers: Vec<(u64, u64)> = (0..N as u64).map(|id| (next_rand(&mut seed) % 86_400_000, id)).collect();

    // Approach 1: a plain Vec; to find the next due timer, scan for the minimum.
    let mut list = timers.clone();
    let t = Instant::now();
    let mut fired_list = Vec::with_capacity(FIRE);
    for _ in 0..FIRE {
        let (pos, _) = list.iter().enumerate().min_by_key(|(_, t)| **t).unwrap();
        fired_list.push(list.swap_remove(pos)); // O(1) remove once found
    }
    let t_list = t.elapsed();

    // Approach 2: a min-heap. Reverse turns Rust's max-heap into a min-heap.
    let mut heap: BinaryHeap<Reverse<(u64, u64)>> = timers.iter().map(|&t| Reverse(t)).collect();
    let t = Instant::now();
    let mut fired_heap = Vec::with_capacity(FIRE);
    for _ in 0..FIRE {
        let Reverse(next) = heap.pop().unwrap(); // O(log n)
        fired_heap.push(next);
    }
    let t_heap = t.elapsed();

    assert_eq!(fired_list, fired_heap); // same timers, same order
    black_box((&list, &heap));
    println!("fire the earliest {FIRE} of {N} timers:");
    println!("  Vec, scan for minimum each time: {:>8.1} ms", t_list.as_secs_f64() * 1e3);
    println!("  BinaryHeap (min-heap) pop:       {:>8.3} ms", t_heap.as_secs_f64() * 1e3);
}
fire the earliest 1000 of 1000000 timers:
  Vec, scan for minimum each time:   1816.9 ms
  BinaryHeap (min-heap) pop:          0.098 ms

Timers are (due_time, id) tuples. Tuples compare field by field, so equal due times are broken by id, which gives a stable, deterministic order (the tie caveat above). Building the heap from the million timers (collect) happens before the timer starts, and isn't measured.

Exercise 1 — top-k without sorting everything ★★☆

Return the k largest values of a large slice, largest first, in O(n log k) time and O(k) memory. Sorting the whole slice would be O(n log n) and O(n). For [5, 1, 9, 3, 7, 9, 2] and k = 3: [9, 9, 7].

Show solution 
use std::cmp::Reverse;
use std::collections::BinaryHeap;

/// The k largest values, largest first, in O(n log k) time and O(k) memory.
pub fn top_k(values: &[u64], k: usize) -> Vec<u64> {
    let mut heap: BinaryHeap<Reverse<u64>> = BinaryHeap::with_capacity(k + 1); // a min-heap
    for &v in values {
        heap.push(Reverse(v));
        if heap.len() > k {
            heap.pop(); // drop the smallest of the current k+1
        }
    }
    let mut out: Vec<u64> = heap.into_iter().map(|Reverse(v)| v).collect();
    out.sort_unstable_by(|a, b| b.cmp(a)); // largest first
    out
}

fn main() {
    println!("{:?}", top_k(&[5, 1, 9, 3, 7, 9, 2], 3)); // [9, 9, 7]
}

The trick is counter-intuitive: to keep the largest k, use a min-heap, so the smallest of your current candidates is always on top, ready to be evicted. Useful for "top 10 slowest rules" dashboards over millions of evaluations.

Exercise 2 — autocomplete with a range query ★★☆ product skill

A rule-authoring UI suggests fact names as the user types. Given a BTreeSet<String>, return every word starting with a prefix, in sorted order, without scanning the whole set.

Show solution 
use std::collections::BTreeSet;

/// All words starting with `prefix`, in sorted order.
pub fn autocomplete<'a>(words: &'a BTreeSet<String>, prefix: &str) -> Vec<&'a str> {
    words
        .range(prefix.to_string()..) // jump straight to the first word >= prefix: O(log n)
        .take_while(|w| w.starts_with(prefix)) // stop at the first word that doesn't match
        .map(|w| w.as_str())
        .collect()
}

fn main() {
    let words: BTreeSet<String> = ["order", "orderline", "organisation", "outcome", "rule"]
        .iter().map(|s| s.to_string()).collect();
    println!("{:?}", autocomplete(&words, "ord")); // ["order", "orderline"]
}

In sorted order, every word with a given prefix is contiguous and starts at the first word ≥ the prefix. So: one O(log n) jump, then read exactly the k matches. The 'a is a lifetime (chapter 2.11). It says the returned &strs borrow from words.

Exercise 3 — build a heap by hand ★★★

Implement a max-heap on a Vec<i64> with push (sift up) and pop (sift down), using the index formulas from the animation. Pushing 5, 3, 8, 1, 9, 2 and then popping until empty must give 9, 8, 5, 3, 2, 1.

Show solution 
/// A max-heap built by hand on a Vec.
/// Children of index i live at 2i+1 and 2i+2; the parent of i lives at (i-1)/2.
pub struct MaxHeap {
    data: Vec<i64>,
}

impl MaxHeap {
    pub fn new() -> MaxHeap {
        MaxHeap { data: Vec::new() }
    }

    pub fn push(&mut self, value: i64) {
        self.data.push(value);
        let mut i = self.data.len() - 1;
        while i > 0 {
            let parent = (i - 1) / 2;
            if self.data[i] <= self.data[parent] {
                break; // heap property restored
            }
            self.data.swap(i, parent); // sift up
            i = parent;
        }
    }

    pub fn pop(&mut self) -> Option<i64> {
        if self.data.is_empty() {
            return None;
        }
        let last = self.data.len() - 1;
        self.data.swap(0, last);
        let top = self.data.pop();
        let mut i = 0;
        loop {
            let (l, r) = (2 * i + 1, 2 * i + 2);
            let mut largest = i;
            if l < self.data.len() && self.data[l] > self.data[largest] { largest = l; }
            if r < self.data.len() && self.data[r] > self.data[largest] { largest = r; }
            if largest == i {
                break;
            }
            self.data.swap(i, largest); // sift down
            i = largest;
        }
        top
    }
}

impl Default for MaxHeap {
    fn default() -> Self {
        Self::new() // Clippy's suggestion: types with a no-argument new() should implement Default
    }
}

fn main() {
    let mut h = MaxHeap::new();
    for v in [5, 3, 8, 1, 9, 2] {
        h.push(v);
    }
    let mut out = Vec::new();
    while let Some(v) = h.pop() {
        out.push(v);
    }
    println!("{out:?}"); // [9, 8, 5, 3, 2, 1]
}

Popping every element of a heap yields them in sorted order: that's heapsort, O(n log n) (chapter F7). No pointers, no allocations beyond the Vec: the complete-tree shape is what makes the array layout possible.

Common misconceptions and pitfalls

⚠️ "A BST is O(log n)."

Only a balanced one. Unbalanced, it's O(height), up to O(n), and sorted input (IDs, timestamps) is the common worst case. Use a library's balanced structure; don't hand-roll a BST for production.

⚠️ Iterating a heap and expecting sorted order

BinaryHeap::iter() visits items "in arbitrary order" (per its docs). Only repeated pop (or into_sorted_vec) gives sorted output.

⚠️ Forgetting Rust's heap is a max-heap

A timer queue built with plain BinaryHeap<u64> fires the latest deadline first. Wrap with Reverse. .NET's PriorityQueue is the opposite default (min).

⚠️ Assuming equal priorities come out in insertion order

Neither Rust's BinaryHeap nor .NET's PriorityQueue promises FIFO among equals. Add a sequence number to the priority tuple when it matters.

⚠️ "BTreeMap is slow, avoid it."

It's about 5× slower than HashMap for random point lookups (Figure 4), and the right choice whenever you need order, ranges or deterministic iteration. Pick by required operations first, then by speed.

Real-world view: trees and heaps in your products

🏗 Architecture view
  • Workflow timers (in memory): a min-heap of (due_time, sequence, timer_id). peek tells the scheduler how long to sleep; pop fires due timers in O(log n). Cancelled timers are usually left in the heap and skipped when popped ("lazy deletion"), because removing from the middle of a heap is awkward. Chapter 10.6 builds this.
  • Workflow timers (durable): after a restart the heap is rebuilt from the database by a query like WHERE due_at < now() + interval ORDER BY due_at, served by a B-tree index on due_at. Same idea, different storage.
  • Rule engine: ordered indexes (BTreeMap) make range conditions like amount > 10000 cheap: one O(log n) jump, then read the matches. Hash indexes serve equality joins (chapter F4). The engine will use both.
  • Agenda and conflict resolution: when several rules match, the engine must pick which fires first, by salience then recency. That's a priority queue (chapter 9.4).
  • Deterministic output: audit logs, reports and anything replayed should come from ordered structures, as chapter F4 warned.

Summary

  • Tree operations cost O(height). An unbalanced BST degrades to O(n) on sorted input (measured: height 20,000, 300× slower). Balanced trees keep height O(log n).
  • B-trees store many keys per node in a contiguous array: shallow, always balanced, cache-friendly. Rust's BTreeMap (B = 6, 5–11 keys per node) and database indexes (PostgreSQL's default) are B-trees.
  • A binary heap is a complete tree in an array (children at 2i+1, 2i+2). Push sifts up, pop sifts down, both O(log n), and peek is O(1). BinaryHeap is a max-heap; use Reverse for min.
  • Measured: HashMap ≈ sorted Vec (~24–27 ms per million lookups) > BTreeMap (~116 ms) for point lookups. Choose BTreeMap for order, ranges and determinism.
  • Priority queues turn "what's next?" from O(n) to O(log n): measured 1.8 s vs 0.1 ms to fire 1,000 of a million timers. This is the core of your workflow engine's scheduler.
