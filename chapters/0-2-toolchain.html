Toolchain and your first project

Learning objectives

  • Install Rust with rustup, and manage toolchains, channels and components
  • Create, build, run, test, format and lint a project with cargo
  • Read Cargo.toml and Cargo.lock, and explain how version requirements work
  • Choose between debug and release builds, and explain why the difference is so large
  • Pin a compiler version per project and set up a standard CI quality gate
  • Map each Rust tool to its .NET equivalent

Why this matters

💡 Why this matters

Toolchain choices are some of the first decisions you'll make for a client team, and they are hard to change later: how compiler versions are pinned, what the CI gate enforces, how dependencies are locked. The good news: Rust's tooling is famously consistent. One tool, cargo, does almost everything, and every Rust project in the world is laid out and built the same way. Once you know it, you can walk into any Rust codebase and build it in minutes.

Intuition first: the tools and their .NET twins

🧭 Analogy

Think of rustup as the .NET SDK installer combined with global.json: it installs compiler versions and picks the right one for each project. cargo is the dotnet CLI, MSBuild and the NuGet client rolled into one. crates.io is nuget.org. rust-analyzer is the language service behind your editor, like Roslyn inside the C# Dev Kit.

Installing Rust with rustup

Always install through rustup, the official installer and version manager. It lives in your home directory (~/.rustup for toolchains, ~/.cargo/bin for commands), so it needs no admin rights.

  • macOS / Linux / WSL: run the command below, then open a new terminal (or run . "$HOME/.cargo/env").
  • Windows: download and run rustup-init.exe from rust-lang.org/tools/install. It may ask you to install the Visual Studio C++ Build Tools, because Rust on Windows uses the MSVC linker. If you already have Visual Studio with the C++ workload, you're set.

Dependencies, versions and the lockfile

cargo add rand adds the rand crate (random numbers) to Cargo.toml as rand = "0.10.3". That string is a version requirement, not an exact version. Cargo's default is the caret rule: any later version with the same left-most non-zero number is allowed, because SemVer says it should be compatible.

You writeCargo acceptsWhy
"1.2.3">=1.2.3, <2.0.0Major version 1 is the left-most non-zero part
"0.10.3">=0.10.3, <0.11.0Before 1.0, the minor number signals breaking changes
"0.0.3"exactly 0.0.3The patch number is the left-most non-zero part
 Source: The Cargo Book, “Specifying Dependencies”. NuGet's 1.2.3 means “1.2.3 or higher, with no upper bound”, which is looser than Cargo's caret rule.

The versions actually chosen are recorded in Cargo.lock, so every machine builds exactly the same dependency set. cargo new commits it to git by default. The Cargo Book's caution is worth repeating to clients: "Cargo.lock does not affect the consumers of your package, only Cargo.toml does that." A library's users resolve their own versions. For an application or service, keep the lockfile in git and build in CI with --locked, which fails if the lockfile is out of date.

Debug vs release builds

Cargo has two built-in build profiles:

  • dev (used by cargo build, run, test): fast to compile, no optimisation, full debug information. Output goes to target/debug/.
  • release (--release): slower to compile, fully optimised. Output goes to target/release/.

The gap between them is far larger than most .NET developers expect. These are real measurements from this course's lab machine (Apple M2 Pro, Rust 1.99.0, median of three runs):

🟣 Coming from C#/.NET

In .NET, Debug and Release usually differ by a modest factor, because the JIT optimises at runtime either way. Rust has no JIT: the compiler does all the optimising ahead of time, and only in release. Never judge Rust's performance from a debug build.

Formatting, linting, testing and docs

Four commands make up the everyday quality loop. All come with the default rustup install.

  • cargo fmt — formats code with rustfmt. There is one official style, so teams don't argue about formatting. cargo fmt --check only reports differences, which makes it suitable for CI.
  • cargo clippy — runs Clippy, the official linter, with hundreds of lints for bugs, performance and non-idiomatic code.
  • cargo test — compiles and runs every function marked #[test]. Tests usually live in the same file as the code (chapter 3.4).
  • cargo doc — builds HTML API docs from /// comments. Every crate published on crates.io gets its docs hosted automatically on docs.rs.

Editor setup: VS Code

  1. Install the rust-analyzer extension (publisher: rust-lang). This is the official language server.
  2. For debugging, install CodeLLDB. rust-analyzer then shows Run | Debug links above main and above each test.
  3. Open the project folder (the one containing Cargo.toml), not a single file.

You'll see inline errors as you type, greyed inlay hints showing the types the compiler inferred (very helpful while learning), go-to-definition into library source, and refactorings.

Deep dive: what happens when you run cargo build

Cargo works out which crates need (re)building, in dependency order, and calls rustc once per crate. Inside rustc, your code passes through a series of intermediate representations. Step through them:

Why compiles get faster after the first one: dependencies are compiled once and cached in target/, and your own crate is compiled incrementally, reusing unchanged work. cargo check stops after the MIR stage (no code generation), which is why it's the fastest way to ask "does this compile?". rust-analyzer gives you similar feedback continuously as you type.

How rustup chooses the compiler: the cargo and rustc in ~/.cargo/bin are small proxies installed by rustup. Each time they run, they choose a toolchain, in this order of precedence: a +toolchain argument (cargo +nightly build), the RUSTUP_TOOLCHAIN environment variable, a directory override, a rust-toolchain.toml file (searched upward from the current folder), and finally the default.

The benchmark used for Figure 2 (run cargo run and cargo run --release):

use std::time::Instant;

/// Counts primes below `limit` by trial division (deliberately simple).
fn count_primes(limit: u32) -> u32 {
    let mut count = 0;
    for n in 2..limit {
        let mut is_prime = true;
        let mut d = 2;
        while d * d <= n {
            if n % d == 0 {
                is_prime = false;
                break;
            }
            d += 1;
        }
        if is_prime {
            count += 1;
        }
    }
    count
}

/// Sum of squares of the even numbers, written as an iterator chain.
fn sum_even_squares(limit: u64) -> u64 {
    (0..limit).filter(|n| n % 2 == 0).map(|n| n * n % 1_000_007).sum()
}

fn main() {
    let start = Instant::now();
    let primes = count_primes(5_000_000);
    println!("loop:     {primes} primes in {} ms", start.elapsed().as_millis());

    let start = Instant::now();
    let total = sum_even_squares(200_000_000);
    println!("iterator: sum {total} in {} ms", start.elapsed().as_millis());
}
$ cargo run                 (dev profile)
loop:     348513 primes in 1217 ms
iterator: sum 49935891238200 in 2138 ms
$ cargo run --release
loop:     348513 primes in 518 ms
iterator: sum 49935891238200 in 115 ms

Step 2 — write a small program

A dice roller: it takes the number of dice from the command line (default 2), rolls them, and prints the total. Don't worry about every symbol yet; the comments explain the idea, and Module 2 covers each piece.

use std::env;

fn main() {
    // First command-line argument, parsed as a number; default to 2.
    let count: u32 = env::args()
        .nth(1)
        .and_then(|arg| arg.parse().ok())
        .unwrap_or(2);

    // Roll `count` dice and collect the results into a list (a Vec).
    let rolls: Vec<u32> = (0..count).map(|_| rand::random_range(1..=6)).collect();
    println!("{rolls:?} => total {}", total(&rolls));
}

/// Adds up the dice rolls.
fn total(rolls: &[u32]) -> u32 {
    let mut sum = 0;
    for r in rolls { sum += r; }
    return sum;
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn adds_rolls() {
        assert_eq!(total(&[1, 2, 3]), 6);
    }

    #[test]
    fn no_rolls_is_zero() {
        assert_eq!(total(&[]), 0);
    }
}

In Rust, the last expression in a function body is the return value (no semicolon). Writing return there works, but it isn't idiomatic. An even more idiomatic version replaces the whole loop:

/// Adds up the dice rolls.
fn total(rolls: &[u32]) -> u32 {
    rolls.iter().sum()
}

cargo clippy now finishes with no warnings.

Step 6 — pin the toolchain

For real projects, record the compiler version in the repository so every developer and CI agent uses the same one. Create rust-toolchain.toml next to Cargo.toml (the output below came from the greet project you'll build in Exercise 1; the result is the same in any folder):

[toolchain]
channel = "1.99.0"
components = ["rustfmt", "clippy"]
rustup show
active toolchain
----------------
name: 1.99.0-aarch64-apple-darwin
active because: overridden by '~/projects/greet/rust-toolchain.toml'

If the pinned version isn't installed, the first cargo command in the folder installs it automatically. rustup tells you that you can opt out with RUSTUP_AUTO_INSTALL=0. To install explicitly, run rustup install. Upgrading a team means one pull request that changes this file.

Exercises

Exercise 1 — greet ★☆☆

Create a new project greet. It should print Hello, world!, or Hello, <name>! when a name is passed (cargo run -- Sandip). Put the text-building in a separate function, add one test for it, and make sure cargo fmt --check and cargo clippy are clean.

Hint: format!("Hello, {name}!") builds a String, like C# string interpolation. env::args().nth(1).unwrap_or_else(|| "world".to_string()) gives the first argument or a default.

Show solution 
use std::env;

fn main() {
    let name = env::args().nth(1).unwrap_or_else(|| "world".to_string());
    println!("{}", greeting(&name));
}

/// Builds the greeting text for `name`.
fn greeting(name: &str) -> String {
    format!("Hello, {name}!")
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn greets_by_name() {
        assert_eq!(greeting("Ada"), "Hello, Ada!");
    }
}

Exercise 2 — a CI quality gate ★★☆ consultant skill

Write the commands a CI pipeline should run for greet, in order, so that the build fails on unformatted code, any Clippy warning, a failing test or an out-of-date lockfile. Also pin the toolchain.

Show solution 
set -e                                     # stop at the first failing command
cargo fmt --check                          # formatting
cargo clippy --all-targets -- -D warnings  # lints; -D turns warnings into errors
cargo test --locked                        # tests; --locked fails if Cargo.lock is stale
cargo build --release --locked             # the artefact you ship

Plus the rust-toolchain.toml from Step 6, so CI and laptops use the same compiler. --all-targets makes Clippy check tests and examples too. Ordering cheapest-first gives fast feedback. Tested: on the solution to Exercise 1 the whole gate passes (exit code 0).

Exercise 3 — read the dependency tree ★★☆

In hello-rust, run cargo tree. Which crate pulls in libc? Then compare with the eight packages cargo add locked in Step 1: one of them (r-efi) doesn't appear in the tree. Why?

Show solution 
hello-rust v0.1.0 (~/projects/hello-rust)
└── rand v0.10.3
    ├── chacha20 v0.10.2
    │   ├── cfg-if v1.0.5
    │   └── rand_core v0.10.1
    ├── getrandom v0.4.3

getrandom (which asks the operating system for random bytes) depends on libc on Unix-like systems such as macOS. r-efi is a dependency only on UEFI targets. Cargo.lock records versions for every platform so the lockfile is the same on all machines, but cargo tree shows only what applies to the platform you're building for. (cpufeatures is also missing on this machine: it is only needed on some CPU architectures.) Platform-specific dependencies are common, so check cargo tree --target <triple> when you audit a Linux deployment from a Mac.

Common misconceptions and pitfalls

⚠️ Measuring performance in debug builds

The most common way newcomers conclude "Rust is slow". Always benchmark with --release (Figure 2).

⚠️ Committing target/

It can grow to gigabytes and is machine-specific. cargo new already ignores it. Check this when you take over a repository someone else created by hand.

⚠️ Two Rust installations

Installing Rust from an OS package manager (for example Homebrew's rust) as well as rustup puts two different cargos on your PATH. Whichever comes first silently wins. Use rustup only, and check with which cargo (expect ~/.cargo/bin/cargo).

⚠️ Forgetting -- with cargo run

cargo run 5 passes 5 to cargo; cargo run -- 5 passes it to your program. The same rule as dotnet run.

⚠️ Confusing cargo add and cargo install

cargo add adds a library dependency to this project. cargo install builds a command-line tool into ~/.cargo/bin, like dotnet tool install -g.

⚠️ Silencing Clippy instead of reading it

Clippy's suggestions are one of the fastest ways to learn idiomatic Rust. Fix them, or allow a specific lint with a written reason. Never turn them all off.

Real-world view: a client-ready project baseline

🏗 Architecture view

When you set up or review a Rust repository for a client, this is the baseline to check:

  • rust-toolchain.toml pins the compiler and the components CI needs.
  • Cargo.lock is committed for applications and services, and CI builds with --locked.
  • A CI gate runs fmt-check → clippy with -D warnings → tests → release build (Exercise 2).
  • The target/ folder is cached between CI runs, keyed on Cargo.lock and the toolchain version. A cold build of a large service can take many minutes; a warm one is much faster (chapter 6.5).
  • A regular upgrade cadence: bump the toolchain roughly every six weeks, or at least every few releases, so that each upgrade stays small.
  • Release artefacts are built once with --release in CI and promoted through environments, never rebuilt per environment (the same rule as for .NET publish output).

Later chapters add supply-chain checks (cargo deny, cargo audit, chapter 6.4) and minimum-supported-Rust-version policies (chapter 3.5).

Summary

  • rustup installs and selects toolchains (channel + components + targets). Pin per project with rust-toolchain.toml.
  • cargo does everything else: new, check, build, run, test, add, fmt, clippy, doc, tree.
  • Cargo.toml holds version requirements (caret rule by default). Cargo.lock records the exact versions. Commit it for applications and build with --locked.
  • Debug and release can differ by an order of magnitude, because all optimisation happens at compile time. Never benchmark a debug build.
  • A client-ready baseline: pinned toolchain, committed lockfile, CI gate (fmt → clippy -D warnings → test → release build), cached target/, regular upgrades.
