Hashing and maps

Learning objectives

  • Explain how a hash table turns a key into a slot, and why that gives expected O(1) lookups
  • Describe collisions and the two families of fixes (chaining, open addressing), including why deletions leave tombstones
  • Explain load factor and resizing, and read the capacity steps of a real HashMap
  • Describe how SwissTable, the design behind Rust's HashMap, uses one metadata byte per slot and checks 16 slots at once
  • Explain HashDoS, reproduce it, and choose a hasher deliberately (safe default vs fast)
  • Apply the Eq/Hash contract correctly, and choose between HashMap, BTreeMap and a plain Vec

Why this matters

💡 Why this matters

Hash maps are the workhorse of almost every service you've built: caches, lookups by ID, deduplication, grouping. In your products they're everywhere. The rule engine indexes facts by attribute value so a rule can find matching facts without scanning everything. The workflow engine looks up running workflows by ID and remembers which messages it has already processed (idempotency).

They also hide a security trap. In this chapter you'll measure an attacker turning 32,000 innocent-looking keys into 1.4 seconds of CPU instead of 1.7 ms, and see exactly which design choice in Rust's standard library prevents it.

Intuition first: the cloakroom

🧭 Analogy

A theatre cloakroom has 100 numbered hooks. Instead of searching every hook for your coat, the attendant uses a rule to turn your name into a hook number, say "add up the letters, keep the last two digits". To fetch your coat they apply the same rule and walk straight to that hook. That rule is a hash function; the row of hooks is a hash table.

Two people will sometimes get the same hook number: a collision. The cloakroom needs a policy for that, such as "use the next free hook". And if a prankster learns the rule, they can send a hundred friends whose names all add up to the same number, jamming one hook while the attendant searches the whole corridor every time. That is the HashDoS attack.

Core explanation

Basic

Maps and sets

A map (also called a dictionary or associative array) stores key → value pairs and answers "what is the value for this key?". A set stores just keys and answers "is this key present?". Both are abstract data types (chapter F3). The hash table is the most common data structure behind them. In Rust that's HashMap<K, V> and HashSet<T>; in .NET, Dictionary<TKey, TValue> and HashSet<T>.

Hash functions

A hash function turns a key of any size into a fixed-size number. A good one for hash tables is:

  1. Deterministic within a run: the same key always gives the same hash, otherwise you'd never find anything again.
  2. Uniform: it spreads different keys evenly, so similar keys ("order-1", "order-2") land far apart.
  3. Fast, because it runs on every insert and lookup.
  4. For tables exposed to untrusted input, unpredictable to outsiders. That's the HashDoS story below.

The table then reduces the hash to a slot index. When the capacity is a power of two, hash % capacity is a single bitwise AND, which is one reason tables grow by doubling.

Collisions are inevitable

There are vastly more possible keys than slots, so different keys must sometimes share a slot: a collision. They happen sooner than intuition suggests. This is the birthday paradox: with 23 people, there's a better-than-even chance two share a birthday. For n keys spread uniformly over m slots:

$$ P(\text{at least one collision}) \approx 1 - e^{-n^2 / (2m)}, \qquad \text{which reaches } 50\% \text{ at } n \approx 1.18\sqrt{m} $$

A table with a million slots should expect its first collision after only about 1,200 keys. So every hash table needs a collision-resolution strategy. There are two families:

  • Separate chaining: each slot holds a small list of every entry that hashed there. Simple, but every chain is more pointer-chasing (chapter F3).
  • Open addressing: all entries live in the slot array itself. On a collision, follow a fixed probe sequence to the next candidate slot. The simplest is linear probing: try the next slot, then the next. Contiguous, so cache-friendly. Rust's HashMap uses open addressing.

Load factor and resizing

The load factor is entries ÷ slots. As it approaches 1, probe sequences grow long, so tables resize before they're full: allocate a bigger slot array and re-insert every entry, because each key's slot depends on the capacity. Like Vec growth (chapter F2), that's O(n) occasionally and amortised O(1) per insert. You can watch it happen:

len -> capacity:  1->3  4->7  8->14  15->28  29->56  57->112  113->224  225->448  449->896  897->1792

That's real output from Lab step 2 (Rust 1.99.0). capacity() reports how many entries fit before the next resize. From 14 onwards each value is exactly 7/8 of a power of two (14 = 16 × 7/8, 28 = 32 × 7/8, …), so the table keeps at least 1/8 of its slots free. The two smallest steps (3, 7) are one less than a power of two. These numbers are observed behaviour of today's implementation, not a documented guarantee.

The Eq/Hash contract

A map must be able to tell when two keys are "the same". So key types implement two traits (Rust's interfaces, chapter 2.9): Eq (equality) and Hash. The Rust docs state the rule that must hold:

k1 == k2  →  hash(k1) == hash(k2)

Equal keys must produce equal hashes; otherwise an equal key is looked for in the wrong slot and never found. (The reverse needn't hold: different keys may collide.) Usually you don't write these by hand: #[derive(PartialEq, Eq, Hash)] generates both from your struct's fields, consistently.

🟣 Coming from C#/.NET

It's the same contract as overriding Equals and GetHashCode together, and the same bug if you override only one. Two differences:

  • Rust won't let a type be a HashMap key unless it implements Eq and Hash, checked at compile time. Notably f64 implements neither (NaN isn't equal to itself), so HashMap<f64, _> is rejected, where C# accepts Dictionary<double, …>. Real compiler output from this chapter's lab:

Intermediate

SwissTable: how Rust's HashMap is built

Rust's docs say: "The hash table implementation is a Rust port of Google's SwissTable." Abseil's design notes describe the key ideas:

  • The 64-bit hash is split in two: H1 (57 bits) picks where to start looking, and H2 (the remaining 7 bits) is a small fingerprint.
  • Alongside the slot array is a metadata array with one byte per slot: "a single control bit and the 7 bit H2 hash". The control bit marks the slot as empty, deleted (a tombstone) or full.
  • Lookups load 16 metadata bytes at once into a SIMD register and compare all 16 against the wanted H2 in a few instructions. Only the slots whose fingerprint matches, usually one or none, need a real key comparison. In the notes' words: "we can winnow 16 candidates down to only those with a matching H2 hash in only a few instructions".
  • As in the animation, "a deleted element does not cease probing, though an empty element would."

HashDoS: when collisions are chosen by an attacker

Hash tables are O(1) expected (chapter F2), assuming keys spread evenly. If an attacker can compute your hash function, they can craft thousands of keys that all land in the same place. Every insert then probes past every earlier one: O(n) per insert, O(n²) in total. Crosby and Wallach showed this in 2003 against hash tables in Perl, the Squid proxy and the Bro intrusion-detection system, using low-bandwidth crafted input. The pattern still matters: anywhere you put user-supplied strings (JSON object keys, HTTP headers, query parameters, rule-fact attributes) into a hash map, an attacker chooses the keys.

The lab reproduces it with a deliberately weak hash (the sum of the key's bytes) and keys built to share the same sum:

The defence is a keyed, randomised hash. Rust's documentation: "By default, HashMap uses a hashing algorithm selected to provide resistance against HashDoS attacks. The algorithm is randomly seeded… The default hashing algorithm is currently SipHash 1-3, though this is subject to change." SipHash (Aumasson and Bernstein, 2012) is a pseudorandom function: with a secret random key chosen when the map is created, outsiders can't predict which keys collide. A visible side effect is that iteration order changes from run to run (Lab step 1).

🟣 Coming from C#/.NET

.NET makes the same trade-off for strings. Microsoft's docs say string hash codes "can differ across .NET implementations, across .NET versions… This implies that two subsequent runs of the same program may return different hash codes", and System.HashCode "uses a statically initialized random seed". Measured on the lab machine with .NET 10: "apple".GetHashCode() returned 2043132168 in one run and 1156942587 in the next. Never persist a hash code, in either platform.

Choosing a hasher deliberately

The protection has a cost. Rust's own docs say SipHash's "performance is very competitive for medium sized keys", but "other hashing algorithms will outperform it for small keys such as integers… though those algorithms will typically not protect against attacks such as HashDoS." Measured: 1 million inserts plus 1 million lookups of u64 keys took a median of 36 ms with the default (range 34–48 ms over 7 runs) and 22 ms with FNV-1a (range 20–29 ms), a simple non-keyed hash. About 1.6× faster.

Deep dive: why "expected O(1)" really is expected — and what keyed hashing buys you

If n keys are spread uniformly at random over m slots, the average number of keys per slot is the load factor \(\alpha = n/m\). For linear probing, Knuth's classic analysis gives an expected number of probes for an unsuccessful search of about

$$ \tfrac{1}{2}\left(1 + \tfrac{1}{(1-\alpha)^2}\right) $$

That's about 2.5 at \(\alpha = 0.5\), and 32.5 at \(\alpha = 0.875\) for plain linear probing. That steep climb is why tables cap their load factor, and why SwissTable's 16-wide fingerprint filtering matters: it makes each group probe almost as cheap as a single slot, so it can run fuller than a textbook linear-probing table.

All of that assumes the uniform-random spread, which is true only if the keys don't depend on the hash function. A fixed public hash function can be inverted by an adversary, and Figure 4 shows the result. A keyed pseudorandom function restores the assumption: without the secret key, the attacker's crafted keys are no better than random ones. That's precisely the guarantee SipHash was designed to provide (Aumasson and Bernstein's paper is titled "SipHash: a fast short-input PRF"). Randomised seeding per map also means an attacker can't use one map's iteration order to learn about another's.

The probe formula is the standard textbook result for linear probing under uniform hashing. It's shown to explain the shape of the curve, not to predict SwissTable's exact numbers.

Step 1 — lookups, and arbitrary order

use std::collections::HashMap;

fn main() {
    let mut stock: HashMap<&str, u32> = HashMap::new();
    for (sku, qty) in [("apple", 3), ("banana", 7), ("cherry", 1), ("damson", 4), ("elder", 9)] {
        stock.insert(sku, qty);
    }
    // Lookups by key are what a map is for:
    println!("cherry -> {:?}, fig -> {:?}", stock.get("cherry"), stock.get("fig"));
    // Iteration order is "arbitrary": run the program twice and compare.
    let keys: Vec<&str> = stock.keys().copied().collect();
    println!("iteration order: {keys:?}");
}

Step 3 — mount a HashDoS attack (on yourself)

use std::collections::HashMap;
use std::hash::{BuildHasherDefault, Hasher};
use std::time::Instant;

/// A deliberately weak hasher: the hash is just the sum of the bytes.
#[derive(Default)]
struct SumHasher(u64);

impl Hasher for SumHasher {
    fn write(&mut self, bytes: &[u8]) {
        for b in bytes {
            self.0 += *b as u64;
        }
    }
    fn finish(&self) -> u64 {
        self.0
    }
}

/// `n` distinct keys whose bytes all add up to the same total: an attacker's dream.
/// Each key is 4 letters plus their "mirror" (z - letter), so every key sums alike.
fn colliding_keys(n: usize) -> Vec<String> {
    (0..n)
        .map(|mut i| {
            let mut s = String::new();
            let mut mirror = String::new();
            for _ in 0..4 {
                let d = (i % 26) as u8;
                i /= 26;
                s.push((b'a' + d) as char);
                mirror.push((b'z' - d) as char);
            }
            s + &mirror
        })
        .collect()
}

fn main() {
    println!("{:>7} {:>16} {:>18}", "keys", "weak hash (ms)", "default SipHash (ms)");
    for n in [1_000, 2_000, 4_000, 8_000, 16_000, 32_000] {
        let keys = colliding_keys(n);

        let start = Instant::now();
        let mut weak: HashMap<&str, u32, BuildHasherDefault<SumHasher>> = HashMap::default();
        for k in &keys {
            weak.insert(k.as_str(), 1);
        }
        let t_weak = start.elapsed();

        let start = Instant::now();
        let mut safe: HashMap<&str, u32> = HashMap::new();
        for k in &keys {
            safe.insert(k.as_str(), 1);
        }
        let t_safe = start.elapsed();

        assert_eq!(weak.len(), n);
        assert_eq!(safe.len(), n);
        println!("{:>7} {:>16.2} {:>18.3}", n, t_weak.as_secs_f64() * 1e3, t_safe.as_secs_f64() * 1e3);
    }
}

Step 4 — the price of safety

use std::collections::HashMap;
use std::hash::{BuildHasherDefault, Hasher};
use std::hint::black_box;
use std::time::Instant;

/// FNV-1a: a classic, very simple, fast non-cryptographic hash. NOT HashDoS-resistant.
struct Fnv1a(u64);

impl Default for Fnv1a {
    fn default() -> Self {
        Fnv1a(0xcbf2_9ce4_8422_2325)
    }
}

impl Hasher for Fnv1a {
    fn write(&mut self, bytes: &[u8]) {
        for b in bytes {
            self.0 ^= *b as u64;
            self.0 = self.0.wrapping_mul(0x0000_0100_0000_01b3);
        }
    }
    fn finish(&self) -> u64 {
        self.0
    }
}

const N: u64 = 1_000_000;

fn main() {
    // Default (SipHash 1-3, randomly keyed)
    let start = Instant::now();
    let mut a: HashMap<u64, u64> = HashMap::with_capacity(N as usize);
    for i in 0..N { a.insert(i, i); }
    let mut hits = 0;
    for i in 0..N { if a.contains_key(&black_box(i)) { hits += 1; } }
    let t_sip = start.elapsed();

    // Same work with FNV-1a
    let start = Instant::now();
    let mut b: HashMap<u64, u64, BuildHasherDefault<Fnv1a>> = HashMap::with_capacity_and_hasher(N as usize, Default::default());
    for i in 0..N { b.insert(i, i); }
    for i in 0..N { if b.contains_key(&black_box(i)) { hits += 1; } }
    let t_fnv = start.elapsed();

    assert_eq!(hits, 2 * N);
    println!("1M inserts + 1M lookups of u64 keys:");
    println!("  SipHash 1-3 (default): {:>6.1} ms", t_sip.as_secs_f64() * 1e3);
    println!("  FNV-1a:                {:>6.1} ms", t_fnv.as_secs_f64() * 1e3);
}
1M inserts + 1M lookups of u64 keys:
  SipHash 1-3 (default):   36.3 ms
  FNV-1a:                  19.9 ms

Exercise 1 — word counts ★☆☆

Write word_counts(text: &str) -> HashMap<String, usize>, counting each whitespace-separated word case-insensitively. For "Rule fires rule FIRES rule": rule → 3, fires → 2.

Hint: map.entry(key).or_insert(0) gives you a mutable reference to the count, inserting 0 first if the key is missing. One hash lookup instead of two.

Show solution 
use std::collections::HashMap;

/// Count how often each word appears (case-insensitive).
pub fn word_counts(text: &str) -> HashMap<String, usize> {
    let mut counts: HashMap<String, usize> = HashMap::new();
    for word in text.split_whitespace() {
        let key = word.to_lowercase();
        *counts.entry(key).or_insert(0) += 1; // insert 0 if missing, then add 1
    }
    counts
}

fn main() {
    let c = word_counts("Rule fires rule FIRES rule");
    println!("rule={} fires={}", c["rule"], c["fires"]); // rule=3 fires=2
}

The Entry API is the idiomatic way to "update or insert". The C# equivalent needs TryGetValue then an assignment, or CollectionsMarshal.GetValueRefOrAddDefault.

Exercise 2 — bounded idempotency window ★★☆ product skill

A workflow engine receives messages that may be delivered more than once. Build a Dedup that remembers the last capacity message IDs and has first_time(id) -> bool, which is true the first time an ID is seen and false for a duplicate inside the window. Memory must stay bounded.

Hint: combine a HashSet (fast "seen?") with a VecDeque from chapter F3 (remembers arrival order, so you know what to forget).

Show solution 
use std::collections::{HashSet, VecDeque};

/// Remembers the last `capacity` message ids and reports duplicates.
pub struct Dedup {
    seen: HashSet<u64>,   // O(1) "have I seen this?"
    order: VecDeque<u64>, // remembers arrival order, to forget the oldest
    capacity: usize,
}

impl Dedup {
    pub fn new(capacity: usize) -> Dedup {
        Dedup { seen: HashSet::new(), order: VecDeque::new(), capacity }
    }

    /// Returns true the first time an id is seen (process it), false for a duplicate.
    pub fn first_time(&mut self, id: u64) -> bool {
        if self.seen.contains(&id) {
            return false;
        }
        self.seen.insert(id);
        self.order.push_back(id);
        if self.order.len() > self.capacity {
            let oldest = self.order.pop_front().unwrap();
            self.seen.remove(&oldest); // keep memory bounded
        }
        true
    }
}

fn main() {
    let mut d = Dedup::new(2);
    for id in [1, 1, 2, 3, 1] {
        println!("message {id}: {}", if d.first_time(id) { "process" } else { "duplicate, skip" });
    }
}
message 1: process
message 1: duplicate, skip
message 2: process
message 3: process
message 1: process

The last line is the important design point: a bounded window means very late duplicates get through. Choose the window from your delivery guarantees, or make the processing itself idempotent. Chapter 10.1 covers both.

Exercise 3 — case-insensitive keys ★★☆

Customers are looked up by e-mail, and "Ada@Example.com " and "ada@example.COM" must find the same customer. Why does HashMap<String, Customer> fail at this out of the box, and what's the simplest correct fix?

Show solution

String's Eq and Hash compare exact bytes, so the two spellings are different keys with (almost certainly) different hashes. The fix must keep the Eq/Hash contract: normalise the key the same way on every insert and every lookup.

use std::collections::HashMap;

/// Customers keyed by e-mail, treating addresses case-insensitively.
pub fn normalise_email(email: &str) -> String {
    email.trim().to_lowercase()
}

fn main() {
    let mut customers: HashMap<String, &str> = HashMap::new();
    customers.insert(normalise_email("Ada@Example.com "), "Ada");
    println!("{:?}", customers.get(&normalise_email("ada@example.COM"))); // Some("Ada")
}

A sturdier version wraps the key in its own type (a newtype, chapter 3.2) whose constructor normalises, so un-normalised keys can't be used by mistake. In C# you'd pass StringComparer.OrdinalIgnoreCase to the Dictionary constructor, a comparer object that implements both equality and hashing consistently. That's the same contract.

Common misconceptions and pitfalls

⚠️ Depending on iteration order

Tests that compare format!("{map:?}") pass on your machine and fail in CI. Output that should be stable (reports, JSON written to disk, generated code) must come from a BTreeMap or sorted keys.

⚠️ Persisting or sharing hash values

Hash values are seeded per process (Rust) or per run (.NET strings). Storing them in a database or cache, or comparing them across services, breaks silently. For stable fingerprints use a named algorithm with a fixed specification (e.g. SHA-256 for content addressing).

⚠️ Swapping in a "faster hasher" everywhere

It's a real speed-up (about 1.6× measured) and a real vulnerability if any key can be influenced from outside. Restrict fast hashers to trusted internal keys, and record the reasoning in code.

⚠️ Implementing PartialEq by hand but deriving Hash

If equality ignores a field but the hash includes it, equal keys can hash differently, and lookups fail intermittently. Derive both, or hand-write both from the same fields.

⚠️ "Hash tables are always O(1)."

Expected O(1), with a good hash and a sane load factor. Rebuilds are O(n) (pre-size with with_capacity), and adversarial or very poor hashing makes them O(n) per operation (Figure 4).

Real-world view: hashing in your products

🏗 Architecture view
  • Rule engine fact indexes. A rule like "order.customer_id == customer.id" is a join. Indexing facts in a hash map by join key turns "scan all customers for each order" (O(n·m)) into one lookup per order (O(n)). This is the hash join used by databases, and chapter 9.4's Rete memories use the same idea.
  • Tenant-supplied keys. Fact attributes, tag names and JSON fields come from customers. Keep the default hasher for anything they can influence, or one malicious tenant can degrade the engine for everyone.
  • Idempotency in the workflow engine. "Have I already applied event X?" is a set membership question. In memory that's Exercise 2's bounded window. Durably it's a unique index in the database (chapter 10.4).
  • Deterministic replay. Workflow code must make the same decisions when re-run (chapter 10.7). Iterating a HashMap to decide what to do next breaks that, because order changes per process. Use BTreeMap or sorted keys in workflow logic. This is an easy-to-miss rule worth putting in the SDK guidelines.

Summary

  • A hash table computes a key's slot from its hash, giving expected O(1) lookups. Collisions are unavoidable (birthday paradox: about √m keys) and are resolved by chaining or open addressing.
  • Open addressing keeps entries in one array, probes on collision, and needs tombstones for deletion. Tables resize before filling up: observed capacities of 7/8 of a power of two.
  • Rust's HashMap is a SwissTable port: one metadata byte per slot (control bit + 7-bit fingerprint), compared 16 at a time with SIMD.
  • HashDoS turns O(1) into O(n) per insert with attacker-chosen keys (measured: 1,435 ms vs 1.7 ms). The defence is a keyed, randomly seeded hash: SipHash 1-3 by default in Rust. A fast hasher is only acceptable for trusted keys.
  • Equal keys must hash equally. Iteration order is arbitrary and varies per run: never persist hashes or depend on order. Use BTreeMap for ordered or deterministic needs.
