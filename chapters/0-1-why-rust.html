Why this matters

💡 Why this matters

As a consultant, the first question you'll get is rarely "how do lifetimes work?" It is "Should we use Rust for this, and is it a safe bet?" To answer it credibly you need three things: what problem Rust actually solves, what it costs, and evidence from organisations that have used it. This chapter gives you all three, and the rest of the course turns them into skills.

The short version: for decades, programmers had to choose between control and speed (C, C++) and safety and productivity (C#, Java, Go). Rust is the first mainstream language built to offer both. It manages memory without a garbage collector, and the compiler catches the bugs that make C and C++ dangerous. The price is paid up front: a stricter compiler and a steeper learning curve.

Intuition first: three ways to manage memory

Every program borrows memory from the computer and must give it back. There are three broad answers to who gives it back, and when.

🧭 Analogy — returning hired equipment

Picture a construction site that hires equipment.

  • Manual (C/C++): each worker must remember to return what they hired. Forget, and you pay forever (a leak). Return something still in use, and someone gets hurt (a use-after-free).
  • Garbage collector (C#/.NET): a site manager walks around now and then, finds equipment nobody is touching, and returns it. Safe, but the manager costs money, sometimes stops work to do the rounds, and returns things late.
  • Ownership (Rust): every item is signed out to exactly one person, and the site rules are checked before the job starts. When the person signed for the item leaves, it goes back automatically, at a moment you can predict. If the plan breaks the rules, the job never starts.

Core explanation

Basic

What Rust is, in five properties

  1. Compiled to native machine code. No virtual machine or JIT. A Rust program is a single executable, like a .NET NativeAOT build, but without a garbage collector inside it.
  2. No garbage collector. Memory is freed at predictable points that the compiler works out from ownership rules: every value has exactly one owner, and the value is cleaned up when its owner goes away. Module 2 teaches these rules in detail.
  3. Memory safety checked at compile time. Memory safety means a program can never read or write memory it isn't entitled to: no use-after-free, no double free, no buffer overflows, no reading uninitialised memory. In C and C++ these mistakes cause undefined behaviour — the language makes no promise at all about what happens next, which is how many security exploits start.
  4. A strong, expressive static type system. Close to C#'s, with extra features (such as enums that carry data, and no null) that let you encode business rules so that invalid states can't be represented.
  5. Zero-cost abstractions. High-level features such as iterators and generics compile down to code as fast as the low-level version you would write by hand. You don't pay at runtime for writing readable code.
🟣 Coming from C#/.NET

C# is also memory-safe; it gets there with the garbage collector and runtime checks. So for a typical .NET line-of-business service, Rust's headline benefit is not "more safety". It is safety without the runtime: predictable latency (no GC pauses), a smaller memory footprint, small self-contained binaries, and the ability to go places a GC runtime can't easily go (OS kernels, firmware, browser plugins via WebAssembly, libraries called from any other language). Rust also adds one safety guarantee C# doesn't have: no data races (explained below).

Intermediate

What safe Rust guarantees — and what it doesn't

Rust code is safe by default. A small, explicitly marked subset called unsafe Rust (inside unsafe { … } blocks) lets experts do things the compiler can't verify, such as calling C libraries. That is the same idea as C#'s unsafe keyword. In safe code, the compiler guarantees the following:

Versions vs editions

Rust has two separate ideas that .NET developers often mix up:

  • Compiler version (e.g. 1.99.0): a new one ships every six weeks. Upgrading must not break code that compiled before. The project calls this the stability promise.
  • Edition (2015, 2018, 2021, 2024): an opt-in set of language changes that would otherwise break old code, such as new keywords. Each crate (roughly a .NET project) picks its edition in its build file, Cargo.toml.

The rule that makes editions work, quoted from the official Edition Guide: crates in one edition "must seamlessly interoperate with those compiled with other editions." A 2024-edition application can use a library written in 2018 Rust, and the reverse. The current compiler supports every edition.

🟣 Coming from C#/.NET

An edition is like <LangVersion> in a .csproj: each project chooses its own, and projects with different values still work together because they compile to the same intermediate form. The big difference is the runtime. .NET has runtime versions with long-term support (LTS) releases. Rust has no runtime and no official LTS: only the latest stable compiler is supported, for six weeks. Teams rely on the stability promise and simply upgrade the compiler regularly. Chapter 0.2 shows how to pin a compiler version per project.

The six-week release train

Rust ships on a fixed timetable, like a train that leaves on time whether or not a particular feature is on board. There are three release channels:

  • Nightly — built every night from the main branch. Unfinished features are available, but only if you switch them on with a feature flag.
  • Beta — every six weeks a copy of nightly becomes the next beta, for six weeks of testing. Feature flags are not allowed.
  • Stable — after its six weeks in beta, that version becomes the new stable release. Almost everyone uses stable.

New features start as an RFC (Request for Comments), a public design proposal that the relevant Rust team reviews. An accepted feature is built behind a flag on nightly, tested, and then stabilised: the flag is removed and the feature rides the next train to stable. Step through the animation:

Who controls Rust?

Unlike .NET, which Microsoft leads, Rust has no single corporate owner. Three bodies matter:

  • The Rust Project — the open-source teams (language, compiler, library, Cargo, and others) that design and build Rust. Decisions are made in public, through RFCs.
  • The Leadership Council — the project's top governance body, created by RFC 3392 in June 2023. It replaced the earlier "core team" and is made up of representatives of the top-level teams.
  • The Rust Foundation — an independent non-profit announced on 8 February 2021, founded by AWS, Huawei, Google, Microsoft and Mozilla. It holds the trademarks and pays for infrastructure such as crates.io (the package registry, Rust's NuGet). It supports the project but does not design the language.
Deep dive: where the guarantees actually come from

Rust has no runtime doing the checking, so how can it promise memory safety and freedom from data races? Through two compile-time analyses:

  1. Ownership and borrowing. The compiler tracks which variable owns each value, and every reference (a pointer that borrows a value without owning it). The core rule is aliasing XOR mutation: at any moment you can have many readers or one writer, never both. Most memory bugs need both at once. In C++, for example, you hold a pointer into a vector while code adds to the vector, which may move its buffer. Forbid that combination and those bugs can't happen. The lab below shows this rule in action. Chapter 2.3 teaches it properly.
  2. Thread-safety marker traits. The type system records which types are safe to send to, or share with, another thread (the Send and Sync traits, chapter 4.1). Spawning a thread with a value that isn't thread-safe is a compile error. Combined with the aliasing rule, this rules out data races.

These rules are conservative: the compiler rejects some programs that would actually be fine. For the small number of cases where an expert needs to go beyond them (talking to hardware, writing a fast collection), unsafe code is allowed, but it is expected to be wrapped in a safe interface that upholds the rules for its callers.

Is this sound, or just hopeful? The RustBelt project (Jung, Jourdan, Krebbers and Dreyer; POPL 2018) built a formal model of a realistic subset of Rust and machine-checked a proof that its type system is sound. The proof also covers several standard-library types that use unsafe internally, showing their safe interfaces really are safe. It does not cover every line of the real compiler or standard library, but it is strong evidence that the design holds together.

The evidence: why industry is moving

Most of Rust's industrial momentum comes from one statistic, measured independently by several large vendors: in big C and C++ codebases, most serious security bugs are memory-safety bugs.

⚠️ Use these numbers carefully

These figures describe large codebases written in C and C++. They do not mean "70% of bugs in your C# services are memory bugs". C# is already memory-safe. When advising a .NET shop, base the case for Rust on latency, footprint, cost, portability and reach, not on a security statistic that doesn't apply to their code.

Worked example: the compiler as a reviewer

You don't need to understand Rust syntax yet. The point of this lab is to see the difference between catching a bug at runtime and catching it at compile time. You can run every Rust snippet in this course in your browser with the Run ▶ button, which opens the official Rust Playground. Chapter 0.2 sets up your local tools.

Step 1 — the bug in C#

A classic .NET bug: changing a list while you loop over it. It compiles fine and fails only when that line runs.

var scores = new List<int> { 10, 20, 30 };
foreach (var s in scores)
{
    if (s == 10) scores.Add(40);   // modify while enumerating
}
Console.WriteLine("done");
Unhandled exception. System.InvalidOperationException: Collection was modified; enumeration operation may not execute.
   at System.Collections.Generic.List`1.Enumerator.MoveNext()
   at Program.<Main>$(String[] args) in app.cs:line 2

.NET protects you here with a runtime check (a version counter inside List<T>). You find out in testing, or in production.

Step 2 — the same bug in Rust

fn main() {
    let mut scores = vec![10, 20, 30];
    for s in &scores {
        if *s == 10 {
            scores.push(40); // modify while iterating
        }
    }
    println!("done");
}

This never runs. cargo build refuses to produce a program (real output from Rust 1.99.0):

error[E0502]: cannot borrow `scores` as mutable because it is also borrowed as immutable
 --> src/main.rs:5:13

3 |       for s in &scores {
  |       -        -------
  |       |        |
  |       |        immutable borrow occurs here
  |  _____|        immutable borrow later used here
  | |
4 | |         if *s == 10 {
5 | |             scores.push(40); // modify while iterating
  | |             ^^^^^^^^^^^^^^^ mutable borrow occurs here
6 | |         }
7 | |     }
  | |_____- this for loop borrows `scores` immutably, preventing mutation within its body
  |
  = help: consider using an index-based loop instead, or collecting modifications into a separate collection

For more information about this error, try `rustc --explain E0502`.

How to read it: the loop is reading the vector (an "immutable borrow"), and push wants to change it (a "mutable borrow") while the read is still going on. That breaks the "many readers or one writer" rule from the deep dive. In C++ the same code compiles and is undefined behaviour: push may move the buffer, leaving the loop reading freed memory. The Rust compiler even suggests two fixes, which you'll write in Exercise 1.

Step 3 — a fixed version

fn main() {
    let mut scores = vec![10, 20, 30];
    // Decide first, then modify: the read finishes before the write starts.
    let has_ten = scores.contains(&10);
    if has_ten {
        scores.push(40);
    }
    println!("{scores:?}");
}
[10, 20, 30, 40]
✅ The habit to build

Read Rust compiler errors top to bottom, like a code review comment. They name the rule, point at the exact lines, and usually suggest a fix. Many Rust developers describe the compiler as a strict but helpful pair programmer.

Exercises

Exercise 1 — apply the compiler's suggestions ★☆☆

The error in Step 2 suggests "an index-based loop" or "collecting modifications into a separate collection". Starting from the Step 2 code, write both versions, so that the program prints [10, 20, 30, 40]. Use the Run button. You don't need to know Rust yet: copy the shape of Step 2, and rely on the compiler errors and the hints below.

Hints: scores.len() gives the length; for i in 0..n loops over 0 to n−1; scores[i] reads an element; Vec::new() makes an empty list; scores.extend(other) appends another list.

Show solution 
fn main() {
    // Solution A: loop over positions (indices), not over borrowed items.
    let mut scores = vec![10, 20, 30];
    let len = scores.len();          // fix the length before the loop
    for i in 0..len {
        if scores[i] == 10 {
            scores.push(40);         // allowed: no borrow is held across the loop
        }
    }
    println!("A: {scores:?}");

    // Solution B: collect the changes first, apply them afterwards.
    let mut scores = vec![10, 20, 30];
    let mut additions = Vec::new();
    for s in &scores {
        if *s == 10 {
            additions.push(40);      // writes go to a *different* vector
        }
    }
    scores.extend(additions);        // the read borrow ended with the loop
    println!("B: {scores:?}");
}
A: [10, 20, 30, 40]
B: [10, 20, 30, 40]

Notice that in A, len is computed once, so the 40 we add is not visited. With i < scores.len() re-checked each time, the loop would also visit the new element. That is harmless here, but it is the kind of subtle behaviour change to watch for.

Exercise 2 — the one-minute pitch ★★☆ consultant skill

A CTO of a .NET shop asks: "In one minute, what is Rust and why would we care?" Write five bullet points. Be honest about the costs, and don't use the 70% statistic as if it applied to their C# code.

Show a model answer
  • Rust is a compiled language with C/C++-level speed and memory use, but with the memory safety you're used to in C#, enforced by the compiler instead of a garbage collector.
  • No GC means predictable latency and a small footprint: good for hot-path services, proxies, high-volume data processing, edge/IoT and serverless cold starts.
  • It also prevents data races at compile time, which C# can't, so heavily concurrent code is safer to change.
  • The cost is a learning curve of a few months and slower compiles. Start with one well-bounded component, not a rewrite.
  • It's a mature bet: stable since 2015, backed by a foundation (AWS, Google, Microsoft and others), used in the Linux kernel, Android, AWS Lambda's Firecracker and Cloudflare's proxy.

Common misconceptions and pitfalls

⚠️ "Rust is only for systems programming."

It started there, but web services, CLIs, data pipelines and WebAssembly front-ends are all mainstream uses. Modules 7, 9 and 10 build enterprise services.

⚠️ "If it compiles, it's correct."

The compiler removes whole classes of bugs (memory, data races, null), not logic errors, deadlocks or bad architecture. You still need tests (chapter 3.4) and design reviews.

⚠️ "unsafe means Rust isn't really safe."

unsafe doesn't switch off the checks. It permits five specific extra operations, in a small, searchable, reviewable region. Well-run teams keep it rare and audited (chapter 5.1).

⚠️ "Rust is always faster than C#."

Modern .NET is very fast. Badly written Rust (excessive copying, careless allocation) can be slower than good C#. Rust gives you control and predictability. Speed comes from using it well, and from measuring (chapter 6.1).

⚠️ "You must learn C or C++ first."

No. You do need some ideas C# hides (stack vs heap, pointers), and the Foundations module teaches them from scratch.

⚠️ "You'll fight the borrow checker forever."

Most people struggle for a few weeks, then find they design code so that the conflicts don't arise. This course front-loads those ideas so the struggle is shorter.

Summary

  • Rust gives C/C++-level performance and control with memory safety enforced by the compiler instead of a garbage collector.
  • Safe Rust prevents memory errors, null errors and data races at compile time. It does not prevent deadlocks, leaks or logic bugs. unsafe is a small, explicit escape hatch.
  • For .NET teams, the case for Rust is predictable latency, a small footprint, portability and reach. Safety is a bonus, since C# is already memory-safe.
  • The language ships stable versions every six weeks, never breaking old code. Breaking changes go into opt-in editions (2015/2018/2021/2024), and crates of different editions interoperate. There is no official LTS.
  • Adoption evidence (Android, Cloudflare, Discord, AWS, Linux) points to one pattern: adopt Rust for bounded components with a clear driver, not wholesale rewrites.
