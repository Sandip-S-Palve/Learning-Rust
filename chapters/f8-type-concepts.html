Type-system concepts

Learning objectives

  • Explain static vs dynamic typing, keep it separate from "strong vs weak", and say where type inference and nominal typing fit
  • Predict what assignment does under value semantics and under reference semantics, and say why Rust makes every indirection visible in the type
  • Model data with product types (AND) and sum types (OR), count their possible values, and read their memory size
  • Distinguish parametric, ad-hoc and subtype polymorphism, static and dynamic dispatch, and how Rust and .NET compile generics
  • Use expression-oriented code and read the "missing tail expression" error
  • Redesign a flag-based model so that illegal states cannot be represented, and know when that pays off

Why this matters

💡 Why this matters

Chapters F1–F7 were about how data sits in memory and how fast you can process it. This chapter is about what the compiler knows about that data, and so which mistakes it can stop before your code ships. In C# you lean on the type system for some guarantees and on unit tests, null checks and code review for the rest. Rust moves much more of that work into types. Most of what feels new about Rust (no null, match that refuses to compile, explicit &, enums that carry data) comes from the ideas in this chapter.

Both of your products depend on this directly. A rule engine has to decide how to represent facts whose shape it only learns at runtime: a statically typed host carrying dynamically typed values (chapter 9.5). A workflow engine is a set of state machines, and every production incident that reads "the run was marked completed but had no output" is an illegal state that the data model allowed. By the end of this chapter you'll have the words, and the design moves, to talk about both with a client's architects.

Intuition first: forms with "AND" and forms with "OR"

🧭 Analogy

Think of a type as a paper form that a value must fit.

  • A product type is a form where you fill in every box: name and address and phone. A C# class or record and a Rust struct are product types.
  • A sum type is a form that says "tick exactly one of these", where each option has its own sub-boxes: pay by card (card number) or bank transfer (IBAN) or invoice (nothing extra). Rust's enum is a sum type. C# has never had a general one; C# 15 adds a union type, which is in preview as of today.

Most badly designed data models are "OR" forms printed as "AND" forms: one box per option plus a set of tick boxes, with a note at the bottom saying "please only tick one". Nothing enforces the note.

Core explanation

Basic

What a type is

A type is two things at once: a set of possible values (a bool is one of {false, true}; a u8 is one of 0…255) and the operations allowed on those values (you can add two u8s; you can't add a bool to a string). A type checker is the part of the language that refuses operations the type doesn't allow. Everything in this chapter is a variation on two questions: when does the checking happen, and how precisely can a type describe the set of values you actually mean?

Static vs dynamic typing

Under static typing, every expression has a type known before the program runs, and type errors stop the build. Under dynamic typing, types belong to values at runtime and are checked when each operation executes; a type error is an exception in production. You've used both without naming them. C# is statically typed, but its dynamic keyword switches checking off for one variable, and the lab shows the result: fact * 2 on a string compiles, then throws RuntimeBinderException when it runs.

Static typing buys you errors at build time instead of in production, editor tooling that knows what every name is (rename, go-to-definition, completion), and faster code, because the compiler knows sizes and layouts in advance (chapter F1). The price is that you must describe your data up front. Dynamic typing buys flexibility for data whose shape you don't know until runtime, which is exactly a rule engine's situation with customer-defined facts. Statically typed languages handle that case by modelling "a value of some runtime type" as an ordinary type: a sum type of the possible kinds (the Real-world view below).

Strong vs weak: a different axis

People often say "strongly typed" when they mean "statically typed". They're separate questions. Static vs dynamic is about when types are checked. Strong vs weak is an informal description of how much the language converts for you silently. There's no agreed formal definition, so in reviews ask the precise question instead: "which implicit conversions does this language perform?"

LanguageWhen checkedSilent conversionsExample
RustCompile timeAlmost none: not even i32 → i64let t: i64 = count; is error E0308 (Lab step 2)
C#Compile time (except dynamic)Safe widenings: int → long, int → double, user-defined implicit operatorslong t = count; compiles
PythonRun timeFew: "1" + 1 is a TypeErrorDynamic but strict
JavaScriptRun timeMany: "1" + 1 is "11", "6" * "2" is 12Dynamic and permissive

Rust's refusal to widen numbers silently is deliberate. A conversion is either written .into() (only offered when it can't lose information, like i32 → i64), try_into() (may fail, returns a Result), or as (an explicit cast that may truncate). You'll see all three in chapter 2.1. In a code review, an as on a money or ID value is worth a second look.

Type inference and nominal typing

Static typing doesn't mean writing types everywhere. With type inference the compiler works out the types you leave out. C#'s var infers a local's type from its initialiser only. Rust goes further inside a function body: let mut ids = Vec::new(); has no element type yet, and a later ids.push(7u32) settles it as Vec<u32>. Rust deliberately stops at function boundaries. Every function signature spells out its parameter and return types, so a function's contract is always readable without its body, and a change inside one function can't silently change another's types.

Rust and C# are both nominal: what matters is a type's declared name, not its shape. Two structs with identical fields are still different types. (TypeScript is structural: anything with the right fields fits.) Nominal typing is what makes the newtype pattern work. struct Meters(f64) and struct Feet(f64) have the same layout and zero runtime cost, but passing Feet where Meters is expected is a compile error (Lab step 2). That's the class of bug that destroyed NASA's Mars Climate Orbiter in September 1999: ground software from Lockheed Martin produced thruster impulse in pound-force seconds, and the NASA system that consumed it expected newton-seconds. Both were plain numbers, so nothing objected.

Value semantics vs reference semantics

What does b = a do? There are two possible answers, and mixing them up is one of the most common sources of bugs in any language.

  • Value semantics: b gets its own copy of the value. Changing b can't affect a. In C#: struct, record struct, int, DateTime.
  • Reference semantics: b gets a copy of a reference, so a and b are two names for one object on the heap. Changing the object through b is visible through a. In C#: class, record (a record class), arrays, string (immutable, so you rarely notice), delegates.

Two names for one object is called aliasing. Aliasing is harmless while nobody mutates. Aliasing plus mutation is the source of a whole family of bugs: a method that "just reads" a list while another component adds to it, a cached object changed by a caller who didn't know it was shared, the "collection was modified" exception from chapter 0.1, and, with threads, data races (chapter F9).

In C#, which semantics you get is decided by the type's declaration, which may be in another file or another assembly. You can't tell from var b = a; whether you just copied or aliased. Rust makes a different choice: every type has value semantics. let b = a; always transfers the value itself. If the type is a small plain value like i32 or a Copy struct, the bits are copied and both stay usable. Otherwise the value is moved and a can't be used any more (chapter 2.2 covers this in full). Indirection exists in Rust only when you ask for it, and then it's visible in the type: &Customer (a shared reference), &mut Customer (an exclusive, mutable reference), Box<Customer> (an owned heap pointer), Rc/Arc (shared ownership, chapter 2.12).

Equality follows the same split. For a C# class, == means "same object" unless the type overrides it. A record overrides it to compare fields, which is why the lab's two identical MoneyRecords are == but not ReferenceEquals. In Rust, == always compares values, and a type has no == at all until you derive or implement PartialEq (chapter 2.9). Identity ("is this the same allocation?") is a separate, explicit question: std::ptr::eq.

Product types

A product type holds several fields at the same time. Rust has three forms: a struct with named fields, a tuple struct with positional fields (struct Meters(f64);), and an anonymous tuple ((u8, bool)). The name comes from counting. If a type has 2 possible values (bool) and another has 256 (u8), a pair of them has 2 × 256 = 512 possible values. Product types multiply.

The smallest product is the empty one: the unit type (), which has exactly one value, also written (). It's Rust's "nothing interesting here", like C#'s void, but it's a real type you can store in a variable or a HashMap<String, ()>. It takes zero bytes (Lab step 3). In C# terms, void can't be used as a type argument, which is why .NET needs both Action and Func<T>, and Task and Task<T>. Rust needs only one of each, because "returns nothing" is just "returns ()".

Sum types

A sum type (also called a tagged union or discriminated union) is a value that is exactly one of several variants, each of which can carry its own data. Rust's enum is a sum type:

enum Payment {
    Card { last4: u16 },
    Bank { iban_id: u64 },
    Invoice,
}

A Payment is a Card with a last4, or a Bank with an iban_id, or an Invoice with nothing. A Card has no iban_id field at all, not even a null one. Counting again: the number of possible values is the sum of the variants' counts. Product and sum types together are called algebraic data types. (Careful: "ADT" also abbreviates abstract data type from chapter F3, a different idea. Say the full name in documents.)

Two sum types from the standard library replace two things C# developers take for granted:

  • Option<T> is Some(T) or None. It replaces null. Rust references can never be null, so "might be missing" has to be stated in the type, and the compiler makes you handle the None case before you can use the value. Tony Hoare, who introduced null references in ALGOL W in 1965, later called that decision his "billion-dollar mistake".
  • Result<T, E> is Ok(T) or Err(E). It replaces exceptions for expected failures: the possible failure appears in the function's signature, not just in its documentation (chapter 2.6).
🟣 Coming from C#/.NET: what you've used instead of sum types
  • enum + fields. A C# enum is a set of named integers. It can't carry per-case data, so the data goes in nullable fields next to it, and nothing links "Status is Failed" to "Error is set". An enum variable can also hold any integer: (Payment)7 is legal, which is why the compiler can never treat a switch over an enum as complete (Lab step 4).
  • Class hierarchy + pattern matching. abstract record Shape with Circle and Rect subclasses is the closest classic equivalent, but the hierarchy is open: anyone can add a subclass in another assembly, so the compiler again can't know a switch is complete.
  • Nullable reference types (C# 8+) are compile-time annotations and flow-analysis warnings. They catch many null bugs, but a string (non-nullable) can still be null at runtime, from older libraries, deserialisation, or default. Rust's Option is the type itself, not an annotation.
  • C# 15 union (preview). public union Pet(Cat, Dog, Bird); declares a closed set of case types with exhaustive switch checking. Unlike Rust's enum, the cases are existing types rather than named variants, and the generated form is a struct that stores its contents as object?, boxing value-type cases (per Microsoft's docs). F# has had full discriminated unions since its first release.
⚠ Verify

As of 2026-10-31, C# union types are documented as a preview feature of C# 15 / .NET 11. .NET 11's general release is expected in November 2026, but that date comes from third-party reporting, not an official announcement. Check the C# "What's new" page before relying on the feature or its exact syntax in a client recommendation.

Pattern matching and exhaustiveness

You take a sum type apart with match, which picks the arm for the variant actually present and binds its fields to names:

fn fee_cents(p: &Payment) -> u32 {
    match p {
        Payment::Card { .. } => 30,
        Payment::Bank { .. } => 10,
        Payment::Invoice => 0,
    }
}

Because a Rust enum is closed (its variants are listed in one place and can't hold anything else), the compiler can check exhaustiveness: a match that forgets a variant is error E0004, not a warning. That turns adding a variant into a guided refactoring. Add Wallet to Payment, and the build lists every place in the codebase that now has to decide what a wallet payment means (Lab step 4). The equivalent C# code compiles with warnings CS8524 or CS8509 and throws SwitchExpressionException at runtime. A catch-all arm (_ => …) gives up that safety, so use it on purpose, not by habit.

Intermediate

Sum types in memory

Figure 1 showed the layout: a tag plus a slot as big as the largest variant, rounded up to the alignment. Payment is 16 bytes, because its largest variant holds a u64 (8 bytes, alignment 8) and the tag needs at least one more byte, which rounds to 16. Option<u64> is also 16 bytes, because every one of the 2⁶⁴ bit patterns of a u64 is a valid number, leaving nowhere to hide "None".

When the payload has impossible bit patterns, the compiler uses them instead. This niche optimisation is why Option<&u64>, Option<Box<u64>> and Option<NonZeroU32> are the same size as the type inside, and Option<bool> fits in one byte (a bool only uses 0 and 1, leaving 254 spare patterns). The niche optimisation for Option of a reference, Box, function pointer or NonZero* is guaranteed by the standard library docs. The practical consequence: Rust's replacement for null costs nothing compared with a nullable pointer, so there's no performance argument for avoiding Option.

Deep dive: the algebra of types, and refactoring with it

Write \(|T|\) for the number of values of type T. The names "product" and "sum" are literal:

$$ |(A, B)| = |A| \times |B| \qquad |\,\texttt{enum}\{A, B\}\,| = |A| + |B| \qquad |\texttt{Option<}T\texttt{>}| = 1 + |T| $$

The unit type () has 1 value (the "1" in Option's formula is None). An enum with no variants, enum Never {}, has 0 values, so no value of it can ever be created. Rust uses this idea for the never type !, the return type of functions that never return, such as std::process::exit. Functions count too: there are \(|B|^{|A|}\) different functions from A to B (one choice of output per input), which is why function types are sometimes called exponentials.

This algebra is practical, because the usual laws hold and let you refactor with confidence. The distributive law \(A \times (B + C) = A \times B + A \times C\) says these two designs hold exactly the same information:

// A × (B + C): shared fields once, plus a sum for what varies
struct Run { id: u64, tenant: String, status: Status }
enum Status { Running { worker: String }, Failed { error: String } }

// A × B + A × C: the shared fields repeated in every variant
enum Run2 {
    Running { id: u64, tenant: String, worker: String },
    Failed  { id: u64, tenant: String, error: String },
}

The first form is usually better: code that only needs id doesn't have to match. When you see the same fields repeated across every variant, factor them out. A model is correct when its count matches reality. If your type admits 64 states and the domain has 4, the other 60 are bugs waiting for a code path (Figure 4).

Generics: parametric polymorphism

Generics let you write code once for many types: Vec<T>, HashMap<K, V>, fn largest<T>(items: &[T]) -> T. You already know them from C#'s List<T>. As in C#, a generic function may only do with T what its constraints promise. C# writes where T : IComparable<T>; Rust writes a trait bound, T: PartialOrd. A trait is Rust's version of an interface: a named set of methods a type can implement. You'll study traits in depth in chapters 2.9 and 3.1. For now, treat them as interfaces.

The big difference is how generics become machine code:

  • .NET: shared code, specialised by the runtime. Generics are kept in the compiled assembly (reified; reflection can see List<int>). Microsoft's docs describe the rule: the runtime creates a specialised copy "one time for each unique value type" argument, while all reference-type arguments share a single copy, "because all references are the same size".
  • Rust: monomorphisation at compile time. The compiler generates a separate copy of the generic function for every concrete type it's used with, value or reference alike. largest::<i32>, largest::<f64> and largest::<char> in Lab step 5 are three different functions in the binary, each optimised and inlined as if written by hand. That's a large part of what "zero-cost abstraction" (chapter 0.1) means.
  • Java: type erasure. One copy for everything, with type arguments erased at compile time. Worth knowing so you can explain why the three platforms behave differently.

Monomorphisation's costs are a larger binary and longer compile times when a generic is used with many types. Chapter 6.2 shows how to measure and control both.

Polymorphism styles

Polymorphism means one piece of code working with values of several types. Christopher Strachey's 1967 lecture notes gave us the split between parametric and ad hoc polymorphism; Cardelli and Wegner's 1985 survey refined it into the classification still used today. In the terms you'll use in reviews:

StyleIdeaC#Rust
ParametricSame code for every TGenericsGenerics (monomorphised)
Ad hocDifferent code per type, under one nameMethod and operator overloading; implicit conversionsNo function overloading. Traits play this role: impl Display for Money gives Money its own formatting. Operators are traits too (Add, chapter 2.9)
Subtype (inclusion)A value of a derived type is usable where the base is expected; calls dispatch at runtimeClass inheritance, virtual/override, interfacesNo data inheritance. dyn Trait trait objects provide runtime dispatch over any type implementing the trait
Closed setA fixed list of alternatives, handled by matchingPattern matching over a hierarchy (open), or C# 15 unionsenum + match (exhaustive)

The practical question in Rust is usually static vs dynamic dispatch. With static dispatch (generics) the compiler knows the concrete type, calls the method directly, and can inline it. With dynamic dispatch (&dyn Rule, Box<dyn Rule>) the method is looked up at runtime in a vtable, a table of function pointers, exactly like a C# virtual or interface call. You need dynamic dispatch whenever the concrete type isn't known until runtime: a Vec holding several different rule types, or plugins loaded from configuration.

Neither is "better". Static dispatch is faster per call and lets the optimiser see through the abstraction. Dynamic dispatch keeps one copy of the code, allows mixed collections, and lets you choose implementations at runtime. Chapter 3.1 builds the full decision guide; your rule engine will use both.

Deep dive: the expression problem — enums vs traits as an architecture decision

In a 1998 email to the Java-genericity mailing list (whose recipients included Mads Torgersen, later the lead designer of C#), Philip Wadler named the expression problem: can you add both new cases and new operations to a data type without changing existing code, while keeping static type safety? The two common designs each make one direction easy and the other hard:

Add a new operation (e.g. explain())Add a new case (e.g. a Between node)
Enum + match (closed set)Easy: write one new function with a matchTouches every existing match, but E0004 lists them all for you
Trait + impls (open set, OO style)Touches every implementation: add a method to the trait and implement it everywhereEasy: a new type with an impl, even in another crate

This is a real design decision in your rule engine. The expression AST (number, variable, add, compare…) is a closed set you own, and you'll keep adding passes over it: evaluate, type-check, explain, optimise. That's the enum's strength (Exercise 3; chapters 9.2–9.3). The pluggable evaluator layer (DMN tables, Rete, a scripting engine, a customer's own plugin) is an open set where third parties add cases. That's the trait's strength (chapters 9.5–9.6). Choosing the wrong one for either layer is a cost you'll pay on every future feature.

Expressions vs statements

An expression produces a value; a statement does something and produces nothing. In C#, if, switch statements and blocks are statements; to get a value you switch to the expression forms (cond ? a : b, switch expressions, lambdas). Rust is expression-oriented: nearly everything produces a value.

  • A block { … } evaluates to its last expression, written without a semicolon.
  • if/else and match are expressions: let base = if w <= 2 { 5 } else { 9 }; (both branches must have the same type).
  • loop can return a value: break value;.
  • A function's body is a block, so its result is usually just its last expression. return is for leaving early.
  • A semicolon turns an expression into a statement and throws its value away. The statement's value is ().
  • let is a statement, and assignment x = 5 is an expression of type (), so C#'s a = b = 0 chaining doesn't work in Rust.

The rule about semicolons produces the most common beginner error in Rust, and Lab step 2 shows it: a function ending in w * h; returns (), not u32. The compiler's message tells you exactly that, and suggests removing the semicolon. Expression orientation pairs naturally with sum types: let fee = match payment { … }; computes a value from every case with no "unassigned variable" path, which is one more class of bug that can't be written.

Applying it

Making illegal states unrepresentable

Yaron Minsky of Jane Street put this design principle in four words: "make illegal states unrepresentable". If a combination of values is invalid in your domain, choose types in which it can't be constructed at all. Then no code path, test gap or future maintainer can produce it. Here's a workflow run modelled the way most C# codebases do it, with flags and nullable fields:

class WorkflowRun
{
    public bool IsRunning { get; set; }
    public bool IsCompleted { get; set; }
    public bool IsFailed { get; set; }
    public string? Worker { get; set; }   // only meaningful while running
    public string? Output { get; set; }   // only meaningful when completed
    public string? Error { get; set; }    // only meaningful when failed
}

Six independent fields with two meaningful options each give 2⁶ = 64 representable states. The domain has four: pending, running, completed, failed. Try it:

The enum version has exactly four shapes, and each carries only the data valid in that state: a Failed run can't have an output, because the variant has no such field. Code that handles a status uses match, so a new status added later (say, Cancelled) flags every place that must handle it. State transitions become functions that take the old state and return the new one, so "start a run that is already completed" is an Err you must handle, not a silent overwrite (Lab step 6). The same principle has several tools:

  • Sum types instead of flag combinations, as above. This is the single most effective change in most models.
  • Newtypes with validated constructors. A Percentage whose field is private and whose only constructor checks 0–100 (Exercise 2). Code that receives a Percentage never needs to re-check it. Alexis King's essay calls this "parse, don't validate": turn unstructured input into a precise type once, at the boundary, instead of checking it repeatedly deep inside.
  • Units and identifiers as distinct types: TenantId vs UserId, Meters vs Feet, Cents vs Euros. Swapped arguments become compile errors.
  • Precise standard types: NonZeroU32, Duration instead of a bare number of "seconds (probably)", and Option only where absence is genuinely possible.
  • Typestate, a type per stage (Draft → Published) so that calling publish() twice doesn't compile. That's chapter 3.2.

Know when to stop. If several yes/no options really are independent (every combination is valid), separate bools or a bit-flag set are the honest model. The goal is to make the type's count match the domain's count, not to turn everything into an enum.

Step 3 — value semantics, and products vs sums in memory

#[derive(Clone, Copy)]
struct Point {
    x: i32,
    y: i32,
}

#[derive(Clone)]
struct Customer {
    name: String,
    credit_limit: u32,
}

fn main() {
    // Copy type: assignment copies the bits. Two independent values.
    let a = Point { x: 1, y: 2 };
    let mut b = a;
    b.x = 99;
    println!("a = ({}, {}), b = ({}, {})", a.x, a.y, b.x, b.y);

Step 5 — generics, trait objects and fat pointers

use std::mem::size_of;

trait Rule {
    fn name(&self) -> String;
    fn evaluate(&self, amount: u32) -> bool;
}

struct MaxAmount(u32);
struct EvenOnly;

impl Rule for MaxAmount {
    fn name(&self) -> String { format!("amount <= {}", self.0) }
    fn evaluate(&self, amount: u32) -> bool { amount <= self.0 }
}

impl Rule for EvenOnly {
    fn name(&self) -> String { "amount is even".to_string() }
    fn evaluate(&self, amount: u32) -> bool { amount.is_multiple_of(2) }
}

/// Parametric polymorphism + static dispatch: the compiler makes one copy per concrete R.
fn check_static<R: Rule>(rule: &R, amount: u32) -> bool {
    rule.evaluate(amount)
}

/// Subtype-style polymorphism + dynamic dispatch: one copy; the call goes through a vtable.
fn check_dynamic(rule: &dyn Rule, amount: u32) -> bool {
    rule.evaluate(amount)
}

/// Generic over any T that can be compared: the bound says what T must support.
/// Panics if `items` is empty (chapter 2.6 shows how to return an Option instead).
fn largest<T: PartialOrd + Copy>(items: &[T]) -> T {
    let mut best = items[0];
    for &x in items {
        if x > best {
            best = x;
        }
    }
    best
}

fn main() {
    println!("static : {}", check_static(&MaxAmount(500), 420));
    println!("static : {}", check_static(&EvenOnly, 421));

    // A heterogeneous list needs dynamic dispatch: the element types differ.
    let rules: Vec<Box<dyn Rule>> = vec![Box::new(MaxAmount(500)), Box::new(EvenOnly)];
    for r in &rules {
        println!("dynamic: {:<16} -> {}", r.name(), check_dynamic(r.as_ref(), 420));
    }

    println!("largest i32: {}", largest(&[3, 9, 4]));
    println!("largest f64: {}", largest(&[2.5, 0.1]));
    println!("largest char: {}", largest(&['q', 'z', 'a']));

    println!("size of &MaxAmount: {} bytes (thin pointer)", size_of::<&MaxAmount>());
    println!("size of &dyn Rule : {} bytes (data pointer + vtable pointer)", size_of::<&dyn Rule>());
}

static : false
dynamic: amount <= 500    -> true
dynamic: amount is even   -> true
largest i32: 9
largest f64: 2.5
largest char: z
size of &MaxAmount: 8 bytes (thin pointer)

check_static is compiled twice (once for MaxAmount, once for EvenOnly); check_dynamic once. The Vec<Box<dyn Rule>> holds two different types, which is only possible through dynamic dispatch, the shape of a rule set loaded from configuration. largest works for i32, f64 and char because each satisfies the bound PartialOrd + Copy. And the last two lines measure Figure 3: a thin pointer is 8 bytes, a &dyn fat pointer 16.

Step 6 — expressions, and a state machine with no illegal states

fn shipping_cost(weight_kg: u32, express: bool) -> u32 {
    let base = if weight_kg <= 2 { 5 } else { 5 + (weight_kg - 2) * 2 }; // `if` produces a value
    let surcharge = match (express, weight_kg) {
        (false, _) => 0,
        (true, 0..=2) => 10,
        (true, _) => 25,
    }; // `match` produces a value
    base + surcharge // no semicolon: this is the function's result
}

fn main() {
    // A block is an expression: its value is its last expression.
    let discount = {
        let loyalty_years = 4;
        let pct = loyalty_years * 2;
        pct.min(10) // value of the block
    };
    println!("discount = {discount}%");

    // `loop` can return a value with `break value`.
    let mut attempt = 0;
    let first_success = loop {
        attempt += 1;
        if attempt * attempt > 20 {
            break attempt;
        }
    };
    println!("first attempt with attempt² > 20: {first_success}");

    println!("1 kg standard: {}", shipping_cost(1, false));
    println!("5 kg express:  {}", shipping_cost(5, true));

}

1 kg standard: 5
5 kg express:  36

No variable is ever declared first and assigned later: every value comes out of an if, a match, a block or a loop. The match on a tuple (express, weight_kg) with ranges (0..=2) is a preview of chapter 2.5. Finally, Figure 4's model as running code:

/// Each variant carries exactly the data that is valid in that state, and nothing else.
#[derive(Debug)]
enum RunStatus {
    Pending,
    Running { worker: String, started_at: u64 },
    Completed { output: String, finished_at: u64 },
    Failed { error: String, attempts: u32 },
}

fn describe(s: &RunStatus) -> String {
    match s {
        RunStatus::Pending => "waiting for a worker".to_string(),
        RunStatus::Running { worker, started_at } => format!("running on {worker} since t={started_at}"),
        RunStatus::Completed { output, finished_at } => format!("done at t={finished_at}: {output}"),
        RunStatus::Failed { error, attempts } => format!("failed after {attempts} attempt(s): {error}"),
    }
}

/// A transition consumes the old state and returns the new one.
fn start(s: RunStatus, worker: &str, now: u64) -> Result<RunStatus, String> {
    match s {
        RunStatus::Pending => Ok(RunStatus::Running { worker: worker.to_string(), started_at: now }),
        other => Err(format!("cannot start a run that is {other:?}")),
    }
}

fn main() {
    let runs = [
        RunStatus::Pending,
        RunStatus::Running { worker: "w-7".into(), started_at: 100 },
        RunStatus::Completed { output: "approved".into(), finished_at: 160 },
        RunStatus::Failed { error: "timeout".into(), attempts: 3 },
    ];
    for r in &runs {
        println!("{}", describe(r));
    }
    let next = start(RunStatus::Pending, "w-2", 200).unwrap();
    println!("{}", describe(&next));
    println!("{}", start(next, "w-3", 210).unwrap_err());
}
waiting for a worker
running on w-7 since t=100
done at t=160: approved
failed after 3 attempt(s): timeout
running on w-2 since t=200
cannot start a run that is Running { worker: "w-2", started_at: 200 }

start consumes the old status and returns a new one, so a run can't be "running and pending" at the same time. Starting a run that's already running is an Err value the caller must deal with. Result is itself a sum type, the subject of chapter 2.6.

Exercise 1 — replace the flags ★★☆ product skill

A multi-tenant SaaS models accounts in C# as bool IsTrial, IsActive, IsSuspended, IsClosed plus nullable TrialEndsAt, Plan, SuspendReason and ClosedAt. (a) How many states can that represent, counting each nullable as set/unset? (b) Model it as a Rust enum Account where each state carries only its valid data (a suspended account keeps its plan). (c) Write can_log_in(&Account, now) -> bool and suspend(Account, reason) -> Result<Account, String>, where only an active account can be suspended.

Show solution

(a) 4 booleans and 4 set/unset fields: 2⁸ = 256 representable states, for a domain of 4. (b) and (c):

/// The lifecycle of a tenant account. Every variant holds only what is valid in that state.
#[derive(Debug, PartialEq)]
enum Account {
    Trial { ends_at: u64 },
    Active { plan: String },
    Suspended { plan: String, reason: String },
    Closed { closed_at: u64 },
}

fn can_log_in(a: &Account, now: u64) -> bool {
    match a {
        Account::Trial { ends_at } => now < *ends_at,
        Account::Active { .. } => true,
        Account::Suspended { .. } | Account::Closed { .. } => false,
    }
}

/// Only an Active account can be suspended; the plan carries over into the new state.
fn suspend(a: Account, reason: &str) -> Result<Account, String> {
    match a {
        Account::Active { plan } => Ok(Account::Suspended { plan, reason: reason.to_string() }),
        other => Err(format!("only active accounts can be suspended, got {other:?}")),
    }
}

fn main() {
    let a = Account::Active { plan: "pro".to_string() };
    let s = suspend(a, "unpaid invoice").unwrap();
    println!("{s:?}, can log in: {}", can_log_in(&s, 0));
    println!("{}", suspend(Account::Closed { closed_at: 9 }, "x").unwrap_err());
    println!("trial at t=50: {}", can_log_in(&Account::Trial { ends_at: 100 }, 50));
}
Suspended { plan: "pro", reason: "unpaid invoice" }, can log in: false
only active accounts can be suspended, got Closed { closed_at: 9 }
trial at t=50: true

suspend takes the account by value and moves the plan into the new state, so there's no moment where the account is both active and suspended. The | in can_log_in matches either of two variants in one arm. There's no _ arm, on purpose: add a PastDue state later and the compiler makes you decide whether it can log in.

Exercise 3 — a rule-expression AST ★★★ lead-in to Module 9

Define enum Expr { Num(f64), Var(String), Add(…), Mul(…) } for expressions like amount * 0.02 + 5. Write eval(&Expr, &HashMap<String, f64>) -> Result<f64, String> (an unknown fact is an error) and show(&Expr) -> String. Then answer: what changes if you add a Neg node? What changes if you add a third operation, count_vars?

Show solution 
use std::collections::HashMap;

/// A tiny rule-expression language. `Box` gives the recursive variants a known size.
enum Expr {
    Num(f64),
    Var(String),
    Add(Box<Expr>, Box<Expr>),
    Mul(Box<Expr>, Box<Expr>),
}

fn eval(e: &Expr, facts: &HashMap<String, f64>) -> Result<f64, String> {
    Ok(match e {
        Expr::Num(n) => *n,
        Expr::Var(name) => *facts.get(name).ok_or(format!("unknown fact `{name}`"))?,
        Expr::Add(a, b) => eval(a, facts)? + eval(b, facts)?,
        Expr::Mul(a, b) => eval(a, facts)? * eval(b, facts)?,
    })
}

fn show(e: &Expr) -> String {
    match e {
        Expr::Num(n) => n.to_string(),
        Expr::Var(name) => name.clone(),
        Expr::Add(a, b) => format!("({} + {})", show(a), show(b)),
        Expr::Mul(a, b) => format!("({} * {})", show(a), show(b)),
    }
}

fn main() {
    // fee = amount * 0.02 + 5
    let fee = Expr::Add(
        Box::new(Expr::Mul(Box::new(Expr::Var("amount".into())), Box::new(Expr::Num(0.02)))),
        Box::new(Expr::Num(5.0)),
    );
    let facts = HashMap::from([("amount".to_string(), 1_000.0)]);
    println!("{} = {:?}", show(&fee), eval(&fee, &facts));
    println!("{:?}", eval(&fee, &HashMap::new()));
}
((amount * 0.02) + 5) = Ok(25.0)
Err("unknown fact `amount`")

Why Box<Expr>? An Expr that directly contained two Exprs would need infinite size; a Box is a fixed 8-byte pointer to a heap value (chapter F1), so the size is known. The ? after each recursive call returns early on the first error (chapter 2.6). Adding Neg breaks both eval and show with E0004 until you handle it. Adding count_vars is one new function and touches nothing else. That's the expression problem from the deep dive, and the reason chapter 9.2 uses an enum for the AST.

Common misconceptions and pitfalls

⚠️ "Strongly typed" means "statically typed"

Two different axes. Python is dynamic and fairly strict; C is static and converts liberally. Ask which conversions happen silently, and when errors are reported.

⚠️ "A Rust struct is like a C# struct, so keep it small"

The C# advice ("structs should be small and immutable") exists because C# structs are copied on every assignment and boxed when cast to an interface. A Rust struct of any size is moved, not deep-copied, unless it's Copy, and there's no boxing. Model with structs freely; reach for Box for a reason (recursion, trait objects, very large values), not by default.

⚠️ Boolean blindness and stringly typed data

process(order, true, false) and status: String hide meaning and admit nonsense ("Compelted"). Use an enum, even a two-variant one: process(order, Mode::DryRun, Notify::No).

⚠️ The catch-all arm as a habit

_ => … silences E0004 forever, including for variants added next year. Prefer listing the variants; keep _ for genuinely open sets (numbers, strings), or for enums from other crates marked #[non_exhaustive], where the compiler requires it.

⚠️ Reaching for dyn because "that's what interfaces are"

C# habit says "program to an interface", meaning dynamic dispatch. In Rust, start with generics when the type is known at compile time, and use dyn when you need mixed collections or runtime choice. Both are traits; the dispatch is a separate decision.

⚠️ Trusting nullable annotations as guarantees

C# nullable reference types are warnings over annotations. Deserialised JSON, reflection, default and older libraries can still hand you null in a non-nullable string. Validate at boundaries in .NET. At a .NET ↔ Rust boundary, the Rust side's Option is the real contract.

⚠️ The trailing semicolon

fn f() -> u32 { x * 2; } returns (). Read error E0308's "found ()" as "you probably have a semicolon too many".

Real-world view: types in your two products

🏗 Architecture view
  • Rule engine, fact model. Customers define facts at runtime, so the engine is a statically typed program carrying dynamically typed values. The standard Rust answer is a sum type: enum Value { Null, Bool(bool), Int(i64), Decimal(…), Text(String), List(Vec<Value>), Map(…) }. serde_json::Value is exactly this shape for JSON. Type-checking a rule against a declared fact schema at authoring time moves errors from production to the editor; chapter 9.5 designs this "typed vs dynamic" trade-off.
  • Rule engine, AST and plugins. An enum for the expression AST (closed, many passes) and a trait for pluggable evaluators (open, chosen at runtime): the two halves of the expression problem, each with the right tool.
  • Workflow engine, run and step states. RunStatus-style enums make "completed without output" unrepresentable. Transitions as functions returning Result give you a checked state machine. Events in the history log (chapter 10.4) are an enum too, and adding an event kind forces every replay handler to decide what to do with it.
  • Identifiers and money. Newtypes for TenantId, WorkflowId, RuleSetVersion, and integer Cents (never floats) prevent the swapped-argument and unit bugs that slip through code review, at zero runtime cost.
  • API boundaries. At the JSON edge, an enum becomes a tagged object ({"status":"failed","error":"…"}), which serde produces from one attribute (chapter 7.1). .NET clients can read it with System.Text.Json polymorphism ([JsonPolymorphic]/[JsonDerivedType]) into a record hierarchy, or, once it ships, a C# union.
  • Consultant's review checklist: clusters of bools plus nullables (count the states); strings used as enums; _ => arms on domain enums; raw u64/f64 for IDs, money and durations; Box<dyn Trait> where a generic would do, and the reverse.

Summary

  • Static vs dynamic is about when types are checked; "strong vs weak" is an informal word for silent conversions. Rust is static with almost no implicit conversions, infers types inside functions, and is nominal, so newtypes like Meters catch unit bugs for free.
  • C# decides value vs reference semantics per type declaration, invisibly at each use. In Rust every type is a value; copies (.clone()) and sharing (&, &mut, Box, Rc) are explicit in the code.
  • Products (structs) are AND and multiply their values; sums (enums) are OR and add them. Option replaces null and Result replaces exceptions for expected failures. Niche optimisation makes Option<&T> free, and exhaustive match (E0004) turns new variants into a compiler-generated to-do list, where C# only warns.
  • Generics are parametric polymorphism, monomorphised in Rust (one copy per type) and shared across reference types in .NET. Traits give ad-hoc polymorphism, and dyn Trait gives runtime dispatch through a 16-byte fat pointer. Enums vs traits is the expression problem, a real architecture choice.
  • Rust is expression-oriented (blocks, if, match, loop all produce values; a trailing ; yields ()). Use sum types, newtypes and validated constructors to make illegal states unrepresentable: the flag model admitted 64 states for a 4-state domain.
