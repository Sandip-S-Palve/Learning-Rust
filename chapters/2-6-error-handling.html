Error handling

Learning objectives

  • Decide between Result (recoverable errors) and panic! (bugs and broken invariants), and explain what each does at run time
  • Propagate errors with ?, and explain the From conversion it performs
  • Write an error type by hand (Display, Error, source, From) and with thiserror, and add context with anyhow
  • Print and inspect error chains ({}, {:#}, {:?}, source(), downcast_ref) and choose a strategy for libraries vs applications
  • Compare Rust's errors with .NET exceptions on visibility, cost and control flow, using measurements from both runtimes

Why this matters

💡 Why this matters

In C#, any method can throw, and its signature doesn't say so. You learn which exceptions File.ReadAllText throws from the documentation, if you look. The compiler won't tell you that you forgot one, and a catch (Exception) far up the stack catches bugs and expected failures alike. It works, mostly, but the failure paths of a system are invisible in its code, and they're where production incidents live.

Rust splits errors in two. Failures a caller can handle (a missing file, a bad rule, a timed-out call) are ordinary return values of type Result, written in the signature and impossible to ignore silently. Bugs (an index out of range, a broken invariant) panic, and the program, or at least that thread, stops. For your rule engine that means a rule that fails to parse is a value you can report to the author, line by line. For your workflow engine it means every step's failure modes are visible in its type, so the retry and compensation logic of chapters 10.3 and 10.5 can be checked by the compiler rather than discovered in an incident review.

Intuition first: the return slip and the fire alarm

🧭 Analogy
  • Result is a delivery that comes back with a slip: either the parcel (Ok) or a note saying why it couldn't be delivered (Err: "address not found", "refused"). Whoever ordered it must read the slip before using the parcel, because the box can't be opened otherwise.
  • ? is "send it back up": if I got a failure slip, I attach it to my own reply and return immediately. Each manager on the way up can add a line to the slip ("while preparing the March invoice…"): that's context.
  • A panic is the fire alarm. It isn't for "the customer wasn't home". It's for "the building is on fire": something that should be impossible has happened, and carrying on would be worse than stopping. Everyone leaves (the stack unwinds, running every destructor on the way out) and the building is evacuated, unless a fire wall (a thread boundary, catch_unwind) contains it.

.NET exceptions use the fire alarm for both: a missing file and a null-reference bug travel the same way, and neither appears on the delivery slip.

C#
// The signature doesn't say it can fail.
int ParseLimit(string s) => int.Parse(s.Trim()); // may throw

try {
    var limit = ParseLimit(input);
    Use(limit);
} catch (FormatException e) {
    Log(e.Message);
}
Rust
// The signature says it can fail, and how.
fn parse_limit(s: &str) -> Result<u32, std::num::ParseIntError> {
    s.trim().parse::<u32>()
}

match parse_limit("50x") {
    Ok(limit) => println!("limit {limit}"),
    Err(e) => println!("bad limit: {e}"),
}

Core explanation

Basic

Two kinds of error

The Book: "Rust groups errors into two major categories: recoverable and unrecoverable errors." And: "Rust doesn't have exceptions. Instead, it has the type Result<T, E> for recoverable errors and the panic! macro that stops execution when the program encounters an unrecoverable error." The whole chapter follows from choosing the right one, and the question that decides it is who can do something about this?

Result<T, E>

Result is an ordinary enum from the standard library, exactly the kind chapter 2.5 taught: enum Result<T, E> { Ok(T), Err(E) }. A function that can fail returns one, and its signature tells the caller both what success produces (T) and what failure looks like (E). "42".parse::<u32>() returns Result<u32, ParseIntError>; std::fs::read_to_string returns Result<String, std::io::Error>. You can't use the u32 inside without dealing with the Err case, whether by match, if let, a method, or ?.

Result has the same toolbox as Option (chapter 2.5), plus a few error-specific methods (Lab step 1):

You wantWrite
A fallback valuer.unwrap_or(100), unwrap_or_default(), unwrap_or_else(|e| …)
Transform the success valuer.map(|n| n * 2)
Transform or wrap the errorr.map_err(|e| MyError::Parse(e))
Chain another fallible stepr.and_then(validate), or ?

Crash if it failedr.unwrap(), r.expect("reason it can't fail")

Result is marked #[must_use]: calling a fallible function and ignoring the result is a compiler warning (Lab step 2, w3). C# has no equivalent for exceptions. Nothing tells you that you didn't handle one.

The ? operator

Matching every Result by hand would bury the logic. The question mark operator does the common thing: on Ok(v) it evaluates to v; on Err(e) it returns from the current function immediately. The Rust Reference states it precisely: "Result::Err(e) returns Result::Err(From::from(e))." That From::from is the important detail. On the way out, ? converts the error into the function's own error type, if a conversion exists:

use std::num::ParseIntError;

fn total_limit(a: &str, b: &str) -> Result<u32, ParseIntError> {
    let x = a.trim().parse::<u32>()?; // on Err: return it now
    let y = b.trim().parse::<u32>()?;
    Ok(x + y)
}

println!("{:?} {:?}", total_limit("40", "2"), total_limit("40", "two"));

Two rules come with it. ? only works inside a function whose return type can carry the failure: a Result (or an Option, where None returns early). Using it in a function that returns (), such as a plain main, is error E0277, and the compiler suggests changing the signature (Lab step 2, e1). And the error types must be convertible; if they aren't, you get "? couldn't convert the error" (e2).

main itself may return Result<(), E>. If it returns Err, the standard library prints Error: followed by the error's Debug form to stderr and exits with code 1. The toolchain's source does exactly attempt_print_to_stderr(format_args_nl!("Error: {err:?}")) and returns ExitCode::FAILURE. That Debug output is meant for developers, which is one reason applications use anyhow, whose Debug form is a readable error chain (Lab step 3).

Panics

A panic happens when you call panic!, when unwrap() or expect() meets an Err or None, when an index is out of range, or when arithmetic overflows in a debug build (chapter 2.1). By default the panic unwinds: it walks back up the thread's stack, running every live value's destructor, exactly as chapter 2.2 showed. If nothing contains it, the thread ends. If that thread is main, the process exits with code 101 (Lab step 4).

A panic is not a way to report bad input. It means "the program has a bug or its assumptions are broken". The good uses:

  • Invariants that can't fail if the code is correct: expect with a message saying why it can't fail, so the panic message documents the broken assumption: config.get("db").expect("validated at startup").
  • Tests, examples and prototypes, where unwrap keeps the code short.
  • Unrecoverable startup problems in an application's main, though returning a Result from main often reads better.

Panics can be contained at a boundary. A panicking thread reports Err to whoever calls join() (Lab step 4), and std::panic::catch_unwind turns a panic in a closure into an Err. That's how a server keeps one bad request, or a rule engine one faulty plugin, from taking the process down. It's a fire wall, not a control-flow mechanism: Lab step 5 measures a caught panic at about 13 µs, four times the cost of a .NET exception.

🟣 Coming from C#/.NET: exceptions vs Result
  • Visibility. A C# signature never says what it throws (C# has no checked exceptions), so failure handling relies on documentation and discipline. A Rust signature says Result<T, RuleError>, and the compiler checks that callers handle it, or explicitly pass it on with ?.
  • Expected failures. .NET's own guidance points the same way for common cases: "If the performance cost of exceptions is prohibitive, some .NET library methods provide alternative forms of error handling", the Try* pattern (int.TryParse, TryGetValue), and it says to "check for error conditions in code if the event happens routinely". In Rust every fallible API is "the Try pattern", with the error's details included instead of a bare bool.
  • Bugs. NullReferenceException and IndexOutOfRangeException correspond to panics: both mean the code is wrong. Rust removes the first entirely (no null) and makes the second a panic.
  • Wrapping and chains. InnerException ↔ Error::source(); "wrap with a more specific exception" ↔ map_err or anyhow's context; catch (FormatException) ↔ matching an error enum's variant, or downcast_ref.
  • Cleanup. finally/using ↔ Drop, which runs on ? returns and during panics alike (chapter 2.2).
Intermediate

Writing an error type

A real operation fails in several ways (the file is missing, a number is malformed, an operator is unknown), and the caller may want to treat them differently. The idiomatic error type is an enum with one variant per failure, carrying the details. To be a well-behaved error it implements three standard traits:

New syntax: impl Display for RuleError { … } is a trait implementation, like implementing an interface in C# (class RuleError : IFormattable). Traits were introduced in chapter F8 and are covered fully in chapter 2.9; here you only need to fill in the methods each one requires.

  • Display: the human message, what {} prints: "line 2: value is not a number". Lowercase, no trailing period, and without the underlying cause's text, which belongs in source.
  • std::error::Error: marks it as an error and provides source(), the underlying cause (the ParseIntError inside BadNumber), so reporters can walk the whole chain. It's the equivalent of InnerException.
  • From conversions: impl From<std::io::Error> for RuleError lets ? turn an I/O error into a RuleError automatically.

Lab step 2 writes all of this by hand for a rule loader. The output shows the two layers ("line 2: value is not a number", "caused by: invalid digit found in string"), produced by walking source(). In the first version of that program, the I/O variant's message also included the cause's text, so the report printed "No such file or directory" twice. The rule that fixes it: a cause goes either in the message or in source(), never both.

thiserror and anyhow

The hand-written impls are mechanical, and two crates, used by most of the ecosystem, remove the boilerplate. They're published by the same author (David Tolnay, per crates.io) for the two sides of the library/application split.

  • thiserror (crates.io: "derive(Error)"): #[derive(thiserror::Error)] on your enum generates Display from #[error("…")] attributes, source() from fields named source or marked #[source], and From impls from #[from]. It's the hand-written version from Lab step 2, in a third of the lines (Lab step 3), and callers still get a real enum to match.
  • anyhow (crates.io: "Flexible concrete Error type built on std::error::Error"): anyhow::Result<T> holds any error. ? converts into it from every error type. .context("…") and .with_context(|| …) add context as the error propagates, and bail!("…") returns an ad-hoc error. Its alternate Display ({:#}) prints the whole chain on one line, and its Debug form (what main prints) is a numbered "Caused by" list.

Lab step 3 combines them: a rules module with a thiserror enum, and an application layer using anyhow that adds "loading rules for tenant … from …" on top. The typed error isn't lost inside the anyhow::Error: e.downcast_ref::<RuleError>() recovers it when the application needs to react to a specific failure.

Comparing the strategies

There are four common choices for E. The explorer shows exactly what each one gives the person reading the log and the code handling the error. Every output was produced by one Rust program running the same rule loader four ways.

The guideline the explorer illustrates: libraries return precise error enums (thiserror), because their callers need to react to specific failures, and an enum makes those failures part of the API. Applications use anyhow (or a similar type) with context at each layer, because at the top the goal is a good message and a log entry, not a match. A String error loses the cause and any structure, so avoid it beyond prototypes. Box<dyn Error> holds any error through dynamic dispatch (chapter F8) and is the standard-library-only middle ground; anyhow::Error is essentially a better version of it, with context and backtraces.

How an error travels

Deep dive: how ? is defined, and why it works on Option too

? is defined through two traits, Try and FromResidual (stable to use, still unstable to implement for your own types). For Result the Reference gives it as roughly:

// `expr?` on a Result is roughly:
match expr {
    Ok(val) => val,
    Err(e) => return Err(From::from(e)),
}

For Option, None returns None. You can't mix them in one function: ? on an Option inside a function returning Result doesn't compile. Convert explicitly with .ok_or(MyError::Missing)?. Because the conversion is From::from, adding impl From<sqlx::Error> for RepoError once makes every ? on a database call convert automatically. And because it's a return, everything in scope is dropped normally: locks released, transactions rolled back by their guards (chapter 2.2).

Deep dive: panic = "abort", backtraces, and what unwinding costs

Unwinding needs tables in the binary describing each frame's cleanup, and it runs every destructor. Setting panic = "abort" in a Cargo profile makes any panic stop the process immediately instead: smaller binaries and no unwinding cost, but no destructors, no catch_unwind, and a panicking thread kills the whole process. Embedded systems and some services that prefer a fast crash-and-restart choose it.

Setting RUST_BACKTRACE=1 makes panics print a stack trace (the note at the end of every panic message in Lab step 4 says so). anyhow's docs: "If you want panics and errors to both have backtraces, set RUST_BACKTRACE=1; if you want only errors to have backtraces, set RUST_LIB_BACKTRACE=1." The cost measured in Lab step 5 (about 13 µs per caught panic on the lab Mac) comes from formatting the panic message, allocating its payload and walking the unwind tables. It's the right price for a crash and the wrong one for a parse error.

Step 1 — Result and its methods

use std::num::ParseIntError;

// A function that can fail says so in its return type.
fn parse_limit(s: &str) -> Result<u32, ParseIntError> {
    s.trim().parse::<u32>()
}

fn main() {
    // 1. Handling both outcomes with match.
    for input in ["500", " 42 ", "-3", "lots", ""] {
        match parse_limit(input) {
            Ok(n) => println!("1. {input:?} -> Ok({n})"),
            Err(e) => println!("1. {input:?} -> Err: {e}"),
        }
    }

    // 2. Result's methods, the same toolbox as Option's.
    let good = parse_limit("500");
    let bad = parse_limit("lots");
    println!("2. map(x2):        {:?} / {:?}", good.clone().map(|n| n * 2), bad.clone().map(|n| n * 2));
    println!("   unwrap_or(100): {} / {}", good.clone().unwrap_or(100), bad.clone().unwrap_or(100));
    println!("   ok():           {:?} / {:?}", good.clone().ok(), bad.clone().ok());
    println!("   map_err:        {:?}", bad.clone().map_err(|e| format!("limit: {e}")));
    println!("   is_ok / is_err: {} / {}", good.is_ok(), bad.is_err());
    println!("   and_then:       {:?}", good.clone().and_then(|n| if n <= 1_000 { Ok(n) } else { parse_limit("x") }));

    // 3. Collecting: the first error stops everything...
    let all: Result<Vec<u32>, ParseIntError> = ["1", "2", "3"].iter().map(|s| parse_limit(s)).collect();
    let one_bad: Result<Vec<u32>, ParseIntError> = ["1", "x", "3", "y"].iter().map(|s| parse_limit(s)).collect();
    println!("3. collect all good: {all:?}");
    println!("   collect with bad:  {one_bad:?}");

    // ...or keep going and gather every error.
    let (oks, errs): (Vec<_>, Vec<_>) = ["1", "x", "3", "y"].iter().map(|s| parse_limit(s)).partition(|r| r.is_ok());
    let oks: Vec<u32> = oks.into_iter().map(Result::unwrap).collect();
    let errs: Vec<String> = errs.into_iter().map(|r| r.unwrap_err().to_string()).collect();
    println!("   partition: ok {oks:?}, errors {errs:?}");

    // 4. A Result you ignore is a warning: Result is #[must_use].
    let _ = parse_limit("ignored on purpose"); // `let _ =` says "I mean it"
}

Step 2 — an error type by hand, and ?

use std::fmt;
use std::num::ParseIntError;

// One error type for the whole "load rules" operation: an enum of everything that can go wrong.
#[derive(Debug)]
enum RuleError {
    Io(std::io::Error),
    BadNumber { line: usize, source: ParseIntError },
    UnknownOperator { line: usize, op: String },
}

// Display: the message for humans (what `{}` prints).
impl fmt::Display for RuleError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            RuleError::Io(_) => write!(f, "could not read the rules file"), // the cause is in source()
            RuleError::BadNumber { line, .. } => write!(f, "line {line}: value is not a number"),
            RuleError::UnknownOperator { line, op } => write!(f, "line {line}: unknown operator {op:?}"),
        }
    }
}

// Error: marks it as an error type and exposes the underlying cause, if any.
impl std::error::Error for RuleError {
    fn source(&self) -> Option<&(dyn std::error::Error + 'static)> {
        match self {
            RuleError::Io(e) => Some(e),
            RuleError::BadNumber { source, .. } => Some(source),
            RuleError::UnknownOperator { .. } => None,
        }
    }
}

// From: lets `?` convert an io::Error into a RuleError automatically.
impl From<std::io::Error> for RuleError {
    fn from(e: std::io::Error) -> Self {
        RuleError::Io(e)
    }
}

#[derive(Debug)]
struct Rule {
    field: String,
    op: String,
    value: u32,
}

fn parse_line(line_no: usize, line: &str) -> Result<Rule, RuleError> {
    let parts: Vec<&str> = line.split_whitespace().collect();
    let [field, op, value] = parts[..] else {
        return Err(RuleError::UnknownOperator { line: line_no, op: line.to_string() });
    };
    if ![">", ">=", "==", "<"].contains(&op) {
        return Err(RuleError::UnknownOperator { line: line_no, op: op.to_string() });
    }
    // map_err converts the ParseIntError and adds the line number; `?` returns it early.
    let value = value
        .parse::<u32>()
        .map_err(|source| RuleError::BadNumber { line: line_no, source })?;
    Ok(Rule { field: field.to_string(), op: op.to_string(), value })
}

fn load_rules(path: &str) -> Result<Vec<Rule>, RuleError> {
    let text = std::fs::read_to_string(path)?; // io::Error -> RuleError via From
    let mut rules = Vec::new();
    for (i, line) in text.lines().enumerate().filter(|(_, l)| !l.trim().is_empty()) {
        rules.push(parse_line(i + 1, line)?);
    }
    Ok(rules)
}

fn report(path: &str) {
    match load_rules(path) {
        Ok(rules) => {
            let r = &rules[0];
            println!("{path}: {} rules, first: {} {} {}", rules.len(), r.field, r.op, r.value);
        }
        Err(e) => {
            println!("{path}: error: {e}");
            // Walk the chain of causes through Error::source.
            let mut cause = std::error::Error::source(&e);
            while let Some(c) = cause {
                println!("    caused by: {c}");
                cause = c.source();
            }
        }
    }
}

fn main() -> Result<(), RuleError> {
    std::fs::write("rules_ok.txt", "amount >= 100\ncountry == 31\n")?;
    std::fs::write("rules_badnum.txt", "amount >= 100\nvip == yes\n")?;
    std::fs::write("rules_badop.txt", "amount => 100\n")?;
    for p in ["rules_ok.txt", "rules_badnum.txt", "rules_badop.txt", "missing.txt"] {
        report(p);
    }
    println!("--- now letting main itself return the error:");
    load_rules("missing.txt")?;
    println!("never printed");
    Ok(())
}

Step 3 — thiserror for the library, anyhow for the application

// ---------- Library layer: a precise error type, generated by thiserror ----------
mod rules {
    use std::num::ParseIntError;

    #[derive(Debug, thiserror::Error)]
    pub enum RuleError {
        #[error("could not read the rules file")]
        Io(#[from] std::io::Error), // #[from] writes the From impl and marks the source
        #[error("line {line}: value is not a number")]
        BadNumber { line: usize, source: ParseIntError }, // a field named `source` is the cause
        #[error("line {line}: unknown operator {op:?}")]
        UnknownOperator { line: usize, op: String },
    }

    pub struct Rule {
        pub field: String,
        pub op: String,
        pub value: u32,
    }

    fn parse_line(line: usize, text: &str) -> Result<Rule, RuleError> {
        let parts: Vec<&str> = text.split_whitespace().collect();
        let [field, op, value] = parts[..] else {
            return Err(RuleError::UnknownOperator { line, op: text.to_string() });
        };
        if ![">", ">=", "==", "<"].contains(&op) {
            return Err(RuleError::UnknownOperator { line, op: op.to_string() });
        }
        let value = value.parse().map_err(|source| RuleError::BadNumber { line, source })?;
        Ok(Rule { field: field.into(), op: op.into(), value })
    }

    pub fn load(path: &str) -> Result<Vec<Rule>, RuleError> {
        let text = std::fs::read_to_string(path)?;
        text.lines()
            .enumerate()
            .filter(|(_, l)| !l.trim().is_empty())
            .map(|(i, l)| parse_line(i + 1, l))
            .collect()
    }
}

// ---------- Application layer: anyhow, with context added on the way up ----------
use anyhow::{Context, Result, bail};

fn load_tenant_rules(tenant: &str) -> Result<usize> {
    if tenant.is_empty() {

Step 4 — panics, contained and not

use std::panic;
use std::thread;

fn rule_at(rules: &[&str], i: usize) -> String {
    rules[i].to_uppercase() // indexing out of range panics
}

fn main() {
    let rules = ["amount >= 100", "vip == 1"];

    // 1. A panic inside a thread doesn't take the process down: join() reports it as an Err.
    for (name, job) in [
        ("index", 0usize),
        ("unwrap", 1),
        ("expect", 2),
        ("explicit", 3),
    ] {
        let handle = thread::spawn(move || match job {
            0 => rule_at(&rules, 5),
            1 => "lots".parse::<u32>().unwrap().to_string(),
            2 => std::env::var("RULES_PATH_THAT_IS_NOT_SET").expect("RULES_PATH must be set by the deployment"),
            _ => panic!("invariant broken: rule {} has no operator", 7),
        });
        match handle.join() {
            Ok(v) => println!("1. {name}: ok {v}"),
            Err(payload) => {
                let msg = payload
                    .downcast_ref::<String>()
                    .cloned()
                    .or_else(|| payload.downcast_ref::<&str>().map(|s| s.to_string()))
                    .unwrap_or_default();
                println!("1. {name}: the thread panicked: {msg}");
            }
        }
    }

    // 2. catch_unwind at a boundary (e.g. one plugin rule must not crash the engine).
    let result = panic::catch_unwind(|| rule_at(&rules, 9));
    println!("2. catch_unwind returned is_err = {}", result.is_err());

    // 3. An uncaught panic on the main thread ends the process with exit code 101.
    println!("3. now panicking on the main thread...");
    let _ = rule_at(&rules, 2);
}

Step 5 — the cost of failing: Result vs panics vs exceptions

Parse 200,000 strings, of which 0, 1, 10 or 50% are invalid, using each language's two styles: failure as a value (Rust Result, C# TryParse), and failure as unwinding (a Rust panic caught with catch_unwind, a C# exception caught with catch).

use std::hint::black_box;
use std::panic;
use std::time::Instant;

const N: usize = 200_000;

fn inputs(fail_pct: usize) -> Vec<String> {
    (0..N)
        .map(|i| if i % 100 < fail_pct { format!("{}x", i % 9_000) } else { format!("{}", i % 9_000) })
        .collect()
}

// The Rust way: failure is a value.
fn with_result(items: &[String]) -> usize {
    items.iter().filter(|s| s.parse::<u32>().is_ok()).count()
}

// Exceptions-as-control-flow, imitated: panic on bad input and catch the unwind per item.
fn with_panics(items: &[String]) -> usize {
    items
        .iter()
        .filter(|s| panic::catch_unwind(|| s.parse::<u32>().unwrap()).is_ok())
        .count()
}

fn ns_per_item(items: &[String], f: fn(&[String]) -> usize) -> f64 {
    (0..3)
        .map(|_| {
            let t = Instant::now();
            black_box(f(black_box(items)));
            t.elapsed().as_secs_f64() * 1e9 / N as f64
        })
        .fold(f64::INFINITY, f64::min)
}

fn main() {
    panic::set_hook(Box::new(|_| {})); // silence the panic messages for the benchmark
    println!("{N} parses per run, best of 3, ns per item:");
    println!("{:>8} {:>10} {:>16}", "failing", "Result", "panic + catch");
    for pct in [0, 1, 10, 50] {
        let items = inputs(pct);
        assert_eq!(with_result(&items), with_panics(&items));
        println!("{:>7}% {:>10.1} {:>16.1}", pct, ns_per_item(&items, with_result), ns_per_item(&items, with_panics));
    }
}

static int WithTryParse(string[] items)
{
    int ok = 0;
    foreach (var s in items) if (int.TryParse(s, out _)) ok++;
    return ok;
}

// Exceptions as control flow.
static int WithExceptions(string[] items)
{
    int ok = 0;
    foreach (var s in items)
    {
        try { int.Parse(s); ok++; }
        catch (FormatException) { }
    }
    return ok;
}

{

    {
        var sw = Stopwatch.StartNew();
        f(items);
        best = Math.Min(best, sw.Elapsed.TotalNanoseconds / N);
    }
    return best;
}

Two lessons, one expected and one not. Expected: making failure a value removes its cost entirely, which is why Rust APIs never throw. Unexpected if you assume Rust is always faster: a caught panic was about four times as expensive as a .NET exception here. Exercise 1 — a config error type by hand ★☆☆

Write parse_setting(line: &str) -> Result<(String, u32), ConfigError> for lines like max_retries = 3, with a hand-written ConfigError enum (missing =, empty key, bad value with its ParseIntError as the source) implementing Display and Error. Use ? at least twice.

Show solution 
use std::fmt;
use std::num::ParseIntError;

#[derive(Debug, PartialEq)]
enum ConfigError {
    MissingEquals(String),
    EmptyKey,
    BadValue { key: String, source: ParseIntError },
}

impl fmt::Display for ConfigError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            ConfigError::MissingEquals(line) => write!(f, "expected key=value, got {line:?}"),
            ConfigError::EmptyKey => write!(f, "key is empty"),
            ConfigError::BadValue { key, .. } => write!(f, "value of {key:?} is not a number"),
        }
    }
}

impl std::error::Error for ConfigError {
    fn source(&self) -> Option<&(dyn std::error::Error + 'static)> {
        match self {
            ConfigError::BadValue { source, .. } => Some(source),
            _ => None,
        }
    }
}

fn parse_setting(line: &str) -> Result<(String, u32), ConfigError> {
    let (key, value) = line.split_once('=').ok_or_else(|| ConfigError::MissingEquals(line.to_string()))?;
    let key = key.trim();
    if key.is_empty() {
        return Err(ConfigError::EmptyKey);
    }
    let value = value
        .trim()
        .parse()
        .map_err(|source| ConfigError::BadValue { key: key.to_string(), source })?;
    Ok((key.to_string(), value))
}

fn main() {
    for line in ["max_retries = 3", "timeout", " = 5", "workers = many"] {
        match parse_setting(line) {
            Ok((k, v)) => println!("{line:?} -> {k} = {v}"),
            Err(e) => {
                let cause = std::error::Error::source(&e).map(|c| format!(" (caused by: {c})")).unwrap_or_default();
                println!("{line:?} -> error: {e}{cause}");
            }
        }
    }
    assert_eq!(parse_setting("a=1"), Ok(("a".to_string(), 1)));
    assert_eq!(parse_setting("=1"), Err(ConfigError::EmptyKey));
    assert!(matches!(parse_setting("a"), Err(ConfigError::MissingEquals(_))));
    assert!(matches!(parse_setting("a=x"), Err(ConfigError::BadValue { .. })));
    println!("ok");
}

"timeout" -> error: expected key=value, got "timeout"
" = 5" -> error: key is empty

ok_or_else turns the Option from split_once into a Result so ? can use it; map_err wraps the ParseIntError with the key that failed. Deriving PartialEq lets tests compare errors directly. ParseIntError implements it too. Many error types (like io::Error) don't, which is why tests usually use matches!.

Exercise 2 — report every bad rule ★★☆ product skill

A rule author pastes twenty rules into the editor. Write validate(text: &str) -> Result<Vec<Rule>, Vec<RuleError>> that returns all the errors with their line numbers, not just the first, using a thiserror enum.

Show solution 
use std::num::ParseIntError;

#[derive(Debug, thiserror::Error)]
enum RuleError {
    #[error("line {line}: expected `field op value`")]
    Shape { line: usize },
    #[error("line {line}: unknown operator {op:?}")]
    UnknownOperator { line: usize, op: String },
    #[error("line {line}: value is not a number")]
    BadNumber { line: usize, source: ParseIntError },
}

#[derive(Debug)]
struct Rule {
    field: String,
    op: String,
    value: u32,
}

fn parse_line(line: usize, text: &str) -> Result<Rule, RuleError> {
    let parts: Vec<&str> = text.split_whitespace().collect();
    let [field, op, value] = parts[..] else {
        return Err(RuleError::Shape { line });
    };
    if ![">", ">=", "==", "<"].contains(&op) {
        return Err(RuleError::UnknownOperator { line, op: op.into() });
    }
    let value = value.parse().map_err(|source| RuleError::BadNumber { line, source })?;
    Ok(Rule { field: field.into(), op: op.into(), value })
}

// Report every bad line, not just the first: an editor or API caller wants all of them at once.
fn validate(text: &str) -> Result<Vec<Rule>, Vec<RuleError>> {
    let mut rules = Vec::new();
    let mut errors = Vec::new();
    for (i, l) in text.lines().enumerate().filter(|(_, l)| !l.trim().is_empty()) {
        match parse_line(i + 1, l) {
            Ok(r) => rules.push(r),
            Err(e) => errors.push(e),
        }
    }
    if errors.is_empty() { Ok(rules) } else { Err(errors) }
}

fn main() {
    let good = "amount >= 100\ncountry == 31\n";
    let bad = "amount >= 100\nvip == yes\n\ntier\nage => 18\n";
    match validate(good) {
        Ok(rules) => println!("good: {} rules, last {} {} {}", rules.len(), rules[1].field, rules[1].op, rules[1].value),
        Err(errs) => println!("unexpected: {errs:?}"),
    }
    match validate(bad) {
        Ok(_) => println!("unexpected success"),
        Err(errs) => {
            println!("bad: {} errors", errs.len());
            for e in &errs {
                println!("  - {e}");
            }
        }
    }
    assert_eq!(validate(bad).unwrap_err().len(), 3);
    assert!(matches!(validate(bad).unwrap_err()[0], RuleError::BadNumber { line: 2, .. }));
    println!("ok");
}
good: 2 rules, last country == 31
bad: 3 errors
  - line 2: value is not a number
  - line 4: expected `field op value`
  - line 5: unknown operator "=>"
ok

? and collect stop at the first failure, which is right for "load and run" and wrong for "validate and report". Here each line's Result is matched and errors are accumulated; the function's own Result type, Vec<RuleError> as the error, says "possibly many errors". Exercise 3 — panic or Result? ★★☆

For each situation in the workflow engine, decide: return a Result, or panic (expect/unreachable!)? Then check.

  1. A step's JSON payload from a client fails to deserialize.
  2. The database is unreachable while saving a step's state.
  3. After if queue.is_empty() { return; }, the code calls queue.pop().
  4. A state machine match reaches an arm that the transition table says can't happen.
  5. A required environment variable is missing when the service starts.
  6. A plugin rule supplied by a customer divides by zero.
Show solution
  1. Result. Bad input from outside is expected; report it to the client (HTTP 400).
  2. Result. It's transient and recoverable: retry, back off, or fail the step (chapters 6.6 and 10.5).
  3. expect is fine: queue.pop().expect("checked non-empty above"). The None case is impossible if the code is correct, and the message documents why. (Better still, restructure with while let Some(job) = queue.pop() or let Some(job) = queue.pop() else { return };, which removes the question.)
  4. panic (unreachable!("…")), if it truly can't happen: it's a bug in the engine. If persisted data could ever contain that combination, for example from an older version, it's input, and it should be a Result (chapter 10.7).
  5. Result from main (or a clear expect). It's unrecoverable for the process but not a bug; with anyhow and context the operator gets a readable message and exit code 1.
  6. Contain it. Customer code panicking must not take down the engine: run plugins behind a boundary (catch_unwind, a separate thread, or a WebAssembly sandbox, chapter 9.6) and convert the panic into an error for that rule only.

Common misconceptions and pitfalls

⚠️ unwrap() on input from outside

Files, requests, environment variables and databases fail in production. Use ? with context; reserve unwrap for tests and expect for real invariants, with a message saying why it holds.

⚠️ Using panics as exceptions

catch_unwind around normal logic is slow (Lab step 5), doesn't catch aborts, and hides bugs. Return Result.

⚠️ Errors without context

"No such file or directory (os error 2)" with no file name is a support ticket. Add context where the information exists: .with_context(|| format!("reading {path}")).

⚠️ Printing the cause twice

If Display includes the inner error's text and source() returns it, every reporter shows it twice (the first version of Lab step 2 did). Put the cause in one place: source().

⚠️ anyhow in a library's public API

Callers can't match on anyhow::Error without downcasting to types they may not know about. Libraries expose enums; applications convert them into anyhow.

⚠️ let _ = fallible(); to silence the warning

It silences the warning and the failure. Handle it, log it, or propagate it; use let _ = only when the failure truly doesn't matter, and say so in a comment.

Real-world view: failure in your products

🏗 Architecture view
  • Rule engine: parsing returns all errors with locations (Exercise 2); evaluation returns Result<Value, EvalError> for type mismatches and missing facts. Customer-supplied rule code runs behind a panic boundary so one bad rule can't stop the engine (chapter 9.6).
  • Workflow engine: a step's error type distinguishes retryable (timeout, unavailable) from permanent (validation, denied) failures, and the retry policy matches on that, which makes it explicit and compiler-checked (chapters 10.3, 10.5). Panics in step code are caught at the worker boundary and recorded as step failures, not process crashes.
  • Error layers: crates in the workspace define thiserror enums; the service binary uses anyhow with context, and maps errors to HTTP status codes or gRPC statuses at the edge (chapter 7.2).
  • Observability: log the error chain with {:#} or as structured fields, and attach the error to the tracing span (chapter 6.3), so each log line tells the whole story.
  • Review checklist: unwrap on external data; expect without a reason; String errors in library APIs; missing context on I/O; causes duplicated in Display; catch_unwind used for flow; ignored Results.

Summary

  • Rust has no exceptions: recoverable failures are Result<T, E> values, written in the signature and #[must_use]; bugs and broken invariants panic.
  • ? returns Err(From::from(e)) early, converting error types through From; it needs a function returning Result/Option. main can return Result (Debug to stderr, exit 1).
  • An error type is an enum implementing Display (message), Error (source() = the cause) and From; thiserror derives all three. Put a cause in source() or the message, never both.
  • Libraries expose precise enums; applications use anyhow with context at each layer, printed as {:#} or a "Caused by" list; downcast_ref recovers the typed error.
  • Panics unwind (running Drop) and end the thread (exit code 101 on main); contain them at boundaries only. Measured: Result about 2 ns per failure, a .NET exception about 3.1 µs, a caught Rust panic about 13 µs.
