Graphs

Learning objectives

  • Model a problem as a graph: vertices, edges, directed vs undirected, weighted, cycles, DAGs
  • Choose a representation (adjacency list vs matrix) and build one in Rust with indices
  • Run breadth-first and depth-first search by hand and in code, and know what each is for
  • Order dependencies with topological sort, group them into parallel layers, and detect cycles
  • Find weighted shortest paths with Dijkstra's algorithm, and know its key restriction

Why this matters

💡 Why this matters

Both of your products are graph engines in disguise. A workflow definition is a directed graph of steps: which steps can run in parallel, which must wait, and whether someone has accidentally created a loop that will never finish. A rule set is a graph of facts and rules: rule B needs a value that rule A computes, so A must evaluate first, and a circular dependency must be rejected when the rules are saved, not discovered at 3 a.m. in production.

You also meet graphs in every architecture review: service call maps ("what breaks if the database is down?"), package dependency trees (cargo tree from chapter 0.2), permission hierarchies, network routes.

Intuition first: a city map and a recipe

🧭 Analogy
  • A city map is a graph: junctions connected by roads, some one-way, each with a travel time. "How do I get from A to B fastest?" is a shortest-path question.
  • A recipe is a directed graph with no loops: you must chop before you fry, and preheat before you bake, but chopping and preheating can happen at the same time. Working out a valid order is a topological sort. A recipe that says "fry the sauce, which requires the finished dish" is a cycle: impossible to cook.

Core explanation

Basic

Vocabulary

A graph is a set of vertices (also called nodes) connected by edges. Trees (chapter F5) are a special case: connected and with no cycles.

  • Directed vs undirected: a one-way street (A → B) vs a two-way road (A — B). Dependencies are directed; "these services share a network" is undirected.
  • Weighted: edges carry a number (latency, cost, distance).
  • Path: a sequence of edges from one vertex to another. A cycle is a path that returns to its start.
  • DAG (directed acyclic graph): directed, with no cycles. Workflows, build systems, spreadsheets and rule dependencies are all DAGs, or must be.
  • Degree: the number of edges touching a vertex. In directed graphs this splits into in-degree (edges arriving) and out-degree (edges leaving).
  • Sparse vs dense: most real graphs are sparse, each vertex connected to a few others rather than to all.

In Rust, vertices are usually just indices (0..V) into vectors. That's the arena pattern from chapters F3 and F5, with no pointers and no ownership puzzles. If your vertices have names, keep a HashMap<String, usize> from name to index alongside (Lab step 2 does this).

Breadth-first and depth-first search

Almost every graph algorithm is built on one of two ways to visit everything reachable from a start vertex:

  • Breadth-first search (BFS) uses a queue (FIFO, chapter F3). It visits everything 1 hop away, then 2 hops, and so on, in expanding rings. So it finds shortest paths by number of edges.
  • Depth-first search (DFS) uses a stack (LIFO): follow one path as deep as it goes, then back up. It underlies cycle detection, topological sorting and maze solving.

Both mark vertices as seen so that nothing is visited twice, which makes each run O(V + E): every vertex and edge handled once. Explore them interactively:

Topological sort: ordering dependencies

Given a DAG of "must happen before" edges, a topological sort lists the vertices so that every edge points forward. A valid order exists if and only if there's no cycle. Kahn's algorithm (1962) is the one to know, because it does three jobs at once:

  1. Count each vertex's in-degree (how many prerequisites it has).
  2. Every vertex with in-degree 0 is ready. Take the ready ones, and for each of their outgoing edges, decrement the target's in-degree. Targets that reach 0 become ready.
  3. Repeat. If you run out of ready vertices before all are done, the leftovers are stuck on a cycle (or downstream of one).

Process the ready set one batch at a time and you get layers: everything in a layer can run in parallel. That is exactly how a workflow engine schedules independent steps.

Intermediate

Cycle detection with DFS colours

Kahn tells you that there's a cycle and which steps are stuck. To show a user the cycle itself ("credit_score → risk_rule → decision → credit_score"), use DFS with three colours: white (not visited), grey (on the current path, entered but not finished) and black (finished). Meeting a grey vertex means you've walked back onto your own path: a cycle, which you can read off by following parent links. Exercise 1 implements it. Tarjan's 1972 paper extended these DFS ideas into linear-time algorithms for strongly connected components, the maximal groups of vertices that all reach each other, which is the general way to find every cycle at once.

Weighted shortest paths: Dijkstra

When edges have weights, the fewest hops isn't the cheapest route. Dijkstra's algorithm (1959) finds the cheapest path from a start vertex to all others, provided no weight is negative:

  1. Distance to the start is 0; everything else is ∞.
  2. Repeatedly take the unsettled vertex with the smallest known distance (a min-heap from chapter F5) and settle it. Its distance is now final.
  3. For each edge out of it, see whether going through it gives a neighbour a shorter distance; if so, update and push.

With a binary heap, Dijkstra runs in O((V + E) log V). Its one hard rule: no negative weights. Settling the closest vertex assumes no later path can get cheaper, and a negative edge breaks that. For graphs with negative weights, the Bellman–Ford algorithm (O(V·E)) works and also detects negative cycles. For unweighted graphs, plain BFS is simpler and faster.

🟣 Coming from C#/.NET

The .NET base class library has no general graph type; teams roll their own adjacency lists or use a NuGet package. Rust is similar: the standard library gives you the building blocks (Vec, VecDeque, BinaryHeap, HashMap), and the widely used petgraph crate (version 0.8.3 on crates.io as of this writing, with over half a billion downloads) provides graph types plus toposort, dijkstra, strongly connected components and more. Lab step 5 uses it. Write the algorithm yourself once to understand it, then use the library in production.

Deep dive: why recursion is the wrong tool for DFS on user-supplied graphs

Textbooks write DFS recursively. It's elegant, and every call frame remembers where it was. But each recursion level costs a stack frame (chapter F1), and the depth equals the longest path explored. A workflow or rule graph uploaded by a customer can be a chain of 100,000 steps. Recursive DFS on that is a stack overflow: a crash triggered by input, which is a denial-of-service vector.

The fix is mechanical. Replace the call stack with an explicit Vec used as a stack, as Lab step 1's dfs and Exercise 1's find_cycle do. The memory moves to the heap, where the limit is gigabytes, not megabytes, and the depth is bounded by your data size rather than by the thread's stack. For algorithms that need "post-order" (do something after all children finish, as the colour-based cycle check does), store (vertex, next-neighbour-index) pairs on the stack so you can resume each vertex where you left off.

Also validate graph size at the API boundary: cap the number of steps per workflow and rules per set. Linear-time algorithms are cheap, but unbounded input never is.

Step 1 — BFS and DFS

use std::collections::VecDeque;

/// Undirected graph as an adjacency list: adj[v] = neighbours of v (sorted).
fn build(n: usize, edges: &[(usize, usize)]) -> Vec<Vec<usize>> {
    let mut adj = vec![Vec::new(); n];
    for &(a, b) in edges {
        adj[a].push(b);
        adj[b].push(a);
    }
    for list in &mut adj {
        list.sort_unstable();
    }
    adj
}

/// Breadth-first search: visit in rings of increasing distance. Returns (order, distances).
fn bfs(adj: &[Vec<usize>], start: usize) -> (Vec<usize>, Vec<Option<usize>>) {
    let mut dist = vec![None; adj.len()];
    let mut order = Vec::new();
    let mut queue = VecDeque::new();
    dist[start] = Some(0);
    queue.push_back(start);
    while let Some(v) = queue.pop_front() {
        order.push(v);
        for &w in &adj[v] {
            if dist[w].is_none() {
                dist[w] = Some(dist[v].unwrap() + 1);
                queue.push_back(w);
            }
        }
    }
    (order, dist)
}

/// Depth-first search with an explicit stack (no recursion, so no stack-overflow risk).
fn dfs(adj: &[Vec<usize>], start: usize) -> Vec<usize> {
    let mut seen = vec![false; adj.len()];
    let mut order = Vec::new();
    let mut stack = vec![start];
    while let Some(v) = stack.pop() {
        if seen[v] {
            continue;
        }
        seen[v] = true;
        order.push(v);
        for &w in adj[v].iter().rev() {
            if !seen[w] {
                stack.push(w); // pushed in reverse so the smallest neighbour is explored first
            }
        }
    }
    order
}

fn main() {
    let names = ["A", "B", "C", "D", "E", "F", "G", "H"];
    // A-B, A-C, B-D, B-E, C-F, E-G, F-G, G-H
    let adj = build(8, &[(0, 1), (0, 2), (1, 3), (1, 4), (2, 5), (4, 6), (5, 6), (6, 7)]);
    let (order, dist) = bfs(&adj, 0);
    let show = |v: &[usize]| v.iter().map(|&i| names[i]).collect::<Vec<_>>().join(" ");
    println!("BFS from A: {}", show(&order));
    let d: Vec<String> = (0..8).map(|i| format!("{}={}", names[i], dist[i].unwrap())).collect();
    println!("hops from A: {}", d.join(" "));
    println!("DFS from A: {}", show(&dfs(&adj, 0)));
}
BFS from A: A B C D E F G H
hops from A: A=0 B=1 C=1 D=2 E=2 F=2 G=3 H=4
DFS from A: A B D E G F C H

The two functions differ in essentially one line: VecDeque::pop_front (queue) vs Vec::pop (stack). BFS marks a vertex when it's discovered, so it's never queued twice. This DFS marks on pop and skips repeats, which reproduces the classic recursive visiting order.

Step 2 — dependency layers and cycle detection (Kahn)

use std::collections::{HashMap, VecDeque};

/// A directed graph of named steps; an edge a -> b means "a must finish before b".
struct Deps {
    names: Vec<String>,
    index: HashMap<String, usize>,
    out: Vec<Vec<usize>>,
}

impl Deps {
    fn new() -> Deps {
        Deps { names: Vec::new(), index: HashMap::new(), out: Vec::new() }
    }

    /// Map a name to a node index, creating the node on first use.
    fn node(&mut self, name: &str) -> usize {
        if let Some(&i) = self.index.get(name) {
            return i;
        }
        let i = self.names.len();
        self.names.push(name.to_string());
        self.index.insert(name.to_string(), i);
        self.out.push(Vec::new());
        i
    }

    /// `step` needs `prerequisite` to finish first.
    fn needs(&mut self, step: &str, prerequisite: &str) {
        let (s, p) = (self.node(step), self.node(prerequisite));
        self.out[p].push(s);
    }

    /// Kahn's algorithm, grouped into layers: every step in a layer can run in parallel.
    /// Returns Err(stuck steps) if there is a cycle.
    fn layers(&self) -> Result<Vec<Vec<&str>>, Vec<&str>> {
        let n = self.names.len();
        let mut indegree = vec![0; n];
        for targets in &self.out {
            for &t in targets {
                indegree[t] += 1;
            }
        }
        let mut ready: VecDeque<usize> = (0..n).filter(|&v| indegree[v] == 0).collect();
        let mut layers = Vec::new();
        let mut done = 0;
        while !ready.is_empty() {
            let mut layer: Vec<usize> = ready.drain(..).collect();
            layer.sort_unstable_by(|a, b| self.names[*a].cmp(&self.names[*b])); // deterministic output
            for &v in &layer {
                done += 1;
                for &w in &self.out[v] {
                    indegree[w] -= 1;
                    if indegree[w] == 0 {
                        ready.push_back(w);
                    }
                }
            }
            layers.push(layer.iter().map(|&v| self.names[v].as_str()).collect());
        }
        if done == n {
            Ok(layers)
        } else {
            Err((0..n).filter(|&v| indegree[v] > 0).map(|v| self.names[v].as_str()).collect())
        }
    }
}

fn main() {
    let mut g = Deps::new();
    g.needs("credit_score", "load_customer");
    g.needs("order_total", "load_orders");
    g.needs("risk_rule", "credit_score");
    g.needs("risk_rule", "order_total");
    g.needs("discount_rule", "order_total");
    g.needs("decision", "risk_rule");
    g.needs("decision", "discount_rule");

    match g.layers() {
        Ok(layers) => {
            for (i, layer) in layers.iter().enumerate() {
                println!("layer {i}: {}", layer.join(", "));
            }
        }
        Err(stuck) => println!("cycle! stuck: {stuck:?}"),
    }

    println!("-- after adding: credit_score needs decision --");
    g.needs("credit_score", "decision");
    match g.layers() {
        Ok(layers) => println!("{layers:?}"),
        Err(stuck) => println!("cycle detected; these steps can never become ready: {}", stuck.join(", ")),
    }
}
layer 0: load_customer, load_orders
layer 1: credit_score, order_total
layer 2: discount_rule, risk_rule
layer 3: decision
-- after adding: credit_score needs decision --

Result is Rust's "success or error" type (chapter 2.6): Ok(layers) or Err(stuck), and match handles both. Notice the deliberate sort inside each layer. Iteration order must be deterministic for output, tests and replay, the lesson from chapter F4.

Step 3 — Dijkstra

use std::cmp::Reverse;
use std::collections::BinaryHeap;

/// Shortest distances from `start` in a graph with non-negative edge weights.
/// adj[v] = list of (neighbour, weight). Returns (distance, previous node) per node.
fn dijkstra(adj: &[Vec<(usize, u64)>], start: usize) -> (Vec<u64>, Vec<Option<usize>>) {
    let mut dist = vec![u64::MAX; adj.len()];
    let mut prev = vec![None; adj.len()];
    let mut heap = BinaryHeap::new(); // min-heap via Reverse (chapter F5)
    dist[start] = 0;
    heap.push(Reverse((0, start)));
    while let Some(Reverse((d, v))) = heap.pop() {
        if d > dist[v] {
            continue; // a stale entry: we already found a shorter way to v
        }
        for &(w, weight) in &adj[v] {
            let nd = d + weight;
            if nd < dist[w] {
                dist[w] = nd;
                prev[w] = Some(v);
                heap.push(Reverse((nd, w)));
            }
        }
    }
    (dist, prev)
}

fn main() {
    // Services and network latency in ms between them (directed calls).
    let names = ["gateway", "auth", "rules", "workflow", "db"];
    let mut adj = vec![Vec::new(); names.len()];
    let mut call = |a: usize, b: usize, ms: u64| adj[a].push((b, ms));
    call(0, 1, 4);  // gateway -> auth
    call(0, 2, 15); // gateway -> rules (slow link)
    call(1, 2, 3);  // auth -> rules
    call(1, 3, 10); // auth -> workflow
    call(2, 3, 2);  // rules -> workflow
    call(3, 4, 5);  // workflow -> db
    call(2, 4, 12); // rules -> db

    let (dist, prev) = dijkstra(&adj, 0);
    for (i, name) in names.iter().enumerate() {
        // Walk the `prev` links backwards to recover the path.
        let mut path = vec![i];
        while let Some(p) = prev[*path.last().unwrap()] {
            path.push(p);
        }
        path.reverse();
        let route: Vec<&str> = path.iter().map(|&v| names[v]).collect();
        println!("{name:>8}: {:>2} ms via {}", dist[i], route.join(" -> "));
    }
}
 gateway:  0 ms via gateway
    auth:  4 ms via gateway -> auth
   rules:  7 ms via gateway -> auth -> rules
workflow:  9 ms via gateway -> auth -> rules -> workflow
      db: 14 ms via gateway -> auth -> rules -> workflow -> db

The "stale entry" check is the standard trick for heaps without a decrease-key operation: push a vertex again whenever its distance improves, and ignore outdated copies when they pop. Rust's BinaryHeap has no decrease-key operation, so this is the idiomatic form.

Step 4 — BFS at scale

use std::collections::VecDeque;
use std::time::Instant;

fn next_rand(s: &mut u64) -> u64 { *s ^= *s << 13; *s ^= *s >> 7; *s ^= *s << 17; *s }

fn main() {
    const V: usize = 1_000_000;
    const E: usize = 5_000_000;
    let mut seed = 11;
    let mut adj: Vec<Vec<u32>> = vec![Vec::new(); V];
    for _ in 0..E {
        let a = (next_rand(&mut seed) % V as u64) as usize;
        let b = (next_rand(&mut seed) % V as u64) as u32;
        adj[a].push(b); // directed edge a -> b
    }
    let list_bytes: usize = adj.iter().map(|l| l.capacity() * 4).sum::<usize>() + V * std::mem::size_of::<Vec<u32>>();
    println!("adjacency list: {:.0} MB", list_bytes as f64 / 1e6);
    println!("adjacency matrix (1 bit per cell) would need: {:.0} GB", (V as f64 * V as f64 / 8.0) / 1e9);

    let start = Instant::now();
    let mut seen = vec![false; V];
    let mut queue = VecDeque::from([0u32]);
    seen[0] = true;
    let mut reached = 0;
    while let Some(v) = queue.pop_front() {
        reached += 1;
        for &w in &adj[v as usize] {
            if !seen[w as usize] {
                seen[w as usize] = true;
                queue.push_back(w);
            }
        }
    }
    println!("BFS reached {reached} of {V} vertices in {:.1} ms", start.elapsed().as_secs_f64() * 1e3);
}

Using u32 instead of usize for vertex IDs halves the edge storage, a common trick once you know your graph has fewer than 4 billion vertices. Not every vertex is reached: with random directed edges, some vertices have no path in from vertex 0.

Exercise 1 — show the user the cycle ★★★ product skill

A rule-set editor must reject circular dependencies and show the loop. Write find_cycle(adj) -> Option<Vec<usize>> that returns one cycle as a node list with the first node repeated at the end, for example [1, 2, 3, 1]. It must not use recursion.

Show solution 
/// Find one cycle in a directed graph, returned as a list of nodes
/// (first node repeated at the end), or None if the graph is acyclic.
/// Uses DFS with three colours: 0 = unvisited, 1 = on the current path, 2 = finished.
pub fn find_cycle(adj: &[Vec<usize>]) -> Option<Vec<usize>> {
    let n = adj.len();
    let mut colour = vec![0u8; n];
    let mut parent = vec![usize::MAX; n];
    for root in 0..n {
        if colour[root] != 0 {
            continue;
        }
        // Explicit stack of (node, index of next neighbour to try): iterative DFS.
        let mut stack = vec![(root, 0usize)];
        colour[root] = 1;
        while let Some(top) = stack.last_mut() {
            let v = top.0;
            if top.1 < adj[v].len() {
                let w = adj[v][top.1];
                top.1 += 1; // next time, try the following neighbour
                if colour[w] == 0 {
                    colour[w] = 1;
                    parent[w] = v;
                    stack.push((w, 0));
                } else if colour[w] == 1 {
                    // w is on the current path: walk parents back from v to w.
                    let mut cycle = vec![w];
                    let mut x = v;
                    while x != w {
                        cycle.push(x);
                        x = parent[x];
                    }
                    cycle.push(w);
                    cycle.reverse();
                    return Some(cycle);
                }
            } else {
                colour[v] = 2; // all neighbours done
                stack.pop();
            }
        }
    }
    None
}

fn main() {
    let cyclic = vec![vec![1], vec![2], vec![3], vec![1]]; // 0 -> 1 -> 2 -> 3 -> 1
    let dag = vec![vec![1, 2], vec![3], vec![3], vec![]];
    println!("{:?}", find_cycle(&cyclic)); // Some([1, 2, 3, 1])
    println!("{:?}", find_cycle(&dag));    // None
}

The stack holds (vertex, next neighbour to try), so each vertex resumes where it left off: post-order without recursion. Meeting a grey (1) vertex means we've looped back onto our own path. Map the indices back to names in the error message: "credit_score → risk_rule → decision → credit_score".

Exercise 2 — blast radius ★★☆ consultant skill

Given which services call which (depends_on[a] = services a calls), list every service affected, directly or transitively, if service failed goes down.

Show solution 
use std::collections::VecDeque;

/// Everything that (directly or transitively) depends on `failed`.
/// `depends_on[a]` lists what a calls; we search the reversed edges from `failed`.
pub fn impacted_by(depends_on: &[Vec<usize>], failed: usize) -> Vec<usize> {
    let n = depends_on.len();
    let mut callers = vec![Vec::new(); n]; // reverse the edges once: O(V + E)
    for (a, targets) in depends_on.iter().enumerate() {
        for &b in targets {
            callers[b].push(a);
        }
    }
    let mut seen = vec![false; n];
    let mut queue = VecDeque::from([failed]);
    seen[failed] = true;
    let mut out = Vec::new();
    while let Some(v) = queue.pop_front() {
        for &c in &callers[v] {
            if !seen[c] {
                seen[c] = true;
                out.push(c);
                queue.push_back(c);
            }
        }
    }
    out.sort_unstable();
    out
}

fn main() {
    let names = ["gateway", "auth", "rules", "db", "reports"];
    // gateway -> auth -> db ; gateway -> rules -> db ; reports -> rules
    let deps = vec![vec![1, 2], vec![3], vec![3], vec![], vec![2]];
    let hit: Vec<&str> = impacted_by(&deps, 2).iter().map(|&i| names[i]).collect();
    println!("if rules fails: {hit:?}"); // ["gateway", "reports"]
}

The key move is reversing the edges: "who calls X" is a search along reversed "X calls" edges. BFS also tells you each service's distance from the failure, which is useful for ordering an incident's impact list.

Exercise 3 — isolated groups ★☆☆

Count the connected components of an undirected graph (groups of vertices reachable from each other). Example: 6 vertices with edges 0–1, 1–2, 3–4 have 3 groups: {0,1,2}, {3,4}, {5}.

Show solution 
use std::collections::VecDeque;

/// Number of connected components in an undirected graph.
pub fn components(n: usize, edges: &[(usize, usize)]) -> usize {
    let mut adj = vec![Vec::new(); n];
    for &(a, b) in edges {
        adj[a].push(b);
        adj[b].push(a);
    }
    let mut seen = vec![false; n];
    let mut count = 0;
    for start in 0..n {
        if seen[start] {
            continue;
        }
        count += 1; // a new, untouched group
        let mut queue = VecDeque::from([start]);
        seen[start] = true;
        while let Some(v) = queue.pop_front() {
            for &w in &adj[v] {
                if !seen[w] {
                    seen[w] = true;
                    queue.push_back(w);
                }
            }
        }
    }
    count
}

fn main() {
    println!("{}", components(6, &[(0, 1), (1, 2), (3, 4)])); // 3
}

Each BFS from an unseen vertex floods exactly one component. Still O(V + E) in total, because seen stops any vertex being processed twice. Practical uses: finding which tenants' data are entangled, or which workflow steps can be deployed independently.

Common misconceptions and pitfalls

⚠️ Forgetting the "seen" set

Without it, any cycle makes BFS or DFS loop forever, and even acyclic graphs with shared descendants get revisited exponentially often. Mark vertices the moment they're discovered (BFS) or entered (DFS).

⚠️ Recursive DFS on input-sized graphs

One long chain in a customer's workflow and the thread's stack overflows (deep dive). Use an explicit stack.

⚠️ Dijkstra with negative weights

It silently gives wrong answers, with no error. Use Bellman–Ford, or redesign the weights.

⚠️ An adjacency matrix for a big sparse graph

O(V²) memory: 125 GB at a million vertices, versus 51 MB for lists. Matrices are only right for small or genuinely dense graphs.

⚠️ Non-deterministic topological orders

Many orders are usually valid. If you pick among ready steps by iterating a HashMap, the order changes per run, which breaks replay and makes logs hard to compare. Sort ready steps by a stable key, as Lab step 2 does.

Real-world view: graphs in your products

🏗 Architecture view
  • Workflow definitions are validated as DAGs when saved: run Kahn, and if there's a cycle, report it with Exercise 1's path. At run time, the layers give the steps that can run in parallel, and in-degree counting tells the engine when a step's last prerequisite finished, which is what triggers it (chapter 10.3).
  • Rule dependencies: when rules derive facts that other rules consume, the engine orders evaluation topologically and rejects cycles. Some rule styles (forward chaining, Rete) do allow recursion through facts. That's a deliberate design choice you'll revisit in chapter 9.1.
  • Incremental re-evaluation: when one fact changes, only rules reachable from it in the dependency graph need re-checking: a BFS from the changed vertex. This is the idea behind Rete's efficiency, and behind spreadsheet recalculation.
  • Operations: blast-radius analysis (Exercise 2), deployment ordering (topological), and detecting dependency cycles between microservices in architecture reviews.

Summary

  • Graphs are vertices plus edges (directed or not, weighted or not). DAGs, with no cycles, model dependencies, workflows and rule evaluation order.
  • Use adjacency lists (Vec<Vec<usize>>, vertices as indices) for sparse graphs: measured 51 MB vs 125 GB for a matrix at 1M vertices.
  • BFS (queue) explores in rings and gives fewest-hop paths; DFS (stack) dives deep and underlies cycle detection. Both are O(V + E). Use explicit stacks, not recursion, for input-sized graphs.
  • Kahn's topological sort orders dependencies, groups them into parallel layers, and reveals cycles (stuck vertices). DFS colours recover the actual cycle to show the user.
  • Dijkstra plus a min-heap finds cheapest paths with non-negative weights in O((V + E) log V). Use petgraph in production once you understand the algorithms.
