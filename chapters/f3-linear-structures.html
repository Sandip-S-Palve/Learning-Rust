Linear data structures

Learning objectives

  • Distinguish an abstract data type (what operations you get) from a data structure (how it's stored)
  • Explain arrays, dynamic arrays, linked lists, stacks, queues, deques and ring buffers, and the cost of each operation
  • Predict, then measure, why contiguous structures usually beat linked ones on modern hardware
  • Pick the right Rust type ([T; N], Vec, VecDeque, LinkedList) and know its .NET counterpart
  • Use a stack, a queue and a ring buffer to solve real problems (bracket matching, task queues, sliding windows)

Why this matters

💡 Why this matters

Your workflow engine is, at its heart, a set of queues: tasks waiting for workers, events waiting to be applied. Your rule engine's expression parser needs a stack (chapter 9.2), and its time-window rules ("more than 5 failed logins in the last 10 events") need a ring buffer. Pick the wrong structure and you get the result measured in this chapter: draining a 100,000-item queue takes 750 ms instead of 0.2 ms, from changing one type.

These are also the structures Rust's ownership rules interact with most visibly. Knowing why a linked list is awkward in Rust prepares you for Module 2.

Intuition first: seats on a train vs a treasure hunt

🧭 Analogy
  • An array is a train: carriages coupled in a row, seats numbered. To reach seat 37 you compute where it is and walk straight there. To add a carriage in the middle you have to uncouple and shift everything behind it.
  • A linked list is a treasure hunt: each clue tells you where the next one is hidden. Inserting a new clue is easy if you're standing at the right spot: rewrite one note. But to reach clue 37 you must follow 36 clues, and each one might be across town.

Core explanation

Basic

Interface vs implementation

Computer science separates two ideas that you already separate in .NET as interface vs class:

  • An abstract data type (ADT) says which operations exist and how they behave. Example: a stack offers push, pop and peek, last-in-first-out.
  • A data structure says how the data is laid out in memory. Example: a dynamic array or a linked list.

One ADT can be implemented by several structures with very different costs. That's exactly the choice this chapter teaches you to make.

Arrays

An array is a fixed number of same-sized elements stored back to back. Because they're contiguous, the address of element i is pure arithmetic:

$$ \text{address}(i) = \text{base} + i \times \text{size\_of}(T) $$

So indexing is O(1) whatever the length, and scanning in order is as cache-friendly as it gets. In Rust, [u64; 4] is an array of exactly four u64s. Its length is part of its type, fixed at compile time, so it can live directly on the stack or inside a struct.

Dynamic arrays: Vec<T>

A dynamic array is an array that can grow. You met its layout in F1 (a pointer, a length and a capacity on the stack; the elements on the heap) and its amortised O(1) push in F2. Here is what happens when it fills up:

Inserting or removing anywhere except the end means shifting every later element by one: O(n − i). Removing the first element of a Vec is therefore O(n). Remember this; it's the queue pitfall measured below.

Linked lists

A linked list stores each element in its own node: the value plus a pointer to the next node, and in a doubly linked list also one to the previous node. Rust's std::collections::LinkedList is doubly linked, so each node holds a value and two 8-byte pointers, each node is a separate heap allocation.

  • Strength: once you hold a pointer to a node, inserting or removing next to it is O(1): rewire two pointers, move nothing. Joining two lists is O(1).
  • Weakness: reaching the i-th element means following i pointers, O(n). Every hop may be a cache miss. Every node carries pointer overhead and its own allocation.

Rust's own documentation is unusually blunt about it:

"NOTE: It is almost always better to use Vec or VecDeque because array-based containers are generally faster, more memory efficient, and make better use of CPU cache."
— std::collections::LinkedList documentation

Stacks (LIFO)

A stack ADT gives you push (add on top), pop (remove from top) and peek (look at the top): last in, first out. The call stack from F1 is one; so is an undo history. In Rust a Vec is the stack: push and pop work at the end, amortised O(1), and last() peeks. In .NET, Stack<T> "is implemented as an array", the same design.

Stacks are the natural tool whenever something must be closed in the reverse order it was opened: nested brackets in an expression, nested function calls, nested XML or JSON. Exercise 1 checks brackets in a rule expression with one.

Queues (FIFO) and deques

A queue ADT gives you enqueue at the back and dequeue at the front: first in, first out, like a checkout line. Task queues, message buffers and breadth-first search (chapter F6) all use one. A deque (double-ended queue, said "deck") allows push and pop at both ends.

The obvious implementation, a Vec where you push at the end and remove index 0, is a trap: every dequeue shifts everything, O(n). The right one is a ring buffer.

Ring buffers

A ring buffer (circular buffer) is an array whose ends are joined logically: it keeps the index of the head (the oldest element) and a length, and wraps indices around with the remainder operator, (head + i) % capacity. Dequeuing just advances the head, and nothing moves.

Rust's VecDeque is exactly this: "a double-ended queue implemented with a growable ring buffer". Its docs give the default queue usage as push_back to enqueue and pop_front to dequeue. .NET's Queue<T> is the same idea ("implements a generic queue as a circular array").

ℹ️ An honest note about the linked-list measurement

I tried to make std::LinkedList's nodes scattered by allocating and freeing other blocks in random order first. On this macOS allocator it made no difference: the nodes still landed close together (about 1 ms either way). So the "scattered" figure comes from a list stored in one array whose links are randomised (Lab step 2), which isolates the effect exactly. In long-running services node placement depends on the allocator and on history. The point stands either way: following pointers costs, from 8× to 50×, and a Vec is never worse.

Why linked lists are awkward in Rust

In a doubly linked list, every middle node is pointed to by two other nodes (its predecessor and its successor). Rust's ownership rule (chapter 2.2) says every value has exactly one owner. So a doubly linked list can't be built from plain owning pointers. It needs shared ownership with reference counting (Rc/Weak, chapter 2.12), or carefully reviewed unsafe code, which is what std::LinkedList uses internally behind a safe interface. That's not a flaw: the compiler is pointing out that the ownership of a linked structure is genuinely complicated. The idiomatic alternatives:

  • Use Vec or VecDeque. Usually faster anyway.
  • Store nodes in a Vec and use indices as links, as Lab step 2 does. You get linked-list flexibility, one allocation, and no ownership puzzles. You'll use this arena pattern for graphs (F6, chapter 2.12) and for the Rete network (chapter 9.4).
Deep dive: "Are lists evil?" — reading a famous benchmark critically

Bjarne Stroustrup (creator of C++) popularised a thought experiment in his FAQ: insert random integers into a sorted sequence, then remove them from random positions. Vector or list? Intuition says list, because insertion and removal are O(1). His answer is that vectors win by a wide margin. To insert into a sorted sequence you first have to find the position. On a list that's a pointer-chasing O(n) walk; on a vector it's a cache-friendly scan (or a binary search). Shifting elements with a memory copy is very fast on contiguous data. His conclusions, quoted from the FAQ: "don't store data unnecessarily, keep data compact, and access memory in a predictable manner".

A fair critique (the GitHub project random_insert) points out that the benchmark mostly measures searching, the list's weak spot, rather than insertion, its strength. Both views are right. For architecture reviews, the lesson is:

  • A linked list pays off only when you already hold a pointer to where the change happens, and you make many changes there. Examples: an LRU cache that moves an entry to the front on every hit (a hash map gives you the node directly), kernel or allocator free-lists, or splicing large lists in O(1).
  • If you must search to find the position, a contiguous structure almost always wins.
  • Always ask what a benchmark is really measuring before generalising from it, including the ones in this course.

Step 1 — Vec vs LinkedList

use std::collections::LinkedList;
use std::hint::black_box;
use std::time::Instant;

const N: u64 = 1_000_000;

/// Tiny deterministic random-number generator (xorshift), so we need no crates.
fn next_rand(state: &mut u64) -> u64 {
    *state ^= *state << 13;
    *state ^= *state >> 7;
    *state ^= *state << 17;
    *state
}

/// Average time of `f` over 10 runs, in milliseconds.
fn time_ms(f: impl Fn() -> u64) -> f64 {
    let start = Instant::now();
    for _ in 0..10 {
        black_box(f());
    }
    start.elapsed().as_secs_f64() * 1000.0 / 10.0
}

fn main() {
    // 1. A Vec: one contiguous block.
    let vec: Vec<u64> = (0..N).collect();

    // 2. A LinkedList built in one go on a quiet heap: its nodes are allocated
    //    back to back, so they happen to sit next to each other in memory.
    let fresh: LinkedList<u64> = (0..N).collect();

    // 3. A LinkedList built on a "used" heap, as in a long-running service:
    //    allocate blocks the same size as a list node (value + 2 pointers = 24 bytes),
    //    free them in random order, then build the list. The allocator hands the
    //    freed slots back in that scrambled order, so consecutive nodes are far apart.
    let mut blocks: Vec<Box<[u64; 3]>> = (0..N).map(|i| Box::new([i; 3])).collect();
    let mut seed = 42;
    for i in (1..blocks.len()).rev() {
        let j = (next_rand(&mut seed) % (i as u64 + 1)) as usize;
        blocks.swap(i, j); // shuffle (Fisher–Yates)
    }
    drop(blocks); // frees every block, in shuffled order
    let aged: LinkedList<u64> = (0..N).collect();

    println!("sum over 1,000,000 u64 values (average of 10 runs):");
    println!("  Vec:                 {:>6.2} ms", time_ms(|| vec.iter().sum()));
    println!("  LinkedList (fresh):  {:>6.2} ms", time_ms(|| fresh.iter().sum()));
    println!("  LinkedList (aged):   {:>6.2} ms", time_ms(|| aged.iter().sum()));
}
sum over 1,000,000 u64 values (average of 10 runs):
  Vec:                   0.11 ms
  LinkedList (fresh):    0.84 ms
  LinkedList (aged):     0.86 ms

The comment in step 3 states the intent. As the note above explains, on this machine the allocator didn't actually scatter the nodes, which is why "aged" matches "fresh". Try it on Linux or Windows: allocator behaviour differs by platform, and so may your result.

Step 2 — isolate the cost of scattering

use std::hint::black_box;
use std::time::Instant;

const N: usize = 1_000_000;

/// Tiny deterministic random-number generator (xorshift).
fn next_rand(state: &mut u64) -> u64 {
    *state ^= *state << 13;
    *state ^= *state >> 7;
    *state ^= *state << 17;
    *state
}

/// A singly linked list stored in one Vec: node i holds a value and the
/// index of the next node (usize::MAX marks the end).
struct Node {
    value: u64,
    next: usize,
}

/// Follow the links from `head`, adding up values.
fn sum_list(nodes: &[Node], head: usize) -> u64 {
    let (mut total, mut i) = (0, head);
    while i != usize::MAX {
        total += nodes[i].value;
        i = nodes[i].next;
    }
    total
}

/// Build a list whose visiting order is `order` (a permutation of 0..N).
fn build(order: &[usize]) -> Vec<Node> {
    let mut nodes: Vec<Node> = (0..N).map(|i| Node { value: i as u64, next: usize::MAX }).collect();
    for w in order.windows(2) {
        nodes[w[0]].next = w[1];
    }
    nodes
}

fn time_ms(nodes: &[Node], head: usize) -> f64 {
    let start = Instant::now();
    for _ in 0..10 {
        black_box(sum_list(black_box(nodes), head));
    }
    start.elapsed().as_secs_f64() * 1000.0 / 10.0
}

fn main() {
    // Links follow memory order: node 0 -> 1 -> 2 ... (like a lucky, fresh list)
    let in_order: Vec<usize> = (0..N).collect();
    // Links jump around memory at random (like a list on a fragmented heap)
    let mut shuffled = in_order.clone();
    let mut seed = 42;
    for i in (1..N).rev() {
        let j = (next_rand(&mut seed) % (i as u64 + 1)) as usize;
        shuffled.swap(i, j);
    }
    let a = build(&in_order);
    let b = build(&shuffled);
    println!("following 1,000,000 links (average of 10 runs):");
    println!("  neighbours in memory:  {:>7.2} ms", time_ms(&a, in_order[0]));
    println!("  scattered in memory:   {:>7.2} ms", time_ms(&b, shuffled[0]));
}
following 1,000,000 links (average of 10 runs):
  neighbours in memory:     0.51 ms
  scattered in memory:     26.72 ms

Same nodes, same number of steps, same O(n): about 50× apart purely because of where the next node lives. That's chapter F1's latency ladder in action. This index-linked list is also your first arena.

Step 3 — the queue trap

use std::collections::VecDeque;
use std::hint::black_box;
use std::time::Instant;

const N: usize = 100_000;

fn main() {
    // A queue: add at the back, take from the front, N times.

    // Vec used as a queue: remove(0) shifts every remaining element left.
    let start = Instant::now();
    let mut v: Vec<usize> = (0..N).collect();
    let mut total = 0;
    while !v.is_empty() {
        total += v.remove(0);
    }
    let t_vec = start.elapsed();
    black_box(total);

    // VecDeque (a ring buffer): pop_front just moves the head index.
    let start = Instant::now();
    let mut q: VecDeque<usize> = (0..N).collect();
    let mut total = 0;
    while let Some(x) = q.pop_front() {
        total += x;
    }
    let t_deque = start.elapsed();
    black_box(total);

    println!("draining a {N}-element queue from the front:");
    println!("  Vec::remove(0):         {:>9.3} ms", t_vec.as_secs_f64() * 1000.0);
    println!("  VecDeque::pop_front():  {:>9.3} ms", t_deque.as_secs_f64() * 1000.0);
}
draining a 100000-element queue from the front:
  Vec::remove(0):           753.273 ms
  VecDeque::pop_front():      0.174 ms

Draining with remove(0) shifts n−1, then n−2, … elements: about n²/2 = 5 billion element moves, O(n²) in total. The ring buffer does O(1) per dequeue, about 4,000× faster here. while let Some(x) = q.pop_front() means "keep going while there's something to take" (chapter 2.5).

Exercise 1 — balanced brackets in a rule expression ★☆☆

Write balanced(expr: &str) -> bool, which checks that (), [] and {} are balanced and correctly nested, ignoring other characters. "(price > 10) && [a, {b}]" is balanced; "(a]", "((a)" and "a)" are not.

Show solution 
/// Are all brackets in `expr` balanced and correctly nested?
pub fn balanced(expr: &str) -> bool {
    let mut stack: Vec<char> = Vec::new();
    for c in expr.chars() {
        match c {
            '(' | '[' | '{' => stack.push(c),
            ')' | ']' | '}' => {
                let expected = match c {
                    ')' => '(',
                    ']' => '[',
                    _ => '{',
                };
                if stack.pop() != Some(expected) {
                    return false; // wrong kind of opener, or nothing open at all
                }
            }
            _ => {} // ignore everything else
        }
    }
    stack.is_empty() // anything still open means unbalanced
}

fn main() {
    for e in ["(price > 10) && [a, {b}]", "", "(a]", "((a)", "a)"] {
        println!("{e:?} balanced: {}", balanced(e));
    }
}

Each opener is pushed. Each closer must match the most recent unclosed opener, which is exactly LIFO. O(n) time, O(depth) space. Chapter 9.2's parser uses the same idea at a larger scale.

Exercise 2 — a fixed-capacity ring buffer ★★☆

Implement a ring buffer of i64 with a fixed capacity, whose push overwrites the oldest value when full (like a "last N events" telemetry buffer), and a to_vec returning values oldest-first. After pushing 1…5 into capacity 3, to_vec() must be [3, 4, 5].

Show solution 
/// A fixed-capacity ring buffer that overwrites the oldest value when full.
pub struct Ring {
    slots: Vec<i64>, // storage, allocated once
    head: usize,     // index of the oldest value
    len: usize,      // how many slots are in use
}

impl Ring {
    pub fn new(capacity: usize) -> Ring {
        Ring { slots: vec![0; capacity], head: 0, len: 0 }
    }

    /// Add a value; if full, the oldest value is overwritten.
    pub fn push(&mut self, value: i64) {
        let cap = self.slots.len();
        let tail = (self.head + self.len) % cap; // first free slot, wrapping around
        self.slots[tail] = value;
        if self.len == cap {
            self.head = (self.head + 1) % cap; // the oldest value was overwritten
        } else {
            self.len += 1;
        }
    }

    /// The values from oldest to newest.
    pub fn to_vec(&self) -> Vec<i64> {
        let cap = self.slots.len();
        (0..self.len).map(|i| self.slots[(self.head + i) % cap]).collect()
    }
}

fn main() {
    let mut r = Ring::new(3);
    for v in 1..=5 {
        r.push(v);
    }
    println!("{:?}", r.to_vec()); // [3, 4, 5]
}

When full, the tail slot is the head slot, so writing there overwrites the oldest value, and the head moves on. One allocation for the buffer's whole life, O(1) per push. Ideal for "keep the last N" with bounded memory.

Exercise 3 — a sliding-window rule ★★☆ product skill

A rule needs "the average of the last k readings" after every new reading. Write moving_average(values: &[f64], k: usize) -> Vec<f64> in O(n) total. Recomputing the sum of k values each time would be O(n·k). For [10, 20, 30, 40] and k = 2 the answer is [10, 15, 25, 35].

Show solution 
use std::collections::VecDeque;

/// Moving average of the last `k` values, for each new value.
pub fn moving_average(values: &[f64], k: usize) -> Vec<f64> {
    let mut window: VecDeque<f64> = VecDeque::with_capacity(k);
    let mut sum = 0.0;
    let mut out = Vec::with_capacity(values.len());
    for &v in values {
        window.push_back(v);
        sum += v;
        if window.len() > k {
            sum -= window.pop_front().unwrap(); // drop the oldest: O(1)
        }
        out.push(sum / window.len() as f64);
    }
    out
}

fn main() {
    println!("{:?}", moving_average(&[10.0, 20.0, 30.0, 40.0], 2)); // [10.0, 15.0, 25.0, 35.0]
}

Keep a running sum: add the newcomer, subtract whoever falls out of the window. The deque gives O(1) at both ends. This is the core of every windowed aggregate in a rule or stream engine. .unwrap() says "I know this is present". It's safe here because we just checked the length (chapter 2.6 covers it).

Decision guide

Common misconceptions and pitfalls

⚠️ Using a Vec (or C# List<T>) as a queue

remove(0) / RemoveAt(0) is O(n). Lab step 3: about 750 ms vs 0.17 ms. Use VecDeque / Queue<T>.

⚠️ "Linked lists have O(1) insertion, so they're faster for inserts."

Only at a node you already hold. Finding the spot is O(n) pointer-chasing. See the deep dive.

⚠️ Assuming a VecDeque is one contiguous slice

It may wrap around (Figure 3). Use as_slices() to get the two parts, or make_contiguous() (which, per its docs, "does not allocate") when you need one slice, for example to sort it.

⚠️ Unbounded queues

A queue that producers can fill faster than consumers drain grows until the process runs out of memory. Production queues need a bound and a policy when full: block the producer, reject, or drop the oldest. That's called backpressure, and chapter 4.7 builds it with Tokio.

⚠️ Forgetting with_capacity

If you know roughly how many items are coming, Vec::with_capacity(n) / VecDeque::with_capacity(n) avoids every intermediate reallocation and copy (Figure 2).

Real-world view: these structures in your products

🏗 Architecture view
  • Workflow engine task dispatch: each worker pool pulls from a FIFO queue. In memory that's a VecDeque, bounded for backpressure. Across machines it's a durable queue in the database (chapter 10.5). Same ADT, very different data structure.
  • Rule engine parsing: operator-precedence parsing and bracket validation use stacks (chapter 9.2).
  • Windowed rules and metrics: "count failures in the last 100 events" or "average latency over the last minute" are ring buffers with running aggregates (Exercise 3), O(1) per event and fixed memory.
  • Audit and debugging: keep the last N decisions per tenant in a fixed ring buffer. That bounds memory however busy a tenant gets, which matters when one noisy customer shouldn't starve the others.
  • Undo/redo in a rule-authoring UI: two stacks. Undo pops from one and pushes onto the other.

Summary

  • An abstract data type (stack, queue, deque) says what operations you get; a data structure (array, dynamic array, linked list, ring buffer) says how it's stored and therefore what each operation costs.
  • Arrays and Vec give O(1) indexing and the best cache behaviour; inserting or removing at the front is O(n). Vec is Rust's list and its stack.
  • Ring buffers (VecDeque, .NET Queue<T>) give O(1) at both ends by wrapping indices. Never use Vec::remove(0) as a queue (about 750 ms vs 0.17 ms measured).
  • Linked lists give O(1) changes only at nodes you already hold, and pay for every pointer hop: 8× to 50× slower traversals measured. In Rust, prefer Vec/VecDeque or an index-linked arena.
  • Production queues must be bounded (backpressure). Ring buffers with running aggregates power windowed rules in O(1) per event.
