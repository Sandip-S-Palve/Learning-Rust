Structs, enums and pattern matching

Learning objectives

  • Define named, tuple and unit structs, add behaviour in impl blocks, and choose between &self, &mut self, self and associated functions
  • Model alternatives with enums whose variants carry data, and use Option's methods instead of hand-written matches
  • Write match with every kind of pattern (literals, ranges, or-patterns, bindings, @, guards, nested and slice patterns) and predict which arm runs
  • Read exhaustiveness errors (E0004), and use if let, while let, let-else, let chains and matches! where each fits
  • Compare Rust's structs, enums and match with C# classes, records and switch expressions, and design state machines the compiler checks

Why this matters

💡 Why this matters

Chapter F8 made the case for product types, sum types and "make illegal states unrepresentable". This chapter is the Rust you write every day to do it. Nearly every type in your two products is a struct or an enum: a rule's condition, an operator, an expression tree, a workflow step, its state, the events that move it on. Nearly every decision about them is a match.

In C# you would reach for classes, records, an inheritance hierarchy and switch expressions, and the compiler would warn if a switch missed a case, but only when it could see the whole hierarchy, and you'd still need a default that throws. In Rust, an enum's variants are closed and known, and a match that misses one doesn't compile. For a workflow engine that is the difference between "a new state was added and the compiler showed every place that must decide what to do with it" and "a new state was added and an old switch fell through to default: throw in production at 3 a.m."

Intuition first: forms and multiple-choice boxes

🧭 Analogy
  • A struct is a paper form: every box must be filled in (name, amount, currency). Leave one out and the form is rejected (error E0063).
  • An enum is a set of tick-boxes where you tick exactly one, and each choice opens its own small sub-form: "Card: number and expiry", "Invoice: due date", "Cash: nothing more".
  • match is the clerk's checklist, read from the top, stopping at the first line that fits. The rule that makes it Rust: the checklist must have a line for every possible tick-box, or the clerk refuses to start work.
  • Patterns are stencils laid over the form: "a card payment, any number, expiry before 2027". Where a stencil has a hole, the matching part of the form is copied out into a name you can use.

A C# class hierarchy is more like forms that anyone can extend with a new page later. That's flexible, but the clerk can never be sure the checklist is complete.

Core explanation

Basic

Structs: three shapes

A struct groups named values into one type (a product type, chapter F8). Rust has three shapes:

struct RetryPolicy { max_attempts: u32, backoff_ms: u64 } // named fields
struct StepId(u64);                                       // tuple struct (a newtype)
struct Approved;                                          // unit struct: no fields, 0 bytes

let p = RetryPolicy { max_attempts: 3, backoff_ms: 500 };
let id = StepId(7);
let a = Approved;
println!("{} {} {}", p.max_attempts + p.backoff_ms as u32, id.0, std::mem::size_of_val(&a));

Named-field structs are the default. Tuple structs have positional fields (.0, .1); with one field they're F8's newtype, the cheapest way to stop a StepId being passed where a RuleId is expected. Unit structs have no data and take no space (Lab step 1 prints 0); they serve as markers and as types that exist only to implement behaviour (chapter 2.9).

Every field must be given a value when you construct a struct (forgetting one is error E0063, Lab step 2). Rust has no constructors that run automatically and no "default" field values, so the conventional constructor is an ordinary function, usually called new. Two pieces of syntax save typing. Field init shorthand lets you write RetryPolicy { max_attempts, backoff_ms } when variables of those names exist. Struct update syntax, RetryPolicy { backoff_ms: 2_000, ..other }, takes the remaining fields from another value. Note that "takes" means moves: non-Copy fields are moved out of other (chapter 2.2, Lab step 2). It's a cousin of C#'s with expression, with ownership attached.

Behaviour: impl blocks, methods and associated functions

Data and behaviour are declared separately. An impl block attaches functions to a type. The Book's definition: methods "are defined within the context of a struct (or an enum or a trait object…), and their first parameter is always self". The kind of self is the ownership rule from chapters 2.2 and 2.3, applied to the receiver:

A method is called with a dot. The Book explains why the call site never needs &: "When you call a method with object.something(), Rust automatically adds in &, &mut, or * so that object matches the signature of the method." So step.record_attempt() and Step::record_attempt(&mut step) are the same call. An associated function has no self, like C#'s static methods, and is called with ::. "These are often called new, but new isn't a special name and isn't built into the language." Self (capital S) inside an impl is an alias for the type being implemented.

Trying to change a field through &self is error E0594, and the compiler suggests &mut self (Lab step 2). That's the C# rule "a readonly method can't modify state" enforced on every method, because the receiver states the intent.

Enums: alternatives that carry data

Each variant of a Rust enum can carry its own data, in any of the three struct shapes:

enum Payment {
    Pending,                                  // unit-like
    Authorized(u32),                          // tuple-like
    Captured { amount: u32, refunded: bool }, // struct-like
    Failed(String),
}

let p = Payment::Captured { amount: 9_900, refunded: false };
if let Payment::Captured { amount, .. } = p {
    println!("captured {amount}");
}

That's F8's sum type in code: a Payment is exactly one of these, and the data that only makes sense for Captured can't exist on a Pending payment. In memory, an enum is a tag saying which variant it is, plus room for the largest variant's data (F8 measured this, including the niche optimisation that makes Option<&T> pointer-sized). Enums get impl blocks and derive exactly like structs (Lab step 3).

match and patterns

match compares a value against a list of patterns. The Book: "it compares the resultant value against the pattern of each arm, in order. If a pattern matches the value, the code associated with that pattern is executed." Two properties make it more than C#'s switch. It's an expression (chapter F8), so each arm produces a value and all arms must produce the same type. And it's exhaustive: "Matches in Rust are exhaustive: We must exhaust every last possibility in order for the code to be valid."

The pattern language is the same everywhere patterns appear (match, let, if let, function parameters, for loops). Lab step 4 runs every form:

A match guard adds a condition: Payment::Authorized(n) if n > 1000 => …. The arm applies only if the pattern matches and the guard is true; otherwise matching continues with the next arm. The compiler can't reason about arbitrary conditions, so guards don't count towards exhaustiveness, and you still need an arm without the guard. Order matters: the first arm that fits wins, so specific arms go before general ones. Put a _ first and every later arm is dead, which the compiler reports as an unreachable pattern (Lab step 2, w8).

if let, while let, let-else, let chains and matches!

Writing a full match when you care about one case is noisy, so Rust has shorter forms. They all rest on one distinction. A refutable pattern can fail to match (Some(x) fails on None); an irrefutable one can't ((a, b) on a pair). A plain let needs an irrefutable pattern (otherwise error E0005, which suggests let-else).

  • if let PAT = expr { … } else { … }: run code when one pattern matches.
  • while let PAT = expr { … }: loop while it matches, as in while let Some(job) = queue.pop().
  • let-else: let Some(x) = expr else { return …; }; binds x for the rest of the function if the pattern matches. If it doesn't, the else block must leave (return, break, continue or panic), which the compiler checks (Lab step 2, e5). It's the "guard clause" style: handle the failure first, then carry on with the happy path at the same indentation.
  • Let chains (Rust 1.88, edition 2024): "This feature allows &&-chaining let statements inside if and while conditions, even intermingling with boolean expressions." They replace nested if lets (Lab step 4, section 7). They are "only available in the Rust 2024 edition, as this feature depends on the if let temporary scope change for more consistent drop order."
  • matches!(value, PAT): a pattern test as a bool, as in .filter(|p| matches!(p, Payment::Captured { .. })).
🟣 Coming from C#/.NET: records, hierarchies and switch expressions
  • Struct vs class vs record. A Rust struct is a value: no inheritance, no hidden reference, no null, and the same type whether it lives on the stack or inside a Box. #[derive(Debug, Clone, PartialEq, Hash)] gives what a C# record generates; struct update syntax is with, but it moves rather than copies.
  • Enums vs C# enums. A C# enum is a named integer: any integer can be cast to it, and it carries no data. A Rust enum is closed (no invalid values) and its variants carry data. The C# idiom for the same thing is an abstract record plus subclasses, or the C# 15 union types in preview (chapter F8).
  • Exhaustiveness: warning vs error. Lab step 5 shows C# compiling a switch that forgot Failed, with warning CS8509, and the program throwing SwitchExpressionException when a Failed arrived. The warning couldn't even name the missing case ("the pattern '_' is not covered"), because a class hierarchy is open: anyone can add a subclass. In Rust it's error E0004, naming the exact missing pattern.
  • Pattern syntax is close. C# property patterns { Amount: > 10_000 }, relational patterns, list patterns [var first, .., var last] and when guards all have Rust equivalents (struct patterns, ranges, slice patterns, if guards). The concepts transfer directly; Rust adds exhaustiveness and binding by reference.

Exhaustiveness in practice

Try the compiler's check yourself. The explorer below is a match on a four-variant Payment with nine candidate arms. Untick arms to see exactly what rustc 1.99 says:

Three things the explorer shows that are worth knowing:

  • rustc reports missing variants first. If some variant appears in no arm at all, the error lists only those. Keep just Pending, Authorized(0) and Failed: rustc reports only Captured { .. }, although authorized amounts above 0 are unhandled too. Tick Captured { .. } and a second error appears for Authorized(1_u32..=u32::MAX) (the "Authorized(0) only" preset). Fixing one E0004 can reveal another.
  • Guards never help. With only the guarded arm for Authorized, the match isn't exhaustive. Integer literals cover just themselves, so Authorized(0) leaves 1..=u32::MAX to be handled, and rustc names that range.
  • _ silences the check, for the future too. Tick _ and everything compiles. That's convenient today, but if someone adds a Refunded variant next year, this match will quietly send it to the _ arm. For enums you own, especially states and events, list the variants explicitly so new ones become compile errors. Exercise 2 shows this.

For enums in a library that may gain variants, the author can mark them #[non_exhaustive]. Code in other crates must then include a _ arm, so adding a variant isn't a breaking change (chapter 3.5).

State machines: match on (state, event)

The most valuable use of exhaustiveness in your products is a state machine written as one match over a (state, event) tuple. Every combination is either a transition or an explicit rejection, and the compiler proves nothing is forgotten. Lab step 6 runs a workflow step's lifecycle, with retries, timers and final states, written this way. Guards express conditions (if attempt >= MAX_ATTEMPTS), @ bindings keep the whole state when an arm only needs to pass it through (s @ State::Waiting { .. }), and or-patterns group final states (State::Completed | State::Failed { .. }). Taking state by value and returning the new state means the old one can't be reused by accident (chapter 2.2). Chapter 10.3 builds the workflow engine's step model from this shape.

Recursive enums need Box

A rule expression tree is naturally an enum whose variants contain more expressions: And(Expr, Expr). But an enum's size is the size of its largest variant, and a variant containing itself would be infinitely large:

Deep dive: binding modes — what match &value does to your bindings

When you match a reference against a pattern that isn't a reference pattern, Rust automatically dereferences and switches bindings to borrow (default binding modes, often called "match ergonomics"). In Lab step 4, section 3, match &order { Order { country, .. } … } binds country as a &String, and the program prints that type. So matching through a reference never moves anything out. Inside a by-value let, write ref to borrow a field instead of moving it (section 2: let Order { id, ref country, .. } = order; keeps order usable).

Rust 2024 tightened the rules where they were surprising. The edition guide: "When the default binding mode is not move, writing mut, ref, or ref mut on a binding is an error", and "reference patterns can only match against references in the scrutinee when the default binding mode is move". Deep dive: what a match compiles to

A match on an enum is a test of its tag, and the compiler picks the cheapest machine code: a jump table, a chain of compares, or, for small arms, no branches at all. Here is a six-way operator match compiled with -O for the lab Mac (arm64):

#[derive(Clone, Copy)]
pub enum Op { Gt, Ge, Lt, Le, Eq, Ne }
#[unsafe(no_mangle)]
pub fn eval_enum(op: Op, lhs: i64, rhs: i64) -> bool {
    match op { Op::Gt => lhs > rhs, Op::Ge => lhs >= rhs, Op::Lt => lhs < rhs, Op::Le => lhs <= rhs, Op::Eq => lhs == rhs, Op::Ne => lhs != rhs }
}

No jumps: it computes all six comparisons (cset) and selects the right one by the tag (csel), which is cheaper than an unpredictable branch on modern CPUs. A match on strings compiles to length checks and byte comparisons, which is why Lab step 7 measures matching on a parsed enum as 1.6× faster than matching on the operator's text. The bigger benefit is that an invalid operator is rejected once, at parse time, instead of on every evaluation.

Step 1 — structs, methods and derive

use std::mem::size_of;

// A named-field struct; derive generates Debug, Clone, PartialEq and Default for it.
#[derive(Debug, Clone, PartialEq, Default)]
struct RetryPolicy {
    max_attempts: u32,
    backoff_ms: u64,
}

// A tuple struct: fields by position. A one-field tuple struct is a newtype (chapter F8).
#[derive(Debug, Clone, Copy, PartialEq)]
struct StepId(u64);

// A unit struct: no fields, zero bytes. Useful as a marker.
#[derive(Debug)]
struct Approved;

#[derive(Debug, Clone)]
struct Step {
    id: StepId,
    name: String,
    retry: RetryPolicy,
    attempts: u32,
}

impl Step {
    // An associated function (no self): the conventional constructor.
    fn new(id: u64, name: &str) -> Self {
        Step { id: StepId(id), name: name.to_string(), retry: RetryPolicy::default(), attempts: 0 }
    }

    // &self: reads the step.
    fn can_retry(&self) -> bool {
        self.attempts < self.retry.max_attempts
    }

    // &mut self: changes it in place.
    fn record_attempt(&mut self) {
        self.attempts += 1;
    }

    // self: consumes the step and returns a modified one (builder style).
    fn with_retries(mut self, max_attempts: u32, backoff_ms: u64) -> Self {
        self.retry = RetryPolicy { max_attempts, backoff_ms }; // field init shorthand
        self
    }

    // self: consumes the step and gives back one of its parts.
    fn into_name(self) -> String {
        self.name
    }
}

fn main() {
    // 1. Constructing, and the three kinds of struct.
    let mut charge = Step::new(7, "charge-card").with_retries(3, 500);
    let id = charge.id;
    println!("1. {:?} id.0 = {}, {:?}, size_of::<Approved>() = {}", id, id.0, Approved, size_of::<Approved>());

    // 2. Methods: `charge.record_attempt()` is sugar for `Step::record_attempt(&mut charge)`.
    while charge.can_retry() {
        charge.record_attempt();
    }
    Step::record_attempt(&mut charge); // the same call, written out
    println!("2. attempts = {}, can_retry = {}", charge.attempts, charge.can_retry());

    // 3. Struct update syntax: take the rest of the fields from another value.
    let gentle = RetryPolicy { backoff_ms: 2_000, ..RetryPolicy::default() };
    let notify = Step { id: StepId(8), name: String::from("notify"), ..charge.clone() };
    println!("3. {gentle:?}; notify.retry == charge.retry: {}", notify.retry == charge.retry);

    // 4. Derived Debug, single-line and pretty.
    println!("4. {notify:?}");
    println!("{notify:#?}");

    // 5. A consuming method: `charge` can't be used afterwards (E0382 if you try).
    let name = charge.into_name();
    println!("5. took the name out: {name:?}");
}

Step 6 — a rule expression tree and a workflow state machine

use std::collections::HashMap;

// ---------- Part A: a rule expression tree ----------
#[derive(Debug, Clone, Copy)]
enum Op { Gt, Ge, Eq, Ne }

#[derive(Debug)]
enum Expr {
    Num(i64),
    Field(String),
    Cmp(Box<Expr>, Op, Box<Expr>), // Box: the sub-expressions live on the heap
    And(Box<Expr>, Box<Expr>),
    Or(Box<Expr>, Box<Expr>),
    Not(Box<Expr>),
}

#[derive(Debug, PartialEq)]
enum Value { Int(i64), Bool(bool) }

fn eval(e: &Expr, facts: &HashMap<&str, i64>) -> Result<Value, String> {
    match e {
        Expr::Num(n) => Ok(Value::Int(*n)),
        Expr::Field(name) => match facts.get(name.as_str()) {
            Some(v) => Ok(Value::Int(*v)),
            None => Err(format!("unknown field {name:?}")),
        },
        Expr::Cmp(l, op, r) => match (eval(l, facts), eval(r, facts)) {
            (Ok(Value::Int(a)), Ok(Value::Int(b))) => Ok(Value::Bool(match op {
                Op::Gt => a > b,
                Op::Ge => a >= b,
                Op::Eq => a == b,
                Op::Ne => a != b,
            })),
            (Err(e), _) | (_, Err(e)) => Err(e),
            _ => Err(String::from("comparison needs two numbers")),
        },
        Expr::And(l, r) => match eval(l, facts) {
            Ok(Value::Bool(false)) => Ok(Value::Bool(false)), // short-circuit
            Ok(Value::Bool(true)) => eval(r, facts),
            Ok(Value::Int(_)) => Err(String::from("AND needs booleans")),
            Err(e) => Err(e),
        },
        Expr::Or(l, r) => match eval(l, facts) {
            Ok(Value::Bool(true)) => Ok(Value::Bool(true)),
            Ok(Value::Bool(false)) => eval(r, facts),
            Ok(Value::Int(_)) => Err(String::from("OR needs booleans")),
            Err(e) => Err(e),
        },
        Expr::Not(inner) => match eval(inner, facts) {
            Ok(Value::Bool(b)) => Ok(Value::Bool(!b)),
            Ok(Value::Int(_)) => Err(String::from("NOT needs a boolean")),
            Err(e) => Err(e),
        },
    }
}

fn cmp(field: &str, op: Op, n: i64) -> Expr {
    Expr::Cmp(Box::new(Expr::Field(field.to_string())), op, Box::new(Expr::Num(n)))
}

// ---------- Part B: a workflow step's state machine ----------
#[derive(Debug, Clone, PartialEq)]
enum State {
    Pending,
    Running { attempt: u32 },
    Waiting { attempt: u32, until: u64 },
    Completed,
    Failed { reason: String },
}

#[derive(Debug)]
enum Event { Start, Succeeded, Errored(String), TimerFired(u64) }

const MAX_ATTEMPTS: u32 = 3;

// Match on the (state, event) pair: every combination is handled, or the code doesn't compile.
fn transition(state: State, event: Event) -> Result<State, String> {
    match (state, event) {
        (State::Pending, Event::Start) => Ok(State::Running { attempt: 1 }),
        (State::Running { .. }, Event::Succeeded) => Ok(State::Completed),
        (State::Running { attempt }, Event::Errored(reason)) if attempt >= MAX_ATTEMPTS => {
            Ok(State::Failed { reason: format!("{reason} (after {attempt} attempts)") })
        }
        (State::Running { attempt }, Event::Errored(_)) => {
            Ok(State::Waiting { attempt, until: u64::from(attempt) * 1_000 }) // linear backoff
        }
        (State::Waiting { attempt, until }, Event::TimerFired(now)) if now >= until => {
            Ok(State::Running { attempt: attempt + 1 })
        }
        (s @ State::Waiting { .. }, Event::TimerFired(_)) => Ok(s), // too early: stay
        (s @ (State::Completed | State::Failed { .. }), e) => {
            Err(format!("{s:?} is final; ignored {e:?}"))
        }
        (s, e) => Err(format!("illegal: {e:?} in {s:?}")),
    }
}

fn run(events: Vec<Event>) {
    let mut s = State::Pending;
    for ev in events {
        let label = format!("{ev:?}");
        match transition(s.clone(), ev) {
            Ok(next) => {
                println!("B. {label:<26} -> {next:?}");
                s = next;
            }
            Err(msg) => println!("B. {label:<26} -> rejected: {msg}"),
        }
    }
    println!("   ---");
}

Step 7 — operators as text vs as an enum

use std::hint::black_box;
use std::mem::size_of;
use std::time::Instant;

// Version A: the operator kept as text and compared on every evaluation.
struct TextCond {
    op: String,
    rhs: i64,
}

fn eval_text(c: &TextCond, lhs: i64) -> bool {
    match c.op.as_str() {
        ">" => lhs > c.rhs,
        ">=" => lhs >= c.rhs,
        "<" => lhs < c.rhs,
        "<=" => lhs <= c.rhs,
        "==" => lhs == c.rhs,
        "!=" => lhs != c.rhs,
        other => panic!("unknown operator {other}"), // only discovered while evaluating
    }
}

// Version B: the operator parsed once into an enum; invalid text is rejected at parse time.
#[derive(Clone, Copy)]
enum Op { Gt, Ge, Lt, Le, Eq, Ne }

struct EnumCond {
    op: Op,
    rhs: i64,
}

fn parse_op(s: &str) -> Option<Op> {
    Some(match s {
        ">" => Op::Gt,
        ">=" => Op::Ge,
        "<" => Op::Lt,
        "<=" => Op::Le,
        "==" => Op::Eq,
        "!=" => Op::Ne,
        _ => return None,
    })
}

fn eval_enum(c: &EnumCond, lhs: i64) -> bool {
    match c.op {
        Op::Gt => lhs > c.rhs,
        Op::Ge => lhs >= c.rhs,
        Op::Lt => lhs < c.rhs,
        Op::Le => lhs <= c.rhs,
        Op::Eq => lhs == c.rhs,
        Op::Ne => lhs != c.rhs,
    }
}

fn best_of_5(mut f: impl FnMut() -> usize) -> (f64, usize) {
    let mut best = f64::INFINITY;
    let mut hits = 0;
    for _ in 0..5 {
        let t = Instant::now();
        hits = black_box(f());
        best = best.min(t.elapsed().as_secs_f64() * 1e3);
    }
    (best, hits)
}

    let text: Vec<TextCond> = (0..1_000)
        .map(|i| TextCond { op: ops[i % 6].to_string(), rhs: (i as i64 * 37) % 1_000 })
        .collect();
    let parsed: Vec<EnumCond> = text
        .iter()
        .map(|c| EnumCond { op: parse_op(&c.op).expect("valid operator"), rhs: c.rhs })
        .collect();
    let facts: Vec<i64> = (0..10_000).map(|i| (i * 7919) % 1_000).collect();

#[derive(Debug, Clone, Copy, PartialEq)]
struct Money {
    cents: i64,
    currency: Currency,
}

impl Money {
    fn new(cents: i64, currency: Currency) -> Self {
        Money { cents, currency }
    }

    // Adding different currencies isn't an error you can ignore: the type says "maybe".
    fn add(self, other: Money) -> Option<Money> {
        if self.currency == other.currency {
            Some(Money { cents: self.cents + other.cents, ..self })
        } else {
            None
        }
    }

    fn is_zero(&self) -> bool {
        self.cents == 0
    }
}

fn main() {
    let a = Money::new(1_250, Currency::Eur);
    let b = Money::new(750, Currency::Eur);
    let c = Money::new(500, Currency::Usd);
    println!("{:?}", a.add(b));
    println!("{:?}", a.add(c));
    assert_eq!(a.add(b), Some(Money::new(2_000, Currency::Eur)));
    assert_eq!(a.add(c), None);
    assert!(Money::new(0, Currency::Usd).is_zero());
    println!("a is still usable (Money is Copy): {a:?}");
}

Exercise 2 — add cancellation, with the compiler's help ★★☆ product skill

Add a Cancelled { by: String } state and a Cancel(String) event to Lab step 6's state machine. A step may be cancelled while Pending or Waiting, but not while Running, and Cancelled is final. First remove the catch-all (s, e) => arm so the compiler lists every pair you haven't decided.

Show solution 
#[derive(Debug, Clone, PartialEq)]
enum State {
    Pending,
    Running { attempt: u32 },
    Waiting { attempt: u32, until: u64 },
    Completed,
    Failed { reason: String },
    Cancelled { by: String }, // new
}

#[derive(Debug)]
enum Event {
    Start,
    Succeeded,
    Errored(String),
    TimerFired(u64),
    Cancel(String), // new
}

const MAX_ATTEMPTS: u32 = 3;

// No catch-all `(s, e) =>` arm: every illegal pair is listed, so adding a State or Event
// variant makes this match fail to compile until the new cases are decided.
fn transition(state: State, event: Event) -> Result<State, String> {
    use Event::*;
    use State::*;
    match (state, event) {
        (Pending, Start) => Ok(Running { attempt: 1 }),
        (Pending | Waiting { .. }, Cancel(by)) => Ok(Cancelled { by }),
        (Running { .. }, Cancel(_)) => Err(String::from("can't cancel a running step; wait for it")),
        (Running { .. }, Succeeded) => Ok(Completed),
        (Running { attempt }, Errored(reason)) if attempt >= MAX_ATTEMPTS => {
            Ok(Failed { reason: format!("{reason} (after {attempt} attempts)") })
        }
        (Running { attempt }, Errored(_)) => Ok(Waiting { attempt, until: u64::from(attempt) * 1_000 }),
        (Waiting { attempt, until }, TimerFired(now)) if now >= until => Ok(Running { attempt: attempt + 1 }),
        (s @ Waiting { .. }, TimerFired(_)) => Ok(s),
        (s @ (Completed | Failed { .. } | Cancelled { .. }), e) => Err(format!("{s:?} is final; ignored {e:?}")),
        (s @ Pending, e @ (Succeeded | Errored(_) | TimerFired(_))) => Err(format!("illegal: {e:?} in {s:?}")),
        (s @ Running { .. }, e @ (Start | TimerFired(_))) => Err(format!("illegal: {e:?} in {s:?}")),
        (s @ Waiting { .. }, e @ (Start | Succeeded | Errored(_))) => Err(format!("illegal: {e:?} in {s:?}")),
    }
}

fn main() {
    let cancelled = transition(State::Pending, Event::Cancel(String::from("ops")));
    println!("{cancelled:?}");
    assert_eq!(cancelled, Ok(State::Cancelled { by: String::from("ops") }));

    let running = transition(State::Pending, Event::Start).unwrap();
    println!("{:?}", transition(running.clone(), Event::Cancel(String::from("ops"))));
    assert!(transition(running, Event::Cancel(String::from("ops"))).is_err());

    let waiting = State::Waiting { attempt: 1, until: 1_000 };
    assert!(matches!(transition(waiting, Event::Cancel(String::from("sla"))), Ok(State::Cancelled { .. })));
    let done = State::Cancelled { by: String::from("ops") };
    println!("{:?}", transition(done, Event::Start));
    // The original retry path still works.
    let mut s = State::Pending;
    for e in [Event::Start, Event::Errored(String::from("timeout")), Event::TimerFired(1_000), Event::Succeeded] {
        s = transition(s, e).unwrap();
    }
    assert_eq!(s, State::Completed);
    println!("retry path ends in {s:?}; ok");
}
Ok(Cancelled { by: "ops" })

retry path ends in Completed; ok

Without the catch-all, the last three arms list the illegal pairs explicitly, grouped with or-patterns. It's more typing, and that's the point. I checked what happens if someone later adds a Paused state without updating this function: error[E0004]: non-exhaustive patterns: `(State::Paused, _)` not covered. The compiler forces a decision about pausing in every combination. With the catch-all it would have compiled and silently rejected every event while paused. use State::*; inside the function shortens the arms without polluting the module.

Common misconceptions and pitfalls

⚠️ Reaching for _ in matches on your own enums

It compiles today and hides tomorrow's new variant. List variants explicitly, especially for states, events and commands; use _ for open-ended types like integers and strings.

⚠️ Arm order with guards and ranges

The first matching arm wins, and the compiler can't detect a guard that overlaps a later arm (Lab step 4's classify, Exercise 3). Order specific to general, and test boundaries.

⚠️ unwrap() everywhere

It turns None into a crash. Use unwrap_or, ?, let-else or a match; keep unwrap/expect for cases that truly can't happen, with expect explaining why (chapter 2.6).

⚠️ Expecting struct update to copy

..other moves other's non-Copy fields (e6). Clone first if you still need other.

⚠️ Booleans and strings where an enum belongs

is_active: bool, is_deleted: bool allows the impossible "active and deleted"; op: String allows "=>". Model the real alternatives as an enum (chapter F8) and parse text into it at the boundary (Lab step 7).

⚠️ Writing getters and setters for every field

That's a C#/Java habit. Inside a module, fields are accessed directly; expose methods that mean something (record_attempt, can_retry) and control visibility with modules (chapter 2.7).

Real-world view: types in your products

🏗 Architecture view
  • Rule engine: the parsed rule is an Expr enum tree; operators, value types and actions are enums; evaluation is a recursive match (Lab step 6). Adding an operator makes every unfinished match a compile error, which is exactly the checklist a language implementer wants (chapters 9.2–9.3).
  • Workflow engine: step state and events are enums and transitions are one exhaustive match, so persisted states can only be ones the code knows how to resume (chapters 10.3, 10.7). Serialising enums with data maps naturally to tagged JSON (chapter 7.1).
  • Parse at the boundary: API payloads and rule text become structs and enums once, at the edge. Inside, functions take types that can only hold valid data, so validation code doesn't repeat.
  • Commands and queries: &self methods are queries, &mut self methods commands, self methods finish or convert, and the signatures document intent.
  • Review checklist: _ arms on owned enums; boolean flag combinations that should be an enum; String fields holding a fixed set of values; unwrap() on data from outside; struct update syntax that moves more than intended; unreachable-pattern warnings left in the build.

Summary

  • Structs come in three shapes (named, tuple/newtype, unit); every field is set at construction. Behaviour goes in impl blocks: &self reads, &mut self changes, self consumes, no self constructs.
  • #[derive(...)] generates Debug, Clone, Copy, PartialEq, Hash, Default and the rest; derive only what the type should be able to do.
  • Enum variants carry their own data; Option<T> replaces null, and its methods (map, unwrap_or, and_then, ?) cover most uses without a match.
  • match tests arms top to bottom (pattern, then guard) and must be exhaustive; guards don't count. rustc reports wholly missing variants first. Avoid _ on your own enums so new variants become compile errors.
  • if let, while let, let-else, let chains (edition 2024) and matches! are the short forms. A state machine as one match on (state, event) is the most valuable pattern for the workflow engine.
