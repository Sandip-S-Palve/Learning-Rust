Borrowing and references

Learning objectives

  • Use shared (&T) and mutable (&mut T) references to let code use a value without taking ownership of it
  • State the two rules of references, aliasing XOR mutation and references are always valid, and explain the bugs each one rules out
  • Predict how long a borrow lasts under non-lexical lifetimes, and read errors E0502, E0499, E0506, E0505, E0597 and E0106
  • Recognise reborrowing, two-phase borrows and disjoint field borrows, and restructure code that fights the borrow checker
  • Compare borrowing with .NET's object references, ref/in parameters and "collection was modified" exceptions

Why this matters

💡 Why this matters

Chapter 2.2 left an obvious question open: if passing a value to a function moves it, how does a function just look at something? Cloning everything would be absurd. The answer is borrowing: handing out a reference that lets code use a value for a while, without owning it.

In C#, references are the default and nobody tracks them. Any number of variables, fields, closures and threads can point at the same List<T>, and any of them can change it. That freedom is behind a familiar family of bugs: InvalidOperationException: Collection was modified, a method that misbehaves when the caller passes the same object as two arguments, a "read-only" view that changes underneath its reader, and data races between threads. All of them come from the same thing: something is being read through one path while it's mutated through another.

Rust's borrow rules forbid exactly that combination, at compile time. You can have many readers or one writer, never both at once, and no reference can outlive what it points to. Every chapter from here on depends on this. For your rule engine, it's what lets a thousand rules evaluate the same facts in parallel with no locks, because the compiler has proved nobody is writing to them (chapter 4.1).

Intuition first: lending the original

🧭 Analogy

Back to chapter 2.2's signed original contract in its owner's cabinet. Copying it is expensive and handing it over gives it away. Usually you just want to lend it.

  • Shared borrow (&T): the reading room. Any number of colleagues can read the contract at the same time. While anyone is reading, nobody may write on it, not even the owner.
  • Mutable borrow (&mut T): checking it out for editing. Exactly one person has it, and nobody else may read or write it, again including the owner, until it's returned.
  • The owner can't shred a lent document. It can't move or drop the value while any borrow is still in use, so no reader is ever left holding a pointer to a shredded page.
  • Loans end when the borrower is done, at the last moment the reference is used, not at some formal deadline. That's non-lexical lifetimes, and it's why most code just works.

In .NET, everyone gets a photocopy of the cabinet key. Anyone can open it and scribble on the contract at any time, and the only protection is whatever discipline (or locks) your team remembers to use.

C#
var rules = new List<string> { "amount > 100" };

Describe(rules);            // the callee could also change it
rules.Add("vip");           // `view` sees the change

Core explanation

Basic

References and borrowing

A reference is a pointer to a value that doesn't own it. You create one with the & operator, and the Book names the act: "We call the action of creating a reference borrowing." The function below borrows the rule list, reads it, and gives it back simply by returning:

fn describe(rules: &[String]) -> usize {
    rules.iter().map(|r| r.len()).sum()
}

let rules = vec![String::from("amount > 100")];
let chars = describe(&rules); // lend it…
println!("{chars} {rules:?}"); // …still ours

New syntax you can read as LINQ for now: rules.iter() walks the items by reference, .map(|r| r.len()) is Select(r => r.Length) (|r| … is a closure, Rust's lambda), and .sum() is Sum(). Like LINQ, an iterator chain is lazy and runs only when consumed; unlike LINQ, it compiles to a plain loop with no allocations or virtual calls. Chapter 2.10 covers closures and iterators fully; until then, read filter, map, any, max_by_key and collect as Where, Select, Any, MaxBy and ToList.

Three things to notice. The parameter type &[String] and the argument &rules both say "borrowed". &rules is a &Vec<String>, and Rust converts it to the slice &[String] automatically: borrowing a slice is the idiomatic parameter type, and Clippy suggests it (chapter 2.4 explains slices). And when describe returns, its reference simply goes away. Dropping a reference never drops the value it points to; only the owner does that.

A shared reference, &T, is read-only. You can have as many as you like, and they are Copy (chapter 2.2): let b = a; copies the reference and both stay usable. To use the value behind a reference you dereference it with *, but for method calls, field access, indexing and printing Rust does that for you (auto-deref), so rules.len() works whether rules is a Vec or a &Vec.

In memory, a reference is just an address. Lab step 1 prints it: &rules is the address of the Vec's 24-byte header on the stack, the owner's own slot, not the heap buffer. A reference to a sized type is one pointer, 8 bytes. A reference to a slice or str is a fat pointer, 16 bytes: an address plus a length.

Mutable references

A mutable reference, &mut T, lets the borrower change the value. It needs a mut binding to borrow from (otherwise error E0596, Lab step 2), and an explicit &mut at the call site, so a reader of the code can see which calls may change their arguments:

fn add_rule(rules: &mut Vec<String>, rule: &str) {
    rules.push(rule.to_string());
}

let mut rules = Vec::new();
add_rule(&mut rules, "vip == true"); // visibly lends write access
let mut retries = 3;
let r = &mut retries;
*r += 1;                             // `*` to write through it
println!("{} {retries}", rules.len());

C# has nothing like that call-site marker for objects: AddRule(rules, …) looks the same whether or not the method mutates the list. (C#'s ref keyword is the closest thing; see the .NET callout below.)

The two rules

The Book states the rules of references in two lines:

  1. "At any given time, you can have either one mutable reference or any number of immutable references."
  2. "References must always be valid."

The first is usually called aliasing XOR mutation: a value can have many readers, or one writer, but never both at once. "At any given time" doesn't mean "while the variables exist". It means while the references are still going to be used. Here's the classic violation, holding a reference into a Vec while pushing to it:

// Holding a shared borrow into a Vec while pushing to it.
fn main() {
    let mut steps = vec![String::from("validate"), String::from("charge")];
    let first = &steps[0];            // shared borrow of `steps` starts…
    steps.push(String::from("ship")); // …mutable borrow needed here
    println!("first step: {first}");  // …shared borrow still used here
}
error[E0502]: cannot borrow `steps` as mutable because it is also borrowed as immutable

  |
4 |     let first = &steps[0];            // shared borrow of `steps` starts…
  |                  ----- immutable borrow occurs here
5 |     steps.push(String::from("ship")); // …mutable borrow needed here
  |     ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ mutable borrow occurs here
6 |     println!("first step: {first}");  // …shared borrow still used here
  |                            ----- immutable borrow later used here

This isn't pedantry. push may find the buffer full, allocate a bigger one, copy the elements across and free the old buffer. first would then point into freed memory. In C or C++ that's a use-after-free; in C# the runtime prevents the crash but you get the analogous logic bug (Lab step 4). Rust refuses to compile it, and the error tells you the three facts that matter: where the shared borrow started, where the conflicting mutable borrow is, and where the shared borrow is used later.

The rule rules out more than memory errors. If nothing can change a value while you hold a &T to it, then a reader never sees a half-finished update, a method can't be surprised by its own arguments aliasing each other, and two threads can't race on it. The Book draws exactly that conclusion: "The benefit of having this restriction is that Rust can prevent data races at compile time" (chapters F9 and 4.1).

fn main() {
    let mut steps = vec![String::from("validate"), String::from("charge")];
    let first = &steps[0]; // shared borrow #1 starts
    let count = &steps; // shared borrow #2: many readers are fine
    println!("{first}, {} steps", count.len()); // last use of both: they end
    steps.push(String::from("ship")); // a brief &mut, nothing else alive
    let m = &mut steps; // an exclusive borrow starts
    m.push(String::from("refund")); // last use of m: it ends
    println!("{steps:?}"); // the owner can read again
}

References must always be valid

The second rule says a reference can never outlive the value it points to: there are no dangling references. The Book: "the compiler guarantees that references will never be dangling references." Two errors enforce it. Borrowing a value that dies too soon:

// A reference that would outlive the value it points to.
fn main() {
    let r;
    {
        let rule = String::from("amount > 100");
        r = &rule;
    } // `rule` is dropped here
    println!("{r}");
}

Read the second help: "you are more likely to want to return an owned value". A function that creates data returns it by value, which is cheap (a move, chapter 2.2). A function returns a reference only when it points into something the caller passed in, and spelling out that connection is what lifetimes are for (chapter 2.11). For the same reason, a reference is never null: Rust uses Option<&T> for "maybe a reference" (chapter 2.5).

🟣 Coming from C#/.NET: object references vs borrows, and C#'s own ref safety
  • A C# class reference is not a borrow. It's a shared, mutable, untracked pointer that keeps the object alive (via the GC) and lets anyone change it. Rust has nothing that does all of that at once; the closest is Rc<RefCell<T>> (chapter 2.12), and its clumsiness is deliberate.
  • C#'s ref, in and ref readonly are the true cousins of &mut T and &T. C# even has ref safety rules: Microsoft's docs define a "ref safe context" and "the compiler ensures that a reference can't escape its ref safe context". Returning a reference to a local is a compile error in C# too (Lab step 4 shows CS8168). The difference is scope. C#'s rules cover only ref variables and ref structs like Span<T>, and say nothing about aliasing. Rust applies both rules to every reference.
  • No aliasing rule in C#. static void AddTwice(ref int a, ref int b) can be called as AddTwice(ref z, ref z), and Lab step 4 shows it returns 40 instead of 12. The Rust equivalent, add_twice(&mut z, &z), doesn't compile.
  • Iterator invalidation is a runtime check in .NET. List<T>'s docs: "An enumerator remains valid as long as the collection remains unchanged… the enumerator is irrecoverably invalidated and the next call to MoveNext or IEnumerator.Reset throws an InvalidOperationException." In Rust, that's error E0502 at compile time.
Intermediate

The borrow checker and non-lexical lifetimes

The borrow checker is the part of the compiler that enforces both rules. It works on a simplified control-flow form of each function (MIR), one function at a time, looking only at signatures across function boundaries. For each borrow it computes the set of program points where the reference may still be used, and reports an error if a conflicting access happens at any of those points. Then it's gone: borrow checking emits no code and costs nothing at run time.

How long a borrow lasts used to be decided by scope: a reference stored in a variable stayed borrowed until the variable's closing brace. That rejected a lot of obviously fine code. Since Rust 2018 the checker uses non-lexical lifetimes (NLL): a borrow lasts until the reference's last use. NLL shipped with the 2018 edition. The old checker's migration mode was removed in Rust 1.63 (2022), whose release notes say: "Remove migrate borrowck mode for pre-NLL errors". Since then NLL is the only borrow checker, in every edition. The difference is easy to see, because the old compiler still runs. Here is one program, compiled by rustc 1.30 (October 2018, the last release before NLL) and by today's 1.99:

#![allow(unused)]
fn main() {
    let mut v = vec![1, 2, 3];
    let a = &v;
    println!("{}", a[0]);
    v.push(5);
}

Reborrowing: why passing a &mut doesn't use it up

Shared references are Copy; mutable references can't be, since a copy would give two writers. So by the move rules of chapter 2.2, passing r: &mut String to a function should move r and leave it unusable. It doesn't, because the compiler inserts a reborrow: f(r) becomes f(&mut *r), a new mutable borrow through r that lasts only for the call. While it's alive r is frozen, and afterwards r works again (Lab step 3, section 3). The implicit reborrow happens where the target type is known to be a reference, such as a function argument or an annotated let. A plain let r2 = r; moves the &mut, and using r afterwards is E0382 (Exercise 3, snippet e).

Two-phase borrows: v.push(v.len())

Strictly, v.push(v.len()) takes &mut v for the receiver and then reads v.len() for the argument, which looks like E0502. It compiles because of two-phase borrows. The rustc dev guide: they "are a more permissive version of mutable borrows" that first act as shared borrows during a reservation phase and become full mutable borrows only when activated, when push actually runs. They apply only to certain implicit mutable borrows: autoref'd method receivers, reborrowed function arguments, and compound assignment operators. "Explicit &mut … in source code is never two-phase." The design point is that common nested calls just work without you thinking about them.

Disjoint borrows: fields, slices and methods

The borrow checker tracks places, not just variables. Borrowing engine.rules immutably and engine.hits mutably at the same time is fine inside one function, because they're different fields (Lab step 3, section 4). For two parts of one slice, split_at_mut hands you two non-overlapping &mut halves (section 5). But a method borrows self as a whole, whatever fields it touches inside, because the caller checks only the signature:

// A method borrows the whole struct, even if it only touches one field.
struct Engine {
    rules: Vec<String>,
    hits: u32,
}

impl Engine {
    fn rules(&self) -> &[String] {
        &self.rules
    }
    fn hits_mut(&mut self) -> &mut u32 {
        &mut self.hits
    }
}

fn main() {
    let mut engine = Engine { rules: vec![String::from("amount > 100")], hits: 0 };
    let rules = engine.rules();     // borrows all of `engine` immutably
    let hits = engine.hits_mut();   // needs all of `engine` mutably
    *hits += rules.len() as u32;
}
error[E0502]: cannot borrow `engine` as mutable because it is also borrowed as immutable
  --> errs/e10.rs:19:16
   |
18 |     let rules = engine.rules();     // borrows all of `engine` immutably
   |                 ------ immutable borrow occurs here
19 |     let hits = engine.hits_mut();   // needs all of `engine` mutably
   |                ^^^^^^^^^^^^^^^^^ mutable borrow occurs here
20 |     *hits += rules.len() as u32;
   |              ----- immutable borrow later used here

Fixes, in order of preference: finish with the first borrow before the second (copy out rules.len() first), access the fields directly inside the type's own module, or restructure: split the struct so the parts that change independently are separate values. Chapter 3.2 calls this "borrow-friendly design".

Designing with the borrow checker

Most borrow errors in real code come from a few shapes, and each has a standard restructuring:

  • Read, then write: collect, then apply. Evaluate with shared borrows into a list of changes, let those borrows end, then apply the list with one mutable borrow. That's the rule engine in Lab step 4, and it's also easier to test, log and replay (chapter 10.2's event sourcing is this idea scaled up).
  • Copy out what you need. Instead of holding a &Job while mutating the list, take its id (a Copy u32) and let the borrow end (Exercise 2).
  • Use indices or keys instead of long-lived references into a collection you're changing: for i in 0..v.len(), or retain/drain/extract_if, which let the collection do the editing safely (Lab step 3, section 6).
  • Shrink the borrow with a block { … } or by moving the last use earlier.
  • Interior mutability (Cell, RefCell, Mutex) moves the check from compile time to run time, for the genuine cases where shared mutation is the design (chapter 2.12). Lab step 5 shows that the rule still holds there: a violation becomes a panic instead of a compile error.
Deep dive: aliasing XOR mutation makes code faster, too

If a: &mut i32 is the only path to its value, nothing else, including a b: &i32 parameter, can change it or observe the change. rustc tells LLVM this (the noalias attribute on &mut parameters, on by default since Rust 1.54 once LLVM's bugs with it were fixed), and the optimiser uses it. The same function with raw pointers, which carry no such promise, compiled with -O for the lab Mac (arm64):

// `a` is &mut, so the compiler may assume nothing else (including `b`) points at it.
#[unsafe(no_mangle)]
pub fn add_twice(a: &mut i32, b: &i32) {
    *a += *b;
    *a += *b;
}

// Raw pointers carry no such promise: `a` and `b` might be the same address.
#[unsafe(no_mangle)]
pub unsafe fn add_twice_raw(a: *mut i32, b: *const i32) {
    unsafe {
        *a += *b;
        *a += *b;
    }
}

Fortran compilers have long made the no-aliasing assumption for array arguments; C added restrict for it and left it to the programmer to get right. Rust gets the same assumption for every &mut, checked by the compiler.

Deep dive: where the borrow checker is too strict, and Polonius

The borrow checker is sound (it never accepts a program that breaks the rules) but not complete: it rejects some correct programs. The best-known one is "NLL problem case #3", a conditional return of a borrow:

use std::collections::HashMap;

// Sound, but rejected by today's borrow checker ("NLL problem case #3").
fn get_or_insert(map: &mut HashMap<u32, String>, key: u32) -> &String {
    if let Some(v) = map.get(&key) {
        return v; // the shared borrow is returned on this path only…
    }
    map.insert(key, String::from("default")); // …but is treated as alive here too
    map.get(&key).unwrap()
}

fn main() {
    let mut cache = HashMap::new();
    println!("{}", get_or_insert(&mut cache, 1));
}
error[E0502]: cannot borrow `*map` as mutable because it is also borrowed as immutable
 --> errs/pc3.rs:8:5
  |
4 | fn get_or_insert(map: &mut HashMap<u32, String>, key: u32) -> &String {
  |                       - let's call the lifetime of this reference `'1`
5 |     if let Some(v) = map.get(&key) {
  |                      --- immutable borrow occurs here
6 |         return v; // the shared borrow is returned on this path only…
  |                - returning this value requires that `*map` is borrowed for `'1`
7 |     }
8 |     map.insert(key, String::from("default")); // …but is treated as alive here too
  |     ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ mutable borrow occurs here

On the return v path the borrow must last as long as the caller's ('1), and today's checker applies that requirement on every path, including the one where we didn't return. The program is fine. The idiomatic workaround already exists for maps, the Entry API, which does lookup-or-insert in a single borrow (chapter 2.8):

use std::collections::HashMap;

// The idiomatic fix today: the Entry API does the lookup-or-insert in one borrow.
fn get_or_insert(map: &mut HashMap<u32, String>, key: u32) -> &String {
    map.entry(key).or_insert_with(|| String::from("default"))
}

fn main() {
    let mut cache = HashMap::new();
    println!("{}", get_or_insert(&mut cache, 1));
    cache.insert(2, String::from("custom"));
    println!("{}", get_or_insert(&mut cache, 2));
}

The fix in the compiler is Polonius, a new formulation of borrow checking that is flow-sensitive, so it knows a borrow isn't live on paths where it wasn't returned. The Rust blog's August 2026 post enabled "Polonius alpha" on nightly "in preparation for stabilization in the next few months", using exactly this shape (get_mut_or_default) as its headline example.

Step 1 — borrowing, dereferencing, and what a reference is

use std::mem::size_of;

// Borrows the rule set: reads it, gives it back automatically.
// (&[String], a slice, accepts a borrowed Vec and more: Clippy's ptr_arg, chapter 2.4.)
fn describe(rules: &[String]) -> usize {
    rules.iter().map(|r| r.len()).sum() // auto-deref: no `*` needed for methods
}

// Borrows mutably: may change the caller's value, can't keep it.
fn add_rule(rules: &mut Vec<String>, rule: &str) {
    rules.push(rule.to_string());
}

fn main() {
    // 1. Shared and mutable borrows of one owner.
    let mut rules = vec![String::from("amount > 100"), String::from("country == NL")];
    let chars = describe(&rules); // lend it out…
    println!("1. {} rules, {chars} chars; still mine: {:?}", rules.len(), rules); // …and still own it
    add_rule(&mut rules, "vip == true");
    println!("   after add_rule: {} rules", rules.len());

    // 2. Explicit dereference with `*` for plain values.
    let mut retries = 3;
    let r = &mut retries;
    *r += 1; // write through the reference
    println!("2. retries = {retries}");

    // 3. A reference is a pointer to the owner's location, here the stack slot of `rules`.
    let shared = &rules;
    println!("3. &rules  = {:p} (address of the Vec header on the stack)", &rules);
    println!("   shared  = {:p} (the same address: shared points at the owner)", shared);
    println!("   buffer  = {:p} (the heap data, untouched)", rules.as_ptr());

    // 4. Sizes: a reference is one pointer; a slice reference also carries a length.
    println!("4. size_of::<&Vec<String>>()  = {}", size_of::<&Vec<String>>());
    println!("   size_of::<&mut u64>()       = {}", size_of::<&mut u64>());
    println!("   size_of::<&str>()           = {}", size_of::<&str>());
    println!("   size_of::<&[u64]>()         = {}", size_of::<&[u64]>());

    // 5. Shared references are Copy: hand out as many as you like.
    let a = &rules;
    let b = a; // copies the reference, `a` is still usable
    println!("5. a and b both read: {} / {}", a[0], b[1]);

Step 3 — what NLL, reborrowing and split borrows allow

struct Engine {
    rules: Vec<String>,
    hits: u32,
}

impl Engine {
    fn rules(&self) -> &[String] {
        &self.rules
    }
    fn record_hit(&mut self) {
        self.hits += 1;
    }
}

fn append_bang(s: &mut String) {
    s.push('!');
}

fn main() {
    // 1. Non-lexical lifetimes: a borrow ends at its last use, not at the closing brace.
    let mut steps = vec![String::from("validate"), String::from("charge")];
    let first = &steps[0];
    println!("1. first step: {first}"); // last use of `first`: the shared borrow ends here
    steps.push(String::from("ship")); // so this mutable borrow is fine
    println!("   steps: {steps:?}");

    // 2. Two-phase borrow: `v.len()` is evaluated before `push` activates its &mut.
    let mut sizes = vec![10, 20];
    sizes.push(sizes.len());
    println!("2. sizes: {sizes:?}");

    // 3. Reborrowing: passing a &mut to a function lends it for the call, it isn't moved.
    let mut msg = String::from("done");
    let r = &mut msg;
    append_bang(r); // implicitly append_bang(&mut *r)
    append_bang(r); // r is still usable
    r.push('?');
    println!("3. msg: {msg}");

    // 4. Disjoint fields: borrowing two different fields at once is fine…
    let mut engine = Engine { rules: vec![String::from("amount > 100")], hits: 0 };
    let rules = &engine.rules;
    let hits = &mut engine.hits;
    *hits += rules.len() as u32;
    // …but a method call borrows the *whole* struct, so finish with `rules` first.
    let count = engine.rules().len();
    engine.record_hit();
    println!("4. {count} rule(s), hits = {}", engine.hits);

    // 5. Two mutable halves of one slice, proven disjoint by split_at_mut.
    let mut balances = [100, 200, 300, 400];
    let (left, right) = balances.split_at_mut(2);
    left[0] -= 50;
    right[1] += 50; // a transfer between two elements, both borrowed mutably
    println!("5. balances: {balances:?}");

    // 6. Index-based edits instead of iterator invalidation (compare errs/e8.rs).
    let mut queue = vec![1, 2, 3];
    let n = queue.len();
    for i in 0..n {
        if queue[i] == 2 {
            queue.push(4); // allowed: no borrow of `queue` is held across the loop
        }
    }
    queue.retain(|job| *job != 1); // or let the collection do the editing
    println!("6. queue: {queue:?}");
}

Step 4 — a borrow-friendly rule engine, and the C# aliasing bugs

A small version of the rule engine: rules evaluate orders with shared borrows only, producing actions; then one exclusive borrow applies them. The signatures alone tell you which phase can change what.

use std::collections::HashMap;

struct Order {
    id: u32,
    amount: i64, // cents
    country: String,
}

struct Rule {
    name: String,
    min_amount: i64,
    country: Option<String>,
    discount_pct: i64,
}

enum Action {
    Discount { order: u32, cents: i64, rule: String },
}

// Phase 1, read-only: many rules look at the same orders through shared borrows.
// The signature promises the caller that nothing is modified.
fn evaluate(rules: &[Rule], orders: &[Order]) -> Vec<Action> {
    let mut actions = Vec::new();
    for order in orders {
        for rule in rules {
            let country_ok = rule.country.as_deref().is_none_or(|c| c == order.country);
            if order.amount >= rule.min_amount && country_ok {
                actions.push(Action::Discount {
                    order: order.id,
                    cents: order.amount * rule.discount_pct / 100,
                    rule: rule.name.clone(),
                });
            }
        }
    }
    actions
}

// Phase 2, exclusive: one mutable borrow applies every change.
fn apply(actions: &[Action], orders: &mut [Order], audit: &mut HashMap<String, u32>) {
    for action in actions {
        let Action::Discount { order, cents, rule } = action;
        if let Some(o) = orders.iter_mut().find(|o| o.id == *order) {
            o.amount -= cents;
        }
        *audit.entry(rule.clone()).or_insert(0) += 1;
    }
}

fn main() {
    let rules = vec![
        Rule { name: "big-order".into(), min_amount: 10_000, country: None, discount_pct: 5 },
        Rule { name: "nl-promo".into(), min_amount: 0, country: Some("NL".into()), discount_pct: 10 },
    ];
    let mut orders = vec![
        Order { id: 1, amount: 25_000, country: "NL".into() },
        Order { id: 2, amount: 4_000, country: "DE".into() },
        Order { id: 3, amount: 12_000, country: "DE".into() },
    ];
    let mut audit = HashMap::new();

    let actions = evaluate(&rules, &orders); // shared borrows end when evaluate returns
    apply(&actions, &mut orders, &mut audit); // now an exclusive borrow is allowed

    for o in &orders {
        println!("order {}: {:>7.2} {}", o.id, o.amount as f64 / 100.0, o.country);
    }
    let mut hits: Vec<_> = audit.iter().collect();
    hits.sort();
    println!("rule hits: {hits:?}");
}

order 2:   40.00 DE
order 3:  114.00 DE

Step 5 — moving the check to run time: RefCell, and what it costs

RefCell<T> (chapter 2.12) enforces the same rule while the program runs: it counts active borrows and refuses a conflicting one. Here is e1.rs's mistake again, hidden from the compiler:

use std::cell::RefCell;

fn main() {
    // The same aliasing mistake as errs/e1.rs, but hidden from the compiler inside a RefCell.
    let steps = RefCell::new(vec![String::from("validate"), String::from("charge")]);

    let reader = steps.borrow(); // run-time shared borrow (a counter goes to 1)
    println!("first step: {}", reader[0]);
    println!("try_borrow_mut while reading: {:?}", steps.try_borrow_mut().map(|_| ()));
    drop(reader); // shared borrow released (counter back to 0)
    steps.borrow_mut().push(String::from("ship"));
    println!("after release: {} steps", steps.borrow().len());

    let _reader = steps.borrow();
    steps.borrow_mut().push(String::from("refund")); // the rule is still enforced: by a panic
}

The rule didn't go away; the moment you find out moved, from cargo build to production. That's the honest comparison with .NET's "collection was modified" check. And speed?

use std::cell::RefCell;
use std::hint::black_box;
use std::sync::Mutex;
use std::time::Instant;

const N: u64 = 100_000_000;

// The borrow checker verified this at compile time: nothing to check at run time.
#[inline(never)]
fn via_mut_ref(counter: &mut u64) {
    for i in 0..N {
        *counter += black_box(i) & 1;
    }
}

// RefCell checks the borrow rules at run time, on every borrow_mut() (chapter 2.12).
#[inline(never)]
fn via_refcell(counter: &RefCell<u64>) {
    for i in 0..N {
        *counter.borrow_mut() += black_box(i) & 1;
    }
}

// A Mutex enforces the same rule across threads, with an atomic lock/unlock (chapter 4.2).
#[inline(never)]
fn via_mutex(counter: &Mutex<u64>) {
    for i in 0..N {
        *counter.lock().unwrap() += black_box(i) & 1;
    }
}

fn best_of_5(mut f: impl FnMut()) -> f64 {
    (0..5)
        .map(|_| {
            let t = Instant::now();
            f();
            t.elapsed().as_secs_f64() * 1e9 / N as f64
        })
        .fold(f64::INFINITY, f64::min)
}

fn main() {
    let mut plain = 0u64;
    let cell = RefCell::new(0u64);
    let lock = Mutex::new(0u64);

    let t_ref = best_of_5(|| via_mut_ref(&mut plain));
    let t_cell = best_of_5(|| via_refcell(&cell));
    let t_lock = best_of_5(|| via_mutex(&lock));

    assert_eq!(plain, *cell.borrow());
    assert_eq!(plain, *lock.lock().unwrap());
    println!("{N} increments each, best of 5, ns per increment:");
    println!("  &mut u64 (checked at compile time) : {t_ref:.2}");
    println!("  RefCell<u64> (checked at run time) : {t_cell:.2}");
    println!("  Mutex<u64>   (lock per increment)  : {t_lock:.2}");
}
100000000 increments each, best of 5, ns per increment:
  &mut u64 (checked at compile time) : 0.49
  RefCell<u64> (checked at run time) : 0.40
  Mutex<u64>   (lock per increment)  : 6.57

Two conclusions, one of them maybe surprising. Compile-time borrows cost nothing at run time, by construction. But RefCell's run-time check is also very cheap: here it was within noise (the generated code adds one load and one branch per increment, and LLVM even removed the borrow counter's increment and decrement). So the reason to prefer plain references isn't speed. It's that a mistake becomes a compile error you fix in a minute instead of a panic in production. Reach for RefCell when shared mutation is the design, not to silence the borrow checker. The Mutex cost is real, and chapter 4.2 deals with it.

struct Job {
    id: u32,
    priority: u8,
    running: bool,
}

fn mark_running(jobs: &mut [Job], id: u32) {
    for j in jobs.iter_mut().filter(|j| j.id == id) {
        j.running = true;
    }
}

// Fix 1: copy out what you need (a u32 is Copy), so the shared borrow ends at once.
fn start_next(jobs: &mut [Job]) -> Option<u32> {
    let id = jobs.iter().filter(|j| !j.running).max_by_key(|j| j.priority)?.id;
    mark_running(jobs, id); // no shared borrow is alive any more
    Some(id)
}

// Fix 2: borrow mutably from the start and change the job in place.
fn start_next_in_place(jobs: &mut [Job]) -> Option<u32> {
    let next = jobs.iter_mut().filter(|j| !j.running).max_by_key(|j| j.priority)?;
    next.running = true;
    Some(next.id)
}

fn main() {
    let mut jobs = vec![
        Job { id: 1, priority: 3, running: false },
        Job { id: 2, priority: 9, running: false },
        Job { id: 3, priority: 5, running: false },
    ];
    assert_eq!(start_next(&mut jobs), Some(2));
    assert_eq!(start_next_in_place(&mut jobs), Some(3));
    assert_eq!(start_next(&mut jobs), Some(1));
    assert_eq!(start_next(&mut jobs), None);
    assert!(jobs.iter().all(|j| j.running));
    println!("started 2, 3, 1, then None: ok");
}

next is a &Job into jobs, and it's still used (next.id) when mark_running needs &mut access to the whole slice. That's E0502. Fix 1 copies the u32 out at once, so the shared borrow ends on the same line; it's the "copy out what you need" pattern, and it also works when the mutation happens far away, such as in a database. Fix 2 borrows mutably from the start with iter_mut() and edits the job in place, with one borrow and no second search. The signature changed from &mut Vec<Job> to &mut [Job]: it never adds or removes jobs, so it shouldn't ask for the power to.

  • b: the same statements with the last use of r moved first. Under NLL, r's borrow is over before s.len().
  • c: a two-phase borrow: v.len() runs while push's &mut is only reserved.
  • d: two shared borrows at once (first and the one for len). Many readers are fine. (The mut isn't even needed; rustc warns about it.)
  • e: let r2 = r1; with no type annotation moves the &mut (it isn't Copy), so using r1 afterwards is E0382. let r2: &mut String = r1; would reborrow instead. Then r2.push(…) followed by r1.push(…) compiles, because r2 isn't used again.
  • f: view's last use is the first println!, so the += 1 after it is fine. Swap the two lines and you get E0506.

Common misconceptions and pitfalls

⚠️ "A borrow lasts until the end of the scope"

Not since Rust 2018: it lasts until the reference's last use (Figure 2). If an error seems wrong, find the "borrow later used here" label. That use is what keeps the borrow alive.

⚠️ Cloning to make the borrow checker happy

It compiles, but it hides the design question. First try ending the borrow earlier, copying out an id, or collect-then-apply (Exercise 2, Lab step 4).

⚠️ Storing references in long-lived structs too early

A struct holding &T needs lifetime parameters (chapter 2.11) and freezes what it points to for its whole life. In application code, prefer owned data or ids. Keep references for short-lived views.

⚠️ Taking &Vec<T> or &String parameters

Take &[T] and &str: they accept more callers at no cost, and Clippy's ptr_arg lint flags the other form (chapter 2.4).

⚠️ Methods that return a reference into self, then mutate

A getter like fn rules(&self) -> &[String] borrows all of self for as long as its result is used (e10). Copy out what you need, or reach the fields directly.

⚠️ "RefCell turns off the borrow checker"

It moves the same rule to run time, and violations panic (Lab step 5). It's for designs that genuinely need shared mutation, not for silencing errors.

Real-world view: borrowing in your products

🏗 Architecture view
  • Rule engine evaluation: evaluate(&rules, &facts) is read-only by signature, so it can run on many threads over the same facts with no locks. The compiler proves no rule mutates shared state (chapter 4.1 adds the threads). Mutation is confined to one apply phase.
  • Collect, then apply = auditable: producing a Vec<Action> before mutating gives you a natural point to log, dry-run, or persist decisions. For the workflow engine, that's the step outcome you write to the event log before updating state (chapter 10.2).
  • APIs that say what they do: &self methods are queries; &mut self methods are commands; self methods consume. That's CQS, enforced by the compiler instead of by naming conventions.
  • Ids over references across components: store StepId/RuleId and look things up, rather than holding references between long-lived objects. It plays well with the borrow checker, serialisation and persistence.
  • Review checklist: clones added to silence E0502; &Vec/&String parameters; &mut where & would do; RefCell used to dodge a design problem; structs holding references in application code; long-lived getters returning references into self.

Summary

  • Borrowing creates a reference: &T to read (many at once, Copy), &mut T to modify (exclusive, visible at the call site). A reference is just an address (8 bytes; 16 for slices and &str), and dropping it never drops the value.
  • Two rules: aliasing XOR mutation (many readers or one writer, never both) and references are always valid (no dangling, no null). Together they rule out use-after-free, iterator invalidation, aliasing surprises and data races, at compile time and with zero run-time cost.
  • Under non-lexical lifetimes, a borrow lasts until its last use, not the end of the scope. Of 522 explorer programs, rustc 1.99 accepts 219 and the lexical-era rustc 1.30 accepted 30.
  • Know the errors by number: E0502/E0499 (overlap), E0506/E0505 (assign or move while borrowed), E0597/E0106 (dangling), E0596 (not mut). Reborrowing, two-phase borrows and disjoint field borrows make most natural code compile.
  • When the checker objects, restructure: end the borrow earlier, copy out ids, collect then apply, use indices or retain. RefCell moves the same rule to run time (a panic, not a compile error), at very little speed cost.
