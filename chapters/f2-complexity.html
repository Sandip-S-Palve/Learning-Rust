Measuring cost: complexity

Learning objectives

  • Describe how an algorithm's cost grows with input size, using Big-O, Ω and Θ, both intuitively and formally
  • Read code and state its time and space complexity, including costs hidden inside library calls
  • Distinguish worst-case, best-case, average, amortised and expected cost, and know which one an SLA cares about
  • Explain why constants and caches still matter, and where the crossover points are
  • Recognise exponential-time traps such as catastrophic regex backtracking, and choose safe alternatives

Why this matters

💡 Why this matters

The most valuable question an architect can ask about any design is "what happens at 10× the data?" Complexity analysis answers it before you build anything. It's the vocabulary for spotting the List.Contains inside a loop that passes every test and then takes production down at month-end. In this chapter you'll measure exactly that kind of code: 1.5 seconds versus 1 millisecond for the same answer on 100,000 items, and a one-line regular expression that takes 10 seconds on a 26-character input.

For your products, complexity decides whether the rule engine can evaluate a million facts, and whether the workflow engine can track a million timers, on one machine.

Intuition first: finding a name in a phone book

🧭 Analogy

To find "Okafor" in a 1,000-page phone book you could read page 1, then page 2, and so on: up to 1,000 page-reads. Or you could open the middle, see "M", know Okafor is in the second half, open the middle of that, and keep halving. About 10 page-reads, because 1,000 halves to 1 in 10 steps. Double the book to 2,000 pages and the first method needs up to 2,000 reads, but the second needs just one more.

Complexity isn't about how fast you read a page. It's about how the number of page-reads grows as the book gets bigger.

Core explanation

Basic

What we count, and why not seconds

An algorithm is a step-by-step procedure, such as "check every page" or "halve the range". Its running time in seconds depends on the machine, the compiler and the cache (chapter F1). Its growth doesn't. So we count basic steps (comparisons, additions, memory reads) as a function of the input size, written n, and ask how that count grows as n grows. This is the algorithm's time complexity. The memory it needs is its space complexity.

Logarithms in one minute

The phone-book trick introduced the one piece of maths this chapter needs. \(\log_2 n\) ("log base 2 of n") is how many times you can halve n before reaching 1. Equivalently, it's the power you raise 2 to in order to get n: \(\log_2 1024 = 10\) because \(2^{10} = 1024\).

n161,0001,000,0001,000,000,000
\(\log_2 n\) (rounded up)4102030
 Logarithms grow extremely slowly: a thousand times more data adds only about 10 steps. In complexity, "log" means log base 2 unless stated otherwise. The base only changes a constant factor, which Big-O ignores anyway.

Big-O: describing growth

Big-O notation names the shape of the growth, ignoring two things that stop mattering as n gets large:

  1. Constant factors: 3n steps and 100n steps both grow linearly, so both are O(n).
  2. Smaller terms: n² + 50n + 7 is dominated by n² once n is large, so it's O(n²).

Reading complexity from code

Four rules cover most real code:

  1. Sequence adds: an O(n) loop followed by another O(n) loop is O(n + n) = O(n).
  2. Nesting multiplies: a loop of n iterations whose body does O(n) work is O(n × n) = O(n²).
  3. Halving gives a log: a loop that halves (or doubles) its range each time runs O(log n) times.
  4. Library calls have costs too. vec.contains(&x) is a hidden loop. Look up the cost of every collection operation you call inside a loop.
C# — looks like one loop, is O(n·m)
// List<T>.Contains "performs a linear search;
// therefore, this method is an O(n) operation"
var common = a.Where(x => b.Contains(x)).Count();
Rust — the same trap
// Vec::contains also scans: O(m) per call

Intermediate

The formal definitions

Big-O is an upper bound: a guarantee that, beyond some size, the cost never exceeds a constant multiple of the bound.

$$ f(n) \in O(g(n)) \iff \exists\, c > 0,\ n_0 \ \text{such that}\ 0 \le f(n) \le c \cdot g(n)\ \text{for all}\ n \ge n_0 $$

Two companions complete the set:

  • Ω (Big-Omega) is a lower bound: \(f(n) \ge c \cdot g(n)\) for all \(n \ge n_0\). "It takes at least this long."
  • Θ (Big-Theta) is a tight bound: both O and Ω hold, so f grows exactly like g, up to constants.

Worked example. Show that \(f(n) = 3n^2 + 5n + 2\) is \(O(n^2)\). Choose \(c = 4\). We need \(3n^2 + 5n + 2 \le 4n^2\), that is \(n^2 - 5n - 2 \ge 0\), which is true for every \(n \ge 6\). So \(c = 4, n_0 = 6\) works. It's also \(\Omega(n^2)\) (take \(c = 3, n_0 = 1\)), hence \(\Theta(n^2)\).

ℹ️ How people actually use the words

In everyday engineering "O(n²)" is usually said where Θ(n²) is meant: "it grows like n²". Being O(n²) technically also allows faster growth below the bound. Be precise when it matters (a contract, a design review). Otherwise follow the convention.

Worst, best and average case

One algorithm can have different costs on different inputs of the same size. Linear search finds the target in 1 step if it's first (best case), needs n steps if it's missing (worst case), and about n/2 on average if it's present at a random position. All three are O(n) here, but they aren't always the same class: quicksort is O(n log n) on average and O(n²) in its worst case (chapter F7).

For services, the worst case is usually the one that matters. Your p99 latency and SLA are made of worst cases, and an attacker can choose worst-case inputs. The deep dive shows that taken to the extreme.

Amortised cost: why Vec::push is O(1)

A Vec keeps spare capacity. When it's full, push allocates a bigger buffer and copies every element across, which costs O(n). So how can the docs promise that push takes "amortized O(1) time"?

Amortised means averaged over a long sequence of operations. If capacity doubles each time it fills, the copies happen at sizes 4, 8, 16, …, up to the largest power of two below n, and their total is less than 2n:

$$ \underbrace{4 + 8 + 16 + \dots + 2^{k}}_{\text{elements copied while growing}} \;<\; 2^{k+1} \;\le\; 2n \quad\Longrightarrow\quad \frac{\text{total copies}}{n} < 2 = O(1) $$

Measured in the lab: pushing one million values into a Vec<u64> went through capacities 4, 8, 16, …, 1,048,576 and copied 1,048,572 elements in total, which is 1.05 copies per push. Two caveats from the official docs: the growth factor is not guaranteed ("Vec does not guarantee any particular growth strategy"), but amortised O(1) push is. And an individual push can still be slow (a 1-million-element copy), which matters for latency-sensitive code. Use Vec::with_capacity(n) when you know the size up front.

Deep dive: exponential time in the wild — catastrophic regex backtracking

Most regular-expression engines, including .NET's default engine, backtrack: when a partial match fails, they go back and try another way of splitting the input among the pattern's parts. For patterns with nested repetition such as (a+)+b, a string of n a's with no b can be split in about \(2^{n}\) ways, and the engine tries them all before giving up. That is exponential time from a one-line pattern. Microsoft's documentation warns about precisely this ("In a worst-case scenario, execution time can double for each additional character in the input string").

Measured on the lab Mac, .NET 10, Regex.IsMatch on "aaa…a>":

using System.Diagnostics;
using System.Text.RegularExpressions;

// A classic "catastrophic backtracking" pattern (Microsoft docs use the similar (a+)+$).
var backtracking = new Regex(@"(a+)+b");
var linear = new Regex(@"(a+)+b", RegexOptions.NonBacktracking);

linear.IsMatch("warm-up"); backtracking.IsMatch("warm-up");
foreach (var n in new[] { 16, 18, 20, 22, 24, 26 })
{
    var input = new string('a', n) + ">";   // almost matches, then fails
    var sw = Stopwatch.StartNew();
    backtracking.IsMatch(input);
    var tBack = sw.Elapsed.TotalMilliseconds;
    sw.Restart();
    linear.IsMatch(input);
    var tLin = sw.Elapsed.TotalMilliseconds;
    Console.WriteLine($"n={n,2}  backtracking {tBack,9:F2} ms   NonBacktracking {tLin,6:F3} ms");
}

Rust's regex crate never backtracks. Its documentation guarantees that "all regex searches in this crate have worst case O(m * n) time complexity", where m is the size of the regex and n the length of the text. In effect it tracks every possible position in the pattern at once rather than trying them one by one. The cost of that guarantee: features that need backtracking (look-around, back-references) aren't supported. cargo add regex, then:

use regex::Regex;
use std::time::Instant;

fn main() {
    let re = Regex::new(r"(a+)+b").unwrap();
    for n in [1_000usize, 10_000, 100_000, 1_000_000] {
        let input = "a".repeat(n) + ">";
        let start = Instant::now();
        let matched = re.is_match(&input);
        println!("n={n:>9}  matched={matched}  {:.3} ms", start.elapsed().as_secs_f64() * 1000.0);
    }
}
n=     1000  matched=false  0.020 ms
n=    10000  matched=false  0.013 ms
n=   100000  matched=false  0.134 ms
n=  1000000  matched=false  1.264 ms

The middle of three runs of exactly this program (release build). The first row includes one-time warm-up. Your timings will vary. The shape (flat, then linear: 10× the input, about 10× the time) is the point. With the $-anchored variant (a+)+$, the crate answered in microseconds even at a million characters. It evidently didn't need to scan the whole input, a reminder that guarantees are worst-case bounds, not typical speeds.

Why this is an architecture topic, not trivia: an attacker who can submit input to a backtracking regex can freeze a server thread for seconds per request, a ReDoS (regular-expression denial of service). Your rule engine will very likely offer a "matches pattern" operator on customer data. Choose a linear-time engine (Rust's regex; in .NET, NonBacktracking or timeouts), cap pattern and input sizes, and document the supported syntax. Note also Microsoft's caution that .NET's protections guard against expensive input and assume the pattern is trusted. Customer-authored patterns need their own limits.

Hands-on lab: count, then time

Create a project with several programs in src/bin/ (as in F1) and run them with cargo run --release --bin <name>.

Step 1 — count comparisons

/// Returns (found, comparisons) for a front-to-back scan.
fn linear_search(v: &[u32], target: u32) -> (bool, u32) {
    let mut comparisons = 0;
    for &x in v {
        comparisons += 1;
        if x == target {
            return (true, comparisons);
        }
    }
    (false, comparisons)
}

/// Returns (found, comparisons) for binary search on a sorted slice.
fn binary_search(v: &[u32], target: u32) -> (bool, u32) {
    let (mut lo, mut hi) = (0, v.len()); // search the half-open range [lo, hi)
    let mut comparisons = 0;
    while lo < hi {
        let mid = lo + (hi - lo) / 2;
        comparisons += 1;
        if v[mid] == target {
            return (true, comparisons);
        } else if v[mid] < target {
            lo = mid + 1;
        } else {
            hi = mid;
        }
    }
    (false, comparisons)
}

fn main() {
    println!("{:>11} {:>14} {:>14}", "n", "linear (worst)", "binary (worst)");
    for n in [16u32, 1_000, 1_000_000, 100_000_000] {
        let v: Vec<u32> = (0..n).map(|i| i * 2).collect(); // sorted even numbers
        let missing = 1; // odd, so never present: forces the worst case
        let (_, lin) = linear_search(&v, missing);
        let (_, bin) = binary_search(&v, missing);
        println!("{n:>11} {lin:>14} {bin:>14}");
    }
}
          n linear (worst) binary (worst)
         16             16              5
       1000           1000             10
    1000000        1000000             20
  100000000      100000000             27

Counting steps instead of timing gives exact, machine-independent numbers: Big-O made visible. The binary column grows by one each time n roughly doubles. (Searching for a missing value takes one comparison more than \(\lfloor \log_2 n \rfloor\) in the worst case, hence 5 for n = 16.) The 100-million case allocates 400 MB; reduce it if your machine is small.

Step 2 — watch amortisation happen

fn main() {
    let mut v: Vec<u64> = Vec::new();
    let mut copies = 0; // elements moved during reallocations
    let mut last_cap = v.capacity();
    let n = 1_000_000;
    print!("capacities:");
    for i in 0..n {
        if v.len() == v.capacity() {
            copies += v.len(); // a full Vec must move its elements to grow
        }
        v.push(i);
        if v.capacity() != last_cap {
            if v.capacity() <= 2048 { print!(" {}", v.capacity()); }
            last_cap = v.capacity();
        }
    }
    println!(" ...");
    println!("pushed {n} values; final capacity {}; elements copied while growing: {copies}", v.capacity());
    println!("copies per push: {:.3}", copies as f64 / n as f64);
}

Step 3 — three algorithms, one question

use std::collections::HashSet;
use std::hint::black_box;
use std::time::Instant;

/// O(n²): compare every pair.
fn has_dup_pairs(v: &[u64]) -> bool {
    for i in 0..v.len() {
        for j in (i + 1)..v.len() {
            if v[i] == v[j] {
                return true;
            }
        }
    }
    false
}

/// O(n log n): sort a copy, then duplicates must be neighbours.
fn has_dup_sort(v: &[u64]) -> bool {
    let mut sorted = v.to_vec();
    sorted.sort_unstable();
    sorted.windows(2).any(|w| w[0] == w[1])
}

/// O(n) expected: remember what we've seen in a hash set.
fn has_dup_hash(v: &[u64]) -> bool {
    let mut seen = HashSet::with_capacity(v.len());
    for x in v {
        if !seen.insert(*x) {
            return true;
        }
    }
    false
}

/// Average time of `f` over enough runs to be measurable, in microseconds.
fn time_us(f: impl Fn() -> bool) -> f64 {
    let runs = 5;
    let start = Instant::now();
    for _ in 0..runs {
        black_box(f());
    }
    start.elapsed().as_secs_f64() * 1e6 / runs as f64
}

fn main() {
    println!("{:>7} {:>12} {:>12} {:>12}", "n", "pairs O(n²)", "sort", "hash");
    for n in [10, 100, 1_000, 10_000, 100_000] {
        // Distinct values in scrambled order: the worst case (no duplicate to stop early).
        let v: Vec<u64> = (0..n as u64).map(|i| i.wrapping_mul(2_654_435_761) % 1_000_000_007).collect();
        let v = black_box(v);
        let pairs = if n <= 100_000 { time_us(|| has_dup_pairs(&v)) } else { f64::NAN };
        println!("{:>7} {:>10.1}µs {:>10.1}µs {:>10.1}µs", n, pairs, time_us(|| has_dup_sort(&v)), time_us(|| has_dup_hash(&v)));
    }
}
      n  pairs O(n²)         sort         hash
     10        0.3µs        0.6µs        2.0µs
    100        4.0µs        1.7µs        2.8µs
   1000      291.6µs       19.9µs       25.9µs
  10000    20065.6µs      125.9µs       90.6µs
 100000  1484006.8µs     1013.3µs     1030.9µs

Check the O(n²) column against the theory: each 10× increase in n should make it about 100× slower. From 1,000 to 10,000 it went 292 µs → 20 ms (69×), and from 10,000 to 100,000, 20 ms → 1.48 s (74×). That's close to 100×, and short of it because the early sizes fit in cache (chapter F1). Exercises

Exercise 1 — classify the code ★☆☆

Give the time complexity of each, in terms of n = v.len() (and m = w.len() where present):

// (a)
let first = v[0];
// (b)
let total: u64 = v.iter().sum();
// (c)
for x in &v { if w.contains(x) { /* ... */ } }
// (d)
let mut i = v.len();
while i > 1 { i /= 2; }
// (e)
for x in &v { for y in &v { if x < y { /* ... */ } } }
// (f)
v.sort(); let found = v.binary_search(&42).is_ok();
Show solution
  • (a) O(1): indexing a Vec is constant time.
  • (b) O(n): visits every element once.
  • (c) O(n·m): contains on a Vec is a hidden O(m) loop. If n ≈ m, that's quadratic.
  • (d) O(log n): halving.
  • (e) O(n²): nested loops over the same data.
  • (f) O(n log n): the sort dominates the O(log n) search. Sorting first only pays off if you then search many times.
Exercise 2 — fix the month-end report ★★☆ consultant skill

Two systems each export 50,000 customer IDs, half of them shared. A report counts the shared IDs with a.iter().filter(|x| b.contains(x)).count(). Rewrite it to be O(n + m), then measure both versions.

Hint: use std::collections::HashSet; then let in_b: HashSet<u64> = b.iter().copied().collect(); builds the set once.

Show solution 
use std::collections::HashSet;
use std::time::Instant;

/// O(n·m): for every id in `a`, scan all of `b`.
fn common_nested(a: &[u64], b: &[u64]) -> usize {
    a.iter().filter(|x| b.contains(x)).count()
}

/// O(n + m) expected: put `b` in a hash set once, then each lookup is O(1).
fn common_hashed(a: &[u64], b: &[u64]) -> usize {
    let in_b: HashSet<u64> = b.iter().copied().collect();
    a.iter().filter(|x| in_b.contains(x)).count()
}

fn main() {
    // Two systems' customer ids: 50,000 each, half of them shared.
    let a: Vec<u64> = (0..50_000).collect();
    let b: Vec<u64> = (25_000..75_000).collect();

    let start = Instant::now();
    let n1 = common_nested(&a, &b);
    let t1 = start.elapsed();

    let start = Instant::now();
    let n2 = common_hashed(&a, &b);
    let t2 = start.elapsed();

    assert_eq!(n1, n2);
    println!("common ids: {n1}");
    println!("nested: {:>8.1} ms", t1.as_secs_f64() * 1000.0);
    println!("hashed: {:>8.1} ms", t2.as_secs_f64() * 1000.0);
}
common ids: 25000
nested:    161.1 ms
hashed:      1.1 ms

About 150× faster at this size, and the gap widens as data grows: double both lists and the nested version takes about 4× longer, the hashed one about 2×. The same fix applies in C#: build a HashSet<T> from b once, then test membership.

Exercise 3 — why doubling? ★★☆

Suppose a growable array added a fixed 100 slots whenever it was full, instead of doubling. How many element copies would 1,000,000 pushes cost? What's the amortised cost per push, and its complexity class?

Show solution

Reallocations happen at sizes 100, 200, …, 999,900, copying \(100 \cdot (1 + 2 + \dots + 9999) = 100 \cdot \tfrac{9999 \cdot 10000}{2} = 4{,}999{,}500{,}000\) elements, about 5,000 copies per push. The total grows as n²/200, so it's O(n²) total and O(n) amortised per push. Doubling gives about 1 copy per push, O(1). A simulation agrees exactly:

/// Count element copies needed to push `n` items when a full buffer grows by `grow(cap)`.
fn copies(n: u64, grow: impl Fn(u64) -> u64) -> u64 {
    let (mut len, mut cap, mut copied) = (0u64, 0u64, 0u64);
    while len < n {
        if len == cap {
            copied += len; // move everything into the bigger buffer
            cap = grow(cap);
        }
        len += 1;
    }
    copied
}

fn main() {
    let n = 1_000_000;
    let doubling = copies(n, |c| if c == 0 { 4 } else { c * 2 });
    let plus_100 = copies(n, |c| c + 100);
    println!("doubling: {doubling:>13} copies ({:.2} per push)", doubling as f64 / n as f64);
    println!("+100:     {plus_100:>13} copies ({:.0} per push)", plus_100 as f64 / n as f64);
}
doubling:       1048572 copies (1.05 per push)
+100:        4999500000 copies (5000 per push)

Notice the doubling simulation reproduces the real Vec measurement from Step 2 exactly (1,048,572). The key insight: any constant factor of growth (×1.5, ×2) gives amortised O(1); any constant amount of growth (+100) gives O(n).

Common misconceptions and pitfalls

⚠️ "O(1) means fast."

It means doesn't grow. A hash lookup is O(1) expected but costs more than scanning a 4-element array. Figure 3 shows the O(n²) method winning at n = 10.

⚠️ "Average case is what matters."

For a service, the tail matters: p99 latency, SLAs and adversarial inputs. Know the worst case of every algorithm on your request path.

⚠️ Hidden loops in one-liners

List.Contains, vec.contains, Vec::insert(0, x) (O(n): shifts everything) and string concatenation in a loop each hide an O(n) inside an innocent-looking call.

⚠️ "Amortised O(1) means every call is fast."

Individual calls can be O(n): the push that triggers a million-element copy. For hard latency bounds, pre-size with with_capacity, or use structures without big reallocations.

⚠️ "Testing with small data proves it scales."

The O(n²) report in Exercise 2 takes 0.3 µs at n = 10 and looks perfect in every unit test. Always test with production-sized, and worst-case-shaped, data.

Real-world view: complexity decisions in your products

🏗 Architecture view
  • Rule engine matching. The naive approach re-checks every rule against every fact whenever anything changes: O(rules × facts) per change. With 1,000 rules and 1,000,000 facts that's 10⁹ checks per update. The Rete algorithm (chapter 9.4) exists to make the cost proportional to what changed instead.
  • Workflow timers. Scanning all pending timers every tick is O(n) per tick. A priority queue (chapter F5) finds the next due timer in O(1) and inserts in O(log n), so a million timers cost about 20 steps per insert.
  • Customer-supplied expressions. Anything customers write (rule conditions, regexes, JSON paths) needs a provable worst case and size limits. The deep dive's 10-second regex is a production outage waiting to happen.
  • The N+1 query problem is a complexity bug across a network: O(n) round trips, each costing milliseconds, where O(1) batched query would do. The same analysis applies to I/O as to CPU steps.

Summary

  • Complexity describes how cost grows with input size n. Big-O is an upper bound, Ω a lower bound, Θ a tight bound, ignoring constants and smaller terms.
  • The common classes, from best to worst: O(1), O(log n), O(n), O(n log n), O(n²), O(2ⁿ). Halving gives logs, nesting multiplies, and library calls have costs too (contains is a loop).
  • Amortised cost averages over a sequence: Vec::push is amortised O(1) because capacity grows by a factor (measured: 1.05 copies per push). Expected cost (HashMap) assumes well-behaved hashing.
  • Constants and caches decide small-n performance: the O(n²) method won at n = 10, and lost by about 1,500× at n = 100,000. Use complexity to eliminate designs, and measurement to choose among the rest.
  • Exponential behaviour hides in innocent code. A backtracking regex took 10 s on 26 characters. On untrusted input, require a proven worst case (Rust's regex guarantees O(m·n)).
