Modules, crates and packages

Learning objectives

  • Distinguish packages, crates (library and binary) and modules, and map each to its .NET counterpart
  • Lay out a multi-file crate: how mod declarations map to files, and the errors you get when they don't
  • Control visibility with private items, pub, pub(crate), pub(super) and pub(in path), and predict what code can see what
  • Write paths (crate::, self::, super::, external crates) and every form of use
  • Design a crate's public API with re-exports (pub use) and a prelude, independent of its internal file layout

Why this matters

💡 Why this matters

So far every program has lived in one file. Your rule engine and workflow engine will be tens of thousands of lines across many files and several crates, with a public API that customers build against and internals you need to be free to change. In .NET you organise that with a solution, projects, namespaces and the public/internal keywords, and namespaces in particular carry no protection at all: Microsoft's own docs say "Namespaces have no access restrictions."

Rust's equivalent is smaller and stricter. A module is both a namespace and a privacy boundary. Everything is private unless you say otherwise, and a crate's public API is exactly the set of items you chose to expose, whatever its file layout. Get this right and you can refactor freely behind a stable API. Get it wrong and every internal type becomes a promise you can't break without a major version bump (chapter 3.5).

Intuition first: the company, the departments and the reception desk

🧭 Analogy
  • A package is a company, with one registration document (Cargo.toml).
  • A crate is a building the company runs: at most one office building that other companies can visit (the library crate), and any number of factories that each make one product you can run (binary crates). Visitors from outside only ever see the lobby.
  • Modules are departments and rooms inside a building, nested like an org chart. By default every room is staff-only. A department can see into its own sub-rooms, and sub-rooms can see their parent's rooms, but other departments can't walk in.
  • pub puts a door on the corridor; pub(crate) means staff badges only; pub(super) means "the department next level up may come in".
  • Re-exports are the reception desk: visitors ask for "the engine" at the front desk, and never need to know it lives in room 3.14 of the east wing. You can move the room; reception still answers.

Core explanation

Basic

Crates and packages

The Book's definitions, which you'll hear people use loosely and should use precisely:

  • "A crate is the smallest amount of code that the Rust compiler considers at a time." It's either a library crate ("Library crates don't have a main function, and they don't compile to an executable") or a binary crate, a program with a main. Each crate has a crate root, the file the compiler starts from.
  • "A package is a bundle of one or more crates that provides a set of functionality. A package contains a Cargo.toml file that describes how to build those crates." And: "A package can contain as many binary crates as you like, but at most only one library crate."

Cargo finds the crates by convention. src/lib.rs is the library crate's root, src/main.rs is a binary crate's root, and "each file [in src/bin] will be a separate binary crate". All of them are named after the package unless configured otherwise. Lab step 1's cargo build -v shows the compiler being invoked three times for one package: once for the library, then once per binary, each binary linking the library with --extern. A binary crate in the same package is not inside the library. It uses the library through its public API exactly as another company's code would, which makes it a good test of that API.

Modules and the module tree

Inside a crate, code is organised into a tree of modules. The crate root is the top module, called crate. You declare a module with mod, either inline:

mod billing {
    pub fn total(net: u32) -> u32 {
        net + vat(net)
    }
    fn vat(net: u32) -> u32 {
        net * 21 / 100 // private: only billing (and its children) can call it
    }
}

fn main() {
    println!("{}", billing::total(10_000));
}

or, as soon as it grows, in its own file: mod billing; with a semicolon tells the compiler to load the module's contents from a file. The rules, for a module engine declared in the crate root:

  • The compiler looks for src/engine.rs, or the older style src/engine/mod.rs. Having both is error E0761; having neither is E0583 (Lab step 2).
  • A child module declared inside src/parser.rs (mod lexer;) lives in src/parser/lexer.rs. Since the 2018 edition "a foo.rs and foo/ subdirectory may coexist; mod.rs is no longer needed", and parser.rs + parser/lexer.rs is the modern layout.
  • A file is never compiled just because it exists. It becomes part of the crate only when some module declares it with mod. This is the opposite of a C# project, where every .cs file in the folder is compiled. A forgotten mod line means "unused file", not "missing class".
  • A module is declared once, by its parent. Elsewhere you refer to it with a path or use, never a second mod; the E0583 help says exactly that.

Visibility: private by default

The Reference: "By default, everything is private, with two exceptions: Associated items in a pub Trait are public by default; Enum variants in a pub enum are also public by default." Private means visible in the current module and its descendants. Two rules decide every access:

  1. "If an item is public, then it can be accessed externally from some module m if you can access all the item's ancestor modules from m."
  2. "If an item is private, it may be accessed by the current module and its descendants."

So visibility runs down the tree: children see their ancestors' private items, so a child module can be a private helper of its parent with full access, but parents don't see their children's privates. And rule 1 means a pub fn inside a private module is still unreachable from outside that module's parent, because the path to it is blocked. Between private and pub there are scoped levels:

WrittenVisible inC# nearest

Two details matter for struct design. Making a struct pub doesn't make its fields public: each field is private unless marked pub. And if any field is private, code outside the module can't build the struct with a literal (error E0451) or read that field (E0616). It must go through a constructor, which is how a type enforces its invariants (Lab step 2). Enum variants, by contrast, are public with the enum, because a match outside the module must be able to name them.

Paths and use

Every item has a path, and there are four ways to start one:

  • crate::model::Rule: absolute, from this crate's root. Robust when code moves within a module.
  • self::tax::rate and plain tax::rate: relative to the current module.
  • super::DEFAULT_RATE: from the parent module, like .. in a file path.
  • std::collections::HashMap, ruleset::Engine: from another crate, by name. Dependencies in Cargo.toml are available this way without any extern crate line (unneeded "in 99% of circumstances" since Rust 2018). A leading ::std::… forces the external-crate meaning if a local module has the same name.

A use declaration brings a path's last name into scope so you don't repeat it. Unlike C#'s using, it imports any item (a type, a function, a module, an enum variant), not just namespaces. Lab step 3 shows all of its forms:

use std::collections::{BTreeMap, HashMap}; // several names from one module
use std::fmt::{self, Display};             // the module itself, plus an item
use std::io::Result as IoResult;           // rename to avoid a clash
use std::collections::*;                   // glob: everything public (use sparingly)

fn main() {
    let a: HashMap<u8, u8> = HashMap::new();
    let b: BTreeMap<u8, u8> = BTreeMap::new();
    let c: VecDeque<u8> = VecDeque::new(); // came from the glob
    let r: IoResult<()> = Ok(());
    println!("{} {} {} {:?} {}", a.len(), b.len(), c.len(), r, &1 as &dyn Display);
    let _ = fmt::Error;
}

Conventions the community follows (and rustfmt and Clippy nudge you towards): import types by their own name (use std::collections::HashMap; then HashMap::new()), but import functions by their parent module (use std::mem; then mem::take(…)), so a call site shows where the function comes from. Some names need no import at all: the prelude (Vec, String, Option/Some/None, Result/Ok/Err, Box, the common traits) is in scope in every module. Forgetting a use gives error E0433, with the exact line to add (Lab step 2).

🟣 Coming from C#/.NET
  • Namespaces vs modules. A C# namespace is only a name, and any number of assemblies can add types to it. A Rust module is a single place in one crate's tree, with privacy attached. There's no partial module spread across crates.
  • Defaults. In C#, top-level types default to internal and class members to private (Microsoft Learn). In Rust everything, items and fields alike, defaults to private to its module, a finer grain than the assembly.
  • internal ↔ pub(crate). Lab step 4 shows C# rejecting access to an internal class from another assembly with CS0122. For an internal constructor, though, it reports CS1729, "does not contain a constructor that takes 1 arguments", hiding the constructor rather than saying it's inaccessible. Rust's errors name the item and say it's private (E0624).
  • No InternalsVisibleTo. Rust unit tests live inside the crate (a #[cfg(test)] mod tests, chapter 3.4) and see private items as descendants; integration tests in tests/ are separate crates and see only the public API, deliberately.
  • Compilation by declaration. A C# project compiles every .cs file in its folder; a Rust crate compiles only files reached through mod declarations.

The two cases that surprise C# developers most: a::c::pub_fn is pub, yet unreachable from the crate root, because module c is private to a (rule 1); and a::b::super_fn, marked pub(super), can be called from a and from a::b::d, but not from x or the crate root.

Re-exports and preludes: designing the public API

Without re-exports, a crate's public paths mirror its files: ruleset::engine::Engine, ruleset::parser::parse_rule. That leaks the layout into every caller, and moving a file becomes a breaking change. A re-export, pub use, publishes an item under a new path:

  • pub use engine::{Engine, Verdict}; in lib.rs makes them ruleset::Engine and ruleset::Verdict, while engine stays a private module that you can split, rename or reorganise at will. Lab step 1's cargo doc output shows the result: the documented API is exactly the re-exported items plus the pub modules, and engine, parser and lexer don't appear. Error e1 shows the other side: ruleset::engine::Engine is rejected, with the note "struct Engine is not publicly re-exported" through that path.
  • A pub mod prelude { pub use …; } collects what a typical caller needs, so they write use ruleset::prelude::*; once. The standard library, tokio, bevy and many others do this. Keep a prelude small: everything in it lands in callers' scopes through a glob.

The design rule for both products: decide the public API first, as a small set of re-exported names, and keep every module private unless callers genuinely need to navigate it. Chapter 3.5 adds the semantic-versioning consequences: everything reachable is a promise.

Deep dive: the module system as information hiding

David Parnas's 1972 paper "On the criteria to be used in decomposing systems into modules" argued that a system should be split along decisions likely to change, with each module hiding one such decision behind an interface. Rust's design builds that in: the default is hidden, every widening of visibility is explicit and scoped (pub(super), pub(crate)), and re-exports separate the interface (the paths callers use) from the decomposition (the files). The lexer in Lab step 1 is a small example: Token and tokenize are pub(super), so only the parser knows tokens exist at all, and you could replace the lexer with a hand-written state machine without touching any other module.

The compiler enforces one more Parnas-style rule. A pub function can't expose a type that's less visible than itself in its signature (the private_interfaces and private_bounds lints warn about it). That stops a public API from leaking a type callers can't name.

Deep dive: one crate or several?

Modules organise code inside a crate; crates are the unit of compilation, of parallelism in the build, of dependency, and of pub(crate) privacy. Signs that a module wants to become its own crate in a workspace (chapter 3.5): it's useful on its own (the rule language parser, without the engine); it has heavy dependencies that most of the code doesn't need; or build times suffer because a small change recompiles one huge crate. The cost: anything shared across the boundary must be pub, and the API becomes a real contract. A common shape for your products is a workspace of a few crates, for example rules-core (model, parser), rules-engine, rules-server (binary), each with a deliberately small public API.

//! The rule data model.

#[derive(Debug, Clone, Copy, PartialEq)]
pub enum Op {
    Gt,
    Ge,
    Eq,
}

#[derive(Debug, Clone, PartialEq)]
pub struct Rule {
    pub field: String,
    pub op: Op,
    pub value: i64,
    source_line: usize, // private: callers can read it through a method, never set it
}

impl Rule {
    // pub(crate): the parser (same crate) may construct rules; other crates may not.
    pub(crate) fn new(field: &str, op: Op, value: i64, source_line: usize) -> Rule {
        Rule { field: field.to_string(), op, value, source_line }
    }

    pub fn source_line(&self) -> usize {
        self.source_line
    }
}
//! Turns rule text into `Rule`s.

mod lexer; // a child module: src/parser/lexer.rs

use crate::model::{Op, Rule}; // absolute path from the crate root
use lexer::{Token, tokenize}; // relative path into the child module

#[derive(Debug, PartialEq)]
pub enum ParseError {
    Shape(usize),
    UnknownOperator(usize, String),
    BadNumber(usize),
}

pub fn parse_rule(line_no: usize, text: &str) -> Result<Rule, ParseError> {
    let tokens = tokenize(text);
    let [Token::Word(field), Token::Symbol(op), Token::Word(value)] = tokens.as_slice() else {
        return Err(ParseError::Shape(line_no));
    };
    let op = match op.as_str() {
        ">" => Op::Gt,
        ">=" => Op::Ge,
        "==" => Op::Eq,
        other => return Err(ParseError::UnknownOperator(line_no, other.to_string())),
    };
    let value = value.parse().map_err(|_| ParseError::BadNumber(line_no))?;
    Ok(Rule::new(field, op, value, line_no))
}
//! Splits rule text into tokens. Only the parser needs this.

#[derive(Debug, PartialEq)]
pub(super) enum Token {
    Word(String),
    Symbol(String),
}

// pub(super): visible to the parent module (parser), and nowhere else.
pub(super) fn tokenize(text: &str) -> Vec<Token> {
    text.split_whitespace()
        .map(|t| {
            if t.chars().all(|c| "<>=!".contains(c)) {
                Token::Symbol(t.to_string())
            } else {
                Token::Word(t.to_string())
            }
        })
        .collect()
}
//! Evaluates rules against facts.

use std::collections::HashMap;

use crate::model::{Op, Rule};

#[derive(Debug, PartialEq)]
pub enum Verdict {
    Pass,
    Fail,
    MissingField(String),
}

pub struct Engine {
    rules: Vec<Rule>, // private: the engine controls its own rule list
}

impl Engine {
    pub fn new(rules: Vec<Rule>) -> Engine {
        Engine { rules }
    }

    pub fn evaluate(&self, facts: &HashMap<&str, i64>) -> Vec<(usize, Verdict)> {
        self.rules.iter().map(|r| (r.source_line(), check(r, facts))).collect()
    }
}

// Private helper: not visible outside this module.
fn check(rule: &Rule, facts: &HashMap<&str, i64>) -> Verdict {
    let Some(&actual) = facts.get(rule.field.as_str()) else {
        return Verdict::MissingField(rule.field.clone());
    };
    let ok = match rule.op {
        Op::Gt => actual > rule.value,
        Op::Ge => actual >= rule.value,
        Op::Eq => actual == rule.value,
    };
    if ok { Verdict::Pass } else { Verdict::Fail }
}
// The binary crate: a separate crate that uses the library by its package name.
use std::collections::HashMap;

use ruleset::prelude::*;

fn main() {
    let text = "amount >= 100\ncountry == 31\nvip => 1\nscore > lots";
    let mut rules = Vec::new();
    for (i, line) in text.lines().enumerate() {
        match parse_rule(i + 1, line) {
            Ok(rule) => rules.push(rule),
            Err(e) => println!("skipped: {e:?}"),
        }
    }
    let first: &Rule = &rules[0];
    println!("loaded {} rules; first: {} {:?} {} (line {})", rules.len(), first.field, first.op, first.value, first.source_line());

    let engine = Engine::new(rules);
    let facts = HashMap::from([("amount", 250), ("vip", 1)]);
    for (line, verdict) in engine.evaluate(&facts) {
        println!("line {line}: {verdict:?}");
    }
    assert_eq!(engine.evaluate(&facts)[0].1, Verdict::Pass);
}
// A second binary in the same package: src/bin/*.rs files are binary crates too.
use ruleset::model::Op; // the public module path works as well as the prelude

            Op::Gt => "greater than",

Step 3 — every form of path and use

// Every form of `use` and of paths, in one file (inline modules: `mod name { ... }`).
use std::collections::{BTreeMap, HashMap}; // a nested group
use std::fmt::{self, Display}; // `self` imports the module itself too
use std::io::Result as IoResult; // rename with `as` to avoid a clash with Result

mod billing {
    pub mod tax {
        pub fn rate(country: &str) -> u32 {
            match country {
                "NL" => 21,
                "DE" => 19,
                _ => super::DEFAULT_RATE, // super: the parent module (billing)
            }
        }
    }

    const DEFAULT_RATE: u32 = 20; // private to billing, visible to its child `tax`

    pub fn total(net: u32, country: &str) -> u32 {
        net + net * self::tax::rate(country) / 100 // self: this module
    }
}

struct Money(u32);

impl Display for Money {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        write!(f, "€{}.{:02}", self.0 / 100, self.0 % 100)
    }
}

fn read_config() -> IoResult<String> {
    Ok(String::from("ok")) // String, Ok and Vec need no import: they're in the prelude
}

fn main() {
    use billing::tax::rate; // `use` works inside a function too, scoped to it
    use crate::billing::total; // absolute path from this crate's root

    let mut by_country: HashMap<&str, u32> = HashMap::new();
    let mut sorted = BTreeMap::new();
    for c in ["NL", "DE", "BE"] {
        by_country.insert(c, total(10_000, c));
        sorted.insert(c, rate(c));
    }
    println!("rates (sorted): {sorted:?}");
    println!("NL total: {}", Money(by_country["NL"]));
    println!("::std path: {}", ::std::cmp::max(3, 7)); // leading :: = an external crate's root
    println!("config: {:?}", read_config());
}

Step 4 — the same boundary in .NET

namespace RulesLib.Model
{
    public class Rule
    {
        public string Field { get; }
        internal Rule(string field) => Field = field; // like pub(crate): only this assembly
    }
}

namespace RulesLib.Parsing
{
    internal static class Lexer // like a private module: invisible outside the assembly
    {
        public static string[] Tokenize(string s) => s.Split(' ');
    }

    public static class Parser
    {
        public static Model.Rule Parse(string s) => new Model.Rule(Lexer.Tokenize(s)[0]);
    }
}

The assembly boundary works like Rust's crate boundary for internal types (CS0122). Notice what's missing: RulesLib.Parsing and RulesLib.Model are just names. Any type in the same assembly can use any internal member in any namespace, and there's no way to say "only the parser may create rules" short of a separate assembly or nesting classes. Rust's pub(crate), pub(super) and private modules express exactly that, inside one crate.

mod workflow {
    pub struct Step {
        name: String,
        attempts: u32,
    }

    impl Step {
        pub fn new(name: &str) -> Step {
            Step { name: name.to_string(), attempts: 0 }
        }

        // Read-only access instead of making the fields public.
        pub fn name(&self) -> &str {
            &self.name
        }

        pub fn attempts(&self) -> u32 {
            self.attempts
        }
    }

    mod retry {
        // pub(super): the parent (workflow) may call it; nothing else can.
        pub(super) fn should_retry(step: &super::Step) -> bool {
            step.attempts < 3 // a child module may read its ancestor's private fields
        }
    }

    pub fn run(step: &mut Step) -> bool {
        step.attempts += 1;
        retry::should_retry(step)
    }
}

fn main() {
    let mut s = workflow::Step::new("charge");
    println!("retry? {}", workflow::run(&mut s));
    println!("{} attempts on {}", s.attempts(), s.name());
}
retry? true
1 attempts on charge

new must be pub for main to construct a step. The fields stay private, and read-only accessor methods give main what it needs without letting it change them. should_retry becomes pub(super), visible to workflow (where run calls it) and nowhere else; plain pub would also compile, because retry is private, but pub(super) states the intent. Notice that should_retry reads step.attempts, a private field of Step, without any change: retry is a descendant of workflow, where Step is defined.

Exercise 2 — design a crate's public API ★★☆ product skill

A workflow library has three internal modules: state (an enum), step (a struct with a private state field) and engine (a run_all function). Arrange visibility and re-exports so that callers write use flow::prelude::*; and can use Step, State and run_all, while all three modules stay private. Write it as inline modules so it runs as one file.

Show solution 
// The library, written inline so the solution runs as one file. In a real crate each
// `mod x { ... }` below is its own file and `mod flow` is the crate root (lib.rs).
mod flow {
    mod state {
        #[derive(Debug, Clone, PartialEq)]
        pub enum State {
            Pending,
            Running { attempt: u32 },
            Completed,
        }
    }

    mod step {
        use super::state::State;

        #[derive(Debug)]
        pub struct Step {
            pub name: String,
            state: State,
        }

        impl Step {
            pub fn new(name: &str) -> Step {
                Step { name: name.to_string(), state: State::Pending }
            }
            pub fn state(&self) -> &State {
                &self.state
            }
            pub fn start(&mut self) {
                self.state = State::Running { attempt: 1 };
            }
            pub fn complete(&mut self) {
                self.state = State::Completed;
            }
        }
    }

    mod engine {
        use super::step::Step;

        pub fn run_all(steps: &mut [Step]) -> usize {
            for s in steps.iter_mut() {
                s.start();
                s.complete();
            }
            steps.len()
        }
    }

    // The public API: flat, short paths, independent of the files above.
    pub use engine::run_all;
    pub use state::State;
    pub use step::Step;

    pub mod prelude {
        pub use super::{State, Step, run_all};
    }
}

use flow::prelude::*;

fn main() {
    let mut steps = vec![Step::new("validate"), Step::new("charge")];
    println!("before: {:?}", steps[0].state());
    let n = run_all(&mut steps);
    println!("ran {n} steps; {} is {:?}", steps[1].name, steps[1].state());
    assert_eq!(steps[1].state(), &State::Completed);
    println!("ok");
}
before: Pending
ran 2 steps; charge is Completed
ok

The three modules are private; the items inside them are pub, which makes them visible to the parent flow, but outsiders can't reach them through the private module paths. The pub use lines then publish them at flow::Step and so on, and the prelude re-exports those again. Inside the library, sibling modules use each other with super::state::State. Split into files, this is exactly lib.rs + state.rs + step.rs + engine.rs, and you can later move Step into step/model.rs without changing a single caller.

Show solution 
(a) compiles   tax is a child of billing; children see their ancestors' private items
(b) compiles   pub(super) in tax = visible in billing, where close() is
(c) compiles   ledger is private to billing, and close() is inside billing

Common misconceptions and pitfalls

⚠️ Creating a file and expecting it to compile

Nothing happens until its parent declares mod name;. And declare each module once: elsewhere, refer to it with use crate::…, never a second mod.

⚠️ "It's pub, so it's public"

Only if every module on its path is reachable (rule 1). Conversely, a pub item in a private module is a convenient way to share something among siblings without exposing it.

⚠️ Making every module pub to fix errors

Each pub mod turns a file layout into public API. Keep modules private and re-export the items callers need.

⚠️ pub fields on types with invariants

If a Lease must always have an expiry after its start, public fields let anyone break that. Private fields plus a validating constructor make invalid values unrepresentable outside the module (chapter F8).

⚠️ Glob imports in library code

use some_crate::*; can silently change meaning when that crate adds a name. Use globs for preludes, tests and enum variants in a match, and explicit imports elsewhere.

⚠️ Expecting mod.rs

Both layouts work, but don't mix them for one module (E0761). New code uses name.rs + name/, so editor tabs don't all read mod.rs.

Real-world view: structuring your products

🏗 Architecture view
  • Rule engine: a small public API at the crate root (Engine, Rule, parse, EvalError, a prelude), with private modules for the lexer, parser, compiler and evaluator. pub(crate) constructors guarantee that every compiled rule passed validation.
  • Workflow engine: a workspace of crates: a core crate (state machine, events), a persistence crate, a worker binary and an SDK crate for customers. The SDK's public API is the product; everything else stays pub(crate) or private (chapters 3.5, 10.8).
  • API stability: re-exports let you reorganise internals between releases without breaking customers; anything reachable is covered by semver (chapter 3.5).
  • Documentation: cargo doc documents exactly the public API, so reviewing its output is a quick check that nothing leaked (Lab step 1).
  • Review checklist: pub mod that should be private with re-exports; pub fields on types with invariants; pub where pub(crate) would do; glob imports in library code; files without mod declarations; public functions exposing less-visible types.

Summary

  • A package (Cargo.toml) holds at most one library crate (src/lib.rs) and any number of binary crates (src/main.rs, src/bin/*.rs); binaries use the library by name, through its public API.
  • Modules form a tree from the crate root, built by mod declarations: mod x; loads x.rs (or x/mod.rs), and children live in x/. Files without a mod line aren't compiled (E0583 and E0761 for missing or ambiguous files).
  • Everything is private by default, visible in its module and descendants; pub(super), pub(in path), pub(crate) and pub widen it, and a public item is reachable only if every module on its path is. Fields are private separately from their struct (E0451, E0616).
  • Paths start at crate::, self::, super:: or another crate's name; use imports any item, with groups, self, as and globs; the std prelude needs no import.
  • pub use re-exports and a prelude module define a small, stable public API independent of the file layout. Unlike C# namespaces, Rust modules enforce privacy.
