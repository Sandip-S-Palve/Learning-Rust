Concurrency concepts

Learning objectives

  • Distinguish concurrency from parallelism, and processes from threads, and explain what the OS scheduler does with them
  • Tell a data race from a race condition, and say which one safe Rust rules out and which it can't
  • Use locks correctly, recognise the four conditions for deadlock, and prevent it with lock ordering
  • Explain what an atomic operation is, when it beats a lock, and why sharing itself is the expensive part
  • Classify work as CPU-bound or I/O-bound and pick threads or async tasks accordingly
  • Explain how an event loop works, and the difference between readiness I/O (epoll, kqueue) and completion I/O (IOCP, io_uring)

Why this matters

💡 Why this matters

A workflow engine is concurrency in product form. Thousands of workflow runs are in flight at once, most of them waiting: for a timer, an HTTP call, a human approval. A handful of worker threads must keep all of them moving without two workers executing the same step, without losing an update to a run's state, and without freezing when two runs need the same resource. A rule engine adds the other half: evaluating a large rule set over many facts is pure computation that should use every core.

In .NET you already use Task, async/await, lock and ConcurrentDictionary, often without needing the vocabulary underneath. Rust asks for that vocabulary. Its headline promise, "fearless concurrency", is precise: the compiler rules out data races, but not race conditions or deadlocks. You'll measure both in this chapter. As a consultant you'll also be asked "should this service use threads or async?" and "why does Tokio behave differently from the .NET thread pool?" Module 4 answers those for Rust; this chapter gives you the concepts they rest on.

Intuition first: a restaurant kitchen

🧭 Analogy
  • One chef, three dishes is concurrency: start the soup, while it simmers chop the salad, check the oven. Three dishes are in progress; only one thing happens at any instant. It works because most of each dish's time is waiting.
  • Three chefs is parallelism: three things genuinely happen at the same instant. It only helps if there's enough work to keep three pairs of hands busy.
  • One shared notepad of orders is shared state. If two chefs both read "12 portions left", both write "11", one portion vanishes from the count. That's a lost update.
  • A key to the notepad's drawer is a lock. And if chef A holds the knife and waits for the board, while chef B holds the board and waits for the knife, nobody cooks again. That's a deadlock.
  • A waiter who doesn't stand at one table, but walks to whichever table rang its bell, is an event loop. One waiter serves twenty tables because tables spend most of their time not needing anything.

Core explanation

Basic

Processes and threads

A process is a running program with its own private address space (chapter F1): its own code, heap and globals, plus OS resources such as open files and sockets. One process can't read another's memory; they talk through files, pipes or sockets. A crash in one process doesn't corrupt another. That isolation is why browsers run each site in its own process, and why "one container per service" works.

A thread is an independent line of execution inside a process. Every thread has its own stack (chapter F1: its own call frames and local variables) and its own CPU register values, but all threads of a process share the same heap and globals. That's what makes threads fast to communicate, since they just read the same memory, and what makes them dangerous: they can read the same memory at the same time. Rust's spawned threads currently get a 2 MiB stack on all Tier-1 platforms (per the std::thread docs). That's mostly reserved virtual memory, not touched RAM, but it's why "one OS thread per request" stops scaling somewhere in the thousands.

Scheduling

Your machine has a few cores (the lab Mac has 10: 6 performance and 4 efficiency cores) and the OS has hundreds of threads. The scheduler decides which thread runs on which core, and for how long. Two styles matter:

  • Preemptive (OS threads): the OS gives a thread a time slice, then a timer interrupt can stop it at any instruction and run another thread. A thread in an infinite loop can't freeze the machine. The cost: your code can be paused between any two instructions, including in the middle of what looks like a single line, such as counter += 1.
  • Cooperative (async tasks): a task runs until it voluntarily gives control back, in Rust and C# at an .await. Switching is very cheap, but a task that computes for a long time without awaiting holds its thread hostage, and every other task scheduled on that thread waits (chapter 4.7's spawn_blocking exists for exactly this).

Switching between threads (a context switch) means saving one thread's registers, restoring another's, and usually running with cold caches (chapter F1). That costs on the order of microseconds. Creating a thread costs more: Lab step 5 measured about 19 µs to spawn and join an OS thread, against 0.19 µs for a Tokio task, about 100× less.

Data races and race conditions

Here's the bug every concurrent system meets first. counter += 1 looks like one step, but the CPU executes three: load the value into a register, add one, store it back. If two threads interleave those steps, one increment can be lost. You are the scheduler below:

Two terms describe what went wrong, and the difference is central to Rust:

  • A data race is a specific, low-level event. The Rustonomicon defines it as two or more threads concurrently accessing a location of memory, where one or more of them is a write and one or more of them is unsynchronised. In Rust, C and C++ a data race is undefined behaviour (chapter 0.1): the compiler and CPU are allowed to assume it never happens, so the program may do anything. In .NET a data race isn't undefined behaviour: you get wrong numbers, as Lab step 1 shows, but memory safety holds.
  • A race condition is any bug where the outcome depends on timing. It can happen with no data race at all, when every individual access is synchronised but the combination isn't atomic. The classic shape is check-then-act: "if seats are left, take one" done as two separate steps.

Safe Rust guarantees no data races, at compile time. The program in Lab step 1 that lets four threads write one variable doesn't compile. It does not guarantee no race conditions. The Rustonomicon says so plainly: preventing general race conditions is "mathematically impossible" when you don't control the scheduler. Lab step 2 demonstrates it. A counter made of atomic loads and stores, each one perfectly synchronised, still loses about 3 million of 4 million updates, because "load, then store" is two operations.

🟣 Coming from C#/.NET

The C# compiler accepts the racy counter++ from several threads without a word (Lab step 1). Thread safety in .NET is a matter of documentation ("instance members are not guaranteed to be thread safe") and review. In Rust it's part of the type system. Two marker traits, Send ("may be moved to another thread") and Sync ("may be shared between threads"), are worked out automatically for every type, and APIs like thread::spawn require them. Try to send an Rc (a non-atomic reference count) to another thread and you get error E0277 (Lab step 1). Chapter 4.1 covers these traits in full.

Locks

The basic fix is mutual exclusion: make the whole read-modify-write a critical section that only one thread can be inside at a time. A mutex (mutual-exclusion lock) does that: a thread acquires it, others trying to acquire it wait, and it's released on the way out. In C# you write lock (gate) { … }; since .NET 9 the recommended lock object is the dedicated System.Threading.Lock type.

Rust's Mutex<T> differs in one important way: the mutex owns the data it protects. In C# the lock and the data are separate objects connected only by convention, and nothing stops a method from touching the data without taking the lock. In Rust the only way to reach the u64 inside a Mutex<u64> is through lock(), which returns a guard. The guard releases the lock automatically when it goes out of scope (RAII, chapter 2.2), so "forgot to unlock" and "forgot to lock" both become impossible:

C#
private readonly Lock _gate = new();
private long _count;          // protected by _gate… by convention

void Add()
{
    lock (_gate) { _count++; }
}
void Oops() => _count++;      // compiles; no lock taken
Rust
let count = Mutex::new(0u64); // the data lives INSIDE the lock

{
    let mut guard = count.lock().unwrap();
    *guard += 1;
} // guard dropped here: unlocked automatically

// There is no way to reach the u64 without lock().

Variants you'll meet: a reader-writer lock (RwLock, like .NET's ReaderWriterLockSlim) lets many readers in at once or one writer; and message passing avoids shared state altogether by sending values through a channel to the one thread that owns them, the actor style (chapters 4.2 and 8.4). Locks have costs: threads waiting on a contended lock do no useful work (contention), and a lock held for too long serialises your program. The rule of thumb is to hold locks briefly and never across slow operations: I/O, an .await, or a call into code you don't control.

Deadlock

A deadlock is a set of threads each waiting for something another one holds, so none of them can ever proceed. Coffman, Elphick and Shoshani's 1971 survey gave the four conditions that must all hold:

  1. Mutual exclusion: a resource can be held by only one thread.
  2. Hold and wait: a thread holds one resource while waiting for another.
  3. No preemption: a resource can't be taken away; it's only released voluntarily.
  4. Circular wait: there's a cycle of threads, each waiting for the next one's resource.

Break any one and deadlock is impossible. The practical lever is usually the fourth. Draw a wait-for graph (threads and locks as vertices, "holds" and "waits for" as edges) and a deadlock is exactly a cycle, the same cycle detection as in chapter F6. Impose a global lock order (always lock account A before account B, say by lowest ID) and no cycle can form.

Other defences: try_lock or a lock with a timeout (gives up "no preemption" by backing off), holding at most one lock at a time where possible, and never calling unknown code (callbacks, plugins) while holding a lock. Rust doesn't prevent deadlocks. The Rustonomicon explicitly classes deadlocking as "safe": wrong, but not memory-unsafe.

Intermediate

Atomics: indivisible operations

An atomic operation is one the CPU performs as a single indivisible step: no other core can see it half-done. Modern CPUs provide atomic read-modify-write instructions, and both platforms expose them. .NET has Interlocked.Increment, Interlocked.CompareExchange and friends. Rust has types like AtomicU64, AtomicBool and AtomicUsize with methods such as:

  • fetch_add(1): add and return the old value, all in one step. It fixes the counter.
  • compare-and-swap (CAS; Rust compare_exchange(expected, new)): write new only if the value is still expected, otherwise report what it actually is. It's the tool for check-then-act. "If seats are left, take one" becomes a loop that retries when another thread got there first (Exercise 2).

Atomics avoid the waiting a lock causes, but they're not free. Lab step 2 measured 4 threads × 1 million increments: fetch_add took about 51 ms and a Mutex about 78 ms. Counting in a local variable per thread and combining once at the end took 0.4 ms, over 100× faster than either. The expensive part isn't the lock or the instruction. It's sharing: every write to a shared value forces that cache line (chapter F1) to move between cores. The fastest concurrent code shares as little as possible.

Atomic operations also take a memory ordering argument (Relaxed, Acquire, Release, SeqCst). It exists because compilers and CPUs reorder memory operations for speed, and when threads communicate through an atomic flag (for example, "data is ready"), you must say which other reads and writes may not be moved across it. For a plain counter, Relaxed is enough. For anything else, until chapter 4.3 teaches the rules, use a Mutex or SeqCst.

Deep dive: false sharing — when unrelated data collides in the cache

Caches move memory in whole lines: 128 bytes on the lab Mac (measured in chapter F1). If two threads write two different variables that happen to sit in the same line, the line still ping-pongs between their cores on every write, as if they shared data. That's false sharing. The program below has two threads each increment their own counter 20 million times, once with the counters 8 bytes apart, once with each aligned to its own 128-byte line:

use std::sync::atomic::{AtomicU64, Ordering};
use std::thread;
use std::time::Instant;

/// Two counters right next to each other: same 128-byte cache line on the lab Mac.
struct Adjacent {
    a: AtomicU64,
    b: AtomicU64,
}

/// The same two counters, each forced onto its own cache line.
#[repr(align(128))]
struct Padded(AtomicU64);

fn hammer(x: &AtomicU64, y: &AtomicU64) -> f64 {
    let t = Instant::now();
    thread::scope(|s| {
        s.spawn(|| (0..20_000_000).for_each(|_| { x.fetch_add(1, Ordering::Relaxed); }));
        s.spawn(|| (0..20_000_000).for_each(|_| { y.fetch_add(1, Ordering::Relaxed); }));
    });
    t.elapsed().as_secs_f64() * 1e3
}

fn main() {
    let adj = Adjacent { a: AtomicU64::new(0), b: AtomicU64::new(0) };
    let (pa, pb) = (Padded(AtomicU64::new(0)), Padded(AtomicU64::new(0)));
    println!("distance between adjacent counters: {} bytes", (&adj.b as *const _ as usize) - (&adj.a as *const _ as usize));
    println!("same cache line : {:>6.0} ms", hammer(&adj.a, &adj.b));
    println!("own cache lines : {:>6.0} ms", hammer(&pa.0, &pb.0));
}
distance between adjacent counters: 8 bytes
same cache line :    257 ms
own cache lines :     40 ms

About 6× slower (median 253 ms vs 40 ms over three runs) for no logical reason. That's why high-performance libraries pad per-thread counters and queue indices to the cache-line size (#[repr(align(128))] here; crossbeam provides a CachePadded wrapper). In .NET the same fix uses [StructLayout] with explicit padding. Suspect false sharing when adding threads to "independent" work makes it slower.

CPU-bound vs I/O-bound work

The single most useful question to ask about a workload is: what is it waiting for?

  • CPU-bound work spends its time computing: evaluating a rule set, parsing, compressing, hashing. More cores help, up to the number of cores and no further. Lab step 5 counted primes on 1–16 threads: near-linear speed-up to 6 threads (5.7×, the 6 performance cores), a little more from the efficiency cores (6.4× at 10), and nothing at 16. The tools are a fixed pool of about one thread per core (.NET Parallel.For/PLINQ; Rust's rayon, chapter 4.4).
  • I/O-bound work spends its time waiting: for a database, an HTTP call, a disk. Cores are idle anyway, so the goal is to have many operations in flight. 1,000 requests that each wait 20 ms take 20 seconds one at a time, and about 27 ms concurrently (Lab step 5). The question is only what each in-flight operation costs while it waits.

Lab step 5 also shows a trap: work divided into fixed, equal-sized ranges was badly balanced (larger numbers take longer to test), so 2 threads gave 1.6× instead of 2×. The balanced version hands out small blocks dynamically, so fast threads take more. Load balancing is half of parallel performance, and the core idea behind rayon's work stealing.

Deep dive: Amdahl's law — the limit of adding cores

Gene Amdahl's 1967 argument: if a fraction \(p\) of a job can run in parallel and the rest \((1-p)\) is sequential, the best speed-up on \(N\) cores is

$$ S(N) = \frac{1}{(1 - p) + \dfrac{p}{N}} \qquad\Longrightarrow\qquad \lim_{N\to\infty} S(N) = \frac{1}{1-p} $$

With 95% parallel work, no number of cores gets you past 20×; with 90%, past 10×. The sequential part (setup, a final merge, a lock everyone takes) dominates as cores grow. So when a client says "we'll scale by adding cores", ask what fraction of the request path is serialised: a global lock, a single database row everybody updates, a single-threaded event loop.

The lab's 6.4× on 10 cores is mostly not Amdahl. The prime count is almost perfectly parallel; the shortfall is that the M2 Pro's 4 efficiency cores are slower than its 6 performance cores. Real hardware is heterogeneous (efficiency cores, hyper-threading, thermal limits), so measure scaling rather than assuming it.

Threads vs async tasks

For I/O-bound work there are two broad ways to keep many operations in flight:

  1. One OS thread per operation, blocking. Simple code: a thread calls read() and the OS parks it until data arrives. It works up to a few thousand concurrent operations. Beyond that, each waiting thread still costs a stack (2 MiB reserved), kernel bookkeeping and context switches. Lab step 5: 1,000 threads, 56 ms; spawning a thread, about 19 µs each.
  2. Many lightweight tasks on a few threads, non-blocking. A task is a small object (in Rust and C#, a compiler-generated state machine) that runs until it would wait, then gives its thread back. A runtime runs thousands of tasks on a handful of threads. Lab step 5: 1,000 tasks on one thread, 27 ms; spawning a task, about 0.19 µs.

C# async/await and Rust async/.await are both the second kind, and both compile each async function into a state machine. The big differences (chapter 4.5): in Rust a future does nothing until something polls it, and Rust has no built-in runtime, so you choose one, usually Tokio. .NET ships its thread pool, and a Task starts running as soon as you call the method. Either way, the runtime needs a way to learn when a waiting operation can continue. That's the event loop.

Event loops and non-blocking I/O

With non-blocking I/O, a read that has no data yet returns immediately with "would block" instead of parking the thread. On its own that would mean asking every socket over and over (busy polling). The missing piece is an OS facility that watches thousands of sockets and wakes you only for the ones that are ready. An event loop is a thread that waits on that facility and runs whichever tasks it reports:

Readiness vs completion I/O

Operating systems offer two different models for that notification, and the difference shapes runtime design:

Readiness modelCompletion model
Question you ask the OS"Tell me when this socket can be read without blocking""Read into this buffer and tell me when it's done"
Who does the readYou, after the notificationThe kernel, before the notification
Who owns the buffer while waitingYou; no buffer is committed until data is thereThe kernel, for the whole operation; you must not move or free it
OS interfacesepoll (Linux), kqueue (macOS, BSD); older select/poll scan every handle on every callI/O completion ports, IOCP (Windows); io_uring (Linux, since kernel 5.1 in 2019), which uses shared submission and completion queues
Who uses itRust's mio, which Tokio is built on; .NET's socket engine on Linux and macOS (epoll or kqueue).NET on Windows (the thread pool's I/O completion threads); mio on Windows uses an AFD-based "wepoll" strategy to present socket readiness; io_uring runtimes such as tokio-uring

Why does this matter to a Rust architect? Rust's async ecosystem grew up readiness-first: Tokio's I/O traits read into a buffer you lend for the duration of a call. Completion I/O needs the kernel to own the buffer until the operation finishes, even if the task waiting for it is cancelled (dropped) in the meantime. That conflicts with "borrowed for the duration of a call", so io_uring-based Rust runtimes use APIs that take owned buffers and hand them back. It's a direct, practical consequence of Rust's ownership model (chapters 2.2 and 4.6), and the reason "just switch Tokio to io_uring" isn't a one-line change.

Step 2 — a race condition with no data race, and three fixes

use std::sync::atomic::{AtomicU64, Ordering};
use std::sync::Mutex;
use std::thread;
use std::time::Instant;

const THREADS: u64 = 4;
const PER_THREAD: u64 = 1_000_000;

/// Run `work` on THREADS scoped threads and report the elapsed time.
fn timed(label: &str, expected: u64, work: impl Fn() + Sync, read: impl Fn() -> u64) {
    let t = Instant::now();
    thread::scope(|s| {
        for _ in 0..THREADS {
            s.spawn(&work);
        }
    });
    let ms = t.elapsed().as_secs_f64() * 1e3;
    let got = read();
    let verdict = if got == expected { "correct".to_string() } else { format!("LOST {} updates", expected - got) };
    println!("{label:<34} total {got:>9}  {ms:>7.1} ms  {verdict}");
}

fn main() {
    let expected = THREADS * PER_THREAD;
    println!("{THREADS} threads x {PER_THREAD} increments, expected total {expected}");

    // 1. Race condition WITHOUT a data race: each load and store is atomic,
    //    but "read, add one, write back" as a whole is not.
    let a = AtomicU64::new(0);
    timed("atomic load + store (check-then-act)", expected, || {
        for _ in 0..PER_THREAD {
            let v = a.load(Ordering::Relaxed);
            a.store(v + 1, Ordering::Relaxed);
        }
    }, || a.load(Ordering::Relaxed));

    // 2. One indivisible read-modify-write instruction.
    let b = AtomicU64::new(0);
    timed("atomic fetch_add", expected, || {
        for _ in 0..PER_THREAD {
            b.fetch_add(1, Ordering::Relaxed);
        }
    }, || b.load(Ordering::Relaxed));

    // 3. A lock around the whole read-modify-write.
    let m = Mutex::new(0u64);
    timed("Mutex<u64>", expected, || {
        for _ in 0..PER_THREAD {
            *m.lock().unwrap() += 1;
        }
    }, || *m.lock().unwrap());

    // 4. Don't share: count locally, combine once at the end.
    let total = AtomicU64::new(0);
    timed("per-thread count, combine once", expected, || {
        let mut local = 0u64;
        for _ in 0..PER_THREAD {
            local = std::hint::black_box(local + 1);
        }
        total.fetch_add(local, Ordering::Relaxed);
    }, || total.load(Ordering::Relaxed));
}

Version 1 is the important one. It is entirely safe Rust. Every individual access is atomic, so there's no data race and no undefined behaviour, and it's still wrong, because the logic "read, add, write" isn't one indivisible step. That's the race condition the compiler can't see. The other three are correct for different reasons: one indivisible instruction (fetch_add), a critical section (Mutex), or no shared state until the very end.

Step 3 — every possible schedule

Figure 3 claims 18 of 20 schedules lose an update. Rather than trust the widget, enumerate them:

/// Enumerate every way the OS could interleave two threads that each run
/// `load; add 1; store` on a shared counter starting at 0.
fn main() {
    let mut schedules = Vec::new();
    // A schedule is 6 slots; choose which 3 belong to thread 1 (C(6,3) = 20 ways).
    for mask in 0u32..64 {
        if mask.count_ones() == 3 {
            schedules.push(mask);
        }
    }
    let mut lost = 0;
    for &mask in &schedules {
        let mut memory = 0;
        let mut reg = [0, 0]; // each thread's private register
        let mut pc = [0, 0];  // next micro-step per thread: 0 load, 1 add, 2 store
        let mut trace = String::new();
        for slot in 0..6 {
            let t = if mask & (1 << slot) != 0 { 0 } else { 1 };
            match pc[t] {
                0 => reg[t] = memory,
                1 => reg[t] += 1,
                _ => memory = reg[t],
            }
            trace.push_str(&format!("T{}{} ", t + 1, ["L", "A", "S"][pc[t]]));
            pc[t] += 1;
        }
        if memory != 2 {
            lost += 1;
        } else {
            println!("correct: {trace}");
        }
    }
    println!("{} schedules, {} correct, {} lose an update", schedules.len(), schedules.len() - lost, lost);
}

Only the two schedules where one thread runs start-to-finish before the other are correct. With more threads or longer critical sections the number of interleavings explodes, which is why testing alone can't establish that concurrent code is correct. Step 4 — a real deadlock, and lock ordering

use std::sync::mpsc;
use std::sync::{Arc, Mutex};
use std::thread;
use std::time::Duration;

/// Two transfers that take the same two locks in OPPOSITE orders.
fn run(ordered: bool) -> bool {
    let account_a = Arc::new(Mutex::new(100));
    let account_b = Arc::new(Mutex::new(100));
    let (done_tx, done_rx) = mpsc::channel();

    for (first, second, amount) in [(&account_a, &account_b, 10), (&account_b, &account_a, 20)] {
        // With `ordered`, every thread locks A before B, whatever the transfer direction.
        let (l1, l2) = if ordered { (account_a.clone(), account_b.clone()) } else { (first.clone(), second.clone()) };
        let done_tx = done_tx.clone();
        thread::spawn(move || {
            let mut g1 = l1.lock().unwrap();
            thread::sleep(Duration::from_millis(50)); // widen the window, as real work would
            let mut g2 = l2.lock().unwrap();
            *g1 -= amount;
            *g2 += amount;
            done_tx.send(()).unwrap();
        });
    }
    // Watchdog: wait up to 2 s for both transfers.
    (0..2).all(|_| done_rx.recv_timeout(Duration::from_secs(2)).is_ok())
}

fn main() {
    println!("opposite lock order: {}", if run(false) { "finished" } else { "DEADLOCK: neither thread finished within 2 s" });
    println!("same lock order:     {}", if run(true) { "finished" } else { "DEADLOCK" });
    // The deadlocked threads are still blocked forever; exiting main ends the process.
}
opposite lock order: DEADLOCK: neither thread finished within 2 s
same lock order:     finished

Each thread takes its first lock, sleeps 50 ms (standing in for real work), then asks for the second lock, which the other thread holds. Neither will ever finish; the watchdog notices after 2 seconds. The deadlocked threads stay blocked until the process exits. In a server they would sit there for good, holding two accounts locked, and every later request for those accounts would join the queue. With one global order, the identical code always finishes. Notice that nothing here is unsafe: deadlock is a logic bug Rust can't catch.

Step 5 — CPU-bound vs I/O-bound, measured

use std::sync::atomic::{AtomicU64, Ordering};
use std::thread;
use std::time::{Duration, Instant};

/// Is `k` prime? Trial division: deliberately slow, pure CPU work.
fn is_prime(k: u64) -> bool {
    k >= 2 && (2..).take_while(|d| d * d <= k).all(|d| !k.is_multiple_of(d))
}

/// Count primes below `n` on `threads` threads.
/// `dynamic`: threads repeatedly grab the next block of 1,000 numbers from a shared
/// counter, so fast threads simply take more blocks (balanced).
/// Otherwise each thread gets one fixed contiguous range (the last range has the
/// biggest, slowest numbers, so its thread finishes last).
fn cpu_bound(threads: u64, n: u64, dynamic: bool) -> (u64, f64) {
    const BLOCK: u64 = 1_000;
    let next = AtomicU64::new(0);
    let t = Instant::now();
    let total = thread::scope(|s| {
        let handles: Vec<_> = (0..threads)
            .map(|i| {
                let next = &next;
                s.spawn(move || {
                    if dynamic {
                        let mut count = 0;
                        loop {
                            let lo = next.fetch_add(BLOCK, Ordering::Relaxed);
                            if lo >= n {
                                break count;
                            }
                            count += (lo..(lo + BLOCK).min(n)).filter(|&k| is_prime(k)).count() as u64;
                        }
                    } else {
                        let chunk = n / threads;
                        let hi = if i == threads - 1 { n } else { (i + 1) * chunk };
                        (i * chunk..hi).filter(|&k| is_prime(k)).count() as u64
                    }
                })
            })
            .collect();
        handles.into_iter().map(|h| h.join().unwrap()).sum()
    });
    (total, t.elapsed().as_secs_f64() * 1e3)
}

/// Median of three runs, in milliseconds.
fn median3(threads: u64, n: u64, dynamic: bool) -> (u64, f64) {
    let mut runs: Vec<(u64, f64)> = (0..3).map(|_| cpu_bound(threads, n, dynamic)).collect();
    runs.sort_by(|a, b| a.1.total_cmp(&b.1));
    runs[1]
}

fn main() {
    let cores = thread::available_parallelism().unwrap();
    println!("available_parallelism = {cores}");

    println!("--- CPU-bound: primes below 3,000,000 (median of 3 runs) ---");
    cpu_bound(1, 3_000_000, true); // warm-up
    let (_, base) = median3(1, 3_000_000, true);
    for threads in [1, 2, 4, 6, 8, 10, 16] {
        let (count, ms) = median3(threads, 3_000_000, true);
        println!("{threads:>2} threads: {count} primes in {ms:>4.0} ms  speed-up x{:.1}", base / ms);
    }
    let (_, ms) = median3(2, 3_000_000, false);
    println!(" 2 threads, fixed contiguous halves: {ms:>4.0} ms  speed-up x{:.1} (unbalanced)", base / ms);

    println!("--- I/O-bound (simulated): 1,000 requests that each wait 20 ms ---");
    let wait = Duration::from_millis(20);
    let t = Instant::now();
    for _ in 0..100 {
        thread::sleep(wait);
    }
    println!("sequential, first 100 only : {:>6.0} ms (all 1,000 would take ~20 s)", t.elapsed().as_secs_f64() * 1e3);

    thread::scope(|s| {
        for _ in 0..10 {

    println!("10 threads x 100 waits each: {:>6.0} ms", t.elapsed().as_secs_f64() * 1e3);

Exercise 1 — a deadlock-free transfer ★★☆ product skill

Write transfer(from: &Account, to: &Account, amount) where each Account has an id and a Mutex<i64> balance. Run 8 threads doing 10,000 transfers each, half in each direction between the same two accounts. It must never deadlock, and the total must stay 2,000.

Show solution 
use std::sync::{Arc, Mutex};
use std::thread;

struct Account {
    id: u32,
    balance: Mutex<i64>,
}

/// Deadlock-free transfer: always lock the account with the LOWER id first,
/// whichever direction the money moves. One global order means no cycle can form.
fn transfer(from: &Account, to: &Account, amount: i64) {
    if from.id == to.id {
        return;
    }
    let (first, second) = if from.id < to.id { (from, to) } else { (to, from) };
    let mut g1 = first.balance.lock().unwrap();
    let mut g2 = second.balance.lock().unwrap();
    let (from_bal, to_bal) = if from.id < to.id { (&mut *g1, &mut *g2) } else { (&mut *g2, &mut *g1) };
    *from_bal -= amount;
    *to_bal += amount;
}

fn main() {
    let a = Arc::new(Account { id: 1, balance: Mutex::new(1_000) });
    let b = Arc::new(Account { id: 2, balance: Mutex::new(1_000) });
    let handles: Vec<_> = (0..8)
        .map(|i| {
            let (a, b) = (a.clone(), b.clone());
            thread::spawn(move || {
                for _ in 0..10_000 {
                    // half the threads move money a -> b, the other half b -> a
                    if i % 2 == 0 { transfer(&a, &b, 5) } else { transfer(&b, &a, 5) }
                }
            })
        })
        .collect();
    for h in handles {
        h.join().unwrap();
    }
    let (ba, bb) = (*a.balance.lock().unwrap(), *b.balance.lock().unwrap());
    println!("a = {ba}, b = {bb}, total = {}", ba + bb); // total must still be 2000
    assert_eq!(ba + bb, 2_000);
}
a = 1000, b = 1000, total = 2000

Locking by ascending id imposes one global order, which removes Coffman's "circular wait". The slightly fiddly line maps the two guards back to "from" and "to" after locking them in id order. The same-account check matters: locking the same Mutex twice on one thread deadlocks (or panics) by itself. In the workflow engine the same rule applies to rows: lock in a deterministic order (for example ORDER BY id ... FOR UPDATE, chapter 10.4).

Exercise 2 — sell exactly 500 seats ★★☆

500 seats, 8 threads, 100 purchase attempts each. Write try_reserve(&AtomicU32) -> bool without a Mutex, so that exactly 500 succeed: never oversold, never undersold. Why is if remaining.load() > 0 { remaining.fetch_sub(1) } wrong?

Show solution 
use std::sync::atomic::{AtomicU32, Ordering};
use std::thread;

/// Reserve one seat if any are left. compare_exchange makes "check and decrement"
/// a single indivisible step: it only writes `left - 1` if the value is still `left`.
fn try_reserve(remaining: &AtomicU32) -> bool {
    let mut left = remaining.load(Ordering::Relaxed);
    loop {
        if left == 0 {
            return false;
        }
        match remaining.compare_exchange(left, left - 1, Ordering::AcqRel, Ordering::Relaxed) {
            Ok(_) => return true,
            Err(actual) => left = actual, // someone else got there first: retry with the new value
        }
    }
}

fn main() {
    let remaining = AtomicU32::new(500);
    let sold: u32 = thread::scope(|s| {
        let handles: Vec<_> = (0..8)
            .map(|_| s.spawn(|| (0..100).filter(|_| try_reserve(&remaining)).count() as u32))
            .collect();
        handles.into_iter().map(|h| h.join().unwrap()).sum()
    });
    println!("800 attempts, 500 seats: sold {sold}, remaining {}", remaining.load(Ordering::Relaxed));
    assert_eq!(sold, 500); // never oversold, never undersold
}
800 attempts, 500 seats: sold 500, remaining 0

The naive version is check-then-act: two threads can both see 1, both decrement, and the counter wraps around (or you sell seat −1). compare_exchange merges the check and the write into one atomic step. If another thread changed the value in between, it fails, hands back the current value, and the loop retries. This retry loop is the basic pattern of lock-free programming. Chapter 4.3 explains the AcqRel/Relaxed orderings used here.

Exercise 3 — parallel word count, sharing nothing ★☆☆

Using std::thread::scope, count the words in 100,000 log lines on 8 threads, with no Mutex and no atomics. Check it matches the sequential count.

Show solution 
use std::thread;

/// Count words in parallel: split the lines into one chunk per thread,
/// count each chunk independently, then add the results. No shared mutable state.
fn parallel_word_count(lines: &[String], threads: usize) -> usize {
    let chunk = lines.len().div_ceil(threads).max(1);
    thread::scope(|s| {
        let handles: Vec<_> = lines
            .chunks(chunk)
            .map(|part| s.spawn(move || part.iter().map(|l| l.split_whitespace().count()).sum::<usize>()))
            .collect();
        handles.into_iter().map(|h| h.join().unwrap()).sum()
    })
}

fn main() {
    let lines: Vec<String> = (0..100_000).map(|i| format!("rule {i} fired for tenant acme")).collect();
    let sequential: usize = lines.iter().map(|l| l.split_whitespace().count()).sum();
    let parallel = parallel_word_count(&lines, 8);
    println!("sequential {sequential}, parallel {parallel}");
    assert_eq!(sequential, parallel);
}
sequential 600000, parallel 600000

Each thread reads its own slice (chunks) and returns a number; results are combined only after join. Scoped threads may borrow lines because the scope guarantees every thread finishes before lines could be dropped (chapter 4.1). This "split, compute independently, combine" shape is the fastest concurrency there is (Lab step 2's 0.4 ms), and rayon's par_iter (chapter 4.4) does it in one line.

Common misconceptions and pitfalls

⚠️ "Rust prevents concurrency bugs"

It prevents data races. Race conditions (Lab step 2, version 1) and deadlocks (Lab step 4) compile fine. Design and test for them.

⚠️ "Each atomic access is safe, so my logic is safe"

Atomicity covers one operation. Check-then-act across two atomic calls is a race. Use fetch_*, compare_exchange, or one lock around the whole decision.

⚠️ More threads for CPU-bound work

Past the core count you only add switching (Figure 7: 16 threads = 10 threads). For CPU work size the pool to the cores, and watch load balance.

⚠️ Blocking inside async code

A long computation or a blocking call (std::thread::sleep, a synchronous DB driver) inside an async task stalls every task on that worker thread. Cooperative scheduling can't interrupt it. In .NET the thread pool eventually injects more threads; in Tokio you must move the work out (spawn_blocking, chapter 4.7).

⚠️ Holding a lock across slow work

Across I/O, an .await or a callback, a lock turns your concurrent system sequential and invites deadlock. Copy what you need, release, then do the slow part. Microsoft's Lock docs give the same advice for C# async methods.

⚠️ "It passed the tests, so it's thread-safe"

Only 2 of 20 schedules were correct, and a test run sees a few of them. Races hide until production load changes the timing. Prefer designs that make races impossible (no shared mutable state), and model-check the rest (chapter 4.8).

Real-world view: concurrency in your two products

🏗 Architecture view
  • Workflow engine, I/O side. Thousands of runs mostly waiting on timers and external calls: async tasks on Tokio, one task per in-flight step, not one thread per run. Durable timers (chapter 10.6) feed the event loop's timer wheel.
  • Workflow engine, correctness. Two workers must never execute the same step. That's a check-then-act race across processes, so in-memory locks can't solve it. You'll use leases and conditional updates in the database (compare-and-swap in SQL: UPDATE … WHERE version = $expected, chapters 10.4–10.5), the same idea as Exercise 2.
  • Rule engine, CPU side. Evaluating a rule set over a batch of facts is data-parallel: split the facts, evaluate independently, combine (Exercise 3; rayon in chapter 4.4). Keep it off the async worker threads that serve API requests.
  • Hot configuration. Rule sets are read constantly and replaced rarely. Instead of a lock on every read, swap an Arc to the new version atomically (ArcSwap, chapter 9.8). Readers never wait; that's "share less" applied.
  • Lock discipline in reviews: one documented lock order; no lock held across .await, I/O or plugin calls; contention measured, not guessed; per-thread or sharded counters for metrics (false sharing); a deadlock watchdog or lock timeouts in long-running services.

Summary

  • Concurrency is structure (many tasks in progress); parallelism is execution (many at the same instant). Processes are isolated address spaces; threads share a process's heap but each has its own stack. OS threads are scheduled preemptively, async tasks cooperatively.
  • A data race (unsynchronised concurrent access with a write) is undefined behaviour, and safe Rust rules it out at compile time (E0499, Send/Sync). A race condition (timing-dependent logic such as check-then-act) is not prevented: separate atomic load and store calls lost about 3 million of 4 million updates in safe Rust. 18 of 20 interleavings of two increments lose one.
  • Locks give mutual exclusion; Rust's Mutex<T> owns its data and unlocks on drop. Deadlock needs all four Coffman conditions; break circular wait with a global lock order. Rust doesn't prevent deadlocks.
  • Atomics (fetch_add, compare_exchange) are indivisible hardware operations, but sharing itself is the cost: 51 ms atomic, 78 ms mutex, 0.4 ms with no sharing; false sharing made independent counters 6× slower.
  • CPU-bound work scales to the core count (5.7× on 6 performance cores, no gain past 10); I/O-bound work needs many operations in flight, cheapest as async tasks (0.19 µs vs 19 µs per spawn). Event loops wait on readiness APIs (epoll, kqueue: "you can read now") or completion APIs (IOCP, io_uring: "your read is done"), and the latter's kernel-owned buffers shape Rust's async I/O design.
