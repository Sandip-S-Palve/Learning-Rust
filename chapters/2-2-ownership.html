Ownership and moves

Learning objectives

  • State the three ownership rules and use them to predict when a value is freed
  • Explain what a move does in memory, recognise every place one happens, and read error E0382
  • Distinguish Copy, Clone and plain moves, and decide which a type of yours should support
  • Implement Drop, predict drop order, and use RAII guards for resources such as connections and locks
  • Compare Rust's ownership with .NET's garbage collector, IDisposable/using and finalizers, and explain what each guarantees

Why this matters

💡 Why this matters

Every program has to answer "who frees this, and when?" for every piece of memory and every resource. .NET answers it twice. For memory, the garbage collector frees objects at some later point it chooses (chapter F1). For everything else (files, sockets, database connections, locks, leases) it hands the job back to you: implement IDisposable, remember the using, and hope nobody uses the object after it's disposed. Forgotten disposals are among the most common production leaks in .NET services, and analyzers like CA2000 exist because the compiler can't enforce them.

Rust answers the question once, for memory and resources alike, at compile time: every value has exactly one owner, and the value is cleaned up the moment its owner goes away. There's no collector, no forgotten using, and no use-after-dispose, because using a value whose ownership has moved elsewhere doesn't compile. This is the idea everything else in Rust builds on: borrowing (2.3), lifetimes (2.11), smart pointers (2.12), and thread safety (4.1). For your workflow engine it means a worker's lease on a step, a database connection or a lock is released on every exit path, including errors and panics, without a single finally.

Intuition first: one original document

🧭 Analogy

Think of a value as a signed original contract, filed in exactly one cabinet.

  • Ownership: the cabinet it's in is responsible for it. One cabinet at a time.
  • Move: you hand the original to a colleague. Now their cabinet owns it. You can't read it any more. You don't have it, and you certainly mustn't shred it.
  • Clone: you make a certified photocopy. It costs time and paper, and you do it on purpose. Now there are two independent originals.
  • Copy: some things are so small that copying is free and nobody cares which one is "original": a phone number on a sticky note. Those are copied without ceremony.
  • Drop: when a cabinet is cleared out (its owner leaves scope), whatever is still in it goes to the shredder, immediately and exactly once.

In .NET, by contrast, everyone holds a pointer to the same document and a cleaner eventually removes documents nobody points at. That's convenient, but you never know when, and if the document was holding a meeting room booked, the room stays booked until the cleaner comes.

Core explanation

Basic

The three ownership rules

The Rust Book states them exactly:

  1. Each value in Rust has an owner.
  2. There can only be one owner at a time.
  3. When the owner goes out of scope, the value will be dropped.

An owner is usually a variable, but it can also be a struct field, an element of a Vec, or a function parameter. Scopes are the blocks { … } you met in chapter 2.1. "Dropped" means the value's cleanup runs: for a String that frees its heap buffer; for a file, it closes the handle; for a lock guard, it unlocks. Everything else in this chapter follows from these three sentences.

Moves

Recall from chapter F1 that a String is three words on the stack (a pointer, a length and a capacity, 24 bytes in total) pointing at a buffer on the heap. What should let s2 = s1; do?

  • Copying the heap bytes too (a deep copy) would make every assignment potentially expensive. Rust never does that implicitly.
  • Copying only the three words and keeping both variables valid would give the buffer two owners. When both went out of scope, both would free it: a double free, one of the classic memory-safety bugs (chapter 0.1).

Rust's answer is a move. The three words are copied to s2, and s1 stops being usable: it is now moved-from. The heap buffer still has exactly one owner, so it will be freed exactly once. Use s1 afterwards and you get error E0382, "borrow of moved value", at compile time (Lab step 1).

Moves happen in more places than assignment, and you need to recognise all of them:

  • Passing an argument by value: archive(doc) moves doc into the function. Inside a loop, that's error E0382 "value moved here, in previous iteration of loop" (Lab step 1).
  • Returning a value moves it out to the caller. That's how a function can create a String and hand it back without copying.
  • Storing a value in a struct field, a Vec (v.push(s)), a HashMap, or a closure that captures by move.
  • for x in collection moves each element out and consumes the collection; afterwards the collection is gone. (for x in &collection borrows instead: chapter 2.3.)
  • Pattern matching and let (a, b) = pair; move the parts out.

The compiler tracks moves through if/else branches and loops. If a value is moved on some path, it's treated as unusable afterwards on all paths. It also refuses moves that would leave a hole: let first = names[0]; on a Vec<String> is error E0507 "cannot move out of index", because the vector would then contain an element it no longer owns. The fixes are to borrow (&names[0]), clone, take the element out properly (names.remove(0), swap_remove, into_iter), or swap something in its place (std::mem::take, below).

Copy: types that are just bits

Some types have no owned resources at all: their value is their bits. For them a move is pointless ceremony, so they're Copy: assignment duplicates the bits and both variables stay usable. All the scalar types from chapter 2.1 are Copy (integers, floats, bool, char), as are shared references &T, and tuples and arrays whose elements are all Copy. Your own struct can be Copy too, by writing #[derive(Clone, Copy)], but only if every field is Copy. A struct containing a String can't be (error E0204, Lab step 2).

The deeper rule: a type can't be both Copy and implement Drop. The Book states it directly: "Rust won't let us annotate a type with Copy if the type, or any of its parts, has implemented the Drop trait." If copying the bits created a second value with cleanup duties, the cleanup would run twice. So Copy is exactly the set of types for which "two owners" is harmless.

Note what Copy does not mean: it doesn't make a type a "value type" in the C# sense, and non-Copy types aren't "reference types". Every Rust type has value semantics (chapter F8). Copy only decides whether the source stays usable after a move. Both a move and a copy are the same bitwise copy of the stack representation.

Clone: explicit duplication

Clone is how you ask for an independent duplicate of a non-Copy value: let s3 = s2.clone();. For a String or Vec that means a new heap allocation and a copy of every byte, so its cost grows with the size of the data (Lab step 5 measured 2 ms to clone a 10-million-element Vec<u64>, while the move was too small to measure). Making that cost visible in the code, instead of hiding it in an assignment, is the point. #[derive(Clone)] generates a field-by-field clone.

Clone isn't always a deep copy. For Rc and Arc (chapter 2.12) .clone() just increments a reference count and shares the same data. The trait means "give me another owner-able value", and each type documents what that costs. A useful review heuristic: a .clone() on a large collection inside a loop, or one added just to silence the compiler, deserves a second look (chapter 3.2 calls it the "clone everywhere" anti-pattern).

Drop and RAII

When a value is dropped, Rust first runs the type's Drop implementation, if it has one, then drops each of its fields. You implement Drop for types that own something outside Rust's memory, or that must do something when they end:

struct Connection { id: u32 }

impl Drop for Connection {
    fn drop(&mut self) {
        println!("closing connection {}", self.id); // runs exactly once
    }
}

Tying a resource's lifetime to an owner's scope like this is called RAII, "Resource Acquisition Is Initialization", a name inherited from C++: acquire the resource when the value is created, release it when the value is dropped. The standard library uses it everywhere. A File closes its handle on drop. A MutexGuard (chapter F9) unlocks on drop. A Vec frees its buffer and drops each element. A JoinHandle detaches. You'll write your own guards: a pool lease that returns its slot (Lab step 4), a timer that logs elapsed time (Exercise 1), a transaction that rolls back unless committed (chapter 7.4).

The rules you need:

  • Drop order. Variables in a scope are dropped in reverse order of declaration, so later values, which may depend on earlier ones, go first. Struct fields are dropped in declaration order, and array and Vec elements first to last. Figure 2 and Lab step 3 show all of these.
  • A move moves the duty to drop. A value is dropped where its final owner's scope ends: inside the function it was moved into, in the struct it was stored in, or never, if ownership is returned to the caller.
  • Drop early with drop(value) (that's std::mem::drop, a function in the prelude that simply takes ownership and lets it go). You can't call value.drop() yourself: that's error E0040, because the compiler would still drop it again at the end of the scope.
  • Panics run drops. When a panic unwinds the stack, every live value in every frame it passes through is dropped (Lab step 3). Cleanup happens on the error path too, without finally.
🟣 Coming from C#/.NET: RAII vs IDisposable and finalizers

C#'s closest equivalent is IDisposable plus using, and it differs on every guarantee that matters:

  • Opt-in vs automatic. Forget the using and Dispose never runs; only a finalizer, if the class has one, cleans up eventually, "the garbage collector decides when to call it". Since .NET 5, finalizers don't run at application exit at all, per Microsoft's docs. In Rust, the drop runs when the owner's scope ends, with nothing to remember.
  • Use after cleanup. In C# a disposed object is still reachable through every other reference to it, and using it throws ObjectDisposedException at runtime, if the class remembered to check. In Rust, after a move or drop(x), any use of x is a compile error.
  • Double cleanup. Dispose must be written to tolerate being called twice. Rust's drop runs exactly once, by construction.
  • Memory vs resources. .NET uses one mechanism for memory (GC) and another for resources (Dispose). Rust uses ownership for both, so a Vec<File> going out of scope frees the memory and closes every file.

Lab step 4 runs a C# IDisposable through each of these cases next to the Rust equivalent.

Intermediate

What a move costs

A move copies the value's stack representation (24 bytes for a String or Vec, whatever the size of its heap data) and often not even that, because the optimiser frequently builds the value directly in its final location. Lab step 1 prints the heap buffer's address before and after let s2 = s1;: identical. Lab step 5 times moving a Vec of up to 10 million elements: below the timer's ~0.04 µs resolution at every size, while cloning grew from 0.1 µs to about 2 ms. So "pass and return owned values" is cheap in Rust, and that's the idiom. A function that builds a big result returns it by value; there's nothing to gain from out-parameters. The exception is very large types stored inline (a struct holding a 64 KB array), whose moves really do copy every byte. Keep those behind a Box.

The let _ trap and temporaries

A value that's never bound to a name is a temporary, and it's dropped at the end of the statement that created it. That makes two lines that look alike behave very differently (Lab step 3):

let _ = pool.acquire(7);      // `_` binds nothing: the lease is returned HERE, at the end of this statement
let _lease = pool.acquire(8); // a real binding (merely unused): held until the end of the scope

The first line is a real bug when the lease was meant to be held: the step runs without a slot. The same applies to any guard of your own, such as a timer, a lease or a transaction. Use a named binding with a leading underscore whenever the guard's lifetime is the whole point. (let _ = existing_variable;, by contrast, neither moves nor drops anything; _ only matters for values created in that statement.)

The compiler protects the most dangerous case for you. For the standard library's lock guards, the deny-by-default lint let_underscore_lock turns let _ = mutex.lock().unwrap(); into a compile error:

use std::sync::Mutex;

fn main() {
    let state = Mutex::new(0);
    let _ = state.lock().unwrap(); // meant to hold the lock for the next lines
}

Moving out of places you don't fully own

Sometimes you want to move a value out of a struct field or a collection while keeping the container usable. The compiler allows a partial move of a field from a local struct, after which only the remaining fields are usable. For containers and anything behind a reference, the standard tools swap a valid value in as you take the old one out:

struct Job { id: u64, payload: String }

let job = Job { id: 7, payload: String::from("data") };
let payload = job.payload;           // partial move: job.payload is gone…
println!("job {} moved out {payload}", job.id); // …but job.id (Copy) is still usable

let mut buffer = vec![1, 2, 3];
let batch = std::mem::take(&mut buffer);   // take the Vec, leave an empty one behind
let mut slot: Option<String> = Some(String::from("lease-9"));
let taken = slot.take();                    // Some(..) out, None left in the slot
let old = std::mem::replace(&mut buffer, vec![9]); // swap in a specific value
println!("{batch:?} {taken:?} {old:?} {buffer:?} {slot:?}");

mem::take, mem::replace and Option::take come up constantly in state machines: "take the old state out, compute the new one, put it back", a pattern chapter 10.3 builds on.

Deep dive: drop flags — how Rust knows whether to drop after a conditional move

If a value is moved on one branch of an if and not the other, should the end of the scope drop it? The compiler can't always know statically, so, as the Rustonomicon puts it, "Rust actually tracks whether a type should be dropped or not at runtime. As a variable becomes initialized and uninitialized, a drop flag for that variable is toggled." In straight-line code the state is known at compile time and no flag exists. Only conditionally moved values pay for a hidden boolean on the stack.

let conn = Connection { id: 1 };
if send_to_worker {
    worker.take(conn);   // moved on this path only
}
// end of scope: drop `conn` only if it wasn't moved, decided by a hidden flag

This is the whole runtime cost of ownership: occasionally one byte and one branch. There's no reference counting, no tracing, and no pause.

Deep dive: what ownership does not guarantee — leaks are "safe"

Rust guarantees that a value is never freed twice and never used after it's freed. It does not guarantee that every destructor runs. The standard library says so explicitly: mem::forget "is not marked as unsafe, because Rust's safety guarantees do not include a guarantee that destructors will always run". Ways to skip a drop:

  • std::mem::forget(value), or Box::leak, deliberately.
  • A reference cycle of Rcs (chapter 2.12), the one way to leak by accident in safe code.
  • std::process::exit, or a build with panic = "abort": the process ends without unwinding, so no destructors run.

The design consequence: never rely on Drop for correctness across a process boundary. A workflow engine that releases a database lease in a Drop impl must also give the lease a timeout in the database, because the process can be killed. RAII makes the common paths, including errors and panics, correct; durable systems still need expiry for the uncommon ones (chapter 10.5). .NET is in the same position, more so: its finalizers don't run at exit since .NET 5.

Step 1 — moves, clones, and what the compiler refuses

/// Takes ownership of `doc`: when this function ends, the String is dropped.
fn archive(doc: String) -> usize {
    let n = doc.len();
    println!("  archived {n} bytes");
    n
} // `doc` goes out of scope here and its heap buffer is freed

/// Takes ownership and gives it back (with a change) through the return value.
fn stamp(mut doc: String) -> String {
    doc.push_str(" [approved]");
    doc
}

fn main() {
    let s1 = String::from("rule-set v7");
    let s2 = s1; // MOVE: s2 now owns the heap buffer; s1 is no longer usable
    println!("s2 = {s2}");

    let copy = s2.clone(); // CLONE: a second, independent heap buffer
    archive(s2); // MOVE into the function: s2 is gone after this line
    println!("copy still usable: {copy}");

    let doc = stamp(copy); // moved in, moved back out
    println!("doc = {doc}");

    let ids = vec![String::from("a"), String::from("b")];
    for id in ids {
        // `for x in vec` moves each element out; `ids` is consumed by the loop
        print!("{id} ");
    }
    println!();

    let n: u64 = 42;
    let m = n; // u64 is Copy: both remain usable
    println!("n = {n}, m = {m}");
}

Step 2 — Copy and Clone on your own types

/// Small, plain data: every field is Copy, so the whole struct can be Copy.
#[derive(Debug, Clone, Copy, PartialEq)]
struct Money {
    cents: i64,
    currency: [u8; 3],
}

/// Owns a heap String, so it can be Clone but never Copy.
#[derive(Debug, Clone)]
struct Customer {
    name: String,
    limit: Money,
}

fn main() {
    let price = Money { cents: 1_999, currency: *b"EUR" };
    let discounted = price; // implicit bitwise copy; `price` is still valid
    println!("{price:?} / {discounted:?}");

    let c1 = Customer { name: "Acme".to_string(), limit: price };
    let c2 = c1.clone(); // explicit: allocates a new String
    let c3 = c1; // move: no allocation, c1 is now unusable
    println!("{} {} {}", c2.name, c3.name, c3.limit == c2.limit);
}

Step 3 — drop order, early drops, and panics

struct Noisy(&'static str);

impl Drop for Noisy {
    fn drop(&mut self) {
        println!("  drop {}", self.0);
    }
}

#[allow(dead_code)] // the fields exist only so we can watch them being dropped
struct Pair {
    first: Noisy,
    second: Noisy,
}

fn make(name: &'static str) -> Noisy {
    Noisy(name)
}

fn main() {
    println!("1. locals: reverse order of declaration");
    {
        let _a = Noisy("a");
        let _b = Noisy("b");

Step 4 — an RAII lease pool, and the same in C#

A workflow worker takes a slot from a fixed-size pool for the duration of a step. The slot must come back however the step ends:

use std::sync::atomic::{AtomicUsize, Ordering};
use std::sync::Arc;

/// A fixed number of connection slots. `acquire` hands out a Lease;
/// dropping the Lease gives the slot back, whatever path the code takes.
struct Pool {
    free: Arc<AtomicUsize>,
}

struct Lease {
    free: Arc<AtomicUsize>,
    id: usize,
}

impl Pool {
    fn new(size: usize) -> Pool {
        Pool { free: Arc::new(AtomicUsize::new(size)) }
    }
    fn acquire(&self, id: usize) -> Option<Lease> {
        let left = self.free.load(Ordering::Acquire);
        if left == 0 {
            return None;
        }
        self.free.fetch_sub(1, Ordering::AcqRel); // single-threaded demo; see F9 for CAS
        Some(Lease { free: Arc::clone(&self.free), id })
    }
    fn available(&self) -> usize {
        self.free.load(Ordering::Acquire)
    }
}

impl Drop for Lease {
    fn drop(&mut self) {
        self.free.fetch_add(1, Ordering::AcqRel);
        println!("  lease {} returned", self.id);
    }
}

/// Uses a lease and may fail half-way. No `finally`, no `using`: the slot comes back anyway.
fn run_step(pool: &Pool, id: usize, fail: bool) -> Result<(), String> {
    let _lease = pool.acquire(id).ok_or("pool exhausted")?;
    if fail {
        return Err(format!("step {id} failed"));
    }
    println!("  step {id} ok");
    Ok(())
}

fn main() {
    let pool = Pool::new(2);
    println!("available: {}", pool.available());
    let a = pool.acquire(1).unwrap();
    let b = pool.acquire(2).unwrap();
    println!("available after two acquires: {}", pool.available());
    println!("third acquire: {}", if pool.acquire(3).is_none() { "None (exhausted)" } else { "Some" });
    drop(a);
    drop(b);
    println!("available after drops: {}", pool.available());
    println!("{:?}", run_step(&pool, 4, false));
    println!("{:?}", run_step(&pool, 5, true));
    println!("available at the end: {}", pool.available());
}
available: 2
available after two acquires: 0
third acquire: None (exhausted)
  lease 1 returned
  lease 2 returned
available after drops: 2
  step 4 ok
  lease 4 returned
Ok(())
  lease 5 returned
Err("step 5 failed")
available at the end: 2

run_step has three exits (the pool is exhausted, the step fails, the step succeeds) and no cleanup code at all. The lease is returned on each, including the early return Err(…) and the ? (chapter 2.6). The C# version of the same pattern, exercised through each failure mode:

using System.Runtime.CompilerServices;

// 1. With `using`: disposed deterministically at the end of the scope.
{
    using var lease = new Lease("A");
    Console.WriteLine($"inside using:        open = {Lease.Open}");
}
Console.WriteLine($"after using:         open = {Lease.Open}");

// 2. Forgot to dispose: nothing happens until the GC decides to finalize.
Forget();
Console.WriteLine($"after Forget():      open = {Lease.Open}");
GC.Collect();
GC.WaitForPendingFinalizers();
Console.WriteLine($"after forced GC:     open = {Lease.Open}");

// 3. Two references to one object: dispose through one, use through the other.
var first = new Lease("C");
var alias = first;
first.Dispose();
first.Dispose();                       // must be harmless: Dispose has to be idempotent
try { alias.Use(); }
catch (ObjectDisposedException e) { Console.WriteLine($"use after dispose:   {e.GetType().Name}"); }

[MethodImpl(MethodImplOptions.NoInlining)]
static void Forget() => new Lease("B").Use();

class Lease : IDisposable
{
    public static int Open;
    private readonly string _name;
    private bool _disposed;
    public Lease(string name) { _name = name; Open++; }
    public void Use() => ObjectDisposedException.ThrowIf(_disposed, this);
    public void Dispose()
    {
        if (_disposed) return;
        _disposed = true;
        Open--;
        GC.SuppressFinalize(this);
    }
    ~Lease()
    {
        Console.WriteLine($"  finalizer ran for {_name} (on the GC's schedule)");
        Open--;
    }
}

Line by line: with using, C# is as deterministic as Rust. Forgetting it leaves the lease "open" until a garbage collection happens to finalize it; here we had to force one, and in production that might be minutes away, or, at exit, never. The class must make Dispose idempotent by hand. And an alias can still reach the disposed object, so the mistake surfaces at runtime as ObjectDisposedException. In the Rust pool, each of those mistakes is either impossible or a compile error.

Step 5 — the cost of moving vs cloning

use std::hint::black_box;
use std::time::Instant;

fn main() {
    for &n in &[1_000usize, 100_000, 1_000_000, 10_000_000] {
        let v: Vec<u64> = (0..n as u64).collect();
        // best of 5 for each
        let mut t_move = f64::MAX;
        let mut t_clone = f64::MAX;
        let mut v = v;
        for _ in 0..5 {
            let t = Instant::now();
            let moved = black_box(v); // moves the 24-byte Vec header
            t_move = t_move.min(t.elapsed().as_secs_f64() * 1e6);
            v = moved;

            let t = Instant::now();
            let cloned = black_box(v.clone()); // allocates and copies n * 8 bytes
            t_clone = t_clone.min(t.elapsed().as_secs_f64() * 1e6);
            drop(cloned);
        }
        // A move copies 24 bytes: usually below the ~0.04 µs resolution of the timer.
        let mv = if t_move < 0.05 { "< 0.05 µs".to_string() } else { format!("{t_move:.2} µs") };
        println!("{n:>10} elements: move {mv:>10}   clone {t_clone:>8.1} µs");
    }
}

Exercise 2 — the longest name, without cloning ★★☆

Write longest_owned(names: Vec<String>) -> Option<String> that returns the longest name by value, with no .clone() anywhere. Why does the signature take Vec<String> rather than &Vec<String>?

Show solution 
/// Return the longest name, by value, without cloning any String.
/// Taking `Vec<String>` by value means we own every element and may move one out.
fn longest_owned(names: Vec<String>) -> Option<String> {
    let mut best: Option<String> = None;
    for name in names {
        // `name` is moved out of the vector, one element per iteration
        let longer = match &best {
            Some(b) => name.len() > b.len(),
            None => true,
        };
        if longer {
            best = Some(name); // move into `best`; the previous best is dropped here
        }
    }
    best
}

fn main() {
    let names = vec!["acme".to_string(), "initech".to_string(), "globex".to_string()];
    let winner = longest_owned(names);
    // println!("{names:?}"); // E0382: `names` was moved into longest_owned
    println!("{winner:?}");
    assert_eq!(winner.as_deref(), Some("initech"));
    assert_eq!(longest_owned(Vec::new()), None);
}
Some("initech")

Owning the vector is what makes it legal to move an element out and return it: for name in names moves each String out in turn, and the winner is moved into best. Each loser is dropped at the end of its iteration, and the old best when it's replaced. With &Vec<String> you could only look at the strings, so returning an owned one would require a clone (or returning a reference: chapter 2.11). The trade-off is visible at the call site: the caller gives up names. That's the right design when the caller doesn't need the list afterwards.

Common misconceptions and pitfalls

⚠️ "Moves are expensive, so I'll clone or use references everywhere"

A move copies a few machine words; the heap data never moves (Lab steps 1 and 5). Returning owned values is idiomatic and cheap. It's .clone() that costs.

⚠️ Adding .clone() until it compiles

The compiler suggests it because it always works, but usually the right fix is to borrow (&T, chapter 2.3) or to restructure so one owner does the work. Treat each clone on non-trivial data as a decision.

⚠️ let _ = guard()

Drops the guard immediately: the lease is returned, the timer reports 0, the transaction ends at once. The compiler rejects this for standard lock guards (let_underscore_lock), but not for your own types unless you enable let_underscore_drop. Use let _guard = ….

⚠️ Expecting shadowing to drop the old value

The shadowed value lives until the end of its scope (Exercise 3). If it holds a large buffer or a lock, call drop(old) explicitly, or shadow inside a smaller block.

⚠️ Relying on Drop for cross-process correctness

Drops don't run on process::exit, panic = "abort" or a killed process. Database leases and distributed locks need timeouts as well as RAII.

⚠️ Thinking Copy means "C# value type"

All Rust types are values. Copy only means "the source stays usable after assignment", and it's allowed only for plain data without Drop.

Real-world view: ownership in your products

🏗 Architecture view
  • Workflow engine leases: a Lease guard returns a worker slot or a step lease on drop (Lab step 4), backed by a database expiry for crashes. Error paths and panics release it automatically.
  • Connections and transactions: pool connections (chapter 7.4) are RAII guards that return to the pool on drop; a transaction guard rolls back on drop unless commit(self) consumed it. A method taking self by value makes "use after commit" a compile error.
  • Ownership as API design: a function that takes RuleSet by value says "I keep this"; one that takes &RuleSet says "I only look". Signatures document the data flow that C# leaves to comments.
  • Hand-off between components: sending a value into a channel or a spawned task moves it, so the sender can't keep mutating what the receiver now owns. That's a whole class of concurrency bugs ruled out (chapter 4.1).
  • Review checklist: clones in hot loops; let _ = on guards; Copy derived on types that may grow a String; Drop impls doing slow I/O (they run on the caller's thread, including during unwinding); resources whose release must survive a crash.

Summary

  • Every value has one owner; when the owner's scope ends, the value is dropped. That single rule manages memory and resources, deterministically, with no garbage collector.
  • Assignment, passing by value, returning, storing and for x in v move: the stack header is copied, the heap data stays put, and the old name becomes unusable (E0382). Moving out of a collection by index is refused (E0507); use remove, into_iter, mem::take or a borrow.
  • Copy types (scalars, &T, plain structs of them) are duplicated implicitly and can't implement Drop; Clone is explicit and may be expensive (about 2 ms for 80 MB, against a move too small to measure).
  • Drop runs exactly once: locals in reverse declaration order, fields in declaration order, also during panic unwinding. Drop early with drop(x) (never x.drop(), E0040), and beware let _ = guard(), which drops at once.
  • RAII beats IDisposable on every guarantee: it can't be forgotten, there's no use-after-dispose (compile error, not ObjectDisposedException), and no double dispose. But destructors aren't guaranteed to run on process::exit, aborts or leaks, so durable leases still need timeouts.
