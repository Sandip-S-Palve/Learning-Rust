How a program uses memory

Learning objectives

  • Explain bytes, addresses and pointers, and read hexadecimal addresses
  • Describe what lives on the stack and what lives on the heap, and why each exists
  • Predict the size of a struct, including alignment padding, and shrink it by reordering fields
  • Explain caches, cache lines and locality, and why memory access patterns can matter more than instruction counts
  • Name the classic memory bugs (dangling pointer, use-after-free, double free, leak, overflow) that Rust's rules exist to prevent
  • Describe what the .NET garbage collector does for you, so you can see what Rust does differently

Why this matters

💡 Why this matters

In C# you rarely think about where data lives: the CLR and its garbage collector decide. Rust hands that decision back to you, safely. Every rule you'll meet in Module 2 (ownership, borrowing, lifetimes, Box, Rc) is a rule about memory. If you know what the stack and heap are, those rules read as common sense. If you don't, they feel arbitrary.

There's also a performance reason. Your rule engine will hold millions of facts in memory, and your workflow engine will track millions of timers. On real hardware, how data is laid out decides speed: in this chapter you'll measure the same work running 30× slower just because the data was visited in a different order.

Intuition first: one long street of numbered mailboxes

🧭 Analogy

Picture a program's memory as one very long street of mailboxes, each holding exactly one byte and each with a house number: its address. A pointer is a slip of paper with a house number written on it. The paper isn't the house; it tells you where to go.

  • The stack is a pile of trays at the canteen. Each function call puts a tray on top holding that call's local variables. When the function returns, its tray is taken off. Fast, automatic, strictly last-in-first-out, and the pile has a height limit.
  • The heap is a self-storage warehouse. You ask the front desk (the allocator) for a unit of a given size, get a unit number back, and must eventually hand the unit back. It's flexible (any size, any lifetime) but slower, and someone has to remember to return it.

Core explanation

Basic

Bits, bytes and hexadecimal

A bit is a single 0 or 1. A byte is 8 bits and can hold 256 different values (0–255). Memory is addressed byte by byte.

Programmers write addresses and raw bytes in hexadecimal (base 16, digits 0–9 then a–f), prefixed with 0x. One hex digit is exactly 4 bits, so one byte is exactly two hex digits: 0xFF = 255, 0x10 = 16. That's why 0x16d671d88 looks the way it does: it's just a large number. In this course KB, MB and GB mean powers of 1024 (1 KB = 1024 bytes), which is how operating systems report memory.

Addresses and pointers

Every byte has an address. A value bigger than one byte, such as a 4-byte integer, occupies consecutive addresses and is identified by its first one.

A pointer is a value that holds an address. Following a pointer to the data it refers to is called dereferencing. On a 64-bit computer an address is 64 bits, so every pointer is 8 bytes, whatever it points to.

🟣 Coming from C#/.NET

You use pointers all the time without calling them that: a variable of a class type holds a reference, which is a pointer the runtime manages for you. var b = a; on a class copies the 8-byte reference, so both variables see the same object. On a struct, it copies the whole value. Rust has both kinds too, and makes the choice visible in the type: &T is a reference (a pointer you borrow), while plain T is the value itself.

The stack

A stack, as a data structure, is a pile where you can only add or remove at the top: last in, first out (chapter F3 covers it fully). Each thread of a program (an independent path of execution; chapter F9) gets one region of memory managed exactly this way: the stack.

  • Every function call pushes a stack frame: room for its arguments, its local variables, and the address to return to.
  • Returning pops the frame. "Freeing" it is just moving one CPU register (the stack pointer), so it's practically free.
  • The compiler must know each frame's size at compile time. So stack values have a fixed, known size.
  • The stack has a fixed maximum size. On the lab Mac the main thread gets 8 MB (ulimit -s reports 8176 KB). Rust's own spawned threads currently get 2 MiB by default on Tier-1 platforms, per the standard library docs. Exceed it and the program stops with a stack overflow.

The heap

The heap is for data that doesn't fit the stack's rules: data whose size is only known at runtime (a string the user types, a list that grows) or that must outlive the function that created it.

  • The program asks an allocator for n bytes and gets back a pointer to them.
  • The pointer itself usually lives on the stack (or inside another value), and the data lives on the heap.
  • The memory must be given back when it's no longer needed. Who does that, and when, is the whole question chapter 0.1 was about: the programmer (C), a garbage collector (C#), or code the compiler inserts based on ownership (Rust).
  • Allocation costs more than pushing a stack frame: the allocator has to find a free block, and the data ends up somewhere else in memory, which matters for caches (below).

Step through a real program to see both regions at work:

fn add(a: i32, b: i32) -> i32 {
    let sum = a + b; // a local variable in add's frame (Clippy would say: just return a + b)
    sum
}

fn main() {
    let count = 3;
    let name = String::from("Ada"); // text goes on the heap
    let total = add(count, 4);
    println!("{name}: {total}");
}

Intermediate

Alignment and padding

CPUs read memory fastest (and on some CPUs, only correctly) when a value starts at an address that is a multiple of its size. That requirement is the type's alignment: a u32 must start at a multiple of 4, a u64 at a multiple of 8. To satisfy it, the compiler inserts unused padding bytes between fields, and at the end so that arrays of the struct stay aligned too.

Field order therefore matters. Here is one struct, measured two ways:

#[repr(C)] // C rules: fields stay in the order written
struct OrderC { flag: u8, id: u32, qty: u16, price: u64 }

struct OrderRust { flag: u8, id: u32, qty: u16, price: u64 } // default: compiler may reorder
OrderC           24      8
OrderRust        16      8

Same fields, 24 bytes vs 16. With #[repr(C)] the compiler must keep your order and pad around it. With Rust's default layout it is allowed to reorder fields, and in practice it packs them to minimise padding. Use the explorer to see where the bytes go:

🟣 Coming from C#/.NET

C# compilers apply LayoutKind.Sequential to structs by default (keep declared order, like #[repr(C)]). The runtime's own default for classes is Auto (free to reorder). That's the mirror image of Rust, where the default is "free to reorder" and you opt into fixed order with #[repr(C)].

Caches, cache lines and locality

Main memory (RAM) is far slower than the CPU. To hide that, CPUs keep small, very fast copies of recently used memory in caches, arranged in levels: L1 (smallest, fastest), L2, sometimes more, then RAM. Data moves between them in fixed-size blocks called cache lines. On this Mac, sysctl reports a 128-byte line, 128 KB of L1 data cache and 16 MB of L2 per performance-core cluster. Most x86 server CPUs use 64-byte lines.

How much does it matter? This chapter's lab chases pointers through randomly linked arrays of increasing size, so each read must wait for the previous one. That measures the true cost of fetching from each level:

Programs are fast when they have good locality:

  • Spatial locality: using memory next to memory you just used. One cache line brings in neighbours for free.
  • Temporal locality: using the same memory again soon, while it's still cached.

Here's spatial locality measured directly: sum every cell of a grid stored row after row, once in row order and once in column order. It's the same additions, the same data and the same result.

✅ The rule of thumb this gives you

Contiguous beats scattered. A plain array (Rust Vec, C# T[] of structs) walked in order is the fastest data structure on modern hardware for most sizes. Pointer-heavy structures (linked lists, trees of individually allocated nodes) pay a cache miss per hop. Chapters F3–F6 keep returning to this, and it's why Rust code often stores graphs as arrays plus indices (chapter 2.12).

What the .NET garbage collector does for you

To see what Rust changes, it helps to be precise about what the CLR does (all from Microsoft's "Fundamentals of garbage collection"):

  • Allocation is a pointer bump. The managed heap keeps a pointer to the next free address. Allocating "adds a value to a pointer", which Microsoft describes as "almost as fast as allocating memory from the stack".
  • Collection traces from roots (static fields, locals on each thread's stack, CPU registers, GC handles), marks everything reachable, and reclaims the rest.
  • Compaction moves objects together and fixes up every reference. So in .NET, an object's address can change, which is why native interop needs pinning.
  • Generations 0, 1, 2: most objects die young in gen 0, which is collected often and cheaply. Survivors are promoted. A gen 2 collection is a full GC.
  • The large object heap: objects of 85,000 bytes or more go there. It is collected with gen 2 and usually not compacted.
  • Value types live "either on the stack or inline in containing types" (Framework Design Guidelines), so a struct field inside a class is on the heap with its class. Boxing a value type copies it into a new heap object.
🟣 Coming from C#/.NET — the key differences
  • Rust never moves your heap data behind your back. There's no compacting collector, so an address stays valid until the value is moved or freed by your own code, and the compiler checks that.
  • Rust's heap allocation is malloc-style (the system allocator by default), not a pointer bump. It's somewhat costlier per allocation, but frees are immediate and deterministic, with no pauses later. Idiomatic Rust compensates by allocating less: more data stays on the stack or inline.
  • "Value vs reference type" isn't fixed per type in Rust. Any type can live on the stack, inline in another value, or on the heap (via Box, Vec, …). You choose per use.
Deep dive: virtual memory, pages, ASLR — and why benchmarks lie

Virtual memory. The addresses your program prints are virtual. The CPU and operating system translate them to physical RAM locations in fixed-size blocks called pages: 16 KB on this Mac (hw.pagesize: 16384), typically 4 KB on x86-64 Linux and Windows. Each process gets its own private mapping. That's why two programs can both use address 0x102ec9290 without conflict, and why one process can't read another's memory. A page is only given real RAM the first time it is touched (a page fault), which is one reason first runs of a benchmark are slower.

ASLR. Run the lab's address program twice and the stack moves: 0x16d671d88 in one run, 0x16b859d88 in the next. Address Space Layout Randomisation places regions at random offsets on every run, so attackers can't hard-code addresses. Never store raw addresses anywhere they might outlive the process.

How the measurements were made honest. My first version of the grid benchmark reported column order as faster than row order, which is physically implausible. In release mode the optimiser had restructured the loops, because it could see the whole computation. The fix: pass the data through std::hint::black_box (which hides values from the optimiser) and keep each traversal in its own #[inline(never)] function. Likewise, the latency test builds one random cycle through the array (Sattolo's algorithm), so each load depends on the previous one and the CPU can't prefetch or overlap them. The lesson for client work: a microbenchmark result you can't explain is probably measuring the wrong thing. Chapter 6.1 introduces proper tooling (criterion).

use std::hint::black_box;
use std::time::Instant;

/// Tiny deterministic random-number generator (xorshift), so we need no crates.
fn next_rand(state: &mut u64) -> u64 {
    *state ^= *state << 13;
    *state ^= *state >> 7;
    *state ^= *state << 17;
    *state
}

/// Average time of one dependent memory load when the data is `bytes` big.
fn ns_per_load(bytes: usize) -> f64 {
    let n = bytes / std::mem::size_of::<usize>();
    // Build one random cycle through all slots (Sattolo's algorithm):
    // next[i] holds the index to visit after i, so every load depends on the last.
    let mut next: Vec<usize> = (0..n).collect();
    let mut seed = 0x9E37_79B9_7F4A_7C15;
    for i in (1..n).rev() {
        let j = (next_rand(&mut seed) % i as u64) as usize;
        next.swap(i, j);
    }
    let steps = 20_000_000;
    let mut i = 0;
    for _ in 0..n.min(steps) { i = next[i]; } // warm-up pass
    let start = Instant::now();
    for _ in 0..steps {
        i = next[i];
    }
    black_box(i);
    start.elapsed().as_nanos() as f64 / steps as f64
}

fn main() {
    let mut kb = 16;
    while kb <= 512 * 1024 {
        let ns = ns_per_load(kb * 1024);
        let label = if kb >= 1024 { format!("{} MB", kb / 1024) } else { format!("{kb} KB") };
        println!("{label:>7}: {ns:6.2} ns per load");
        kb *= 2;
    }
}

Step 2 — where things live

fn depth(n: u32) {
    let local = n; // one small variable in each call's stack frame
    println!("  depth {n}: local lives at {:p}", &local);
    if n < 3 {
        depth(n + 1);
    }
}

fn main() {
    let a: u64 = 1;
    let b: u64 = 2;
    let on_heap = Box::new(3u64); // Box puts the value on the heap
    let text = String::from("Ada");

    println!("stack: a      at {:p}", &a);
    println!("stack: b      at {:p}", &b);
    println!("heap:  *on_heap at {:p}", on_heap);
    println!("heap:  text's bytes at {:p}", text.as_ptr());
    println!("nested calls:");

}

What to notice: {:p} prints an address. &a means "a reference to a", here used just to get its address. The stack values sit together around 0x16d6…, while the heap values are in a completely different region (0x102e…). Each nested call's local is exactly 0x80 (128) bytes lower than the previous one: each frame is placed below its caller's, because on this platform the stack grows downward. Your addresses will differ, and will change on every run (ASLR).

Step 3 — overflow the stack

fn recurse(n: u64) -> u64 {
    let buffer = [n; 64]; // 512 bytes on the stack in every call
    if n == 0 { 0 } else { buffer[0] + recurse(n - 1) }
}

fn main() {
    println!("{}", recurse(10_000_000));
}
$ cargo run --bin overflow

thread 'main' (4466841) has overflowed its stack
fatal runtime error: stack overflow, aborting
(exit code 134)

Ten million nested calls × at least 512 bytes is about 5 GB, far beyond the 8 MB stack. Rust detects the overflow and aborts cleanly; it never silently corrupts memory. Now try the release build:

$ cargo run --release --bin overflow
50000005000000

It worked, because the optimiser removed the recursion entirely and computed the same sum without nesting 10 million calls. Never rely on this. Optimisations aren't guaranteed, and the debug build in your test suite will still crash. Deep recursion over unbounded input (say, a deeply nested rule expression from a customer) should be written with an explicit stack or a loop. You'll do exactly that in the rule engine (chapter 9.3).

Step 4 — feel the cache

use std::hint::black_box;
use std::time::Instant;

const N: usize = 4096; // a 4096 x 4096 grid of u32 = 64 MB

/// Visit every cell, row by row: consecutive cells are neighbours in memory.
#[inline(never)]
fn sum_by_rows(grid: &[u32], n: usize) -> u64 {
    let mut sum = 0u64;
    for row in 0..n {
        for col in 0..n {
            sum += grid[row * n + col] as u64;
        }
    }
    sum
}

/// Visit every cell, column by column: each step jumps a whole row (16 KB).
#[inline(never)]
fn sum_by_cols(grid: &[u32], n: usize) -> u64 {
    let mut sum = 0u64;
    for col in 0..n {
        for row in 0..n {
            sum += grid[row * n + col] as u64;
        }
    }
    sum
}

fn main() {
    // One flat Vec stored row after row ("row-major"), like a C# int[,].
    let grid: Vec<u32> = (0..N * N).map(|x| x as u32 % 7).collect();
    let n = black_box(N); // hide N from the optimiser so it can't restructure the loops

    let start = Instant::now();
    let a = sum_by_rows(black_box(&grid), n);
    let t_rows = start.elapsed();

    let start = Instant::now();
    let b = sum_by_cols(black_box(&grid), n);
    let t_cols = start.elapsed();

    assert_eq!(a, b);
    println!("row by row:       {:>6} µs", t_rows.as_micros());
    println!("column by column: {:>6} µs", t_cols.as_micros());
}
$ cargo run --release --bin grid
row by row:         2006 µs
column by column:  64585 µs

Always use --release for timing (chapter 0.2). assert_eq! stops the program if the two sums ever differ: a cheap guard that both versions do the same work.

Common misconceptions and pitfalls

⚠️ "C# value types always live on the stack."

Only as locals (and even then the JIT may keep them in registers). A struct field of a class, or an element of an array, lives inline in that object, on the heap. "Value type" describes copy behaviour, not location. The same is true in Rust.

⚠️ "The heap is slow, so avoid it at all costs."

On the lab Mac, allocating and freeing a small Box or String took about 19–24 ns (measured, 10 million iterations, release). One cache miss to RAM costs about 100 ns. Allocating in a hot loop is worth avoiding, but scattering data across memory is often the bigger cost. Measure (chapter 6.1) rather than guess.

⚠️ "Big-O tells you which algorithm is faster."

Big-O (chapter F2) counts operations, but Figure 5 shows identical operation counts differing 32×. For realistic sizes, memory access patterns can outweigh a better complexity class. That's why arrays often beat linked lists even where theory says otherwise (F3).

⚠️ "Rust's default struct layout is the order I wrote."

It isn't guaranteed. Code that depends on field order (FFI, binary file formats, network packets) must use #[repr(C)] or explicit serialisation.

⚠️ "Deep recursion is fine; it worked in release."

As Step 3 showed, the optimiser may hide a stack overflow in release that crashes debug, or a slightly different input may crash production. Bound your recursion, or use an explicit stack.

  • Rule engine: evaluating millions of facts per second means storing them contiguously (vectors of compact structs, or columns of values) rather than a web of individually allocated objects. Rete networks (chapter 9.4) are graphs, and you'll store them as arrays plus indices for exactly the cache reasons above.
  • Workflow engine: each in-flight workflow costs memory. 10 million parked workflows × 1 KB each is about 10 GB. The size of your per-instance struct (padding included) directly sets how many fit per node, and so your cloud bill.
  • Untrusted input and the stack: recursive evaluation of customer-supplied rule expressions is a denial-of-service risk. Cap the nesting depth, or evaluate iteratively.
  • Containers: a Kubernetes memory limit is a hard wall. Rust's deterministic freeing makes memory use predictable and flat. A GC'd service needs headroom for garbage awaiting collection, which is one reason Rust services often run in smaller containers (the Pingora numbers in 0.1).

Multiple choice

  2. 8
  3. 9

Scenario
A client's analytics service stores 50 million Order objects as a List<Order> of classes and iterates over all of them every minute. Profiling shows the CPU mostly waiting on memory. Which change most directly addresses the cause?
  1. Store the data contiguously, e.g. as an array of compact structs (or columns of values), so iteration walks memory in order
  2. Add more CPU cores
  3. Switch to a linked list for faster insertion
  4. Call GC.Collect() before each pass

Correct. A list of class instances is a list of pointers to objects scattered across the heap, so every element is a potential cache miss. Contiguous layout gives spatial locality (Figure 5).

More cores waiting on memory don't help, and may compete for memory bandwidth.

Linked lists make locality worse.

Forcing collections adds pauses and doesn't change the layout.

Summary

  • Memory is a long row of bytes, each with an address. A pointer holds an address and is 8 bytes on 64-bit machines.
  • The stack holds fixed-size local data in per-call frames that vanish on return. It's fast, automatic and size-limited. The heap holds runtime-sized or long-lived data, obtained from an allocator, and must be freed by someone.
  • Alignment forces padding, so field order changes struct size (24 vs 16 bytes in the lab). Rust may reorder fields by default; #[repr(C)] fixes the order.
  • Caches make memory fast only for good locality. Measured on the lab Mac: ~1 ns per load in L1, ~100+ ns from RAM, and the same work 32× slower in the wrong order. Contiguous beats scattered.
  • .NET hides all this with a bump-pointer allocator and a moving, generational GC. Rust gives you the choice explicitly and frees deterministically, which is the subject of Module 2.
