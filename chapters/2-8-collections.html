Standard collections

Learning objectives

  • Use Vec, VecDeque, HashMap, BTreeMap, HashSet and BinaryHeap idiomatically, and choose between them from their costs
  • Explain how ownership works for elements: moving values in and out, borrowing them, and the four ways to iterate (iter, iter_mut, into_iter, drain)
  • Use the Entry API for insert-or-update in one lookup, and look up String keys with &str
  • State what a key type needs (Eq + Hash, or Ord), and read the errors when it's missing
  • Map each collection to its .NET counterpart, and recognise where Rust's borrow rules turn .NET run-time hazards into compile errors

Why this matters

💡 Why this matters

Chapters F3 to F5 taught what dynamic arrays, hash tables, B-trees and heaps are and what they cost. This chapter is about using Rust's versions well, which differs from .NET in ways that matter every day. A collection owns its elements, so putting a String into a Vec moves it, and iterating can borrow, mutate or consume. The borrow checker stops you holding a reference into a map while you insert into it, the bug that .NET only catches at run time or documents as "don't do this". And the Entry API makes "insert or update" a single lookup, with a trap around owned keys that Lab step 5 measures.

For your products these are the core building blocks: the rule engine indexes rules by field in a HashMap, the workflow engine keeps timers in a BinaryHeap, an audit trail in a BTreeMap answers "what happened between 10:00 and 10:05", and a HashSet of processed event ids makes redelivered messages harmless (Lab step 4).

Intuition first: an office's storage

🧭 Analogy
  • Vec is a shelf of numbered boxes: grab box 7 instantly, add to the end cheaply, but inserting at the front means shifting everything.
  • VecDeque is a circular conveyor: load and unload at either end.
  • HashMap is a wall of pigeonholes labelled by a code computed from the name: go straight to the right hole, in no meaningful order.
  • BTreeMap is a filing cabinet in alphabetical order: a few steps to find anything, and "everything from Jansen to Kok" is one easy pull.
  • HashSet/BTreeSet are the same pigeonholes or cabinet holding only names: "have we seen this before?"
  • BinaryHeap is a triage desk: whatever is most urgent is always on top, and nothing else is sorted.

And the Rust part: every item on the shelf belongs to the shelf. You can look at it (borrow), adjust it in place (borrow mutably), or take it away (move it out). While someone is reading a label, nobody may rearrange the shelf.

Core explanation

Basic

The family

Everything except Vec lives in std::collections. The standard library's own guidance, condensed:

VecDeque<T>"efficient insertion at both ends"; a queueget O(1), push/pop at either end O(1)*Queue<T> (no built-in deque)

* amortised (resizing averaged over many operations); ~ expected (a hash table can do worse with collisions, chapter F4). From the std::collections performance table and the BinaryHeap docs. LinkedList exists too, but chapter F3 showed why it rarely wins; the docs agree that "where ties occur, Vec is generally faster than VecDeque, and VecDeque is generally faster than LinkedList."

Collections own their elements

A collection owns what's in it (chapter 2.2). v.push(s) moves s into the vector; dropping the vector drops every element. Getting things back out follows the same rules as everything else:

  • Borrow: &v[i], v.get(i) (an Option<&T>, no panic), map.get(&k), v.first().
  • Borrow mutably: &mut v[i], v.get_mut(i), map.get_mut(&k).
  • Move out: v.pop(), v.remove(i), v.swap_remove(i), map.remove(&k), all returning the value. let s = v[0]; is error E0507 for non-Copy elements, because the vector would be left with a hole (chapter 2.2).

And the borrow rules apply across the collection. While you hold a reference to an element, you can't call anything that might reorganise the storage (push, insert, remove), because a reallocation would leave your reference dangling (Lab step 2, e1: E0502). It's chapter 2.3's rule, and it's exactly the hazard Microsoft documents for CollectionsMarshal.GetValueRefOrAddDefault: "Items should not be added to or removed from the Dictionary while the ref TValue is in use." In C# that's a sentence in the docs; in Rust it's a compile error.

Two more consuming tools you'll use constantly: v.retain(|x| keep(x)) removes elements in place (the fix for "remove while iterating", e5), and v.extend(other) appends another collection's elements. Lab step 1 runs them all.

The Entry API

"Add to the count if present, insert 1 if not" is the most common map operation. The naive version looks the key up twice. The Entry API looks it up once and hands you a view of the slot, either occupied or vacant:

use std::collections::HashMap;

let mut counts: HashMap<&str, u32> = HashMap::new();
for e in ["charge", "refund", "charge"] {
    *counts.entry(e).or_insert(0) += 1; // insert 0 if vacant, then add 1
}
let mut by_field: HashMap<&str, Vec<u32>> = HashMap::new();
by_field.entry("amount").or_default().push(1); // Vec::new() if vacant
let mut cache: HashMap<u32, String> = HashMap::new();
cache.entry(7).and_modify(|v| v.push('!')).or_insert_with(|| "computed".into());
println!("{counts:?} {by_field:?} {cache:?}");

or_insert(v) inserts a ready value, or_insert_with(|| …) computes one only when needed, or_default() uses Default, and and_modify(|v| …) changes an existing value. Each returns &mut V, so you can update in place. That reference borrows the map, so the compiler guarantees nothing else touches the map while you use it, which is the guarantee C#'s CollectionsMarshal can only ask for in its documentation.

One catch: entry takes the key by value. With String keys, map.entry(word.to_string()) allocates a new String on every call, even when the key is already present. Lab step 5 measures that at about 2.3× slower than looking up first with get_mut(&str) and allocating only for new keys.

What a key needs

  • HashMap/HashSet keys need Eq + Hash, and equal values must have equal hashes (chapter F4). Strings, integers, char, bool, tuples of them, and your own types with #[derive(PartialEq, Eq, Hash)] qualify. f64 doesn't, because NaN != NaN breaks Eq (Lab step 2, e3). Use integer cents or an ordered-float wrapper.
  • BTreeMap/BTreeSet keys need Ord, a total order: #[derive(PartialEq, Eq, PartialOrd, Ord)]. The derived order compares fields in declaration order (e4; its help mentions Ord, but deriving Ord also requires PartialOrd, Eq and PartialEq).
  • Don't change a key while it's in a map. Rust only lends keys immutably, so this can't happen by accident, unlike a C# key object whose fields you can still mutate.

Lookups don't need an owned key: a HashMap<String, V> accepts map.get("daily") with a &str. That works because String implements Borrow<str>, which promises that a String and its &str hash and compare identically. The same applies to Vec<T> and &[T], and Box<T> and &T. You'll never write map.get(&"daily".to_string()).

🟣 Coming from C#/.NET
  • List<T> ↔ Vec<T>, nearly one to one (both a pointer, a count and a capacity). RemoveAll ↔ retain (with the opposite predicate), Sort ↔ sort/sort_unstable, BinarySearch ↔ binary_search (returning Result<usize, usize> instead of a negative number).
  • Dictionary ↔ HashMap. TryGetValue ↔ get (an Option); TryAdd ↔ entry(k).or_insert(v); CollectionsMarshal.GetValueRefOrAddDefault ↔ entry(k).or_default(), measured at the same speed-up over the double lookup in both languages (Lab step 5). Both iterate in an unspecified order; Rust's default hasher is randomly seeded per map against HashDoS (chapter F4), so the order varies between runs.
  • PriorityQueue is the opposite way round. Microsoft's docs call it "an array-backed, quaternary min-heap": the lowest priority comes out first. Rust's BinaryHeap is a max-heap; wrap items in Reverse to get min-first behaviour.
  • No built-in deque in .NET. Queue<T> is one-ended and LinkedList<T> is node-based; Rust's VecDeque is a ring buffer with both ends cheap.
  • Modify while iterating. .NET throws InvalidOperationException at run time (chapter 2.3); Rust rejects it at compile time and offers retain/drain/extract_if.
Intermediate

Choosing a collection

Answer two or three questions about how the data is used, and the choice follows from the costs above:

Sorting, searching and deduplicating

sort is stable (equal elements keep their order) and sort_unstable isn't, but is generally faster and allocates nothing; prefer it unless ties must keep their input order. sort_by_key(|x| key) and sort_by(|a, b| …) customise the order, and .then(...) on an Ordering chains tie-breakers (Lab step 3). dedup removes only consecutive duplicates, so sort first, or collect into a HashSet/BTreeSet. binary_search on a sorted slice returns Ok(index) if found and Err(insertion_point) if not, so v.insert(i, x) keeps it sorted. That's often a simpler ordered collection than a BTreeMap for small, read-mostly data.

Capacity and reuse

Every growable collection reserves spare capacity and reallocates when it runs out (chapter F3's amortised doubling; chapter 2.4 watched a String grow). When you know the size, Vec::with_capacity(n) and HashMap::with_capacity(n) allocate once. In a loop, clear() keeps the capacity for the next round, which is chapter 2.4's buffer-reuse lesson. shrink_to_fit() returns memory after a big collection has been trimmed. These matter in a rule engine evaluating millions of facts; they're noise in a CLI that runs once.

Deep dive: why the Entry API needs an owned key, and the ways around it

entry(key) must be able to insert the key if the slot is vacant, so it takes K by value. If K is String and you only have a &str, you must allocate before knowing whether you'll need to. The options:

  • Look up first with get_mut(&str) and allocate only on a miss (Lab step 5's variant B, the fastest here for mostly-hits workloads).
  • Use borrowed keys, HashMap<&str, V>, when the strings outlive the map (variant D: no allocation at all). Chapter 2.11 explains the lifetime this needs.
  • Intern the strings into ids once (chapter 2.4's deep dive) and key the map by u32.
  • The hashbrown crate (the implementation behind std's HashMap) offers an entry API that accepts a borrowed key and converts it only when inserting.
⚠ Verify

In Lab step 5, variant D (borrowed keys, no allocations) measured slower than variant B (owned keys, allocating only on a miss): about 22 vs 17 ns per token, consistently over 3 runs and in either run order. I tested and ruled out key locality and run order as the cause, and haven't established the reason. Don't generalise from this one benchmark: measure your own workload before choosing.

Deep dive: iteration order and determinism

HashMap and HashSet iterate in an order that depends on the hash function's random seed, which is chosen per map at run time to resist HashDoS attacks (chapter F4). The order differs between runs and between two maps with the same contents. That's harmless for lookups and fatal for anything that must be reproducible: snapshot tests, signatures over serialised data, and above all a workflow engine that replays history and must make the same decisions every time (chapter 10.7). The rules: sort before output (Lab step 3 sorts the counts), use BTreeMap where order is part of the meaning, or use an insertion-ordered map such as the indexmap crate. Never let a HashMap's order leak into persisted state.

Hands-on lab

Step 1 — Vec, the workhorse

fn main() {
    // 1. Building: capacity is reserved space, len is what's used.
    let mut ids: Vec<u32> = Vec::with_capacity(8);
    ids.extend([42, 7, 19, 7, 3]);
    ids.push(25);
    println!("1. {ids:?} len {} cap {}", ids.len(), ids.capacity());

    // 2. Reading: indexing panics when out of range, get returns an Option.
    println!("2. ids[0] = {}, get(10) = {:?}, first = {:?}, contains(&19) = {}", ids[0], ids.get(10), ids.first(), ids.contains(&19));

    // 3. Removing: remove keeps order (shifts, O(n)); swap_remove moves the last into the hole (O(1)).
    let mut a = ids.clone();
    let removed = a.remove(1);
    let mut b = ids.clone();
    let swapped = b.swap_remove(1);
    println!("3. remove(1) -> {removed}, {a:?}   swap_remove(1) -> {swapped}, {b:?}");

    // 4. Sorting and friends.
    let mut s = ids.clone();
    s.sort();
    s.dedup(); // removes consecutive duplicates: sort first
    println!("4. sorted+dedup {s:?}, binary_search(&19) = {:?}, binary_search(&20) = {:?}", s.binary_search(&19), s.binary_search(&20));
    let mut words = vec!["validate", "ship", "charge", "notify"];
    words.sort_by_key(|w| w.len()); // stable: equal keys keep their order
    println!("   sort_by_key(len): {words:?}");
    words.sort_unstable_by(|x, y| y.cmp(x)); // descending; unstable is faster, no order guarantee for ties
    println!("   sort_unstable_by(desc): {words:?}");

    // 5. Keeping, splitting, draining.
    let mut queue: Vec<u32> = (1..=10).collect();
    queue.retain(|n| n % 3 != 0); // keep only what passes
    let tail = queue.split_off(5); // queue keeps [..5], tail gets the rest
    let first_two: Vec<u32> = queue.drain(..2).collect(); // take out a range, keep the Vec
    println!("5. retain/split/drain -> queue {queue:?}, tail {tail:?}, drained {first_two:?}");

    // 6. The three ways to iterate, and what they hand you.
    let mut prices = vec![100, 250, 40];
    for p in &prices { print!("{p} "); } // &i32: borrow
    for p in &mut prices { *p += 1; } // &mut i32: change in place
    let total: i32 = prices.into_iter().sum(); // i32: consumes the Vec
    println!("\n6. total after +1 each = {total}");
}

Section 3 shows the trade-off between remove (order kept, everything after shifts) and swap_remove (the last element jumps into the hole, O(1)). For a work list whose order doesn't matter, swap_remove is the fast choice. Section 4: binary_search(&20) returned Err(3), the index where 20 would be inserted to keep the vector sorted.

Step 3 — maps, sets, heaps and deques

use std::cmp::Reverse;
use std::collections::{BTreeMap, BinaryHeap, HashMap, HashSet, VecDeque};

fn main() {
    // 1. HashMap basics: insert returns the old value; get borrows; remove gives the value back.
    let mut limits: HashMap<String, u32> = HashMap::new();
    let old = limits.insert(String::from("daily"), 100);
    let replaced = limits.insert(String::from("daily"), 150);
    limits.insert(String::from("monthly"), 2_000);
    // Lookup with &str although the keys are String (String: Borrow<str>).
    println!("1. insert -> {old:?} then {replaced:?}; get(\"daily\") = {:?}, contains_key(\"weekly\") = {}",
        limits.get("daily"), limits.contains_key("weekly"));
    if let Some(v) = limits.get_mut("monthly") {
        *v += 500;
    }
    println!("   remove(\"monthly\") = {:?}, len now {}", limits.remove("monthly"), limits.len());

    // 2. The Entry API: one lookup, then insert or update.
    let events = ["charge", "refund", "charge", "charge", "notify", "refund"];
    let mut counts: HashMap<&str, u32> = HashMap::new();
    for e in events {
        *counts.entry(e).or_insert(0) += 1;
    }
    let mut by_count: Vec<(&str, u32)> = counts.into_iter().collect();
    by_count.sort_by(|a, b| b.1.cmp(&a.1).then(a.0.cmp(b.0)));
    println!("2. counts: {by_count:?}");

    let rules = [("amount", 1), ("country", 2), ("amount", 3), ("vip", 4), ("amount", 5)];
    let mut by_field: HashMap<&str, Vec<u32>> = HashMap::new();
    for (field, id) in rules {
        by_field.entry(field).or_default().push(id); // or_default: Vec::new() if vacant
    }
    let mut cache: HashMap<u32, String> = HashMap::new();
    cache.entry(7).and_modify(|v| v.push('!')).or_insert_with(|| String::from("computed"));
    cache.entry(7).and_modify(|v| v.push('!')).or_insert_with(|| String::from("computed"));
    println!("   by_field[\"amount\"] = {:?}; cache[7] = {:?}", by_field["amount"], cache[&7]);

    // 3. BTreeMap: sorted by key, so iteration order and range queries are meaningful.
    let mut audit: BTreeMap<u64, &str> = BTreeMap::new();
    for (ts, what) in [(1_030, "ship"), (1_000, "validate"), (1_020, "charge"), (1_045, "notify")] {
        audit.insert(ts, what);
    }
    println!("3. in key order: {audit:?}");
    println!("   range(1_010..1_040): {:?}", audit.range(1_010..1_040).collect::<Vec<_>>());
    println!("   first {:?}, last {:?}", audit.first_key_value(), audit.last_key_value());

    // 4. HashSet: membership and set algebra.
    let allowed: HashSet<&str> = ["NL", "DE", "BE"].into_iter().collect();
    let seen: HashSet<&str> = ["DE", "FR", "NL"].into_iter().collect();
    let mut both: Vec<_> = allowed.intersection(&seen).collect();
    let mut blocked: Vec<_> = seen.difference(&allowed).collect();
    both.sort();
    blocked.sort();
    println!("4. allowed ∩ seen = {both:?}; seen − allowed = {blocked:?}; insert dup -> {}",
        allowed.clone().insert("NL"));

    // 5. BinaryHeap is a max-heap; wrap in Reverse for smallest-first (a timer queue).
    let mut heap = BinaryHeap::from([3, 9, 1, 7]);
    println!("5. max-heap pops: {:?} {:?} {:?}", heap.pop(), heap.pop(), heap.peek());
    let mut timers: BinaryHeap<Reverse<(u64, &str)>> = BinaryHeap::new();
    timers.push(Reverse((1_500, "retry charge")));
    timers.push(Reverse((900, "lease expiry")));
    timers.push(Reverse((1_200, "send reminder")));
    while let Some(Reverse((due, what))) = timers.pop() {
        print!("{}{due}:{what}", if due == 900 { "   timers by due time: " } else { ", " });
    }
    println!();

    // 6. VecDeque: a ring buffer with cheap pushes and pops at both ends.
    let mut work: VecDeque<&str> = VecDeque::from(["b", "c"]);
    work.push_front("a");
    work.push_back("d");
    let front = work.pop_front();
    work.rotate_left(1);
    println!("6. pop_front {front:?}, after rotate_left(1): {work:?}");
}

Step 4 — collections in the products

use std::cmp::Reverse;
use std::collections::{BTreeMap, BinaryHeap, HashMap, HashSet};

struct Rule {
    id: u32,
    field: &'static str,
    min: i64,
}

fn main() {
    // A. Rule engine: index rules by the field they test, so an order only meets relevant rules.
    let rules = [
        Rule { id: 1, field: "amount", min: 10_000 },
        Rule { id: 2, field: "country_code", min: 31 },
        Rule { id: 3, field: "amount", min: 50_000 },
        Rule { id: 4, field: "vip", min: 1 },
    ];
    let mut index: HashMap<&str, Vec<usize>> = HashMap::new();
    for (pos, r) in rules.iter().enumerate() {
        index.entry(r.field).or_default().push(pos);
    }
    let order: HashMap<&str, i64> = HashMap::from([("amount", 25_000), ("vip", 1)]);
    let mut fired: Vec<u32> = order
        .iter()
        .flat_map(|(field, value)| {
            let candidates = index.get(field).map(Vec::as_slice).unwrap_or(&[]);
            candidates.iter().map(|&p| &rules[p]).filter(move |r| *value >= r.min).map(|r| r.id)
        })
        .collect();
    fired.sort_unstable();
    println!("A. checked {} of {} rules; fired {fired:?}",
        order.keys().map(|f| index.get(f).map_or(0, Vec::len)).sum::<usize>(), rules.len());

    // B. Workflow engine: a timer queue, earliest first.
    let mut timers: BinaryHeap<Reverse<(u64, u32)>> = BinaryHeap::new();
    for (due, step) in [(1_500, 7), (900, 3), (1_200, 5), (2_000, 9)] {
        timers.push(Reverse((due, step)));
    }
    let now = 1_300;
    let mut due_now = Vec::new();
    while let Some(&Reverse((due, step))) = timers.peek() {
        if due > now {
            break;
        }
        timers.pop();
        due_now.push(step);
    }
    println!("B. at t={now}: run steps {due_now:?}; next timer at {:?}", timers.peek().map(|r| r.0.0));

    // C. Idempotency: a delivered-twice event is processed once.
    let deliveries = ["evt-1", "evt-2", "evt-1", "evt-3", "evt-2"];
    let mut processed: HashSet<&str> = HashSet::new();
    let handled: Vec<&str> = deliveries.iter().copied().filter(|id| processed.insert(id)).collect();
    println!("C. delivered {} times, handled {handled:?}", deliveries.len());

    // D. Audit log: ordered by timestamp, queried by time window.
    let audit: BTreeMap<u64, &str> = BTreeMap::from([(1_000, "started"), (1_250, "retry"), (1_900, "completed"), (1_100, "charged")]);
    let window: Vec<&str> = audit.range(1_050..=1_300).map(|(_, e)| *e).collect();
    println!("D. events in [1050, 1300]: {window:?}");
}
A. checked 3 of 4 rules; fired [1, 4]
B. at t=1300: run steps [3, 5]; next timer at Some(1500)
C. delivered 5 times, handled ["evt-1", "evt-2", "evt-3"]
D. events in [1050, 1300]: ["charged", "retry"]

A: the field index means an order with two facts meets 3 candidate rules, not all 4; with thousands of rules over hundreds of fields that difference is the whole performance story, and chapter 9.4's Rete network generalises it. B: peek before pop leaves future timers in place. C: HashSet::insert returns false for a duplicate, which is all an idempotency check needs (chapter 10.1). D: one range call answers a time-window query.

Step 5 — counting words: Entry, double lookups and owned keys

use std::collections::HashMap;
use std::hint::black_box;
use std::time::Instant;

const TOKENS: usize = 1_000_000;
const DISTINCT: usize = 10_000;

// A: the Entry API with String keys: entry() needs an owned key, so every call allocates.
fn entry_owned(words: &[String]) -> usize {
    let mut m: HashMap<String, u32> = HashMap::new();
    for w in words {
        *m.entry(w.to_string()).or_insert(0) += 1;
    }
    m.len()
}

// B: look up by &str first; allocate a key only for new words.
fn get_mut_then_insert(words: &[String]) -> usize {
    let mut m: HashMap<String, u32> = HashMap::new();
    for w in words {
        if let Some(c) = m.get_mut(w.as_str()) {
            *c += 1;
        } else {
            m.insert(w.clone(), 1);
        }
    }
    m.len()
}

// C: the C#-habit double lookup: contains_key, then get_mut.
fn contains_then_get(words: &[String]) -> usize {
    let mut m: HashMap<String, u32> = HashMap::new();
    for w in words {
        if m.contains_key(w.as_str()) {
            *m.get_mut(w.as_str()).unwrap() += 1;
        } else {
            m.insert(w.clone(), 1);
        }
    }
    m.len()
}

// D: borrowed keys (&str) that outlive the map: the Entry API with no allocation at all.
fn entry_borrowed(words: &[String]) -> usize {
    let mut m: HashMap<&str, u32> = HashMap::new();
    for w in words {
        *m.entry(w.as_str()).or_insert(0) += 1;
    }
    m.len()
}

fn ns_per_token(words: &[String], f: fn(&[String]) -> usize) -> f64 {
    (0..5)
        .map(|_| {
            let t = Instant::now();
            assert_eq!(black_box(f(black_box(words))), DISTINCT);
            t.elapsed().as_secs_f64() * 1e9 / TOKENS as f64
        })
        .fold(f64::INFINITY, f64::min)
}

fn main() {
    let words: Vec<String> = (0..TOKENS).map(|i| format!("key{}", (i * 7_919) % DISTINCT)).collect();
    println!("{TOKENS} tokens, {DISTINCT} distinct, best of 5, ns per token:");
    println!("  A entry(w.to_string())          {:>6.1}", ns_per_token(&words, entry_owned));
    println!("  B get_mut(&str), else insert    {:>6.1}", ns_per_token(&words, get_mut_then_insert));
    println!("  C contains_key + get_mut        {:>6.1}", ns_per_token(&words, contains_then_get));
    println!("  D HashMap<&str, _> + entry(w)   {:>6.1}", ns_per_token(&words, entry_borrowed));
}

static int TryGetThenSet(string[] words)
{
    var d = new Dictionary<string, int>();
    foreach (var w in words)
    {
        d.TryGetValue(w, out var c);
        d[w] = c + 1;
    }
    return d.Count;
}

// .NET 6+: a ref to the value slot, added if missing: one lookup, like Rust's entry().
static int RefOrAddDefault(string[] words)
{
    var d = new Dictionary<string, int>();
    foreach (var w in words)
        CollectionsMarshal.GetValueRefOrAddDefault(d, w, out _)++;
    return d.Count;
}

Exercise 1 — a sorted report by country ★☆☆

Given a list of orders (id, country, cents), print each country's order ids and total, sorted by country, using one pass over the orders.

Show solution 
use std::collections::BTreeMap;

struct Order {
    id: u32,
    country: &'static str,
    cents: u64,
}

fn main() {
    let orders = [
        Order { id: 1, country: "NL", cents: 25_000 },
        Order { id: 2, country: "DE", cents: 4_000 },
        Order { id: 3, country: "NL", cents: 12_000 },
        Order { id: 4, country: "BE", cents: 9_900 },
        Order { id: 5, country: "DE", cents: 30_000 },
    ];

    // Group order ids by country; BTreeMap keeps the report sorted by country.
    let mut by_country: BTreeMap<&str, (Vec<u32>, u64)> = BTreeMap::new();
    for o in &orders {
        let (ids, total) = by_country.entry(o.country).or_default();
        ids.push(o.id);
        *total += o.cents;
    }
    for (country, (ids, total)) in &by_country {
        println!("{country}: orders {ids:?}, total €{}.{:02}", total / 100, total % 100);
    }
    assert_eq!(by_country.keys().copied().collect::<Vec<_>>(), ["BE", "DE", "NL"]);
    assert_eq!(by_country["NL"].1, 37_000);
    println!("ok");
}

DE: orders [2, 5], total €340.00

ok

A BTreeMap gives the sorted report for free; with a HashMap you'd collect and sort the keys first. or_default() creates the (Vec::new(), 0) tuple for a new country, and destructuring the returned &mut (Vec<u32>, u64) into (ids, total) gives mutable access to both parts.

Exercise 2 — the top k failing rules ★★☆ product skill

The rule engine logs which rule rejected each request. Return the k rules that failed most often, with counts, most frequent first, keeping at most k+1 items in any heap.

Show solution 
use std::cmp::Reverse;
use std::collections::{BinaryHeap, HashMap};

// The k rules that failed most often, without sorting every count.
fn top_k<'a>(failures: &[&'a str], k: usize) -> Vec<(&'a str, u32)> {
    let mut counts: HashMap<&str, u32> = HashMap::new();
    for rule in failures {
        *counts.entry(rule).or_insert(0) += 1;
    }
    // A min-heap of size k: the smallest of the current top k sits on top, ready to be evicted.
    let mut heap: BinaryHeap<Reverse<(u32, &str)>> = BinaryHeap::with_capacity(k + 1);
    for (rule, n) in counts {
        heap.push(Reverse((n, rule)));
        if heap.len() > k {
            heap.pop(); // drop the least frequent
        }
    }
    let mut top: Vec<(&str, u32)> = heap.into_iter().map(|Reverse((n, r))| (r, n)).collect();
    top.sort_by(|a, b| b.1.cmp(&a.1).then(a.0.cmp(b.0)));
    top
}

fn main() {
    let failures = ["amount", "vip", "amount", "country", "amount", "vip", "age", "country", "amount", "vip"];
    let top = top_k(&failures, 2);
    println!("top 2: {top:?}");
    assert_eq!(top, vec![("amount", 4), ("vip", 3)]);
    assert_eq!(top_k(&failures, 10).len(), 4);
    assert!(top_k(&[], 3).is_empty());
    println!("ok");
}
top 2: [("amount", 4), ("vip", 3)]
ok

Counting is the Entry API. The "top k" is a min-heap of size k (a BinaryHeap of Reverse): the least frequent of the current candidates is on top, so each new count either replaces it or is discarded. That's O(n log k) instead of sorting all n counts, which matters when there are millions of distinct keys and k is 10. The 'a in the signature says the returned rule names borrow from the input slice; chapter 2.11 explains it.

Exercise 3 — which collection? ★★☆

Choose a collection for each, then check with Figure 3 and the solution.

  1. Steps of a workflow run, appended as they complete and read in order.
  2. The workflow engine's queue of ready tasks: workers take from the front, retries go to the back, and urgent re-runs to the front.
  3. Compiled rules looked up by rule id on every evaluation.
  4. Lease expiry times, where the engine always needs the next lease to expire.
  5. A tenant's quota usage per day, queried as "the last 30 days".

Show solution
  1. Vec: append at the end, read in order.
  2. VecDeque: cheap at both ends (push_back for retries, push_front for urgent work, pop_front for workers).
  3. HashMap<RuleId, CompiledRule>: no order needed, fastest lookups. (If ids are dense 0..n, a plain Vec indexed by id is faster still.)
  4. BinaryHeap<Reverse<(Instant, LeaseId)>>: always the earliest on top. A BTreeMap also works, and allows cancelling a specific lease, which a heap can't do efficiently, a real consideration (chapter 10.5).
  5. BTreeMap<Date, Usage>: range(today - 30..=today) answers it directly.
  6. HashSet<MessageId>, bounded in practice (old ids expire), or a persistent table, since a crash would empty an in-memory set (chapter 10.1).

Common misconceptions and pitfalls

⚠️ Relying on HashMap iteration order

It changes between runs. Sort, use BTreeMap, or an insertion-ordered map whenever order reaches output, tests or persisted data.

⚠️ entry(key.to_string()) in hot loops

The allocation happens even when the key exists; it was the slowest variant in Lab step 5. Look up by &str first, or key by borrowed strings or ids.

⚠️ Indexing with untrusted keys

map["x"] and v[i] panic when the key or index is missing. For data from outside, use get and handle None.

⚠️ Expecting a min-heap

BinaryHeap pops the largest first, the opposite of C#'s PriorityQueue. Wrap items in Reverse for earliest-deadline-first.

⚠️ f64 keys and sorting floats

f64 isn't Eq/Hash/Ord because of NaN. Store money as integer cents; sort floats with sort_by(|a, b| a.total_cmp(b)).

⚠️ Reaching for LinkedList

Contiguous Vec and VecDeque win almost every real workload (chapter F3; the std docs say the same).

Real-world view: collections in your products

🏗 Architecture view
  • Rule engine: a HashMap<FieldId, Vec<RuleId>> index sends each fact only to rules that test it (Lab step 4); compiled rules live in a Vec indexed by dense ids; the top failing rules come from a bounded heap (Exercise 2).
  • Workflow engine: a VecDeque of ready tasks, a BinaryHeap (or BTreeMap, for cancellation) of timers, a HashSet or persistent table for idempotency, and BTreeMaps wherever replay needs deterministic order (chapter 10.7).
  • Determinism: nothing a workflow decides may depend on HashMap iteration order, because the seed changes per process.
  • Memory and allocation: pre-size collections whose size you know, reuse buffers with clear(), and prefer ids to String keys in hot maps (chapter 6.2 measures these at scale).
  • Review checklist: HashMap order leaking into output; contains_key followed by insert; entry(s.to_string()) in loops; v[i]/map[k] on external input; remove where swap_remove would do; LinkedList; float keys.

Summary

  • Vec for sequences, VecDeque for queues, HashMap/HashSet for unordered lookup, BTreeMap/BTreeSet for ordered keys and ranges, BinaryHeap for "the biggest next" (a max-heap; Reverse for min).
  • Collections own their elements: values move in; you borrow (get, &v[i]), borrow mutably, or move out (pop, remove). No reference into a collection survives a call that may reorganise it (E0502).
  • Iterate with &c (borrow), &mut c (modify), c (consume) or c.drain(..) (empty but keep); remove matching items with retain.
  • The Entry API inserts or updates in one lookup, but needs an owned key: entry(s.to_string()) was the slowest of the measured variants, and looking up by &str first the fastest. Look up String keys with &str.
  • Keys need Eq + Hash (not f64) or Ord. HashMap order is random per run, so sort or use BTreeMap wherever order matters, especially in replayable workflows.
