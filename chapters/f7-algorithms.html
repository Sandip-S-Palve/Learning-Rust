Core algorithms and techniques

Learning objectives

  • Write correct recursive solutions (base case + recursive case) and know when to avoid recursion
  • Apply divide and conquer, and read its cost from a recurrence
  • Compare insertion sort, merge sort and quicksort; explain stability; and know what Rust and .NET actually ship
  • Use binary search, including Rust's partition_point, to search monotonic data
  • Recognise when a greedy choice is safe and when you need dynamic programming, and implement both

Why this matters

💡 Why this matters

Chapters F2–F6 gave you the data structures. This chapter gives you the techniques that recur in every system you'll design: divide a problem in half, pick the locally best option, or remember answers you've already computed. They show up directly in your products. A rule editor suggests "did you mean credit_score?" using edit distance, a dynamic-programming algorithm. The workflow engine merges overlapping maintenance windows with sort-then-sweep. An incident review finds the first bad deploy with binary search.

You'll also settle a question every .NET developer has wondered about: what sort does my platform actually use, and is it stable? The answers differ between Rust and .NET, and that difference has caused real bugs in ported code.

Intuition first: three ways to sort a deck of cards

🧭 Analogy
  • Insertion sort is how you sort a hand of cards: pick up each new card and slide it into place among the ones you already hold. Great for a handful of cards, or a hand that's almost sorted. Painful for a whole deck.
  • Merge sort is a team effort: split the deck in half, give each half to a friend to sort (they split theirs again…), then merge the two sorted piles by repeatedly taking the smaller top card. That's divide and conquer.
  • Quicksort picks one card as a pivot and throws every card onto a "lower" or "higher" pile, then sorts each pile the same way. Fast on average, but if your pivot is always the smallest card (say, on an already-sorted deck), one pile is empty every time and you've gained nothing.

Core explanation

Basic

Recursion

A recursive function solves a problem by calling itself on a smaller version of the same problem. Every correct recursion has two parts:

  1. A base case, small enough to answer directly ("a list of 0 or 1 items is already sorted").
  2. A recursive case that makes progress towards the base case ("sort each half").

Each call is a stack frame (chapter F1), so recursion depth is limited, and input-controlled depth is a crash risk (chapter F6's deep dive). Recursion is the right way to think about many problems. Whether to implement it recursively depends on how deep it can go: merge sort's depth is log₂ n (20 for a million items), which is perfectly safe; walking a customer-supplied chain is not.

Divide and conquer

Divide and conquer splits a problem into independent parts, solves each (usually recursively), and combines the answers. Merge sort is the classic example: split in half, sort both halves, then merge by repeatedly taking the smaller front element. Its cost obeys a recurrence:

$$ T(n) = 2\,T\!\left(\tfrac{n}{2}\right) + c\,n \quad\Longrightarrow\quad T(n) = O(n \log n) $$

Why: there are \(\log_2 n\) levels of halving, and the merges at each level touch all n elements once, so n work per level. Independent halves are also why divide and conquer parallelises well: give each half to a different core (chapter 4.4).

Notice the defaults are opposite. In .NET the method you reach for (List.Sort) is unstable, and LINQ is stable. In Rust the default sort is stable, and you opt into sort_unstable for speed (about 1.5× in the lab). Porting list.Sort(...) to v.sort_by(...) is safe. Porting LINQ OrderBy to sort_unstable_by silently breaks code that relied on equal items keeping their order.

Binary search and partition points

Binary search (chapter F2) finds a value in sorted data in O(log n). The more general form asks: in a sequence where some condition is true for a prefix and false afterwards, where does it flip? Rust's partition_point(pred) answers exactly that: "the index of the first element of the second partition". It's the algorithm behind git bisect ("first commit where the tests fail") and behind finding the first deploy whose error rate crossed a threshold (Exercise 3). The only requirement is monotonicity: once the condition turns false, it stays false.

Intermediate

Greedy algorithms

A greedy algorithm makes the choice that looks best right now and never reconsiders it. It's fast and simple, and optimal only when the problem has the right structure. Two examples:

  • Works: scheduling the most non-overlapping meetings in one room. Always pick the meeting that ends earliest; this provably leaves the most room for the rest. Merging overlapping windows (Exercise 2) is a similar sort-then-sweep.
  • Fails: making change with the fewest coins. "Take the largest coin that fits" is optimal for {1, 5, 10, 25}, but with coins {1, 3, 4} and amount 6, greedy picks 4 + 1 + 1 (3 coins) while the best is 3 + 3 (2 coins). The lab shows both.

The lesson for design reviews: a greedy heuristic needs an argument for why the local choice can't hurt later. Without that argument, treat it as an approximation, which is often fine but should be known.

Dynamic programming

Dynamic programming (DP) applies when a problem breaks into subproblems that overlap: the same smaller question is asked many times. Instead of recomputing, store each answer once. Two styles:

  • Top-down (memoisation): write the natural recursion and cache results in a map. Measured below: Fibonacci(40) drops from 284 ms to 0.007 ms, because the naive version makes about 330 million calls and the memoised one 40 distinct computations.
  • Bottom-up (tabulation): fill a table from the smallest subproblems upwards. No recursion, so no stack risk, and often only the last row needs to be kept.

The classic DP for your products is edit distance (Levenshtein distance): the fewest single-character insertions, deletions or substitutions to turn one string into another. Deep dive: the Ω(n log n) barrier — and how modern sorts are “linear” anyway

Any sort that only learns about the data by comparing pairs needs at least about \(n \log_2 n\) comparisons in the worst case. There are \(n!\) possible orderings of n items, and each comparison has two outcomes, so k comparisons can distinguish at most \(2^k\) cases. To distinguish all orderings you need

$$ 2^k \ge n! \;\Longrightarrow\; k \ge \log_2(n!) \approx n\log_2 n - 1.44\,n $$

(by Stirling's approximation). So merge sort and heapsort are optimal comparison sorts, up to constants.

How then can Rust's documentation promise "linear time on fully sorted and reversed inputs"? Because the bound is about the worst case over all inputs. An adaptive sort first looks for existing sorted runs, which costs n − 1 comparisons to confirm a fully sorted input, and exploits them. That's the "partial run detection of mergesort" in driftsort's description, and it's why the lab's sort took 0.03 ms on 100,000 already-sorted numbers versus 1.4 ms on random ones. Real data is often partly sorted (appending to time-ordered logs, re-sorting after a few changes), so adaptivity pays off in practice.

Sorts that don't compare at all can beat n log n. Counting sort and radix sort exploit the structure of the keys (small integers, fixed-width strings) to run in O(n + k) or O(d·n). MIT's Lecture 5 (in Go further) covers them.

Step 1 — four sorts, three sizes, two input orders

use std::hint::black_box;
use std::time::Instant;

/// Insertion sort: O(n²) worst case, but fast for tiny or nearly sorted input.
fn insertion_sort(v: &mut [u64]) {
    for i in 1..v.len() {
        let mut j = i;
        while j > 0 && v[j - 1] > v[j] {
            v.swap(j - 1, j);
            j -= 1;
        }
    }
}

/// Merge sort: O(n log n) always, stable, needs O(n) extra memory.
fn merge_sort(v: &mut Vec<u64>) {
    if v.len() <= 1 {
        return;
    }
    let mut right = v.split_off(v.len() / 2); // divide...
    merge_sort(v);                            // ...conquer each half...
    merge_sort(&mut right);
    let left = std::mem::take(v);             // ...and combine (merge)
    let (mut i, mut j) = (0, 0);
    v.reserve(left.len() + right.len());
    while i < left.len() && j < right.len() {
        if left[i] <= right[j] { v.push(left[i]); i += 1; } else { v.push(right[j]); j += 1; }
    }
    v.extend_from_slice(&left[i..]);
    v.extend_from_slice(&right[j..]);
}

/// Textbook quicksort with the FIRST element as pivot: O(n log n) on random input,
/// O(n²) on already-sorted input.
fn naive_quicksort(v: &mut [u64]) {
    if v.len() <= 1 {
        return;
    }
    let pivot = v[0];
    let mut store = 1;
    for i in 1..v.len() {
        if v[i] < pivot {
            v.swap(i, store);
            store += 1;
        }
    }
    v.swap(0, store - 1);
    let (left, right) = v.split_at_mut(store - 1);
    naive_quicksort(left);
    naive_quicksort(&mut right[1..]);
}

fn next_rand(s: &mut u64) -> u64 { *s ^= *s << 13; *s ^= *s >> 7; *s ^= *s << 17; *s }

/// Time a closure in milliseconds, formatted for the table.
fn ms(f: impl FnOnce()) -> String {
    let t = Instant::now();
    f();
    format!("{:.2}", t.elapsed().as_secs_f64() * 1e3)
}

fn main() {
    let mut seed = 3;
    for &n in &[1_000usize, 10_000, 100_000] {
        let random: Vec<u64> = (0..n).map(|_| next_rand(&mut seed)).collect();
        let sorted: Vec<u64> = (0..n as u64).collect();
        for (label, data) in [("random", &random), ("sorted", &sorted)] {
            let skip = || "skipped".to_string();

            let t_ins = if n <= 10_000 { ms(|| insertion_sort(&mut a)) } else { skip() };
            let mut b = data.clone();
            let t_mrg = ms(|| merge_sort(&mut b));
            let mut c = data.clone();

            let t_qck = if label == "random" || n <= 10_000 { ms(|| naive_quicksort(&mut c)) } else { skip() };
            let mut d = data.clone();
            let t_std = ms(|| d.sort());

Step 2 — memoisation turns exponential into linear

use std::collections::HashMap;
use std::time::Instant;

/// Plain recursion: recomputes the same subproblems over and over: O(φⁿ) ≈ O(1.618ⁿ).
fn fib_naive(n: u64) -> u64 {
    if n < 2 { n } else { fib_naive(n - 1) + fib_naive(n - 2) }
}

/// Top-down dynamic programming (memoisation): each n computed once: O(n).
fn fib_memo(n: u64, memo: &mut HashMap<u64, u64>) -> u64 {
    if n < 2 {
        return n;
    }
    if let Some(&v) = memo.get(&n) {
        return v;
    }
    let v = fib_memo(n - 1, memo) + fib_memo(n - 2, memo);
    memo.insert(n, v);
    v
}

/// Bottom-up dynamic programming: fill from the smallest case up, O(n) time, O(1) memory.
fn fib_bottom_up(n: u64) -> u64 {
    let (mut a, mut b) = (0u64, 1u64);
    for _ in 0..n {
        (a, b) = (b, a + b);
    }
    a
}

fn main() {
    for n in [30, 35, 40] {
        let t = Instant::now();
        let x = fib_naive(n);
        let t_naive = t.elapsed();
        let t = Instant::now();
        let y = fib_memo(n, &mut HashMap::new());
        let t_memo = t.elapsed();
        let z = fib_bottom_up(n);
        assert!(x == y && y == z);
        println!("fib({n}) = {x:>9}: naive {:>8.1} ms, memoised {:>6.3} ms", t_naive.as_secs_f64() * 1e3, t_memo.as_secs_f64() * 1e3);
    }
    println!("fib(90) = {} (bottom-up, instant)", fib_bottom_up(90));
}
fib(30) =    832040: naive      2.4 ms, memoised  0.014 ms
fib(35) =   9227465: naive     25.9 ms, memoised  0.008 ms
fib(40) = 102334155: naive    283.6 ms, memoised  0.007 ms
fib(90) = 2880067194370816120 (bottom-up, instant)

Each +5 to n multiplies the naive time by about 11 (φ⁵ ≈ 11.1), which is exponential growth you can see. The memoised version stays flat. The bottom-up version needs neither recursion nor a map. Fibonacci itself is a toy, but the same pattern turns real problems from impossible to instant.

Step 3 — stability you can see

fn main() {
    // Orders, already in arrival order (the time is the 3rd field).
    let mut orders = vec![
        ("globex", 250, "09:01"),
        ("acme", 100, "09:02"),
        ("globex", 75, "09:03"),
        ("acme", 300, "09:04"),

    // Group by customer. A STABLE sort keeps each customer's orders in arrival order.
    orders.sort_by_key(|&(customer, _, _)| customer);

    }

Each customer's orders stay in time order, guaranteed by sort_by_key's stability. sort_unstable_by_key makes no such promise. With six items it may happen to give the same output, which is exactly how this kind of bug slips through tests and appears in production with larger data.

Step 4 — greedy vs dynamic programming

/// Greedy change-making: always take the largest coin that fits.
fn greedy_coins(coins: &[u32], mut amount: u32) -> Vec<u32> {
    let mut sorted = coins.to_vec();
    sorted.sort_unstable_by(|a, b| b.cmp(a));
    let mut used = Vec::new();
    for c in sorted {
        while amount >= c {
            amount -= c;
            used.push(c);
        }
    }
    used
}

/// Dynamic programming: best[a] = fewest coins that make amount a.
fn dp_coins(coins: &[u32], amount: u32) -> Option<Vec<u32>> {
    let n = amount as usize;
    let mut best = vec![u32::MAX; n + 1];
    let mut last = vec![0u32; n + 1]; // which coin was used last to reach a
    best[0] = 0;
    for a in 1..=n {
        for &c in coins {
            let c_us = c as usize;
            if c_us <= a && best[a - c_us] != u32::MAX && best[a - c_us] + 1 < best[a] {
                best[a] = best[a - c_us] + 1;
                last[a] = c;
            }
        }
    }
    if best[n] == u32::MAX {
        return None;
    }
    let mut used = Vec::new();
    let mut a = n;
    while a > 0 {
        used.push(last[a]);
        a -= last[a] as usize;
    }
    Some(used)
}

fn main() {
    for coins in [vec![1, 5, 10, 25], vec![1, 3, 4]] {
        let amount = 6;
        println!("coins {coins:?}, amount {amount}: greedy {:?}  dp {:?}", greedy_coins(&coins, amount), dp_coins(&coins, amount).unwrap());
    }
}
coins [1, 5, 10, 25], amount 6: greedy [5, 1]  dp [1, 5]
coins [1, 3, 4], amount 6: greedy [4, 1, 1]  dp [3, 3]

For US-style coins, greedy and DP agree (two coins either way). For {1, 3, 4}, greedy uses 3 coins and DP finds 2. DP considers every way to reach each smaller amount, so it can't be fooled by a locally attractive choice. That costs O(amount × coins) instead of greedy's near-instant answer.

Exercise 1 — “did you mean…?” for fact names ★★☆ product skill

Implement edit_distance(a, b) (Figure 2's algorithm). Check that "kitten" → "sitting" is 3 and that a typo "credit_scor" is distance 1 from "credit_score". A rule editor can then suggest the closest known fact name.

Show solution 
/// Levenshtein edit distance (insertions, deletions, substitutions).
/// table[i][j] = distance between the first i chars of `a` and the first j chars of `b`.
pub fn edit_distance(a: &str, b: &str) -> usize {
    let a: Vec<char> = a.chars().collect();
    let b: Vec<char> = b.chars().collect();
    let mut table = vec![vec![0usize; b.len() + 1]; a.len() + 1];
    for (i, row) in table.iter_mut().enumerate() {
        row[0] = i; // turn a[..i] into "" by i deletions
    }
    for (j, cell) in table[0].iter_mut().enumerate() {
        *cell = j; // turn "" into b[..j] by j insertions
    }
    for i in 1..=a.len() {
        for j in 1..=b.len() {
            let substitute = table[i - 1][j - 1] + usize::from(a[i - 1] != b[j - 1]);
            let delete = table[i - 1][j] + 1;
            let insert = table[i][j - 1] + 1;
            table[i][j] = substitute.min(delete).min(insert);
        }
    }
    table[a.len()][b.len()]
}

fn main() {
    println!("{}", edit_distance("kitten", "sitting"));          // 3
    println!("{}", edit_distance("credit_scor", "credit_score")); // 1
}

Notice .chars(): Rust strings are UTF-8 (chapter 2.4), so we compare characters, not bytes. usize::from(bool) turns false/true into 0/1. Only the previous row is ever needed, so a production version can use O(n) memory instead of O(m·n).

Exercise 2 — merge maintenance windows ★★☆

Given time windows (start, end) in any order, merge overlapping ones. [(9,11), (1,3), (2,5), (10,12), (6,7)] becomes [(1,5), (6,7), (9,12)].

Show solution 
/// Merge overlapping [start, end) time windows.
pub fn merge_windows(mut windows: Vec<(u32, u32)>) -> Vec<(u32, u32)> {
    windows.sort_unstable(); // by start time: O(n log n)
    let mut merged: Vec<(u32, u32)> = Vec::new();
    for (start, end) in windows {
        match merged.last_mut() {
            Some(last) if start <= last.1 => last.1 = last.1.max(end), // overlaps: extend
            _ => merged.push((start, end)),                            // gap: new window
        }
    }
    merged
}

fn main() {
    let w = vec![(9, 11), (1, 3), (2, 5), (10, 12), (6, 7)];
    println!("{:?}", merge_windows(w)); // [(1, 5), (6, 7), (9, 12)]
}

Sort, then sweep once: after sorting by start, a window can only overlap the most recent merged one. O(n log n) overall, dominated by the sort. The match arm with if is a guard (chapter 2.5). sort_unstable is fine here, because windows equal as whole tuples are interchangeable.

Exercise 3 — bisect the bad deploy ★☆☆ consultant skill

Error rates per deploy (oldest first) stay under 1% until something breaks, then stay above. Find the first bad deploy in O(log n) with partition_point, or return None if none is bad.

Show solution 
/// Index of the first deploy whose error rate exceeds 1%.
/// `error_pct` is non-decreasing once things break, so binary search applies.
pub fn first_bad(error_pct: &[f64]) -> Option<usize> {
    let i = error_pct.partition_point(|&e| e <= 1.0); // first index where the predicate is false
    if i < error_pct.len() { Some(i) } else { None }
}

fn main() {
    println!("{:?}", first_bad(&[0.1, 0.2, 0.4, 3.5, 4.0, 7.2])); // Some(3)
    println!("{:?}", first_bad(&[0.1, 0.2]));                     // None
}

Over 1,000 deploys that's at most 10 checks. In real incidents each "check" might be an expensive test run or canary, which is exactly why git bisect uses binary search. If the data isn't monotonic (it recovers, then breaks again), binary search can return a wrong answer silently. Check the assumption.

Common misconceptions and pitfalls

⚠️ Writing your own sort

The lab's hand-written sorts were 3–10× slower than the library on random data, and one had an O(n²) case on sorted data. Use sort or sort_unstable, and write algorithms only to learn them.

⚠️ Assuming .NET and Rust sorts have the same stability

.NET List.Sort: unstable. LINQ OrderBy: stable. Rust sort: stable; sort_unstable: not. Map them deliberately when porting.

⚠️ An inconsistent comparator

A comparison that isn't a total order (say, comparing floats containing NaN with partial_cmp().unwrap(), or a comparator that depends on time) gives garbage order. Rust's docs warn that the sort "may panic". For floats use f64::total_cmp.

⚠️ Trusting a greedy heuristic without proof

It's fast and often right, and occasionally quietly suboptimal ({1, 3, 4} coins). Know which one you have.

⚠️ Deep recursion in production

Fine when depth is log n (merge sort); dangerous when depth follows input (naive quicksort on sorted data, walking chains). Prefer iterative or bottom-up forms when depth is unbounded.

Real-world view: these techniques in your products

🏗 Architecture view
  • Rule editor: edit distance suggests the nearest known fact or function name on a typo; dynamic programming in the UI path, costing O(m·n) per candidate. Cap name lengths.
  • Workflow scheduling: merge maintenance and blackout windows (sort-then-sweep), and assign tasks to the earliest-free worker (greedy plus the min-heap from F5).
  • Deterministic ordering: sort with a stable sort and a full tie-breaker key ((due_time, sequence)) whenever order affects behaviour or replay (chapters F4 and F5).
  • Operations: bisect regressions across deploys or rule-set versions with partition_point logic. Keep version history monotonic and queryable so you can.
  • Batch analytics: divide and conquer over partitions (per tenant, per day) parallelises naturally; chapter 4.4 does it with rayon.

Summary

  • Recursion = base case + progress. It's fine at log n depth, risky when depth follows input. Divide and conquer (merge sort) solves halves and combines them: T(n) = 2T(n/2) + n = O(n log n).
  • Use the library sort. Rust's sort (driftsort-based) is stable; sort_unstable (ipnsort-based) is faster. Both are linear on sorted input. .NET's List.Sort is unstable introsort; LINQ OrderBy is stable.
  • Binary search generalises to partition_point over any monotonic condition (bisecting deploys and versions).
  • Greedy is fast but needs a proof (it fails for coins {1, 3, 4}). Dynamic programming stores overlapping sub-answers: Fibonacci(40) from 284 ms to 0.007 ms, and edit distance in O(m·n).
  • Measured: textbook quicksort is 40× slower on sorted input, while library sorts are effectively instant on it, because real data is often partly sorted.
